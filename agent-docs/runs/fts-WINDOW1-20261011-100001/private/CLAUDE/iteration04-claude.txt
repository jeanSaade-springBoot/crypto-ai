## 2. FINDINGS

### F-20 (CONFIRMED in code): the same hourly SELL is soft at entry but blocks adds and forces exits
*PROJECT EVIDENCE: code plus I3-012.*

**What the code does:**
- **Initial entry:** any quality-valid 1h `SELL` counts as a soft conflict, whatever its confidence. Its effective decision becomes NEUTRAL and the entry is capped at 25% (`HigherTimeframeBuyAssessmentService.java:47,33-34`). Only a `STRONG_SELL` with confidence ≥70 becomes a hard veto (`:46`).
- **Scale-in:** the raw 1h is still applied. The comment at `TradeExecutionValidationService.java:420-431` says "Existing raw 1h progressive-add guard blocked this add".
- **Exit:** the raw 1h is applied too. `evaluateNormalExit` exits on `bearish(1h) && !supportive(5m)` (`PositionExitPolicy.java:25-27`).
  - Exits are checked against the newest signal per timeframe, with no age check and no comparison to when the position opened (`LivePositionProtectionService.java:95-97`).
  - The Javadoc says "a **fresh** 1h SELL" (`:14`). The exit text says "1h **turned** SELL" (`:30`). The code checks neither.

**What happened:**
- I3-012: in 78, 91, 96 and 104, the 1h at entry was SELL and **no new 1h signal arrived** while the position was open (`new_1h_during_hold=0`).
- The two other HTF_SELL_CONFIRMED losses since V107 (72 and 71) had a new 1h signal during the hold. The asymmetry is specific to soft-conflict entries.

**Why it loses by construction:**
- Entry needs a 5m BUY (the wake-up path requires a non-bullish 5m followed by a BUY; `:408-412`).
- The exit fires on the first 5m candle that isn't BUY or WATCH.
- So the position survives only while a single 5m state lasts. That took 1–4 bars here.

**Classification:** a design inconsistency between the FIX-154 entry relaxation and the exit and add policy. Each piece is implemented as written; together the policy contradicts itself. This is a logic-defect candidate, not stale data.

**AGENT INFERENCE:** because the policy is deterministic, Replay should reproduce it exactly. I haven't run Replay.

### F-21 (CONFIRMED in code; DB footprint strongly supports it): the startup import closed open live candles with no analysis record
*PROJECT EVIDENCE: code plus I3-007/008/009/010.*

**Code:**
1. `BinanceWebSocketManager.start()` runs on `ApplicationReadyEvent` (`BinanceWebSocketManager.java:95-96`). In Spring that event fires only after every `ApplicationRunner` has finished. The startup import, `MarketDataBootstrapService` (`@Order(10)`), is one of those runners. **The live WebSocket therefore stays down for the whole import.**
2. The import calls `CandleRepository.upsert` → `write(..., "BACKFILL", null)` (`CandleRepository.java:99-106`). On a duplicate key it runs `closed=GREATEST(closed,VALUES(closed))` (`:173-188`).
   - That **closes an existing RUNTIME `closed=0` row**.
   - It leaves `ingestion_source='RUNTIME'`, writes no close-transition token, and records no analysis outcome.
   - The comment at `:205` ("backfill inserts missing identities only") contradicts the code at `:173-188`.
3. In OFF mode the import doesn't analyse (`MarketDataBootstrapService.java:107-110`).
4. The missed-close detector only picks up rows that have a token (`LocalClosedCandleDetector.java:50`).
5. Authoritative reconciliation only picks up `closed=0` rows (`LocalCandleReconciliationService.java:131`).
6. **Result:** a candle closed by the import is invisible to both. It gets no signal, no SKIPPED/EXPIRED outcome, and no retry.

**DB footprint at the hour boundary.** All times are 2026-10-10.

| UTC | KSA | Event |
|---|---|---|
| 14:59:06 | 17:59:06 | Last price event before the outage |
| 15:00:28–15:02:12 | 18:00:28–18:02:12 | Open 1m/5m/1h rows closed with `ingestion_source=RUNTIME` and no token, in symbol order (BTC 18:00:28–32, PEPE 18:01:26–31, XLM 18:01:26–18:02:12) |
| 15:01:15 | 18:01:15 | First reconciliation activity (its startup delay is 15 s) |
| 15:02:21 | 18:02:21 | Price events and new candles resume (193 events in that minute) |

- Reconciliation recovered only the rows that were **still open** when it reached them:
  - 1h 17:00 KSA: **2 of 21** symbols
  - 5m 17:55 KSA: 2 of 21
  - 1m 17:59 KSA: 10 of 21
- It needed successor proof first (`:198-207`); the 1h 18:00 KSA successor appeared only at 18:02:21 KSA.
- The other **19 / 19 / 11** candles have no outcome row (I3-008) and no signal (I2-007).
- AGENTS.md says each closed candle must end with one durable terminal analysis outcome, and that gap repair must never use a duplicate-key update that finalises a live row. This path breaks both.

**Effect on the frozen trades:**
- Trade 82 (entry 15:03:06 UTC / 18:03:06 KSA) used a 1h signal 63 minutes old and a 5m signal 8 minutes old. Both were within limits, so the entry followed the rules.
- What the missing 17:00 KSA 1h analysis would have said is **unknown**.

**Classification:** a confirmed data-path defect. Its link to 82's loss is not proven.

**A restart is AGENT INFERENCE, but the code leaves little alternative.** A tokenless RUNTIME close with no recovery row can only come from `importCandles`, which is called only by the startup import or the admin controller. I4-001 and I4-005 are meant to confirm the restart and its protection impact.

### F-16: the clock step is located, but unexplained
*PROJECT EVIDENCE: I3-003; the timing estimate is AGENT INFERENCE.*

- `created_at − observed_at` was about 0 for hours, then a single step to about −2.8 s.
- The step falls inside **2026-10-11 02:00–03:00 KSA (2026-10-10 23:00–24:00 UTC)**:
  - Trade 101 at 02:12–02:21 KSA was still around 0.
  - The hourly average of −799 ms suggests the step came at about **02:43 KSA (23:43 UTC)**.
- After that the skew grows by about 36 ms/h, reaching −3.0 s by 09:00 KSA. That's consistent with the later `CLOCK_SKEW` log lines.
- **I3-004:** no `FUTURE_TIMESTAMP` or `STALE` rejections happened anywhere in 16:33 10-10 → 09:42 10-11 KSA. The only non-applied events were 23 ambiguous equal timestamps and 16 duplicate timestamps (`NON_CANONICAL`).
- So the latent risk is still only latent. U-13 is closed: no rejections occurred.

### F-22 (new, PROJECT EVIDENCE): trade 101's hourly support was a blocked BUY
- `HigherTimeframeBuyAssessmentService` and `balancedBuy` read only the 1h decision and confidence. They ignore `final_entry_allowed` on the 1h signal.
- For 101, the 1h BUY had confidence 49 and was entry-blocked, yet it still counted as "bullish". That gave NO_CONFLICT at entry and a PASS on the continuation check at TP.
- The 5m signal of the same trade was downgraded to WATCH when blocked; the 1h kept BUY. Whether that difference between timeframes is intended is **unknown** (U-14).
- This isn't the cause of the loss, which was the FIX-118 rebase floor (F-13). It is a policy question.

### F-19 / U-11 (EXTERNAL RESEARCH)
- Binance documents kline stream updates at "2000ms for the other intervals" ([Binance WebSocket Streams](https://developers.binance.com/docs/binance-spot-api-docs/web-socket-streams)).
- The observed per-symbol cadence matches that: BTC at 12.02 / 14.04 / 16.04.
- The documentation doesn't say whether pushes are skipped when nothing traded. I found no deduplication in `MarketPriceEventService`. SHIB's 25-second silence therefore remains **unexplained**: it may be skipped pushes on low activity, which is AGENT INFERENCE.
