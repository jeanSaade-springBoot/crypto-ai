### B. Spec statements that are wrong compared with the code (material)

**F-01 (BLOCKER): the "Production signal-path sequence" in §3.3 is wrong.**
- [PROJECT EVIDENCE] The spec (line 66) gives: advisory, TP, stop loss, rebase floor, profit lock, SELL, near-TP, add.
- The code runs: advisory, TP, **profit-lock trigger, then stop loss**, then rebase hard floor, then SELL (suppressed while the lock is active), then add. There is **no near-TP step on the signal path**.
- §3.3 also contradicts the spec's own D16 row.
- [AGENT INFERENCE] §3.3 is the sequence the tests must use, and §7.2 treats "stop-loss precedence" as a critical class. Freezing it would put the wrong precedence into the critical-safety fixtures.
- Precedence also differs by path: on the price path stop loss comes before the profit lock. §7.2 must therefore state precedence per path.

**F-02 (BLOCKER): the "same arguments" claim behind D14 is false.**
- [PROJECT EVIDENCE] When the dynamic profit lock is disabled, Production returns "inactive" immediately. It updates no state, and the hard floor cannot fire. When enabled, it calls `ProfitLockPolicy.evaluate` with a literal `true`.
- Replay passes the admin toggle instead. Even with the toggle off, it still runs its rebase branch and the rebase hard-floor exit, and it still updates the highest price.
- The RPR-0.8.4 note says both paths call the policy "with the same arguments". That is wrong whenever the toggle is off. D14 needs a toggle-off fixture.

**F-03 (BLOCKER): Replay makes a live Binance HTTP call that the spec does not register.**
- [PROJECT EVIDENCE] Replay's near-TP harvest step (reachable in exact-price mode) calls `BinanceMinimumExecutionPolicy.evaluate`. That calls Binance REST `GET /api/v3/exchangeInfo`.
- [AGENT INFERENCE] This breaks the §2 "no Binance/HTTP" rule. It applies today's exchange rules to historical decisions. A network failure changes the outcome (the harvest is skipped). The calls also use the same REST rate-limit budget as Production, which AGENTS.md requires to be shared.
- D11 calls this only "quantity-driven non-comparable". Neither the register nor RPR7 lists the HTTP call.

**F-04 (BLOCKER): FIX-122 stop-boundary input is missing from the register.**
- [PROJECT EVIDENCE] Production reads its stop-loss boundary from `wallet_trade`, an account table. Inside a Replay scope it uses Replay's own recorded stops. Outside a scope it falls through to the Production read.
- Every evaluation also writes a `fix122_evaluation` row. That happens during generation, which conflicts with §6.2 item 1.
- `RegressionTestService.start` lets a request set `fix122Enabled=false`, a Replay-only switch that the spec does not retire.
- [AGENT INFERENCE] With entries seeded from Production, Replay's own stops will diverge from Production's. That changes BUY eligibility. This must be added to D18 and E01, and the request-level FIX-122 switch must be retired from the baseline.

**F-05 (BLOCKER): the wallet_settings rule contradicts itself.**
- [PROJECT EVIDENCE] The shared Production `TradeExecutionValidationService` reads `wallet_settings`, with no scope check, for two settings: `requireNewBuyTransition` and `executionProfile` (CONSERVATIVE, BALANCED or AGGRESSIVE).
- [AGENT INFERENCE] The spec requires all of these at once:
  - §8.2: "remove all wallet_settings reads";
  - §5: "no Production class modified";
  - §3.4: Replay calls the shared validation code.
- All three cannot be met together. E10 and the historical-configuration gate (§3.6) also leave out these two settings.

**F-06 (BLOCKER): the seeded-entry lifecycle (Appendix C-1) is underspecified.**
- [PROJECT EVIDENCE] Production progressive adds change the average entry price, raise the stop loss and raise the take profit. Replay currently opens positions only from its own decisions.
- [AGENT INFERENCE] The spec does not define:
  - how seeded entries are injected into Replay;
  - whether Replay's own BUYs and adds are suppressed or only compared;
  - how Production adds and partial harvests are seeded (E09 covers the entry only);
  - which signal stream drives lifecycle context, Production-recorded or Replay-generated.
- If Replay-generated signals drive the lifecycle, signal mismatches flow into lifecycle results. The two metrics would then not be "separate" as §7.1 claims.

**F-07 (BLOCKER): the label model is inconsistent.**
- [PROJECT EVIDENCE] §1 defines only `ANALYSIS_PARITY` as a positive label. §6.1 says the validator "may award only ANALYSIS_PARITY, never lifecycle". Yet §7.1 defines a lifecycle-parity acceptance metric.
- Refusal is a run-level label ("no artifact published"), but D25 and §3.3 refuse per span.
- [AGENT INFERENCE] There is no label that can certify a lifecycle result, and the granularity of a refusal is undefined.

**F-08 (MATERIAL): D26 is incomplete.**
- [PROJECT EVIDENCE] The proven-trade detail and list endpoints in `RegressionTestService` call `TradeInvestmentHistory.closedWallet`, which reads `wallet_trade`.
- `/runs/{id}/fix127` reads Production `signal_processing_work`.
- RPR7-10 and D26 name only `allTradesChart`. This second path must also be registered.

## OBJECTIONS

2. [AGENT INFERENCE] The design has an assumption risk. "Replay-local mirrors, no Production change" cannot cover the wallet reads and fall-through branches inside shared Production classes (F-04, F-05) unless a JDBC- or AOP-level guard is specified. The spec gives no guard mechanism, and E01 is only planned.
3. [AGENT INFERENCE] Statistics: thresholds per exit class are not defined, and the required sample sizes are not estimated (M-09). E06's "99% baseline on existing Production output" has no Replay implementation to compare against yet.
4. [AGENT INFERENCE] Look-ahead risk: candle closure, price-event status, wallet settings and provider configuration are all read in their current state (M-04, F-05).
