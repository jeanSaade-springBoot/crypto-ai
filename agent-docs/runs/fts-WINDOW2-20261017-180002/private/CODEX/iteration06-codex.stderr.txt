# Trade Investigation Agent

## Role

Investigate one Crypto AI Trader trade from durable evidence. Explain what
happened, why the system entered and exited, whether it followed the intended
rules, and whether the entry/exit was supported by the information available
at that time.

Investigations are read-only. Do not change code, configuration, services,
database records, review states, Replay work, or deployment state.

## Required input

Obtain or resolve:

- Environment and application: local, test, or production.
- Database host, port, and schema.
- One trade reference: `paper_position.id`, `wallet_trade.id`, or a symbol plus
  a bounded approximate entry-time window.
- Optional question or suspected issue.

Before analysis, confirm the symbol, trade/position ID, running version or FIX
level, and ingestion mode. Read the actual schema before choosing tables or
columns. Do not assume a table is in `crypto_ai` when it may belong to
`crypto_ai_v2`.

## Evidence rules

- Use configured database and SSH/log connections without displaying secrets.
- Use bounded, read-only queries and targeted log searches.
- Treat stored timestamps as UTC; display both UTC and KSA (`UTC+03:00`).
- Attach record IDs and timestamped log evidence to every factual conclusion.
- Distinguish **confirmed fact**, **supported inference**, and **missing or
  conflicting evidence**.
- Missing logs or records do not prove that no execution/effect occurred.
- A saved signal does not prove execution. A callback return does not prove a
  transaction committed. Under FIX-153, `market_price_event.APPLIED` proves a
  committed successful protection callback, but can be a no-op when there was
  no open position; find the position/trade mutation separately.
- Current configuration does not prove which settings were active at entry. If
  no configuration history exists, report that limitation.

## Investigation workflow

### 1. Resolve identity and environment

Link the trade reference to, where available:

- `paper_position`
- `wallet_trade`
- entry and exit `trade_signal`
- `signal_processing_work`
- wallet/position execution records

Record entry and exit times in UTC and KSA. Confirm whether the trader ran in
local-candle OFF mode or a legacy shared-market mode.

### 2. Collect a small evidence bundle

Start with exact IDs and a narrow time window. Expand only when the evidence
requires it. Collect:

| Evidence | Establishes |
| --- | --- |
| `paper_position` | lifecycle, entry/exit, stop, target, status |
| `wallet_trade` | executed quantity, prices, fees, linked signal |
| `trade_signal` | decision, strategy, scores, entry eligibility, reasons |
| `signal_processing_work` | claim, attempt, completion, expiry, uncertainty |
| `candle` / `technical_indicator` | market data and analysis inputs available then |
| `market_price_event` | intra-candle protection observations and outcomes |
| configuration/version evidence | applicable rules, when historically available |
| application and timing logs | analysis, execution, protection, exceptions, waits |

Avoid fetching large signal explanation fields until they are needed.

### 3. Reconstruct the timeline

Build a timeline, explicitly showing missing stages:

`candle closed ƒ+' signal saved ƒ+' work claimed ƒ+' locks acquired ƒ+' entry committed ƒ+' protection observations ƒ+' exit decision ƒ+' exit committed`

Measure separately:

- candle close to signal generation;
- signal generation to processing/entry;
- observation time to protection completion;
- exit-trigger evidence to recorded exit.

Correlate delays only with logs/events for the same symbol, position, signal,
or price-event identity. A nearby slow SQL query is not proof of causation.

- signal mode, closed-candle identity, freshness, and data quality;

- correct signal/position linkage and absence of duplicate/stale-retry entry;
- quantity, wallet balance, risk limits, fees, and fill/reference-price gap.

- **Execution correctness:** followed or violated the implemented rules.
- **Entry quality:** supported, weak, or unverifiable from contemporaneous
  evidence.

Subsequent price movement may evaluate the outcome; it must never be presented
as information the entry decision had.

### 5. Reconstruct protection and stop-loss behavior

For FIX-153, inspect accepted `LEGACY`/`APPLIED` price events and retain
`PENDING`, `NON_CANONICAL`, and `PROTECTION_NOT_APPLIED` records as evidence
gaps or exclusions. Never substitute candle OHLC for absent intra-candle price
evidence.

For each relevant accepted observation:

1. Determine the then-active stop, target, trailing stop, and profit-lock state.
2. Find the first accepted observation that met an exit threshold.
3. Confirm that protection evaluated it and identify the resulting position or
   wallet execution record.
4. Explain delays, rejections, stale/out-of-order classification, exceptions,
   lock waits, or pool pressure.

Classify the exit path accurately: fixed stop-loss, trailing stop, profit-lock,
take-profit, signal-driven exit, manual exit, or unknown.

### 6. Assess exit correctness and quality

Compare the recorded exit reason, quantity, and price with trigger evidence.
Check threshold reach, accepted-observation identity, protection timing, and
the committed execution. Calculate maximum favourable/adverse movement during
the holding period separately from the contemporaneous exit assessment.

### 7. Reconcile financial results

Recalculate using execution records:

- bought/sold quantities and weighted entry/exit prices;
- gross P&L, fees, and net P&L;
- partial exits, remaining quantity, and realized versus unrealized values.

Flag discrepancies among wallet records, position records, and UI output.

### 8. Diagnose cause and use Replay carefully

Classify findings as one or more of:

- strategy decision;
- data freshness or coverage;
- analysis delay;
- execution failure;
- protection failure;
- database, lock, or connection-pool contention;
- accounting/UI discrepancy;
- insufficient evidence.

Run Replay only as a controlled comparison with equivalent candles, accepted
prices, strategy version, and settings. State every unavailable input or
material difference. Never claim parity by substituting candle OHLC for missing
price evidence or treating `PENDING` as accepted.

## Implemented, unverified: local-candle architecture (FIX-153)

The implemented intended mode is `shared-market.mode=OFF` with trader-owned Binance kline
ingestion and local candle writes. The shared executors and direct-ingestion
path must never run together.

Implemented safeguards:

- Candle writes are monotonic: a late open update cannot reopen or overwrite a
  closed candle.
- A closed-candle transition is admitted exactly once using an atomic upsert
  result plus in-process admission coordination.
- A bounded local detector recovers a closed candle that was committed before
  the in-memory event/dispatcher could start analysis.
- Fresh candles may execute; stale candles are analysed historically only, or
  their already-owned work is expired without business execution.
- Analysis lanes are bounded. Under overload, 1m may retain only the latest
  pending candle; higher intervals use an explicit bounded FIFO policy.
- Historic shared `REVIEW_REQUIRED` evidence must not block OFF-mode work.
- OFF-mode health/admin endpoints must use local-candle health and must not
  query retired shared-market tables.
- Current REST backfill can finalise an interrupted open row but cannot mint a
  runtime close token or dispatch analysis. Runtime close tokens plus
  provenance keep backfill out of detector admission. The approved, pending
  automatic-reconciliation extension will also insert an exact wholly absent
  candle only inside the active quality window, with `BACKFILL` provenance and
  the same no-token/no-dispatch boundary.
- Observed local behavior (2026-10-09): a WebSocket reconnect at a candle-close
  boundary can leave the already-persisted 1m/5m rows open because Binance does
  not replay the final closed-kline event. The current detector recovers missing
  analysis admission, not missing close facts. An authoritative, bounded REST
  repair may therefore finalise the exact `closed=0` row or, under the approved
  gap-backfill scope, insert an exact absent identity. It must preserve existing
  provenance, use `BACKFILL` for an insertion, create no close-transition token,
  and never dispatch historical work. Automatic reconciliation of this reconnect
  case remains a FIX-153 release gate; the one-time local repair is evidence,
  not proof that the gap is closed.
- Approved pending reconciliation design: gap backfill is insert-only (no
  duplicate-key update); it can never alter a live row that appears during a
  REST request. Candidate selection is bounded to the active quality window;
  terminal audit records are not retried. Every candle/work route must produce
  a durable terminal outcome or remain explicitly retryable after a transient
  failure. Historical-only processing has no execution authority.
- The pending universal mutation barrier is an in-memory drain participant,
  not a database or persistent trading fence. Outside drain it must not delay,
  queue, or block fresh trading, signals, or protection. Open-position
  protection during application replacement remains an unresolved release gate.
- Local source now contains the first reconciliation implementation slice:
  V107 durable audit/outcome tables, update-only authoritative open-row repair,
  pure insert-only gap backfill, a dedicated recovery executor, a reconnect
  request hook, and drain participation. It is disabled by default and remains
  unvalidated on MySQL; it has no deployment approval.
- Direct prices are normalised to `DECIMAL(30,12)` before persistence,
  protection and completion. Equal timestamps have one canonical receipt.
- Every processing attempt is freshness-checked after normal locks using the
  database-to-exchange correction. JVM-origin timestamp decisions use the
  separately measured JVM-to-exchange correction. The measurement performs no
  HTTP under execution locks and uses a bounded five-second time-only client.
  General Binance REST calls use the configured request timeout, and scheduled
  clock sampling has a four-thread Spring scheduler pool.
  Bootstrap obtains time/klines before opening its local candle-write
  transaction, so a stalled REST request does not retain database resources.
  REST bootstrap gets Binance server time before klines.
- An ADMIN-only drain stops analysis admission, exits the JVM on successful
  quiesce, and resumes admission on timeout. Price protection pauses during
  the controlled drain window.

## Implemented, unverified: protection price-event state machine

```text

  -> NON_CANONICAL           (invalid, stale, out-of-order, or duplicate)
```

Replay and price authority consume only accepted `LEGACY`/`APPLIED` rows.

operational prerequisite, not a database lease or fence.

# FIX-154 Г?" Implementation Handoff for Code Review

Date: 2026-10-10  
Status: implemented in the local working tree; not deployed.

## Scope

FIX-154 changes only higher-timeframe BUY authority. It does not enable or
change FIX-153 reconciliation/runtime behavior.

The objective is to distinguish trusted, strong bearish 1h evidence from
unknown or weaker evidence without changing a stored historical signal.

## Implemented policy

1. The current 1m BUY still requires fresh 5m and 1h context.
2. A bearish 5m returns the existing `5M_BEARISH_VETO` first.
3. A bearish 1h with `data_quality_valid` `NULL` or `false` returns
   `1H_BEARISH_VETO`.
4. A trusted 1h `STRONG_SELL` with `confidence_score >= 70` returns
   `HTF_TRUSTED_BEARISH_VETO`.
5. A trusted 1h `SELL`, or `STRONG_SELL` with confidence below 70, is a
   SOFT conflict. It passes effective 1h `NEUTRAL` to profile logic and caps
   every allowed initial entry at 25%.
6. A non-bearish 1h with unknown quality keeps its raw decision; FIX-154 does
   not tighten bullish/non-bearish authority merely because historical quality
   is absent.
7. Existing progressive/add logic retains its raw 1h requirement. A SOFT
   conflict cannot authorize an add. Optional `SOFT_HTF_ADD_BLOCKED` evidence
   is observational only.

# FIX-154 Г?" Trusted higher-timeframe BUY validation

Status: implementation design approved. FIX-154 is scheduled before the
remaining FIX-153 runtime release work.

## Purpose and boundary

FIX-154 replaces the current binary fresh-1h bearish veto with a trusted
higher-timeframe assessment. It does not relax the existing 5m confirmation
requirement, risk/reward result, current-1m BTC protection, or profile rules
except where a raw 1h decision would otherwise act as an untrusted veto.

The legacy `src/main/resources/md/FIX-146.md` is an unrelated shared-market
readiness design and is not an implementation source for this fix.

## Current integration points to replace

The 1h/5m blocks in all three paths below must be replaced as a whole by one
shared assessment call. Do not add this decision to `FinalDecisionService`.

1. `TradeExecutionValidationService.validateBuy()` Г?" direct 1m BUYs.
2. `TradeExecutionValidationService.validateBuyContext()` Г?" accumulated/setup
   authority, whose reference may be a 5m signal.
3. `OpportunityConsolidationService.evaluate()` Г?" consolidated BUYs.

Each replacement owns the current lookup, freshness, 5m veto, and 1h veto
block in that method. The remaining profile/consolidation logic consumes the
assessment's effective context; it must not reread the raw 1h decision as an
independent veto.

## Immutable signal evidence

Migration `V107` adds:

```sql
ALTER TABLE trade_signal ADD COLUMN data_quality_valid BOOLEAN NULL;
```

`AnalysisService` writes `MarketContextSnapshot.dataValid()` through the
existing `TradeSignal.builder()` call for every newly generated signal on every
interval. Historic rows are never backfilled: `NULL` means unknown/invalid.

FIX-154 does not depend on `signal_mode` or any other FIX-153 runtime/schema
feature. `data_quality_valid = true` is sufficient evidence eligibility for
this release; false or `NULL` is unusable. Historical-only exclusion is added
later with FIX-153, after its own migration/runtime release is approved.

Historical `btcContextEntryAllowed=false` is audit evidence only. It is never a
FIX-154 usability or hard-veto predicate. The current 1m BTC guard is unchanged.

## Time-bounded selection and fixed freshness

For a request with reference signal `R`, use `R.generatedAt` as `evaluatedAt`.
Select the latest same-symbol 5m and 1h signal such that both its generated
time and its candle close are at or before `evaluatedAt`; no wall-clock lookup
is permitted. Replay supplies the same historical reference time.

Existing fixed freshness limits remain authoritative:

| Interval | Maximum age |
|---|---:|
| 5m | 20 minutes |
| 1h | 3 hours |

`MISSING_5M_CONFIRMATION` and `MISSING_1H_CONTEXT` retain their existing
meaning and priority when their respective interval is missing or stale. A
stale signal is not quietly converted into an allowed BUY just because it is
`NOT_TRUSTED` for FIX-154.

## Usability and 1h strength

A fresh row is usable for FIX-154 only if `data_quality_valid = true`.

FIX-154 v1 does not invent ADX/DMI/VWAP/CMF evidence, because those indicators
are not currently persisted. Its fixed strength definition is:

```text
HARD_BEARISH_CANDIDATE = 1h decision == STRONG_SELL
                         AND confidence_score >= 70
SOFT_CONFLICT          = fresh, quality-valid 1h decision == SELL
                         OR STRONG_SELL with confidence_score below 70
NOT_TRUSTED            = fresh but quality-invalid/unknown/historical-only 1h
                         OR fresh non-bearish 1h
```

`confidence_score` is the persisted effective confidence. `raw_confidence_score`
is explicitly not used. The constant `70` is a named FIX-154 configuration
default, persisted in the audit row, and may change only through a reviewed
strategy change with Replay regression.

## Exact 1h A- 5m decision matrix

First apply existing missing/stale checks. Only then apply this table.

| 1h state | 5m state | Final HTF result before profile | Profile inputs |
|---|---|---|---|
| missing/stale | any | existing `MISSING_1H_CONTEXT` rejection | none |
| any | missing/stale | existing `MISSING_5M_CONFIRMATION` rejection | none |
| NOT_TRUSTED bearish from false/NULL quality | bearish | legacy `5M_BEARISH_VETO` | none |
| NOT_TRUSTED bearish from false/NULL quality | bullish/neutral/watch | `1H_BEARISH_VETO` | none |
| NOT_TRUSTED non-bearish from false/NULL quality | bearish | legacy `5M_BEARISH_VETO` | none |
| NOT_TRUSTED non-bearish from false/NULL quality | bullish/neutral/watch | continue to profile | raw 1h, raw 5m |
| SOFT_CONFLICT | bearish | legacy `5M_BEARISH_VETO` | none |
| SOFT_CONFLICT | bullish/neutral/watch | continue to profile, cap resulting first entry at 25% | effective 1h=`NEUTRAL`, raw 5m |
| HARD_BEARISH_CANDIDATE | bearish, quality-valid | legacy `5M_BEARISH_VETO`; audit `HARD_CONFIRMATION_PRESENT` | none |
| HARD_BEARISH_CANDIDATE | bullish/neutral/watch, quality-valid | `HTF_TRUSTED_BEARISH_VETO` | none |
| fresh, quality-valid non-bearish 1h | non-bearish | continue to profile | raw 1h, raw 5m |

The profile call produces the final decision for every `continue to profile`
row. It may still return its existing insufficient-confirmation code. It must
not consult the raw 1h row after this mapping.

`5m quality=false/NULL` does not alter the legacy 5m fallback. A fresh raw
bearish 5m still returns `5M_BEARISH_VETO`, exactly as today. It merely cannot
act as new FIX-154 hard-veto confirmation or a soft-conflict release.

The veto order is fixed: a bearish 5m returns `5M_BEARISH_VETO` before any
trusted-1h result. If the 1h is hard, audit records `HARD_CONFIRMATION_PRESENT`
on that legacy outcome. When 5m is not bearish, a hard trusted 1h returns
`HTF_TRUSTED_BEARISH_VETO`. The only deliberate lasting relaxation is a trusted
SOFT bearish 1h: an otherwise allowed initial entry is capped at 25%.

## Profile contract

`conservativeBuy`, `balancedBuy`, `balancedBuyWithNeutralFiveException`, and
`aggressiveBuy` receive the assessment's effective 1h/5m contextГ?"not raw
selected 1h evidence. A SOFT conflict maps to `NEUTRAL`, never `WATCH`, then
the validation result is capped with `min(profilePositionPercent, 25)`.
This means the neutral-5m/direct-BUY exception still requires a genuinely
bullish 1h and cannot be unlocked by SOFT evidence. An untrusted non-bearish
1h retains its raw decision so deployment does not accidentally tighten current
bullish authority.

The assessment result carries `maxInitialPercent`: `25` for `SOFT_CONFLICT`,
otherwise no cap. Every caller that selects a size must use
`min(itsCalculatedPercent, maxInitialPercent)` when the cap is present. This
includes direct validation, `validateBuyContext()` callers (the 5m-trigger
path and accumulated evidence), and
`OpportunityConsolidationService.consolidatedPositionPercent()`.

The raw selected signals remain audit evidence. Existing 5m requirements inside
profiles remain unchanged. HARD and untrusted-bearish outcomes never call a
profile method.

### Add-on contract

`ExecutionIntelligenceService.progressivePositionDecision()` already reads raw
1h evidence and requires `WATCH` or bullish support for `SCOUT_ENTRY`,
`CONFIRMATION_ADD`, and `PROGRESSIVE_TREND_ADD`. Keep that check unchanged and
outside the three replacement paths; it already blocks HARD, SOFT, and
untrusted-bearish 1h states. Do not route it through effective FIX-154 context,
which could widen behavior. When that existing check rejects while the assessed
band is SOFT, record `SOFT_HTF_ADD_BLOCKED` as audit/metric evidence only.

## Append-only execution audit

FIX-154 is evaluated during execution/consolidation, not while a signal is
saved. Migration `V107` creates append-only `buy_htf_assessment_audit`:

- primary key ID;
- reference signal ID, evaluation path (`DIRECT_BUY`, `BUY_CONTEXT`,
  `CONSOLIDATION`, `PROGRESSIVE_TREND_ADD`, `CONFIRMATION_ADD`,
  `ACCUMULATED_EVIDENCE_ADD`) and `evaluated_at`; no unique constraint;
- raw/effective 1h and 5m signal IDs, decisions, signal modes, candle closes,
  ages, data-quality values, and usability reasons;
- configured confidence threshold, band, legacy-veto result, profile context,
  final result/reason, Production/Replay mode, and creation timestamp.

The audit is written best-effort after the relevant execution/consolidation
decision is known. A duplicate or persistence failure is logged and increments
`fix154.audit_write_failure_count`; it must never roll back, reject, or alter a
trading decision. It is evidence onlyГ?"not a fence or an input to later trading.

## Revision addendum Г?" Round 5 approval conditions

This addendum governs where it differs from earlier wording.

### Release build decision

The FIX-154 release build includes `V108__fix_153_local_candle_reconciliation.sql`
after the current unreleased FIX-153 V107 migration is renumbered to V108.
This is required even with reconciliation disabled: `candle_analysis_outcome`
is used by ordinary live signal processing, terminal worker outcomes, and the
closed-candle detector. Omitting V108 would cause missing-table SQL failures;
in particular, a normal signal-processing completion would roll back because
its outcome write is inside the processing transaction.

Including V108 ships FIX-153 reconciliation *schema only*. The reconciliation
runtime remains disabled and retains all of its separate release gates.

### No FIX-153 provenance dependency

Ignore earlier references to historical-only status or signal modes in the
FIX-154 band definition and audit payload. FIX-154 v1 eligibility depends only
on time-bounded selection and `data_quality_valid = true`; `signal_mode` is not
read, required, or stored by the FIX-154 audit.

### Effective context is transient

The assessment returns immutable effective decision values separately from the
loaded `TradeSignal` entities. No code may call `setDecision`, mutate, merge,
or save a selected 1h/5m signal to obtain effective `NEUTRAL` context. Profile
methods receive explicit effective decisions (or an immutable assessment
context), while the raw entity remains audit evidence only. A regression test
must load a SOFT 1h signal, execute the assessment/profile path, flush/clear,
and prove its stored decision is unchanged.

### Progressive-path evidence is observational

`progressivePositionDecision()` retains its existing raw-1h support check as
the only decision authority for scout/add paths. If that existing check passes,
FIX-154 performs no assessment lookup and writes no progressive audit row. If
it rejects because raw 1h is bearish, a best-effort audit-only assessment may
record `SOFT_HTF_ADD_BLOCKED` when the band is SOFT. That observation must not
alter the rejection, allow an add, cause a database lookup on passing paths, or
propagate an audit failure into the trading decision.

V108 ships with FIX-154 because the current runtime writes
`candle_analysis_outcome`. Reconciliation remains disabled.

### Round 5 text clarification

This addendum removes any earlier contrary implication: FIX-154 v1 has no
`signal_mode` or historical-only predicate or audit field. Effective 1h/5m
decisions are separate immutable values and never mutate a loaded signal.
Progressive-path assessment is audit-only after its existing raw-1h check has
already rejected; it is skipped entirely when that check passes and never feeds
the scout/add decision.

package com.crypto.position.service;

import com.crypto.domain.SignalDecision;
import com.crypto.domain.TradeSignal;
import org.springframework.stereotype.Component;

/**
 * Shared production/replay exit authority for an already-open long position.
 *
 * The policy deliberately separates short-timeframe noise from a genuine
 * higher-timeframe breakdown:
 *  - a 1m pullback alone never closes the position;
 *  - the existing 1m SELL + bearish 5m confirmation remains valid;
 *  - a fresh 1h SELL may close a position when 5m is no longer supportive;
 *  - a Profit Lock breach is tolerated while 5m/1h still support the bullish thesis.
 */
@Component
public class PositionExitPolicy {

    public Evaluation evaluateNormalExit(TradeSignal current, TradeSignal fiveMinute, TradeSignal oneHour) {
        SignalDecision currentDecision = decision(current);
        SignalDecision fiveDecision = decision(fiveMinute);
        SignalDecision oneDecision = decision(oneHour);

        boolean oneHourBreakdown = bearish(oneDecision)
                && fiveMinute != null
                && !supportive(fiveDecision);
        if (oneHourBreakdown) {
            return Evaluation.exit("HTF_SELL_CONFIRMED",
                    "1h turned " + label(oneDecision)
                            + " while 5m is no longer supportive (" + label(fiveDecision)
                            + "). The higher-timeframe bullish thesis is broken; close the managed position.");
        }

        boolean lowerFrameConfirmed = current != null
                && "1m".equals(current.getInterval())
                && bearish(currentDecision)
                && fiveMinute != null
                && bearish(fiveDecision)
                && (oneHour == null || !bullish(oneDecision));
        if (lowerFrameConfirmed) {
            return Evaluation.exit("SELL_CONFIRMED",
                    "1m " + label(currentDecision) + " is confirmed by bearish 5m while 1h is not bullish.");
        }

        return Evaluation.hold("No confirmed multi-timeframe exit."
                + " current=" + label(currentDecision)
                + ", 5m=" + label(fiveDecision)
                + ", 1h=" + label(oneDecision) + ".");
    }

    public Evaluation evaluateProfitLockBreach(TradeSignal current, TradeSignal fiveMinute, TradeSignal oneHour) {
        SignalDecision currentDecision = decision(current);
        SignalDecision fiveDecision = decision(fiveMinute);
        SignalDecision oneDecision = decision(oneHour);

        // Strong HTF support: tolerate a sharp 1m pullback instead of throwing away the trend.
        if (bullish(oneDecision) && fiveMinute != null && supportive(fiveDecision)) {
            return Evaluation.hold("PROFIT_LOCK_HOLD",
                    "Profit Lock was breached, but higher-timeframe continuation remains healthy:"
                            + " 1h=" + label(oneDecision) + ", 5m=" + label(fiveDecision)
                            + ", current=" + label(currentDecision)
                            + ". Treat the breach as a protected pullback, not an immediate SELL.");
        }

        // Cooling but still-supported trend: WATCH/WATCH is allowed to breathe while the current frame is not bearish.
        if (oneDecision == SignalDecision.WATCH
                && fiveMinute != null && supportive(fiveDecision)
                && !bearish(currentDecision)) {
            return Evaluation.hold("PROFIT_LOCK_HOLD",
                    "Profit Lock was breached during a supported consolidation:"
                            + " 1h=WATCH, 5m=" + label(fiveDecision)
                            + ", current=" + label(currentDecision)
                            + ". Keep the winner protected while waiting for higher-timeframe confirmation.");
        }

        if (bearish(oneDecision)) {
            return Evaluation.exit("PROFIT_LOCK_HTF_EXIT",
                    "Profit Lock was breached and 1h is " + label(oneDecision)
                            + "; higher-timeframe support has failed.");
        }

        if (bearish(currentDecision) && bearish(fiveDecision)) {
            return Evaluation.exit("PROFIT_LOCK_BEARISH_CONFIRMATION",
                    "Profit Lock was breached with bearish 1m and 5m confirmation.");
        }

        return Evaluation.exit("PROFIT_LOCK_EXIT",
                "Profit Lock was breached without enough higher-timeframe bullish support to justify a protected hold:"
                        + " current=" + label(currentDecision)
                        + ", 5m=" + label(fiveDecision)
                        + ", 1h=" + label(oneDecision) + ".");
    }

    private SignalDecision decision(TradeSignal signal) {
        return signal == null ? null : signal.getDecision();
    }

    private boolean supportive(SignalDecision decision) {
        return decision == SignalDecision.BUY
                || decision == SignalDecision.STRONG_BUY
                || decision == SignalDecision.WATCH;
    }

    private boolean bullish(SignalDecision decision) {
        return decision == SignalDecision.BUY || decision == SignalDecision.STRONG_BUY;
    }

    private boolean bearish(SignalDecision decision) {
        return decision == SignalDecision.SELL || decision == SignalDecision.STRONG_SELL;
    }

    private String label(SignalDecision decision) {
        return decision == null ? "MISSING" : decision.name();
    }

```sql
LEFT JOIN crypto_ai.trade_signal entry_signal

LEFT JOIN crypto_ai.trade_signal audit_signal
```
