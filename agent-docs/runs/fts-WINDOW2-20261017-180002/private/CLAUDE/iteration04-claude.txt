## FINDINGS

### F4-1 [PE code]: the confluence columns record only the strongest higher-timeframe signal (corrects F3-7 and U3-2)

- For a 1m signal, confluence reads **both** 5m and 1h (`MultiTimeframeConfluenceService.java:297`).
- It then stores only the one with the largest |trend − 13| (`:73-75`, `:96-100`, `:363-365`).
- So `confluence_higher_signal_generated_at` is not "the 5m that was read". Four cases point at the 1h signal, not the 5m:

| Trade | Signal | Points at |
|---|---|---|
| 172 | 171589 | the 06:00:06.0025 1h signal |
| 158 exit | 166819 | the 03:00:01.5659 1h signal |
| 162 exit | 168277 | the 04:00:09.7942 1h signal |
| — | 166141 | the 03:00:01.5376 1h signal |

- **Audit gap:** the persisted confluence evidence cannot show which 5m was read. This is a forensic-accuracy gap, not a trading defect.

### F4-2 [PE code + DB]: the higher-timeframe lookup cuts off at the 1m signal's own wall-clock time, so the boundary race is real and decided by milliseconds

**Production:**
- Live `generatedAt` is `Instant.now()` (`AnalysisService.java:150`).
- Every Execution-Intelligence (EI) and validation lookup uses `generatedAt <= current.generatedAt` (`ExecutionIntelligenceService.java:2455-2461`, `:2606-2609`; `TradeExecutionValidationService.java:367-379`).

**What each entry saw on its boundary:**

| ID | 1m generated | Same-boundary 5m generated | Visible to entry? |
|---|---|---|---|
| 137 | 156723: 20:55:01.575650 | 156721: 20:55:01.558049 (18 ms earlier) | **yes** |
| 143 | 159408: 22:40:01.633945 (19:40:01.634) | 159407: 22:40:01.635944 (**2 ms later**) | **no** |
| 158 | 165412: 02:35:01.469482 | 165415: 02:35:01.490485 (21 ms later) | **no** |

- **143:** EI deterministically picked the previous 5m BUY, 159285 (22:35:01.553). Its opportunity row 36524 shows `five_minute_decision=BUY` (I3-003). This is a bound-by-generation-time effect, not a commit-visibility race; 159407 was committed at 22:40:02.940, before the opportunity row was written at 22:40:03.051.
- **SETUP_TIMEFRAME_ATR requires the 5m to be bullish, entry-allowed and ATR-immediate** (`ExecutionIntelligenceService.java:1485-1487`). With 159407 (WATCH) visible instead, the route could not have fired. **[AI]** So 143's entry existed only because its 1m analysis started 2 ms before the 5m analysis.
- **158:**
  - The 1m path saw no 5m BUY. Work for 165412 completed 02:35:02.882 with `paper_position_id=NULL`.
  - The entry came from processing the **5m** signal 165415 (work completed 02:35:04.813, `paper_position_id=158`, I3-004), via `SETUP_CONFIRMATION_WAKEUP` reusing 1m 165412.
- **Confluence inside signal building** runs before either row commits. The 5m commit takes about 1.3 s, so on a boundary the 1m confluence practically never sees the same-boundary 5m. 137's confluence used the 20:50:01.42 5m signal, not 156721 (I3-001).

### F4-3 [PE code]: Replay orders same-boundary signals differently from Production. This is a confirmed parity defect.

**Replay mechanics:**
- The timeline sorts by candle close, then by interval: 1h=0, 5m=1, 1m=2 (`RegressionTestWorker.java:557-560`, `:787-793`).
- Replay `generatedAt` is the exact close boundary (`:584`, `:616`).
- `latestAtOrBefore` keeps rows with `!generatedAt.isAfter(ref)` (`ExecutionReplayScope.java:106-120`).

**Result:** in Replay, a 1m signal on a boundary **always** sees that boundary's 5m and 1h, both for confluence and for EI. In Production it sees them only when the 5m analysis happened to call `Instant.now()` first (EI), and essentially never for confluence (F4-2).

**Effect on the six:**

| ID | Expected Replay difference |
|---|---|
| 143 | Would see 5m WATCH 159407. SETUP_TIMEFRAME_ATR returns null, so a different route or no entry. |
| 158 | The 5m is processed before the 1m of 02:35 exists, so a wake-up would bind to the 02:34 1m signal (different price and evidence) or take a direct route on the 1m. |
| 137 | EI parity holds (it saw 156721 in both), but the confluence inputs differ. |

- **[AI]** Production–Replay divergence on every 5-minute-boundary 1m signal. AGENTS.md requires Production and Replay evidence to stay aligned.
- Replay has not been run (U2-9). The divergence is proven from code; its outcome on these trades is inference.

### F4-4 [PE code]: direct-BUY validation trusts only the 5m decision label. F-25 (172) and F-38 (182) are confirmed.

**How validation reads the 5m:**
- `validateBuy` → `htfAssessment.assess` → `balancedBuy` (or its neutral-5m wrapper) uses `decision(fiveMinute)` only (`HigherTimeframeBuyAssessmentService.java:20-21`, `:50`; `TradeExecutionValidationService.java:93-109`, `:300-321`).
- Neither the 5m's `final_entry_allowed` nor its `original_decision` is consulted.

**172 (F-25, confirmed):**
- 5m 171559 is BUY with `final_entry_allowed=0` (RANGE_ENTRY_LOCATION, confidence 49). The 1h is NEUTRAL.
- `balancedBuy:306-308` returns **BALANCED_STRONG 75%**, matching opportunity 39062's text "5m is bullish while 1h is NEUTRAL" (I3-003). Entry Quality then capped it at 25%.
- **Inconsistency between routes:** SETUP_TIMEFRAME_ATR rejects a 5m with `!five.isFinalEntryAllowed()` (`ExecutionIntelligenceService.java:1487`); the direct-BUY route accepts it.

**182 (F-38, confirmed):**
- 5m 176655 is NEUTRAL with `original_decision=STRONG_SELL`. `assess()` treats NEUTRAL as not bearish, so the **5M_BEARISH_VETO (`:22-26`) is bypassed**.
- With the 1h WATCH, the FIX-11G branch (`TradeExecutionValidationService.java:263-284`) grants **BALANCED_NEUTRAL_5M_WATCH_1H 25%**. The size was later capped to 15%.
- **Asymmetry:** other routes do check the original decision. SETUP_TIMEFRAME_ATR and the breakout route veto on `isBearish(current.getOriginalDecision())` (`ExecutionIntelligenceService.java:1478`, `:1518`). The direct validation never checks it for the 5m.

**Classification [AI]:** logic defect (label-only authority). This is distinct from FIX-154 scope. AGENTS.md's FIX-154 notes preserve the legacy `5M_BEARISH_VETO` but do not address a neutralised 5m.

### F4-5 [PE code]: the wallet BUY, managed position and paper open are one transaction, so there is no protection gap (resolves U3-3)

**Transaction scope:**
- `SignalProcessingCoordinator.process` runs `business.apply(signal)` and `store.complete` in one `REQUIRES_NEW` transaction, after the symbol lock (`SignalProcessingCoordinator.java:36-37`, `:64-103`).
- `executed_at`/`opened_at` are `Instant.now()` values captured mid-transaction.
- The commit time is about `signal_processing_work.completed_at` (137: 20:55:04.511; 182: 09:57:06.478, I3-004).
- So the wallet `executed_at` is the **decision/write time inside the transaction, not the commit time**. The 1.5–2.2 s gap is in-transaction work.

**Why there is no gap:**
- Protection takes the same `wallet_symbol_coordination … FOR UPDATE` lock before reading the position (`LivePositionProtectionService.java:54-58`; `WalletTransactionCoordination.java:38-47`, 2 s query timeout).
- A price update for that symbol during the entry transaction **waits**, then sees the committed position. No gap. Rejected.
- **[AI]** Side effect: all ingestion runs on the single WebSocket thread (F3-9). A wait of up to 2 s for one symbol's lock stalls price updates for **all** symbols.
- I3-008 shows a **7214 ms** maximum ingest lag in the 182 window and 1.7–2.2 s maxima in the 158, 162 and 172 windows. Locating them is I4-002.
- The 162 paper `closed_at` coming before the wallet row (F9) is likewise ordering inside one transaction, not commit order (commit 04:26:06.575).

### F4-6 [PE code]: higher-timeframe exits run only when a price update arrives (confirms F3-5)

- Normal exits are evaluated inside `onPrice`: `evaluateNormalExit(one,five,hour)` (`LivePositionProtectionService.java:235-244`).
- It uses the newest *committed* signals (`:95-97`). Signal commits do not trigger this path, so delay = commit + next price update. That is unbounded for thinly traded symbols (172: 37.6 s; 182: 12.7 s).
- **The 172 exit audit credits the 1m SELL** (resolves F2-4): `closePaper(..., one)` passes the newest 1m signal as "context only" (`:391-411`). Crediting `source_signal_id=172587` is a labelling artifact; the trigger was HTF_SELL_CONFIRMED.
- **143:** the hard floor (`entry × 1.0005`, `:210-216`) fires on the first update below it and fills at that update's price. There is no slippage control or limit price. That matches the data (4.027 against a 4.0350 floor). Protection is mechanically correct.

### F4-7 [PE code]: the stop-loss and TP-extension paths behaved as coded for all six

- Stop-loss is absolute (`:174-183`).
- TP extension adds 50% of the entry-to-TP distance (`:108-110`): 143's 4.0647 → 4.0805 → 4.1043 matches.
- The paper TP is kept in sync (FIX-067, `:144-150`).
- No defect for the six.

### F4-8 [PE]: SETUP_TIMEFRAME_ATR's 30% text is accurate at that stage; the cap comes later

- `DEFERRED_POSITION_PERCENT = 30` (`ExecutionIntelligenceService.java:104`, `:1499`). The text "conservative 30%" is printed before Entry Quality capped the size to 25% (opportunity `recommended_position_percent=25`).
- This is an explanation-staging inconsistency (F2-7), not a defect.

## STATUS AFTER ITERATION 4

**Confirmed defects [PE code + DB]:**
1. **Boundary lookup race and Replay-parity divergence (F4-2/F4-3).**
   - Production bounds the higher-timeframe lookup by the 1m signal's wall-clock time; Replay orders 1h → 5m → 1m with identical times.
   - It decided 143's route (2 ms margin) and 158's route.

   - A 5m BUY with its own entry blocked (172), and a 5m STRONG_SELL neutralised to NEUTRAL (182), each authorised entries.
   - Other routes do check these fields.

**Confirmed audit gaps (not P&L):**
- The confluence columns record only the strongest context (F4-1).
- The exit audit credits the newest 1m signal as its source (F4-6).
- SELL fills do not persist the price observation (F2-5).

**Rejected:** a protection gap at entry (F4-5) and incorrect protection mechanics (F4-6, F4-7).

**Design properties:**
- Higher-timeframe exits run only when a price update arrives.
- Stop and floor exits fill at the triggering update with no slippage control.
- Entry transactions hold a symbol lock while ingestion runs on a single WebSocket thread (stall risk; I4-002).

**Valid losing trades on the evidence so far:** 137 and 162 (thin targets; F2-10, F11). Whether 158's loss is attributable to the defect depends on the Replay outcome.
