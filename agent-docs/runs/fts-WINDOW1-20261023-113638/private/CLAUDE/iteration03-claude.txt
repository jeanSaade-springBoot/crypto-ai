**F-I3-02: Normal signal exits run on price ticks, not on signals. So the exit happens on the first price tick after the third timeframe's signal is committed.** [PROJECT EVIDENCE: code]
- `LivePositionProtectionService.java:95-97` reads the newest committed 1m, 5m and 1h signals on each tick.
- `:235-243` then applies `PositionExitPolicy.evaluateNormalExit` (`PositionExitPolicy.java:20-50`).
- Consequence: the exit can only happen after the *last* required signal has committed **and** another price tick for that symbol has arrived.

- **Why 158 and 162 were quick.** Signals become visible only when committed, and `created_at` runs 1.3–2.3 s after `generated_at` (F-I2-09). That fully explains 158 and 162.

- **Exits followed the rules.** HTF_SELL_CONFIRMED for 172 matches the policy: the 1h SELL exit waited 15 minutes, until 5m stopped being supportive (WATCH → NEUTRAL).
- **137 is unresolved.** Its 5m/1h context was cut off by `LIMIT 120` in I2-002 (five trades × up to 26 rows already filled the 120 rows). It is re-requested.

**F-I3-04: The 8-second gap in trade 143 affected EGLD only; the price stream as a whole kept flowing.** [PROJECT EVIDENCE: I2-004 + AGENT INFERENCE]
- **Ticks stored.** EGLD ticks were stored at 22:43:19, :21, :27, :35, :37, … UTC (01:43 KSA, 12 Oct). Both the :21→:27 gap (6 s) and the :27→:35 gap (8 s) skipped the expected 2-second updates.
- **The stream was healthy.** Event IDs kept rising at a steady ~3.4–4 per second across all symbols (1789351 → 1789359 → 1789382 → 1789409).
- **Every message is stored.** `BinanceKlineService.java:106` writes a `market_price_event` for every 1m kline message, with no de-duplication. The only exception is `recordPending` (`MarketPriceEventService.java:52-57`), which drops stale or future-dated observations without a row but logs `[FIX-153][PRICE_NOT_CANONICAL]`.
- **The drop.** The 22:43 UTC 1m candle has high 4.100, low 3.994 and volume 6382.8, about 9.5× the previous minute. The first tick after the gap, at 4.027, came during a fast fall.
- **Three possible causes, none proven:**
  - (a) Binance sent no update because there were no trades. External docs give a 2000 ms cadence but do not say whether an update is sent when nothing traded.
  - (b) Binance messages for EGLD were delayed or dropped.
  - (c) The trader rejected them at input, which would leave a PRICE_NOT_CANONICAL log line.
- (c) can only be ruled out from production logs, which I can't reach.
- [AGENT INFERENCE] Even with no gap, a 4.100 → 3.994 drop within a minute means a fill near the 4.035 floor was not guaranteed. The tick gap made the fill worse; it did not cause the loss.

**F-I3-05: The 1.2–3.2 s gap between the wallet record and the paper record happens inside one transaction. It is not a non-atomic commit.** [PROJECT EVIDENCE: code + AGENT INFERENCE] (resolves U-10, subject to the I3-004 check)
- The live exit path runs inside a single `@Transactional` call (`onPrice`, `LivePositionProtectionService.java:74`). `executeMechanicalExit` (`WalletAutoExecutionService.java:474`) joins that transaction.
- `wallet_trade.executed_at` is set to `Instant.now()` at `:548`. After that, the code still runs:
  - `walletService.currentPortfolioValue()` (`:556`)
  - `walletService.captureSnapshot()` (`:560`)
- Both loop over **every** `wallet_asset` row with one candle query each (`WalletService.java:486-487, 602, 607`). They also run aggregate sums over the cash-flow and trade tables (`:603`).
- Only then does `closePaper` set `closed_at` (`LivePositionProtectionService.java:405`).
- So the lag is time spent on portfolio work inside the transaction, while the symbol and position locks are held.
- [AGENT INFERENCE] This is not an atomicity defect. It is a latency and lock-hold risk: other price ticks for the same symbol wait behind it.
- I haven't traced the entry path. The 1.7–2.2 s entry lag fits the same pattern; DBQ-CLAUDE-I3-004 checks it.

### DB_REQUEST
QueryId: DBQ-CLAUDE-I3-003
Purpose: Inter-arrival gaps between ticks during each frozen trade's life (F-I3-04 baseline, F-I3-03).
SQL:
SELECT pp.id pp_id, COUNT(*) ticks, MAX(g.gap_s) max_gap_s, SUM(g.gap_s>=4) gaps_ge_4s, SUM(g.gap_s>=10) gaps_ge_10s
FROM paper_position pp
JOIN (SELECT symbol, observed_at,
             TIMESTAMPDIFF(MICROSECOND, LAG(observed_at) OVER (PARTITION BY symbol ORDER BY observed_at), observed_at)/1000000 gap_s
      FROM market_price_event
      WHERE symbol IN ('ACEUSDT','SHIBUSDT','DOGEUSDT','XRPUSDT','EGLDUSDT')
        AND observed_at BETWEEN '2026-10-11 20:50:00' AND '2026-10-12 10:10:00') g
  ON g.symbol=pp.symbol AND g.observed_at BETWEEN pp.opened_at AND pp.closed_at
WHERE pp.id IN (182,172,162,158,143,137) GROUP BY pp.id ORDER BY pp.id DESC;
### END_DB_REQUEST
