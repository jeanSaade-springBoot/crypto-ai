**F-I7-02: Correction to F-I6-02. Most I6-004 rows are processing delay, not host-clock lag.** [PROJECT EVIDENCE: code, I6-004]
- **Where the reference time is set.** The fill-price reference time is `Instant.now()` at `PaperTradingService.java:343`. That happens *before* re-validation and before `executeBuy` (`:349-379`). `executed_at` is written later. So "a newer tick was written before `executed_at`" does not, by itself, prove that the clock excluded it.
- **Processing delay (new finding).** Wallet trade 463 (ACE, 2026-10-15) executed at 00:36:09.678 UTC (03:36:09.678 KSA).
  - It used a tick observed at 00:36:00.036 UTC (03:36:00.036 KSA).
  - Another tick was observed at 00:36:02.471 and written at 00:36:02.551 UTC. It was not used.
  - So the fill price was 9.6 s older than the execution time. That is within the 15 s limit, but it is processing delay. Both ticks were 0.1848, so it cost nothing.
- **Clock lag is still proven by some rows.** These are rows where the tick's Binance time is *after* the execution time but the row was written *before* it.
  - Wallet trade 262: written 2026-10-11 04:26:00.824 UTC (07:26:00.824 KSA), Binance time 04:26:03.686 UTC. That is about 2.9 s.

  - Wallet trade 276: written 11:34:59.159 UTC (14:34:59.159 KSA), Binance time 11:35:02.230 UTC. About 3.1 s.
  - Trade 137's wallet trade 344 also fits this pattern.
  - So on 2026-10-11 the host clock ran about 3 s behind Binance. That is more than the 2 s `futureSkew` allowed at ingestion, and ingestion only accepted these ticks because it uses the corrected clock.

## DB REQUESTS

### DB_REQUEST
QueryId: DBQ-CLAUDE-I7-001
Purpose: F-I7-03 / U-25. Distribution of per-trade P&L for boundary vs non-boundary entries, excluding SETUP_CONFIRMATION_WAKEUP, so significance can be estimated.
SQL:
SELECT CASE WHEN MINUTE(s.candle_open_time)%5<>4 THEN 'NON_BOUNDARY' ELSE 'BOUNDARY' END kind,
       COALESCE(eo.execution_source,'NULL') src_group,
       COUNT(*) n, SUM(pp.realized_pnl>0) wins, ROUND(AVG(pp.realized_pnl),6) mean_pnl,
       ROUND(STDDEV_SAMP(pp.realized_pnl),6) sd_pnl,
       ROUND(AVG(CASE WHEN pp.realized_pnl>0 THEN pp.realized_pnl END),6) avg_win,
       ROUND(AVG(CASE WHEN pp.realized_pnl<=0 THEN pp.realized_pnl END),6) avg_loss
FROM paper_position pp JOIN trade_signal s ON s.id=pp.signal_id AND s.interval_code='1m'
LEFT JOIN execution_opportunity eo ON eo.latest_signal_id=pp.signal_id AND eo.status='EXECUTED'
WHERE pp.closed_at IS NOT NULL
GROUP BY kind, (COALESCE(eo.execution_source,'NULL')='SETUP_CONFIRMATION_WAKEUP')
ORDER BY kind LIMIT 10;
### END_DB_REQUEST

### DB_REQUEST
QueryId: DBQ-CLAUDE-I7-002
Purpose: F-I7-04. Wide- vs small-target outcomes grouped by structured close_reason (not free-text exit_reason), with realised R-multiple.
SQL:
SELECT CASE WHEN (ts.take_profit-ts.latest_price)/ts.latest_price*100 <= 0.30 THEN 'TP<=0.30' ELSE 'TP>0.30' END tp_bucket,
       pp.close_reason, COUNT(*) n, SUM(pp.realized_pnl>0) wins, ROUND(SUM(pp.realized_pnl),6) pnl,
       ROUND(AVG((pp.exit_price-pp.entry_price)/NULLIF(pp.entry_price-pp.stop_loss,0)),3) avg_r,
       ROUND(AVG((pp.take_profit-pp.entry_price)/NULLIF(pp.entry_price-pp.stop_loss,0)),3) planned_r
FROM paper_position pp JOIN trade_signal ts ON ts.id=pp.signal_id
WHERE pp.closed_at IS NOT NULL GROUP BY tp_bucket, pp.close_reason ORDER BY tp_bucket, n DESC LIMIT 40;
SELECT pp.id, pp.symbol, pp.close_reason, LEFT(pp.exit_reason,60) exit_head, pp.realized_pnl, pp.closed_at
FROM paper_position pp WHERE pp.closed_at IS NOT NULL AND pp.exit_reason LIKE '%Entry allowed%' ORDER BY pp.id LIMIT 50;
### END_DB_REQUEST

### DB_REQUEST
QueryId: DBQ-CLAUDE-I7-003
Purpose: F-I7-02. Daily host-vs-Binance lag (written time minus Binance time; negative means the host is behind) and the delay from price lookup to execution for BUY fills. Also the denominator for F-I7-01.
SQL:
SELECT DATE(e.created_at) d, COUNT(*) n,
       ROUND(MIN(TIMESTAMPDIFF(MICROSECOND,e.observed_at,e.created_at))/1000,0) min_lag_ms,
       ROUND(AVG(TIMESTAMPDIFF(MICROSECOND,e.observed_at,e.created_at))/1000,0) avg_lag_ms
FROM market_price_event e WHERE e.delivery_status='APPLIED' AND e.created_at >= '2026-10-06 00:00:00'
GROUP BY DATE(e.created_at) ORDER BY d LIMIT 30;
SELECT COUNT(*) buy_fills,
       ROUND(AVG(TIMESTAMPDIFF(MICROSECOND,wt.execution_price_observed_at,wt.executed_at))/1000,0) avg_fill_age_ms,
       ROUND(MAX(TIMESTAMPDIFF(MICROSECOND,wt.execution_price_observed_at,wt.executed_at))/1000,0) max_fill_age_ms,
       SUM(TIMESTAMPDIFF(MICROSECOND,wt.execution_price_observed_at,wt.executed_at) > 5000000) over_5s
FROM wallet_trade wt WHERE wt.side='BUY' AND wt.executed_at >= '2026-10-06 00:00:00';

### DB_REQUEST
QueryId: DBQ-CLAUDE-I7-004
Purpose: U-28 / F-I7-01. Did stop-loss or profit-lock exits happen at prices outside the final 1-minute candle range (a possible protection trigger on a placeholder tick)? Also read the market_price_event schema for a trade-count column.
SQL:
SELECT COLUMN_NAME, DATA_TYPE FROM INFORMATION_SCHEMA.COLUMNS WHERE TABLE_SCHEMA='crypto_ai' AND TABLE_NAME='market_price_event' ORDER BY ORDINAL_POSITION;
SELECT pp.id, pp.symbol, pp.close_reason, pp.exit_price, c.low_price, c.high_price, p.close_price prev_close, pp.realized_pnl, pp.closed_at
FROM paper_position pp
JOIN candle c ON c.symbol=pp.symbol AND c.interval_code='1m' AND c.closed=1 AND pp.closed_at >= c.open_time AND pp.closed_at <= c.close_time
LEFT JOIN candle p ON p.symbol=c.symbol AND p.interval_code='1m' AND p.open_time = c.open_time - INTERVAL 1 MINUTE
WHERE pp.closed_at IS NOT NULL AND pp.close_reason IN ('STOP_LOSS','PROFIT_LOCK','TAKE_PROFIT')
  AND (pp.exit_price > c.high_price OR pp.exit_price < c.low_price)
ORDER BY pp.id LIMIT 100;
### END_DB_REQUEST
