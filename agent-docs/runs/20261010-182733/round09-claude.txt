### B. New findings

**N48 (material). M02's `closed=1` test uses a candle's current state, not its state when Production decided.**
- **[PROJECT EVIDENCE]** Every Replay candle read filters on the row's current `closed` flag. That covers:
  - the timeline (all rows);
  - the indicator snapshot;
  - four shared services that query `closed=1 AND close_time<=t` directly: `ExecutionIntelligenceService.immediatePriceAction`, `PressureReadinessService`, `RecoveryTransitionService`, and the Replay branch of `BtcMarketContextService`. All four are on the BUY evaluation path.
- **[PROJECT EVIDENCE]** Production's data-quality gate takes the latest 210 rows that are `closed=1` when the analysis runs, and allows no missing candle.
- **[PROJECT EVIDENCE]** Rows become closed after the fact through two paths:
  - `finalizeExistingOpenFromAuthoritative` sets `closed=1` and `updated_at=now`;
  - `insertAuthoritativeGapBackfill` inserts a `BACKFILL` row with no close token.
- **[PROJECT EVIDENCE]** In the current worktree this runs automatically. It scans every 5 s, retries with back-off up to 300 s, and records both `local_reconciliation_audit.resolved_at` and a `candle_analysis_outcome` of `SKIPPED_NOT_LIVE`.
- **[PROJECT EVIDENCE: documented investigation; I did not re-query the database or logs]** On 2026-10-09:
  - A reconnect at 04:35:00Z left the 1m candle opened at 04:34 and the 5m candle opened at 04:30 open, for all 21 symbols.
  - Production's 1m and 5m analyses were blocked with `DATA_QUALITY_BLOCKED` until a manual repair closed the 42 rows; the next LIVE signals came at 07:30:07Z.
  - My own investigation log links this outage to the late ETHUSDT trade-59 entry.
- **[AGENT INFERENCE]** Replaying that window today:
  - Every row is now `closed=1` and its identity matches, so M02 *qualifies* the window.
  - A data-quality gate built on today's state would pass.
  - Replay would generate about three hours of 1m/5m signals for 21 symbols that Production could not produce, and could trade on them.
  - A Replay of trade 59 could show an earlier "Production-logic" entry, blaming the strategy for a data outage.
  - With automatic recovery, smaller versions of this (seconds up to about 5 minutes) recur at every reconnect on a candle boundary.
- **[AGENT INFERENCE]** M03's "never fall back to future data" is the right principle. But M02 defines the candle test as `closed=1`, and in exactly this case that is future data.
- **[PROJECT EVIDENCE]** Most of the evidence needed for a rule based on the decision time exists for the OFF-mode era:
  - `candle.updated_at`, which stops changing once a row is closed (`CandleRepository:187, 202`), and `created_at`;
  - `ingestion_source` and `close_transition_token`;
  - `local_reconciliation_audit.resolved_at` and `candle_analysis_outcome`.

  Of these, §3 lists only `candle_analysis_outcome`.
- **[EXTERNAL RESEARCH, R3 and R4]** MySQL auto-updates `updated_at` when any other column changes, unless the statement assigns it explicitly. `CURRENT_TIMESTAMP` is the time the statement started, not when it committed.
  - So the manual repair probably stamped `updated_at` with the repair time; this is unverified.
  - Treating `updated_at ≤ t` as "visible at t" slightly overstates visibility, the same issue as N44 for price events.
- **[AGENT INFERENCE]** The revision needs:
  - one rule for when a candle counts as closed, based on the decision time and used by every Replay candle read;
  - refusal of the analysis claim, or a declared simulation assumption, where that time is unknown (manual repairs, windows before V106/V108, collector-era windows);
  - a §8 test fixture covering a reconnect at a candle boundary followed by recovery;
  - registration of the shared read path (`CandleRepository`, or a Replay-scoped candle provider), subject to the N39 decision.

**N49 (moderate). A third place where Production reads the latest data rather than data as of the signal.**
- **[PROJECT EVIDENCE]** `BtcMarketContextService.relationship` reads candles differently on each side:
  - Production takes the latest N closed candles.
  - Replay takes candles closed at or before `evaluatedAt`.
- **[PROJECT EVIDENCE]** Correlation, beta and sample size decide the relationship type (including LEARNING) and the BTC influence. The same pattern already appears in the data-quality gate (N32) and in `recentSignals` (N47).
- **[AGENT INFERENCE]** For HISTORICAL_ONLY signals, and for LIVE work delayed by more than one interval, Production's stored values include candles that closed *after* the signal's as-of time.
  - Replay cannot and should not reproduce that.
  - There is no trading impact, because historical-only work cannot execute.
  - An exact-match oracle would still raise false alarms. Its eligibility rules must classify these fields by `signal_mode` and processing delay. This extends objections 18 and 23.

**N50 (moderate; sharpens objection 28). Nothing the qualifier can read identifies the code or configuration behind a historical signal.**
- **[PROJECT EVIDENCE]** A search of all migrations for version, commit, hash or fingerprint columns finds only `trade_signal.strategy_version` and `fix122_replay_revision`.
  - `strategy_version` is the hand-set `DYNAMIC_STRATEGY_VERSION` (default `1.0`).
  - The build version is the constant `0.0.1-SNAPSHOT`.
- **[PROJECT EVIDENCE]** The deploy script keeps each release on the host and never prunes it: the JAR plus a `process.json` with its SHA-256 and UTC start time. It does not capture the external `application.yml`.
- **[PROJECT EVIDENCE]** Jenkins keeps archived evidence for only 10 builds.
- **[AGENT INFERENCE]** IDE and manual launches bypass the deploy script, so they leave no release record.
- **[PROJECT EVIDENCE]** `sentiment_provider.updated_at` is not mapped for writes, so MySQL bumps it on every collection-status write. It therefore cannot date a change to `enabled` or `weight`.
- **[AGENT INFERENCE]** §2 is accurate, but the spec gives the qualifier no identity source. As written, `ANALYSIS_PARITY` cannot be earned for any historical window, so RPR6-13 and its tests would ship a label nothing can reach. The revision must choose one of:
  1. Identify code from the host release records, and allow the claim only for windows run by a release proven policy-equivalent to the baseline.
  2. Bring a minimal forward capture of code and configuration identity into scope. That writes to Production, so it falls under N39.
  3. Drop `ANALYSIS_PARITY` from Release 1.
