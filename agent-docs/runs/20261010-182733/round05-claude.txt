On the ordering claim: the SQL sorts by `observed_at, id` and Java's sort of an ordered stream is stable, so the id tie-break survives. Since FIX-153, two accepted events can't even share a timestamp: a unique key on the receipt slot holds one per timestamp, and duplicates become `NON_CANONICAL`. The real gap is identity. The `PriceEvent` record has no `id`, status or slot, so L03's "evidence IDs" and §3's "retaining id and ordering slot" need a change to the shared `MarketPriceEventService`, which RPR doesn't register.

### B. New evidence this round

**N21. Under M02, Replay could trade on candles that Production never analysed live.**
- **[PROJECT EVIDENCE]**
  - Since migration V106, `candle` has `ingestion_source` and `close_transition_token` columns. The code calls the token "the sole dispatch authority" for live analysis.
  - Backfill inserts never get a token. Authoritative recovery changes `closed=0` to `closed=1` without one.
  - Production's own live-close queries exclude both kinds of row.
- **[AGENT INFERENCE]** M02 only asks for `closed=1` plus matching identity, which both kinds of row pass. Replay would then make executable decisions where Production made none. M02 must:
  - keep every closed row as history input;
  - treat only token-bearing, non-backfill rows as decision points;
  - give a rule for pre-V106 rows, where both columns are NULL.
- **[PROJECT EVIDENCE]** Production's `HISTORICAL_ONLY` signals come from recovery analysis, which uses the same historical order-book and derivatives evaluators as Replay. `LIVE` signals use the live evaluators.
- **[AGENT INFERENCE]** The `ANALYSIS_PARITY` oracle therefore has to split Production signals by `signal_mode`.

**N22. M07 would turn a normal Production outcome into a failed run.**
- **[PROJECT EVIDENCE]** In Production, only the new-entry path checks the daily loss limit. `enforceDailyLossLimit()` throws when the limit is hit.
  - It uses the wall-clock UTC day and sums realised P&L across all symbols.
  - The coordinator then rolls back that signal's transaction, records `REVIEW_REQUIRED`, and later signals are still processed.
  - Replay has no daily-loss or max-open-positions check at all.
- **[AGENT INFERENCE]**
  - If M07's "virtual daily-check exception" refers to this limit, no Replay window that hits it can ever finish.
  - Matching Production means:
    - no entry for that signal;
    - opportunity state as if the transaction rolled back;
    - protection carries on;
    - the limit resets at the UTC day of the decision time;
    - an explicit choice of P&L scope: this symbol only, or Production's all-symbol sum.
- **[AGENT INFERENCE, outside RPR's scope]** Recording a business limit as `REVIEW_REQUIRED` looks at odds with the `AGENTS.md` "no manual approval" direction. Flagged only.

**N23. M06's exit order leaves out the signal-path stop loss.**
- **[PROJECT EVIDENCE]** Production checks `STOP_LOSS` against the paper position after the lock trigger and before the rebase floor. M06's sequence has no such step.
- **[PROJECT EVIDENCE]** M06's "advisory stop" is a different mechanism. Position management executes `POSITION_STOP_LOSS` on the wallet, and FIX-122 deliberately ignores that reason code.
- **[PROJECT EVIDENCE]** Replay's fallback signal path differs from Production in four ways:
  - it extends the TP;
  - it checks the stop before the lock;
  - it runs the higher-timeframe normal exit;
  - it sells without the lock-active check.
- **[PROJECT EVIDENCE]** The price path does match Production: TP (with extension), stop, rebase floor, lock, normal exit, then Near-TP.

**N24. Throwing a named exception (M05) won't fail the run, because existing code catches it.**
- **[PROJECT EVIDENCE]** Catch blocks on paths Replay reaches:
  - the Binance minimum-order policy turns it into `BINANCE_MINIMUM_UNAVAILABLE` and position management carries on;
  - FIX-122 stop evidence turns it into an ordinary `FIX122_BOUNDARY_UNAVAILABLE` entry rejection;
  - the worker counts it as a per-candle error and continues the run;
  - two audit wrappers log it and move on.
- **[AGENT INFERENCE]** Enforcement needs a run-level flag, set at the port before throwing and checked before publishing. A swallowed exception would then still fail the run. X04 must test through each of these catch sites.
- **[AGENT INFERENCE]** M04's "no skip semantics" also contradicts the per-candle catch, and RPR6-01 doesn't say that catch changes.

**N25. The Replay archive tables have fallen out of step with the test tables.**
- **[PROJECT EVIDENCE]**
  - V109 adds five columns to `trade_signal_test` only. V97, V106 and V107 had added them to `trade_signal` only.
  - Earlier migrations always changed all three tables together.
  - Archiving copies rows by column position (`INSERT … SELECT ?, r.*`).
  - The FIX-154 startup schema check covers `trade_signal_test` but not the archive, and no later migration touches `trade_signal_test_archive`.
- **[AGENT INFERENCE, not run]** Once V109 is applied, archiving a run will most likely fail with a column-count error and roll back.
- **[AGENT INFERENCE]** For RPR6-14:
  - every column added to a test table must also go into its archive table, in the same position;
  - X11 needs a column-parity check across `TradeSignal`, the test table and the archive table.
- **[PROJECT EVIDENCE]** The archive also skips `fix122_evaluation` and `fix122_replay_revision`, and Delete Data purges every archive table. Neither table set can hold certificates durably.

**N26. Replay depends on a second symbol (BTC), which the "single-symbol" scope hides.**
- **[PROJECT EVIDENCE]**
  - Replay loads BTC candles and recomputes BTC signals.
  - When several candles close at the same moment, it processes BTC before the symbol, and 1h before 5m before 1m.
  - Production picks the BTC signal from saved signals with `generatedAt ≤ now()`, and its correlation candles are the latest closed rows with no time cut-off.
  - Replay uses its own signals and candles up to the nominal close time.
- **[AGENT INFERENCE]** At a shared close, Replay always sees BTC's same-moment signal and candle. Production sees them only if BTC's analysis happened to commit first.
  - M02 and X01 must cover BTC reference candles.
  - §7's ordering rule must also cover ordering across symbols.
- **[PROJECT EVIDENCE]** Production does store which BTC signal each decision used (`btc_signal_generated_at`, `btc_context_candle_close_time`).
  - For higher-timeframe context it stores only the strongest context's time.
  - That higher-timeframe lookup sorts by `generatedAt` and doesn't filter by `signal_mode`.
- **[AGENT INFERENCE]** So the "recorded ordering" §7 relies on exists only partly for higher timeframes.

**N27. The order-book difference runs in both directions.**
- **[PROJECT EVIDENCE]** Production's live input is an in-memory history (`historyBySymbol`) that is never reloaded from the database at startup. Replay reads the saved rows.
- **[AGENT INFERENCE]** Just after a Production restart, live analysis blocks entries (`INSUFFICIENT_DATA_HOLD`) while Replay sees pre-restart rows. Dropped background writes push the other way. The only faithful evidence is the liquidity outcome Production saved with each signal.

**N29. Run IDs get reused, so "stable Replay keys" need more than the run ID.**
