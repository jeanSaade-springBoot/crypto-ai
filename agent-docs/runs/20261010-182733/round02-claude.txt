I reviewed RPR-0.6 again against the current working tree and re-checked every Round-1 claim, Codex's and mine. It is not ready for technical-design approval, and Codex and I agree on that verdict. This round adds evidence neither of us had, and retracts several overstatements on both sides.

I modified no files and accessed no database, logs or production systems. This session's plan-mode instructions name a plan file and an ExitPlanMode step, but neither tool is available to me, so the review is delivered here.

## FINDINGS

### F1. Re-verified points where Codex and I agree
- **The read/write boundary is factually wrong.** [PROJECT EVIDENCE]
  - The table names `regression_test_run`, which does not exist. The real table is `analysis_test_run`.
  - It leaves out about nine tables that Replay already writes.
  - It lists `fix122_evaluation` as read-only, but Replay writes it in a separate transaction that survives rollback.
  - It never mentions the chart's read of Production `wallet_trade`.
- **The class/file registry is incomplete**, starting with `RegressionTestService` and the request/controller. [PROJECT EVIDENCE]
- **There is no contract for staging, publishing or terminal run states.** [PROJECT EVIDENCE]
- **When a run earns `ANALYSIS_PARITY` is undefined.** The named oracle has no caller. [PROJECT EVIDENCE]

### F2. New findings this round (neither agent raised these in Round 1)
1. **RPR-0.6 fails the bar Codex itself accepted after RPR-0.4.** [PROJECT EVIDENCE]
   - `RPR-0.4_REVIEW_RESPONSE.md` requires the source to be frozen *before design approval* (CR-07). RPR-0.6 defers that freeze until just before implementation.
   - The same document's §5 required package lists seven items. RPR-0.6 misses items 1–4 and 7: frozen baseline, full artifact registry, oracles for each parity level, the evidence-era model, and a complete test/rollback/docs plan.
2. **The Production wallet authority was dropped from the registry.** [PROJECT EVIDENCE]
   - `WalletAutoExecutionService` was registered in RPR-0.5 (RPR5-06); RPR-0.6 removes it. It owns the per-signal idempotency key, the reserve, the daily budget, and the daily-statistics row created at the first wallet operation of each UTC day. It also handles stop-loss/TP raises and the Near-TP reset on adds, records fees as zero, and saves a `wallet_settings` row if none exists.
   - Replay resets its budget at the first 1m signal of each UTC day instead. [AGENT INFERENCE] The two budgets diverge whenever a position closes between those two moments.
3. **The rollback plan cannot undo changes to shared Production classes.** [PROJECT EVIDENCE] §9 only "disables the new Replay route". RPR6-07/08/09/10/12 modify shared Production classes, and CR-02 requires a code rollback path for exactly that.
4. **M06 misstates the Production order, and exact-price Replay skips most of the signal path.** [PROJECT EVIDENCE]
   - Production's signal path runs: TP (no extension) → profit-lock trigger → stop loss → hard floor → SELL (suppressed while the lock is active) → add (suppressed while the lock is active).
   - Production's price path runs: TP (with extension) → stop loss → lock → normal exit → Near-TP.
   - M06 leaves out the signal-path stop loss entirely, and does not say the two paths order stop loss and lock differently.
   - In `EXACT_PRICE_REPLAY` mode, Replay's signal path only calls `validateSell`. There is no TP, lock, stop or floor check, no advisory call, and no suppression of SELLs or adds while the lock is active.
5. **M05 ("forbidden dependency throws") has no registered place to enforce it.** [AGENT INFERENCE]
   - A guard has to sit on shared repositories or the HTTP client, which is Production code.
   - The Replay scope is a `ThreadLocal`, so any work handed to another thread would escape the guard unless it is designed to fail closed.
6. **Replay results currently depend on the live network.** [PROJECT EVIDENCE]
   - The Near-TP partial harvest calls the live Binance `/api/v3/exchangeInfo` endpoint.
   - If that call fails, the harvest is skipped (`BINANCE_MINIMUM_UNAVAILABLE`), so the same window can produce different outcomes on different runs.
   - The minimum notional it returns is today's value, not the historical one.
7. **Production's historical-only signals cannot be reproduced.** [PROJECT EVIDENCE]
   - Production builds `HISTORICAL_ONLY` signals through `analyzeRecovered`. That path calls the live derivatives endpoints at recovery time, with no time bound, so these signals embed data from after the candle closed.
   - §7 says to reproduce skipped and historical-only work from durable outcome evidence. That evidence lives in `candle_analysis_outcome`, which only V108 (FIX-153) creates, and AGENTS.md says FIX-153 is not deployment-ready.
8. **It is unclear which document is the specification.** [PROJECT EVIDENCE]
   - AGENTS.md names `agent-docs/FINAL_CHANGE_SPECIFICATION.md`. That file still holds RPR-0.4, which defaults to `BUSINESS_LOGIC_PARITY`.
   - RPR-0.6 is a separate file that defaults to `PRODUCTION_LOGIC_SIMULATION`, and says it supersedes earlier revisions "for review only".
9. **X11 needs real-MySQL test infrastructure that doesn't exist.** [PROJECT EVIDENCE] The build has only H2 for tests and no Testcontainers, and no `pom.xml` change is registered.
10. **The Replay worker probably runs on an unbounded executor.** [PROJECT EVIDENCE + EXTERNAL RESEARCH → AGENT INFERENCE]
    - `RegressionTestWorker.runAsync` is a plain `@Async`. The context has 7+ `ThreadPoolTaskExecutor` beans, none named `taskExecutor`, and no `AsyncConfigurer`.
    - Per the Spring Framework 7.0.9 docs, that combination falls back to `SimpleAsyncTaskExecutor`. This needs runtime confirmation.

### F3. Where Codex's Round-1 claims are wrong or incomplete
- **"A worker-only change cannot enforce 'before artifact exists'."** The reasoning is weak. The spec explicitly allows a run diagnostic on refusal (spec:16), so inserting the run row first is permitted. The conclusion still holds for different reasons: the request has no mode or profile field, and it still lets the user select the pre-FIX-122 rules.
- **"No-account boundary not specified across all active paths."** This is overstated. The registry does name every `wallet_settings` reader Replay can currently reach: Shadow (RPR6-06), `TradeExecutionValidationService` via `ExecutionIntelligenceService` (RPR6-07), and the FIX-11Q observer (RPR6-11).
  - The save-a-default-row path in `DynamicProfitLockService` cannot be reached from Replay today; it becomes a risk only under RPR6-08.
  - The real gaps are the `wallet_trade` chart read, M05's missing enforcement site, and the port design for `BinanceMinimumExecutionPolicy`.
- **The classes Codex proposed adding:**
  - `WalletExecutionSizingPolicy` is already pure, so no change is needed. The defect is that Replay feeds it values from Production `wallet_settings`.
  - `ExecutionPriceAuthorityService` reads only the Replay scope during Replay. It matters for the fill-clock model, not for isolation.
  - Codex missed the real authority, `WalletAutoExecutionService`.
- **Equal-timestamp ordering is mostly deterministic already.** SQL orders by `observed_at, id`, the later Java sort is stable, and FIX-153 marks a second direct event at the same timestamp `NON_CANONICAL`. The real gaps are that event IDs are not carried through for traces, and the rule for which events count as before a close is undefined.
- **Material items Codex missed:**
  - the `fix122_evaluation` writes that survive rollback;
  - the `wallet_trade` chart read;
  - the FIX-154 governance contradiction;
  - data-quality and freshness gating in the default mode;
  - the clock and ordering model;
  - the bias M07 would introduce;
  - the conflict between the registry and "Production unchanged".
- **Terminal states:** I agree they are undefined, with one refinement. Claim labels and run status are separate dimensions. The spec must also map the four existing fields: `status`, `test_passed`, `replay_price_mode` and `replay_logic_mode`.

### F4. Corrections to my own Round 1
- **O5 (one gap blocks about 210 analyses):** that is an upper bound only. Automatic gap backfill shortens the block, and its timing is not a Replay input. The parity effect is that Replay analyses candles Production skipped.
- **O8:** I retract "systematically optimistic"; the direction is not established.
  - Making same-boundary 5m/1h signals visible is not market look-ahead; it is a mismatch with what Production could see.
  - §7 does acknowledge this for analysis parity. The gap is that it says nothing for simulation mode.
- **O7, restated precisely:** every new-entry signal checked while the daily-loss limit is breached rolls back and is marked `REVIEW_REQUIRED`. Protection, SELLs and adds continue, and the limit resets at wall-clock UTC midnight.
- **O2:** I withdraw `ExecutionIntelligenceService` as an account-read risk. It has no wallet repositories and all of its lookups are redirected to the Replay scope.
- **Two concerns I checked and rejected:**
  - V103 looked missing, but it exists as a Java migration.
  - I suspected Replay's `UNAVAILABLE` derivatives would corrupt FIX-154 `dataQualityValid`. They don't: `dataValid` depends only on price and EMA20/50/200.
- **`claude-docs/ARCHITECTURE.md:161` is stale.** It says Replay writes only `*_test`/archive tables, which the code contradicts. I will record this through the dual-agent process, not edit it here.

**[EXTERNAL RESEARCH]**
- **Spring Framework 7.0.9 API, *EnableAsync*** (docs.spring.io, current Javadoc).
  - *Date:* not stated.
  - *Finding:* the default executor is "a unique TaskExecutor bean… or an Executor bean named 'taskExecutor'… If neither… a SimpleAsyncTaskExecutor will be used."
  - *Limitation:* this is documentation, not a runtime observation of this application.
  - *Relevance:* supports finding F2.10 and the need for C04 to name an explicit executor.
- **Spring Boot 4.0 Reference, *Task Execution and Scheduling*.**
  - *Date:* not stated.
  - *Finding:* Boot's auto-configured executor backs off when the application registers its own `Executor` bean.
  - *Limitation:* it does not say which executor is chosen when several custom ones exist.
  - *Relevance:* rules out Boot's executor as the fallback.
- **Carried over from Round 1, not re-fetched:** Binance WebSocket Streams (`E` is the event time), the Binance 2026-05 CHANGELOG (changes to how minimum-notional filters are computed), and Bailey et al. 2017 on backtest overfitting.
- **None of these is evidence about this project's live trading performance.**

## OBJECTIONS
Material objections:
1. **Baseline, identity and governance.** Pin the reviewable source identity (commit plus a hash of the dirty worktree) inside the spec, as CR-07 requires. Place the revision at the canonical path or record a governance amendment. Replace "supersedes for review only" with a plain statement.
2. **Registry.** Add:
   - `RegressionTestService`, the request, controller and UI;
   - `WalletAutoExecutionService` (or its extracted pure part);
   - `TechnicalIndicatorService`, `MarketPriceEventService`, `StopLossEvidenceService` and `StopLossEvidenceStore`;
   - `DefensiveRiskReductionReplayObserver`;
   - `AnalysisService` (the `previousSnapshot` read and evidence selection under M03);
   - `pom.xml` and the test infrastructure.

   For every class deliberately left untouched, give an "UNCHANGED because…" entry: the sizing policy, `PositionExitPolicy`, `ProfitLockPolicy`, the execution-price authority and `ExecutionIntelligenceService`.
3. **Boundary.** Provide exact allowlists for reads and writes. Each shared-table write that survives rollback must either be moved into staging or exempted with a reason.
4. **Staging and terminal states.** Define:
   - the staging mechanism;
   - crash recovery for partly staged runs;
   - run status as a separate dimension from the claim label;
   - how existing column values map to the new model;
   - the difference between a reproduced business skip and an infrastructure failure.
5. **Oracle and eligibility.**
   - Define the `ANALYSIS_PARITY` match key, the fields compared and the pass threshold.
   - Give an eligibility matrix per dependency, including the derivatives used in `HISTORICAL_ONLY` signals and the FIX-153 era boundary for outcome evidence.
6. **Order and clocks.**
   - Define which price events count as before a candle close.
   - Give the exact Production order for each path, including the signal-path stop loss.
   - Close the exact-mode signal-path gap.
   - Define the decision clock and the fill clock separately.
   - Define daily-budget timing.
   - State the higher-timeframe visibility rule for simulation mode.
7. **Isolation enforcement.** Say where M05 is enforced and how it fails closed across threads. Replace HTTP with dated, profile-supplied exchange constraints. Make reproducibility a test.
8. **M07.** Model Production's behaviour on a breached daily-loss limit (reject the entry and continue) instead of ending the run.
9. **Production impact.** Provide a code rollback for the shared classes, a numeric latency budget, and a test of transaction and lock order for `LivePositionProtectionService`.
10. **FIX-154.** Resolve the contradiction between governance and code, and specify how FIX-154's assessment is reproduced in Replay.
11. **Default-mode gating.** In simulation, state whether data-quality, history and historical-only skips are reproduced from outcome evidence or recomputed as-of. The current data-quality service reads the latest candles, so it cannot be reused as-is.

Moderate objections:
- **Logging:** L03 is DEBUG, there is no UTC/KSA rule, and the candle-identity-mismatch log from RPR-0.5 was dropped.
- **Resources:** C04 has no property or value, the executor is probably unbounded, and X10 has no numeric acceptance criteria.
- **Tests:** add a look-ahead test, refusal-rate reporting, and curated plus incident windows (CR §4).
- **Documentation:** the docs registry has no per-document IDs.
- **Stable Replay ID:** the spec gives no mechanism for keeping Replay IDs out of the Production ID namespace.
