## FINDINGS

- **PROJECT EVIDENCE:** RPR-0.6 is not the canonical change contract required by governance. The required artifact remains `agent-docs/FINAL_CHANGE_SPECIFICATION.md` at RPR-0.4, while RPR-0.6 explicitly says it supersedes prior drafts “for review only.” It cannot safely receive the required dual-agent approval in its current location/status.

- **PROJECT EVIDENCE:** The “complete” registry is materially incomplete and names a nonexistent run table. The implementation uses `analysis_test_run`, not `regression_test_run`; `RegressionTestService` owns run creation, cancellation, purge, archive, reset, and Investigation Queue execution, yet is omitted.

- **PROJECT EVIDENCE:** The qualifier-before-write contract is not fully designed. Current `RegressionTestService.start()` creates `analysis_test_run` and `fix122_replay_revision` before the async worker begins. RPR-0.6 registers neither this start path nor the required changes to make a profile/mode available before qualification. The Investigation Queue likewise cannot carry either required value.

- **PROJECT EVIDENCE:** RPR-0.6’s `closed=1` rule does not establish decision-time candle visibility. The current timeline admits open candles; shared snapshot/quality queries use the row’s current closed state. Recovery can subsequently close an existing candle or insert a closed backfill. The current `Candle` projection omits provenance and database timestamps, so it cannot support the proposed historical-finality assertion by itself.

- **PROJECT EVIDENCE:** The proposed isolation boundary lacks an enforceable architecture and overlooks an existing forbidden account read. Current Replay directly reads `wallet_settings` and can invoke Binance HTTP for minimum-notional checks. Separately, the current Replay chart endpoint reads `wallet_trade`, which RPR-0.6 absolutely forbids, but the endpoint is not registered as an exemption, removal, or changed display contract.

- **PROJECT EVIDENCE:** Price-event ordering cannot meet RPR-0.6 as written. The query orders by `observed_at, id`, but maps to a `PriceEvent` that discards `id`; Replay later sorts price events by timestamp only. `MarketPriceEventService` and the event projection are not in the “complete” registry despite §3 requiring retained ID and ordering slot.

- **PROJECT EVIDENCE:** Staging is underspecified. Current Replay persists signals during generation and positions/executions during simulation. RPR-0.6 requires private staging and terminal-only publication but names neither staging objects nor promotion transaction, crash/cancel behavior, archive/purge treatment, retention, or handling of terminal diagnostics. This fails the governance requirement for class/method, database, concurrency, and transaction contracts.

- **PROJECT EVIDENCE:** The claimed current-policy scope is incomplete against the current workspace. `ShadowProductionReplayService` invokes `ExecutionIntelligenceService` and `ExecutionPriceAuthorityService`, but neither is registered. Current execution code also contains FIX-154 higher-timeframe assessment paths; RPR-0.6 permits associated evidence tables but does not define how those policies, audit availability/failure, and as-of ordering participate in Replay.

- **PROJECT EVIDENCE:** `ANALYSIS_PARITY` has no complete earned-claim algorithm. RPR-0.6 acknowledges unavailable deployed JAR/config lineage, but does not define the mandatory fingerprint source, comparison fields, or refusal rule. The existing `ReplayParityValidator` has no production caller and compares only a limited set of signal fields; it is not sufficient evidence for the label.
