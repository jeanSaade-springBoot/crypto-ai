### B. New evidence this round

**N1. Null Replay signal IDs switch off two Production rules in Replay today.**
- **[PROJECT EVIDENCE]** Replay signals never get an ID: `persistTradeSignalTest` skips `id` and never writes one back. Two rules depend on it:
  - **Near-TP harvest:** the bearish streak only advances when the 1m signal's ID is non-null, and a harvest needs a streak of 2. So Replay can never harvest.
  - **BUY_CONTINUATION:** `EntryConsumptionPolicy.resolve(null)` returns `NOT_CONSUMED`, and `markEntryConsumed(null)` does nothing. So Replay never rejects a continuation BUY that Production would reject.
- **[AGENT INFERENCE]** Consequences:
  - Runs from the current code that are labelled `PRODUCTION_PARITY` ran with both rules off. The spec has no plan to relabel them.
  - Both agents' HTTP claims describe a path that can't run today (see C2).
  - Fixing IDs (RPR6-05/X05) makes the live `exchangeInfo` call reachable unless the no-HTTP change (RPR6-10) lands first. The spec doesn't order them.
  - Null IDs currently act as hidden guards in shared code. Each one needs an explicit Replay-scope check, and Replay IDs written to the shared `fix122_evaluation.signal_id` need a namespace that can't collide with Production IDs.

**N2. `ANALYSIS_PARITY` can't pass with the registered classes whenever Production had live derivatives data.**
- **[PROJECT EVIDENCE]** Replay always gets derivatives status `UNAVAILABLE` with a 0 adjustment. Production live analysis calls the futures endpoints and can veto crowded BUYs.
- **[PROJECT EVIDENCE]** Derivatives make up 8% of `rawConfidence`, and the validator compares `rawConfidence`, effective confidence and final decision for exact equality.
- **[AGENT INFERENCE]** Replay contributes 3.2 points. Production contributes 6.64 for BALANCED/HEALTHY (+3.44), 8.0 for FRESH_* (+4.8) and 0.8 for CROWDED (−2.4). That is usually enough to change the rounded integer the validator compares. This depends on derivatives being enabled in Production, which I couldn't check.
- **[PROJECT EVIDENCE]** Spec §2 says derivative data isn't durable. That's only half true: raw funding and open-interest data isn't stored, but every Production signal stores its derivatives outcome (`derivatives_status`, `derivatives_entry_allowed`, `derivatives_confidence_adjustment`, `derivatives_evaluated_at`).
- **[AGENT INFERENCE]** So M03's "stored as-of evidence" route does exist. Using it means changing `AnalysisService` and `DerivativesPositioningService` (plus the order-book, sentiment and fundamentals equivalents), and none of these is registered.

**N3. Production and Replay use different decision clocks, and Replay probably handles the closing price tick in the opposite order.**
- **[PROJECT EVIDENCE]** Production live analysis uses `Instant.now()` as the as-of time for every context lookup, and also as the fill time. Replay uses the nominal candle close for both.
- **[PROJECT EVIDENCE]** Production stores Binance event time `E` as `observed_at`, and runs protection on that tick before publishing the candle-close event. Replay only processes price events with `observedAt ≤ nominal close` before the signal.
- **[AGENT INFERENCE] + [EXTERNAL RESEARCH]** If the closing message's `E` falls after the nominal close, as expected:
  - Replay runs adds, `validateSell` and entries before protection on the closing tick; Production does the reverse.
  - Replay's entry fill uses the last tick before the close.
- **[PROJECT EVIDENCE]** At a shared close, Replay always evaluates 1h, then 5m, then 1m. The stored Production `generated_at` could supply the "recorded ordering" §7 asks for, but the spec doesn't name it.

**N4. Replay reads Production tables that aren't on the permitted list.**
- **[PROJECT EVIDENCE]** Every Replay analysis reads the previous Production `technical_indicator` row. It isn't permitted and has no as-of rule.
- **[PROJECT EVIDENCE]** Fundamentals are selected by the data's own `observedAt`, not by when they were stored. Sentiment is also time-filtered.
- **[AGENT INFERENCE]** Filtering by the data's own timestamp risks look-ahead. M03 needs an availability-time rule, and durable columns already exist for one: `candle.created_at`, `candle.ingestion_source` and `trade_signal.signal_mode`/`generated_at`.

**N5. Deleting Replay data recycles run and trade IDs while Proven records keep the old ones.**
- **[PROJECT EVIDENCE]** Delete Data resets the ID counters on `analysis_test_run` and `wallet_position_test` to 1, but keeps `proven_analyzed_trade`, which is keyed on (run ID, trade ID).
- **[PROJECT EVIDENCE]** `trades()` marks a trade as proven by that pair, and `markProvenSuccess` overwrites on a duplicate key. A code comment acknowledges the ID reuse.
- **[AGENT INFERENCE]** A new run can show false "proven" flags and overwrite an older Proven record. RPR6-05 promises "stable run keys" without addressing this.

**N6. The spec ignores the existing data-source selector and a second entry point.**
- **[PROJECT EVIDENCE]** `ReplayDataSource` defaults to DATABASE. DATABASE mode loads candles without a closed filter, and for an open candle it builds the snapshot from the previous closed candle. DATASET mode loads only closed candles.
- **[PROJECT EVIDENCE]** The investigation-case endpoint hard-codes DATABASE and `fix122Enabled=true`.
- **[AGENT INFERENCE]** The spec's new "mode" field must say whether it replaces DATABASE/DATASET or works alongside it, and the investigation-case path must be registered.

**N7. Replay's HTTP call shares Production's Binance rate-limit gate.**
- **[PROJECT EVIDENCE]** The minimum-notional lookup goes through the shared `BinanceRestAdmissionGate` and isn't cached. A 429 response blocks every REST caller for 60 seconds; a 418 blocks them for 15 minutes.
- **[AGENT INFERENCE]** This path is unreachable today (N1) but becomes a Production-impact path once IDs are fixed. The risk is low (at most one harvest per position), but X04 must test it.

**N8. Replay increments Production's FIX-154 counters.**
- **[PROJECT EVIDENCE]** The metric calls in the BUY validation path have no Replay-scope check; only the audit write is suppressed.
- **[AGENT INFERENCE]** This contaminates monitoring, not trading, but it is shared state missing from the isolation inventory.

**N9. CI deploys LIVE straight after a passing build, with no approval stage.**
- **[PROJECT EVIDENCE]** The Jenkinsfile runs "Build and test", then "Deploy Trader LIVE".
- **[AGENT INFERENCE]** X12 assumes a CI check that doesn't exist, and the Jenkinsfile isn't registered. Rollback for the shared-class changes (RPR6-07/08/09/10/12) has to account for automatic LIVE deployment.

**N10. Production's signal path starts with an advisory hard stop that Replay never runs.**
- **[PROJECT EVIDENCE]** `PositionManagementService.analyze` runs first. When the price is at or below the managed stop, it executes `POSITION_STOP_LOSS` on the wallet.
- **[PROJECT EVIDENCE]** Replay never calls it. The class is in RPR6-09 only as a source of ordered inputs, not as a step Replay must run.

### C. Corrections to my Round-2 findings
- **C1 [PROJECT EVIDENCE] Overstated.** I said M06 leaves out the signal-path stop loss. It doesn't: its "advisory stop" is the `PositionManagementService` hard stop (CR-03). The real gaps are:
  - M06 omits `PaperTradingService`'s own STOP_LOSS step, between the label-free lock and the floor.
  - It gives no separate order for the price path.
  - Its terms are defined only in the RPR-0.4 review response, not in the spec.

  The price path also needed refining: TP (with extension) → SL → rebase hard floor → lock (with its own floor and label checks) → normal HTF exit → Near-TP.
- **C2 [PROJECT EVIDENCE] Wrong as stated.** I said Replay results currently depend on the live network. Today the HTTP call can't run under null IDs (N1); it becomes reachable once X05 is implemented.
- **C3 [PROJECT EVIDENCE] Imprecise.** Production creates the daily-statistics row and budget at the first BUY attempt of the UTC day across all symbols, not at the first wallet operation. That is the only call site.
- **C4 [PROJECT EVIDENCE + AGENT INFERENCE] Not a concurrency risk.** The fallback to `SimpleAsyncTaskExecutor` still looks likely: no executor bean is `@Primary` or named `taskExecutor`, and there's no `AsyncConfigurer`. But `start()` already allows only one PENDING/RUNNING run, so C02 restates existing behaviour. The real resource risk is one run's load on the shared DB pool and CPU, which C04 and X10 don't quantify.
- **C5 [PROJECT EVIDENCE]** The config values I cited (pool size 15, 210 minimum candles, 0 missing candles) come from an `application.yml` headed "LOCAL TEST CONFIGURATION ONLY". Production values are unverified.

### D. Challenges to Codex's claims

- **D6 [PROJECT EVIDENCE]** `PriceEvent` does drop `ordering_slot`, but the slot adds nothing to ordering. Replay only reads LEGACY/APPLIED events sorted by `observed_at, id`, and direct events always use slot 1. Traceability (L03) needs the event `id`.
- **D7** Codex's Round 3 asks for decision/fill clocks and boundary ordering, but without N3's code evidence. Codex didn't raise N1, N2, N5, N6, N9, N10 or the `technical_indicator` read.

## OBJECTIONS
Material objections:
1. **Baseline and governance.**
   - Freeze the commit plus a manifest of the dirty worktree before design approval (CR-07).
   - Put the revision at the canonical path, or record a governance amendment.
   - Replace "supersedes for review only" with a plain statement.
2. **Exact read/write/dependency allowlists.** These must cover:
   - reads of `technical_indicator`, sentiment and fundamentals, with availability-time rules;
   - every Replay-owned write, including the rollback-surviving `fix122_evaluation` write;
   - the Proven and archive tables;
   - the `wallet_trade` chart read;
   - the shared Binance REST gate;
   - shared in-memory state (`Fix154Metrics`, `RegimeStateService`).
3. **A complete registry, following template §6 and §7.**
   - Add: `RegressionTestService`, the controller, request and UI; the investigation-case path; `ReplayDataSource`; extracted `WalletAutoExecutionService` policy; `AnalysisService` and `DerivativesPositioningService` plus the order-book, sentiment and fundamentals as-of services; `MarketPriceEventService`; `StopLossEvidenceService`/`Store`; `DefensiveRiskReductionReplayObserver`; `EntryConsumptionPolicy`; `NearTpFailureProtectionPolicy`; `Fix154Metrics`; `pom.xml` and test infrastructure; the Jenkinsfile.
   - Give an "UNCHANGED because…" entry for every class deliberately left alone.
4. **Identity design.**
   - A Replay ID namespace that can never collide with Production IDs.
   - An inventory of null-ID shortcuts, each replaced with an explicit Replay-scope check.
   - The no-HTTP change (RPR6-10) must land before stable IDs (RPR6-05).
   - Run identity that survives Delete Data.
   - A plan to relabel existing `PRODUCTION_PARITY` runs.
5. **`ANALYSIS_PARITY` oracle.**
   - The match key: symbol, timeframe and `candle_open_time`.
   - Which Production signals are eligible, by `signal_mode` and era.
   - A versioned field set with tolerances.
   - Injection of stored derivatives, liquidity and sentiment outcomes, or explicit exclusion of the affected fields.
   - Refusal reasons.
6. **Clock and order model.**
   - Decision clock and fill clock.
   - Closing-tick precedence, measured from stored data.
   - The exact signal-path and price-path orders.
   - The same-boundary higher-timeframe rule.
   - Daily-budget timing (first BUY attempt, all symbols).
   - Daily-loss limit: the entry is rejected and the run continues.
   - How the global max-open-positions limit applies to a single-symbol account.
7. **Production admission outcomes in simulation.** For each of `DATA_QUALITY_BLOCKED`, `HISTORY_UNAVAILABLE`, `HISTORICAL_ONLY`, `EXPIRED` and `REVIEW_REQUIRED`, state whether Replay:
   - reproduces it from durable evidence (V108-era windows only);
   - recomputes it as-of, using availability time; or
   - refuses or labels the run.

   Simulation must not trade candles Production couldn't have traded, unless the output says so.
8. **Staging and terminal states.**
   - Staging, atomic publication, recovery after crash or restart, cancellation races, and how rollback-surviving writes are treated.
   - Run status kept separate from the parity label.
   - A mapping for the existing `status`, `test_passed`, `replay_price_mode` and `replay_logic_mode` fields.
9. **Isolation enforcement and Production impact.**
   - Name the enforcement site, and make it fail closed across threads; the Replay scope is per-thread (`ThreadLocal`).
   - Replace the HTTP lookup with a dated minimum notional from the profile.
   - Provide a code rollback for the shared classes, given the pipeline deploys LIVE.
   - Set a numeric latency budget.
   - Test transaction and lock order for `LivePositionProtectionService`.
10. **FIX-154.** Treat FIX-154 as active current behaviour (the code outranks AGENTS.md:204 and claude-docs) and define how it is reproduced and audited in Replay.
