### B. New findings this round

**N31. §7 has the fee rule backwards: Production paper trading charges zero fees.**
- **[PROJECT EVIDENCE]** Every automatic wallet execution (six code paths) records `feeUsdt(ZERO)`, and fills use the latest observed price event.
- **[PROJECT EVIDENCE]** The protected-profit floor is entry × 1.0005, i.e. +0.05%.
- **[AGENT INFERENCE]** A Production-logic profile must therefore use zero fees and zero slippage.
  - Any fee changes virtual cash, which feeds `WalletExecutionSizingPolicy.plan` and so changes later position sizes and eligibility.
  - A run with fees is a counterfactual, yet §7 treats zero-fee as the special case that needs a label.
- **[EXTERNAL RESEARCH]** Binance's standard spot fee is about 0.1% per side (D3). At real fees, a "protected-profit" exit at +0.05% loses money.
  - That is a realism question, not a parity one, and the spec should keep the two apart.

**N32. M02 is missing Production's candle data-quality gate.**
- **[PROJECT EVIDENCE]** Before computing indicators, Production calls `CandleDataQualityService.validate`. This checks the latest 210 closed candles and allows no missing ones. On failure Production records `SKIPPED_DATA_UNAVAILABLE`.
- **[PROJECT EVIDENCE]** Replay's snapshot path only checks the candle count.
- **[AGENT INFERENCE]** Replay can therefore produce, and trade on, signals that Production refused to compute.
  - For simulation, M02 needs the same gate, evaluated as of each candle.
  - For ANALYSIS_PARITY, Replay should take the outcome from `candle_analysis_outcome`.
  - Production's own gate checks the *latest* 210 candles, not those as of the event, which matters when its analysis runs late.

**N33. M02: a row still marked open makes Replay re-analyse the previous candle.**
- **[PROJECT EVIDENCE]** Replay's timeline includes every loaded row, closed or not.
- **[PROJECT EVIDENCE]** The snapshot is built only from closed rows at or before that row's open time.
- **[PROJECT EVIDENCE]** Production's `calculateAndPersist` rejects a snapshot whose candle isn't the requested one. The Replay path has no such check.
- **[AGENT INFERENCE]** So a `closed=0` row in mid-window (for example a reconnect gap awaiting reconciliation) has this effect:
  - Replay re-analyses the previous candle one interval later, with later context, and treats it as a new signal.
  - `analysis_test_signal` records the requested open time, while `trade_signal_test` records the previous candle's.
- **[AGENT INFERENCE]** M02 must compare candle identity *after* building the snapshot, not just check `closed=1` on the input row.
  - Because M02 says "exact", it should also state the `close_time = open + interval − 1 ms` convention.
- **[PROJECT EVIDENCE]** An open candle at the end of the window is already skipped (the `evaluationTime > end` check).

**N34. The same candle gets three different as-of clocks.**
- **[PROJECT EVIDENCE]** The as-of clocks differ by signal mode:
  - LIVE signals are stamped with `Instant.now()`.
  - HISTORICAL_ONLY and recovery signals use the candle's `close_time` (open + interval − 1 ms).
  - Replay uses open + interval.
- **[PROJECT EVIDENCE]** The BTC signal lookup only accepts BTC candles that opened at or before `evaluatedAt − interval`.
- **[AGENT INFERENCE]** For a BTC candle that closes at the same moment as the symbol's candle:
  - LIVE: it's a race between the two analyses.
  - HISTORICAL_ONLY: always excluded, because the cut-off is open − 1 ms.
  - Replay: always included.
- **[AGENT INFERENCE]** The oracle needs clock rules for each `signal_mode`. §7's "recorded/inferred ordering" doesn't provide them.

**N35. An exact-match oracle would report mismatches that aren't defects.**
- **[PROJECT EVIDENCE]** Raw confidence gives liquidity a weight of 0.12 and derivatives 0.08.
  - **Liquidity with no samples:** live analysis returns INSUFFICIENT_DATA_HOLD, scored 25 and blocking entry. Historical analysis returns UNAVAILABLE, scored 40, and leaves entry unchanged.
  - **Derivatives failure:** live UNAVAILABLE carries a −10 adjustment; historical UNAVAILABLE carries 0.
  - **Validator:** `ReplayParityValidator` compares raw confidence, effective confidence and liquidity status by exact equality.
- **[AGENT INFERENCE]** The differences run in both directions:
  - With no data, Replay's raw confidence is about 2.6 points higher before rounding (+1.8 liquidity, +0.8 derivatives), and entries that live analysis held back become allowed.
  - When Production had live derivatives data, the gap reverses: for example, base 80 against Replay's 40 is about −3.2 points (status adjustment not checked).
- **[AGENT INFERENCE]** Without rules that take these inputs from Production's stored output, and versioned tolerances, ANALYSIS_PARITY would fail for reasons that aren't logic defects.

**N36. M06: Replay's exact-price path ignores the profit lock for both SELLs and adds.**
- **[PROJECT EVIDENCE]** Production blocks both SELLs and adds while the profit lock is active.
- **[PROJECT EVIDENCE]** Replay's exact path validates SELLs without that check, and adds without it.
- **[PROJECT EVIDENCE]** Replay's exact path never checks TP, lock, STOP_LOSS or floor at the signal's price. Only the fallback path does.
- **[AGENT INFERENCE]** X06 must cover both exact-path cases (see C22).

**N37. Several "permitted evidence" tables in §3 can't prove what Production decided.**
- **[PROJECT EVIDENCE]**
  - `order_book_snapshot` is written asynchronously on a best-effort basis, and dropped when the queue is full.
  - `buy_htf_assessment_audit` is best-effort and dropped on rejection. Its `evaluated_at` holds the signal's `generated_at`, not the evaluation time.
  - `fix122_evaluation` commits in its own transaction, so it survives a business rollback. Replay also writes to it, although §3 lists it as read-only.
  - `execution_opportunity` rows are updated in place.
- **[AGENT INFERENCE]** For these tables, a missing row doesn't prove nothing happened, and a present row doesn't prove the decision committed.
  - No as-of rule can reconstruct a row that is overwritten in place.
  - §3 needs to classify how far each table can be trusted.

**N38. C04 and X10 don't name an actual resource to limit.**
- **[PROJECT EVIDENCE]**
  - `runAsync` is `@Async` with no executor named.
  - The app has seven `ThreadPoolTaskExecutor` beans, none named `taskExecutor` or marked `@Primary`, and no `AsyncConfigurer`.
  - Replay shares the Production database connection pool (Hikari, maximum 15).
  - Protection rejects price events older than 15 s, checked inside the protection transaction (`STALE_PRICE`).
  - Only one run at a time is already enforced.
- **[EXTERNAL RESEARCH]** Spring's documented rule (D2): use the unique TaskExecutor, or one named `taskExecutor`; otherwise fall back to `SimpleAsyncTaskExecutor`, which has no thread limit.
- **[AGENT INFERENCE]** Replay most likely runs on one of those unlimited fallback threads, competing with Production for the database, connection pool and CPU.
  - C02 restates behaviour that already exists.
  - C04 must name a dedicated executor bean and a database budget.
  - X10 needs a measurable Production criterion: under Replay load, no rise in `STALE_PRICE`/NON_CANONICAL outcomes or in protection latency.

**N39. "Production code must remain unchanged" contradicts the spec's own file list.**
- **[PROJECT EVIDENCE]** The handoff note says Production *code* stays unchanged.
- **[PROJECT EVIDENCE]** §4 modifies ten shared Production classes. Jenkins deploys LIVE on every build, with no approval stage and no automatic rollback.
- **[AGENT INFERENCE]** Which one the user means decides the design:
  - If "code unchanged": RPR6-05, -07, -08, -09, -10 and -12 are out of bounds.
  - If "behaviour unchanged": the spec must say so and, in addition, it must:
    - keep the protection and signal paths' lock and transaction order (FIX-124/125/127/153, and AGENTS.md's input → protection order);
    - prove Production equivalence on recorded inputs;
    - give a real code rollback. "Disable the Replay route" doesn't undo a refactor of shared classes.
- **[AGENT INFERENCE]** This needs a user decision.
