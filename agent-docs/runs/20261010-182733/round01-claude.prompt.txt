## 1. Business objective and flow

Replay must use current Production paper-trading policies with an isolated
virtual account. It must never read Production account state, call HTTP, or
call candle-only output historical parity.

1. User selects one symbol, virtual profile, window and mode.
2. Qualifier validates every input before a generated Replay artifact exists.
3. A refusal writes only a run/certificate diagnostic.
4. Qualified analysis uses closed, identity-matching candles.
5. Simulation invokes pure Production policies with only virtual adapters.
6. Results stage privately and publish only on terminal success.

Release 1 labels outcomes only `ANALYSIS_PARITY`,
`PRODUCTION_LOGIC_SIMULATION`, or `REFUSED_INSUFFICIENT_EVIDENCE`.
`ENTRY_DECISION_PARITY` and historical wallet-lifecycle parity are out of scope:
they require account-state evidence that Replay is forbidden to read.

`ShadowProductionReplayService`, `ExecutionReplayScope`,
`TradeExecutionValidationService`, `DynamicProfitLockService`,
`LivePositionProtectionService`, `PositionManagementService`, and
`PaperTradingService`.

Close-message lineage, deployed JAR/config identity and historical
order-book/derivative/sentiment availability are not durable for all old
windows. Strict claims are therefore unreachable for such eras unless a future
approved forward-capture design is implemented.

In scope: single-symbol virtual simulation; qualifier/refusal; closed-candle
identity; virtual settings/constraints; stable Replay IDs; pure policy ports;
staging; resource limits; tests. Out: Production strategy change, real exchange,
Production account reads, multi-symbol scheduling, and retirement of
