### B. New findings this round

**N42. Replay's sentiment uses today's provider settings, and live and historical analysis gate providers differently.**
- **[PROJECT EVIDENCE]** Every analysis path calls `overviewAsOf(symbol, generatedAt)`. Inside it, the provider list and each provider's `enabled` flag and `weight` come from the *current* `sentiment_provider_config` rows. There is no as-of version.
- **[PROJECT EVIDENCE]** Those rows are seeded once from `application.yml`, then edited through `update()`. Each collection overwrites `lastStatus`, and `lastSuccessAt` on success. No history table exists.
- **[PROJECT EVIDENCE]** Which providers count depends on how old the reference time is:
  - **Live** (within 1 s of the wall clock): a provider counts only if its last successful collection is under 2 h old (the `stale-after` default).
  - **Historical** (Replay, and Production's own `HISTORICAL_ONLY` signals): a provider counts if it has any sample in the 24 h window.
- **[PROJECT EVIDENCE]** Sentiment counts as "available" only if at least 50% of the *currently enabled* providers are usable. That switch adds or removes the 15-point sentiment maximum from the score normalisation.
- **[AGENT INFERENCE]** Two effects follow. Both change the total score, so they can change the decision:
  - **Configuration look-ahead.** By default only Fear & Greed (weight 0.15) and Manual News (0.03) are enabled. At its default weight, Manual News can never count as usable. If one more provider is enabled today and had no samples back then, past coverage drops from 1/2 to 1/3. Replay then treats sentiment as unavailable in windows where Production had it.
  - **Different gates.** During a Fear & Greed outage of 2–24 h, Production's live analysis dropped sentiment as stale. Replay still counts the older sample.
- **[AGENT INFERENCE]** M03's "stored as-of evidence" therefore isn't enough for sentiment. The signal itself records `sentimentAvailable` and a per-provider breakdown.
  - The oracle should take Production's stored per-signal sentiment outcome.
  - Simulation should either use a provider set declared in the profile, labelled as such, or refuse.
- **[AGENT INFERENCE, minor]** The live-versus-historical switch compares against the machine clock inside an analysis policy. Sentiment is evaluated first, so a live run rarely crosses the 1 s threshold.

**N43. The `ANALYSIS_PARITY` oracle has never run, and §8 doesn't test whether it catches anything.**
- **[PROJECT EVIDENCE]** `ReplayParityValidator` has no caller anywhere in `src/main` or `src/test`; only `fix-registry.js` mentions it.
- **[PROJECT EVIDENCE]** Only three test classes have Replay, Regression, Shadow or Parity in their names, and none covers the worker or the oracle.
- **[PROJECT EVIDENCE]** The validator compares 13 fields by exact equality. Tests X01–X12 include no test of the oracle's own accuracy.
- **[AGENT INFERENCE]** With no measured baseline, the oracle can be wrong in both directions:
  - false alarms caused by deliberate input differences (N35, N42);
  - false passes, because some decision inputs are never compared: total score, signal mode, and where sentiment, BTC and higher-timeframe context came from.
- **[AGENT INFERENCE]** §8 needs:
  - one fixture of a known-matching pair that must pass;
  - one seeded divergence per compared field, plus one change to the final-decision logic, each of which must fail;
  - for each declared deliberate difference, a fixture showing it is classified as a refusal, not a mismatch;
  - before any run carries the label, a bounded read-only comparison against real `LIVE` signals that reports the mismatch rate per field.

**N44 (moderate). When a price event became visible to Production can't be reconstructed.**
- **[PROJECT EVIDENCE]** A price event is written as `PENDING` and becomes `APPLIED` inside the protection transaction. Production's BUY price lookup sees only rows already committed as `APPLIED`/`LEGACY` at wall-clock time.
- **[PROJECT EVIDENCE]** No column records when that change committed; `created_at` is the receipt time.
- **[AGENT INFERENCE]** Replay treats every event that was *eventually* `APPLIED` as visible from its `observed_at`. An event whose protection transaction was still open is therefore visible to Replay but was invisible to Production. The effect is small and limited to the newest event. Even so, M06 must record it as a simulation assumption, and no parity claim may rely on it.

**N38 update: stronger evidence, not a new objection.**
- **[PROJECT EVIDENCE]** The project uses Spring Boot 4.1.0, with `@EnableAsync` and seven unconditional executor beans. There is no `AsyncConfigurer`, no `@Primary` executor, no bean named `taskExecutor`, and only `spring.task.scheduling` is configured.
- **[EXTERNAL RESEARCH]** Under the documented rule for current versions (R1, R2), `@Async` therefore runs Replay on an unbounded `SimpleAsyncTaskExecutor`. This closes the version caveat I left in Round 6; it still needs runtime confirmation.
- **[EXTERNAL RESEARCH + PROJECT EVIDENCE]** The same Javadoc says exceptions escaping a `void` `@Async` method are only logged. If `runAsync`'s own ERROR update fails, the run row stays `RUNNING`.
- **[AGENT INFERENCE]** M04's "records only terminal run failure" needs someone responsible for recovering runs stuck that way.

### E. External research

- **R1. Spring Framework `@EnableAsync` Javadoc, version 7.0.9**
  - Source: https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/scheduling/annotation/EnableAsync.html (the page shows no date).
  - Finding: Spring uses the single `TaskExecutor` bean, or one named `taskExecutor`; otherwise it falls back to `SimpleAsyncTaskExecutor`. Exceptions from `void` async methods are only logged.
  - Limitations: this is the documented rule, not observed runtime behaviour.
  - Relevance: N38 and M04.
- **R2. Spring Boot reference, "Task Execution and Scheduling", documenting 4.1.1**
  - Source: https://docs.spring.io/spring-boot/reference/features/task-execution-and-scheduling.html (the page shows no date).
  - Finding: when the application defines its own `Executor` beans, Spring Boot doesn't create its default one; `spring.task.execution.mode=force` would change that.
  - Limitations: the page doesn't spell out the case of several custom executors, and the project pins 4.1.0, not 4.1.1.
  - Relevance: N38 and C04.
- Neither source says anything about trading performance.
