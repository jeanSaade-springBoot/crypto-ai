### E3: Where each close reason comes from (PROJECT EVIDENCE, code)

- **Live price path.** `LivePositionProtectionService.onPrice` (`src/main/java/com/crypto/position/service/LivePositionProtectionService.java:95-97`, `:235-238`) produces `SELL_CONFIRMED` and `HTF_SELL_CONFIRMED`. It calls `PositionExitPolicy.evaluateNormalExit` (`src/main/java/com/crypto/position/service/PositionExitPolicy.java:20-50`).
  - `HTF_SELL_CONFIRMED`: the latest 1h is SELL or STRONG_SELL, and the latest 5m is not BUY, STRONG_BUY or WATCH.
  - `SELL_CONFIRMED`: the latest 1m is bearish, the latest 5m is bearish, and the latest 1h is not bullish.
- **Live price path, profit lock.** `PROFIT_LOCK_HARD_EXIT` comes from `LivePositionProtectionService.java:191-197` (the hard floor during a TP-extension rebase) or `:210-216` (lock triggered while price is below entry × 1.0005). A copy of the same check exists in the signal path at `src/main/java/com/crypto/service/PaperTradingService.java:190-195`.
- **Signal path.** `STRONG_SELL` comes from `PaperTradingService.java:197-208`. The close reason is the signal's own decision name, and the close only happens if `TradeExecutionValidationService.validateSell` passes (`src/main/java/com/crypto/service/TradeExecutionValidationService.java:165-191`). That check requires a fresh bearish 5m and a fresh 1h that is not bullish.

## FINDINGS (Iteration 1, all provisional)

- **F1: The selection leaves out every stop-loss loss.** PROJECT EVIDENCE + AGENT INFERENCE. Stop-loss closes write `status=STOPPED` (`LivePositionProtectionService.java:178`, `PaperTradingService.java:183`). The frozen rule takes only `status='CLOSED'`, so all 75 STOPPED losses are excluded. The frozen set therefore holds only signal or profit-lock exits that ended at a loss. That is a valid subset, but not "the latest 6 failed trades". I am not substituting any trade; this is reported as a scope limitation.

- **F2: The newest frozen loss is 20 days older than the snapshot.** PROJECT EVIDENCE. The newest closed at 2026-10-12 10:05 UTC; the snapshot is 2026-11-01 08:17 UTC. Possible reasons: the trader was inactive, later losses were all STOPPED, or there were no CLOSED losses. DBQ-CLAUDE-I1-011 checks this.

- **F3: Candidate rule asymmetry, live exit path versus signal exit path.** PROJECT EVIDENCE (code) + AGENT INFERENCE.
  - The live path takes the newest 1m, 5m and 1h signals with `findTopBy…OrderByGeneratedAtDesc` (lines 95-97) and does not check their age.
  - The signal path (`validateSell`) requires a fresh 5m and a fresh 1h.
  - The signal path also skips SELL while a profit lock is active (`PaperTradingService.java:199-203`). The live normal exit has no such guard when the lock is active but not triggered.
  - **Effect:** a stale 1h SELL could cause `HTF_SELL_CONFIRMED` (trade 172), and a stale 5m SELL could cause `SELL_CONFIRMED` (182, 158, 137).
  - **Status:** not confirmed. It needs the 5m and 1h signal ages at close time (DBQ-CLAUDE-I1-008).

- **F4: "Profit lock" exit closed at a loss (trade 143).** PROJECT EVIDENCE + AGENT INFERENCE. The hard floor is entry × 1.0005. A loss means the exit price was below entry. Either:
  - (a) price jumped past the floor between ticks, after the lock had activated within about 3.5 minutes, or
  - (b) it was the FIX-118 rebase hard-floor branch.

  Needs `position_management_event`, `wallet_managed_position` and price events (DBQ-CLAUDE-I1-006/007/009).

- **F5: Back-to-back EGLDUSDT losses.** PROJECT EVIDENCE. Trade 137 lost -0.075, and trade 143 re-entered EGLDUSDT 1h40m later and lost again. Whether any re-entry cooldown or same-symbol loss rule should have applied is unknown, and is noted for a later iteration.

- **F6: Recorded P&L is gross of fees.** PROJECT EVIDENCE (claude-docs `TRADING_RULES.md` §6, `INVESTIGATION_LOG.md` item 2). Automatic `wallet_trade` rows record `fee_usdt=0`, so real losses are larger. Fees have to be computed from quantity × price (DBQ-CLAUDE-I1-004).

- **F7: The docs conflict with the working tree.** PROJECT EVIDENCE.
  - AGENTS.md and claude-docs say FIX-154 is not implemented.
  - The working tree has `src/main/java/com/crypto/service/HigherTimeframeBuyAssessmentService.java`, and `validateBuy` calls it (`TradeExecutionValidationService.java:145-150`).
  - Which build was running on 2026-10-11/12 is unknown, so current-tree code may not match the code that ran at trade time. This is reported, not resolved.
