1. Five of the six entries had a risk/reward below 1. The stop is held at a fixed 0.5% minimum, while the target uses the much smaller 3×ATR.

### E2: Where the risk/reward comes from (PROJECT EVIDENCE, code in the current tree)

- `AtrRiskService.java:34-45` sets the stop distance to max(2×ATR, 0.5% of price) and the target distance to 3×ATR, with nothing equivalent for the target.
- Whenever ATR% is below 0.25%, the stop is held at 0.5% while the target shrinks with ATR. R:R then equals 6×ATR% and falls below 1.5.
- `getRiskRewardRatio()` / `riskRewardRatio()` is only read in `AnalysisService:540` (persist), `DashboardApiController` and `TradeInspectorService` (display). No entry gate uses it.
- Caveat: the build that ran on 10-11/12 is unknown (iteration-1 U7). The DB values themselves (stop exactly 0.5%, stored R:R 0.33–0.74) show the behavior regardless of build.

### E6: Trade 143 profit-lock timeline (PROJECT EVIDENCE, I1-006, I1-007, code)

- 01:40:03 KSA: entry at 4.033.
- 01:40:23: profit lock activates.
- 01:40:41: target extended 4.0647 → 4.0805 at price 4.067.
- 01:41:13: target extended 4.0805 → 4.1043 at price 4.081.
- Peak price was 4.101 and the stored lock price was 4.07579.
- 01:43:35: exit at 4.027, below both the lock (4.0758) and the floor (entry × 1.0005 = 4.03502).
- The exit wording matches the "triggered" text (`DynamicProfitLockService.java:193`) plus `LivePositionProtectionService.java:212`. It does not match the rebase wording (`:185`). So this was the ACTIVE-lock branch, not the FIX-118 rebase branch.
- When the lock is triggered with 1h=NEUTRAL, 5m=WATCH and 1m=WATCH, `evaluateProfitLockBreach` (`PositionExitPolicy.java:52-92`) falls through to `PROFIT_LOCK_EXIT`.

**AGENT INFERENCE:** a tick between 4.035 and 4.0758 would have exited in profit, so the first tick evaluated at or below the lock was already ≤ 4.027. Possible causes:
- (a) a real price gap of about −1.2% between ticks;
- (b) sparse sampling: about 65 ticks in 3m50s, roughly one every 3.5 s;
- (c) a different 1h/5m state at trigger time.

I2-003 and I2-001 test these.

## FINDINGS (Iteration 2; I have reviewed only my own work)

- **F8: Entries with a structurally negative edge. Likely defect (design or configuration).** PROJECT EVIDENCE (E1, E2) + AGENT INFERENCE.
  - Five of six entries had R:R between 0.33 and 0.74 because of the 0.5% stop floor combined with a 3×ATR target.
  - Gross break-even win rate: 158 needs 74.5%, 162 70%, 182 68%, 137 61%, 172 57%.
  - Assuming Binance's standard spot fee of about 0.1% per side, round trip about 0.2% (EXTERNAL knowledge, not fetched this session; the system records `fee_usdt=0`), 158's full target of +0.17% is a **net loss even if it is hit**. 162 and 182 would net only about +0.02% and +0.04%.
  - No code gate uses `risk_reward_ratio` (E2).
  - These losses are valid under the rules as coded, but the rule set allows entries that cannot pay off at their own target.
  - I3-005 tests this across the whole population before I call it confirmed.

- **F9: WATCH-decision entries.** PROJECT EVIDENCE (E3).
  - Three of six (143, 158, 162) entered on a 1m WATCH through Execution Intelligence routes.
  - 143 entered despite WAIT_FOR_RETRACEMENT and RSI 84.
  - These routes appear to be designed behavior. Whether they are allowed under TRADING_RULES is held for iteration 3. Not called a defect yet.

- **F10: Trade 143 exited through the profit lock at a loss.** PROJECT EVIDENCE (E6) + INFERENCE.
  - The lock earned at a +1.69% peak did not protect any profit: the exit was at −0.15%, below the protected floor.
  - Whether this is a protection defect (missing or late ticks) or market slippage depends on I2-003.
  - This refines F4: it was **not** the rebase branch.

- **F3 (still open): stale higher-timeframe signals in the live exit path.** Not testable until I2-001 returns.
  - In 172, the 1h signal turned SELL but the exit came 15 minutes later. That is consistent with waiting for the 5m to turn non-supportive, not with staleness. This is still unverified.

- **F11: Signal exits limited every loss to below the stop.** PROJECT EVIDENCE (E5).
  - Losses were 0.13–0.35%, against a 0.5% stop.
  - The exits themselves do not look harmful. The losses come mainly from entries that never moved toward their target: best progress was 0–49%, except 143.

- **F12: Traceability gaps (minor).** PROJECT EVIDENCE.
  - 158's work row does not link to the paper position.
  - Two execution messages state a size that differs from the executed size.
  - `paper_position.closed_at` lags the wallet exit by up to 3.2 s.

- **F1 and F7 from iteration 1 still stand.** F1: all STOPPED losses are excluded from the frozen set. F7: FIX-154 code is in the working tree but the docs say it is not implemented.

### DB_REQUEST
