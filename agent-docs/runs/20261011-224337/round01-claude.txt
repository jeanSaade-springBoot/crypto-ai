# FIX-156 RPR-0.9.4: what remains before Replay can reach 98–99% non-wallet parity with Production

**Short answer:** none of the FIX-156 work exists in the code yet. Two register rows are wrong as written, and one requirement cannot be met while Production classes stay unchanged. The spec needs one more revision before it can be frozen.

I did not edit the spec or any code, and I did not touch the database. I also could not write the plan file because no Write tool was available in this session.

**F-A — Nothing from FIX-156 has been built.** [PROJECT EVIDENCE]

**F-B — D01 is wrong as written; the outcome is already the same.** [PROJECT EVIDENCE]
- Production does pass 5m and 1h SELL signals to `validateSell`.
- But `validateSell` first calls `validateBaseSignal(signal, false)`, which rejects any non-1m signal with `NON_EXECUTION_TIMEFRAME`.
- So in Production only a 1m SELL can close a position, exactly as in Replay. D01 should be "Production-proven equivalent" (one fixture), not "Replay change".

**F-C — D08 is largely closed by the code.** [PROJECT EVIDENCE]
- Both wake-up methods return `none()` unless the signal interval is 5m.
- When no position is open, `evaluateBuy` on a 5m or 1h signal returns `CONTEXT_ONLY` before touching opportunity memory.
- So Production trying wake-ups on every signal gives the same entry outcome as Replay trying them only on 5m.
- Still to check: whether the FIX-122 `stopLossEvidence` wrappers have side effects that later change a 1m decision.

**F-D — Material gap: Replay cannot stop reading `wallet_settings` without changing a Production class.** [PROJECT EVIDENCE]
- Replay calls the shared `evaluateBuy` → `validateBuy`.
- `validateBuy` reads `wallet_settings` row 1 for `requireNewBuyTransition` (line 66) and `executionProfile` (line 152), through `settings()` at line 400. That method has no Replay branch.
- This contradicts three things in the spec:
  - Stage 1 says "remove all `wallet_settings` reads" (§2/§4).
  - RPR7-06 says Replay must never call a service that reads an account table.
  - §5 says no Production class may be modified.
- E10 / §3.6 also leave out these two settings, and both change BUY decisions.
- The spec must choose one of:
  - (a) treat these two values as permitted, versioned configuration evidence, captured per decision;
  - (b) declare those decisions non-comparable;
  - (c) reopen the design to allow a scope-aware settings source in Production.

**F-E — D02 has an extra condition the fixtures must cover.** [PROJECT EVIDENCE]
- Production only suppresses a SELL if `profitLock.active()` is true.
- But `profitLock` is forced inactive when `canUseSignalPrice(signal, openedAt)` is false.
- So a SELL whose signal price predates the entry is **not** suppressed even while a lock is active. The Replay mirror and the F3 fixtures need this case.

**F-F — D23 adds an exit class the metrics don't list.** [PROJECT EVIDENCE]
- `PositionManagementService.analyze` can run `executePositionStopLoss` and record `POSITION_STOP_LOSS`.
- Replay never calls it.
- That exit class is missing from the §7.1 per-exit-class list and from the §7.2 critical-safety classes.

**F-G — Price-event ordering in Production is a guess.** [PROJECT EVIDENCE + AGENT INFERENCE]
- `market_price_event` rows are only accepted if `LEGACY`/`APPLIED`, and the query orders by `(observed_at, id)`. The `PriceEvent` record keeps only `observedAt`, `price` and `source`, so the id is lost.
- Production protection runs from `BinanceKlineService:108` (canonical events only) and from `SharedMarketConsumer:513/728` for collector-era data.
- **Inference:** `LEGACY` rows from the collector era may not have been processed by protection in the same order, so the `(observed_at, id)` = processing-order question (F6) is a real risk for collector-era windows.

**F-H — Two things that should be per-span or per-decision are still run-wide.** [PROJECT EVIDENCE]

## OBJECTIONS
1. **F-D blocks the freeze.** As written, the spec requires removing `wallet_settings` reads and also forbids modifying Production classes. Both cannot hold, because the shared BUY validation Replay calls reads `wallet_settings` directly.
2. **D01 is misclassified** (F-B). Fixing it doesn't change scope, but the register has to be correct before the freeze.
3. **The 98–99% target has no numbers behind it.**
   - The coverage threshold, minimum comparable count and confidence-interval method in §7 are all still unset.
   - With n comparable lifecycles and a 99% target, the lower bound only clears 98% if n is in the low hundreds and nearly every case matches.
   - The real risk is that strict exclusions (S01–S03, S09, S12, F7, F10) shrink the denominator until "99%" is measured on a hand-picked subset. Coverage has to be a hard gate, not just something reported next to the rate.
4. **Seeding from recorded entries hides entry divergence.** Lifecycle parity only starts after entry. So BUY-decision parity is the only evidence about entry quality, and S02, S03 and S09 make many live 1m signals non-comparable. The spec should require a reported BUY-decision coverage rate.
5. **POSITION_STOP_LOSS is missing** from the exit classes in §7.1 and §7.2 (F-F).

## UNKNOWNS
- Whether the FIX-122 `stopLossEvidence.evaluate/wakeup` wrappers have side effects on non-1m signals that change later decisions (affects D08 and D18).
- Whether `market_price_event.id` order matches the order Production actually processed events, especially for `LEGACY` / collector-era rows (F6).
- Whether `DynamicProfitLockService.evaluate` and Replay's `profitLockState` produce identical state across the TP-extension rebase (D14). I did not check this here.
- Whether any history exists for `wallet_settings` or other configuration (E10). I did not query the database, so all coverage and rate figures remain unmeasured: E03, E06, E07 and E08.
