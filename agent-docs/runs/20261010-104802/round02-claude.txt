### B. Resolved: Replay does process candles that never closed (`closed=0`) [PE]
1. Replay builds its candle timeline without a "closed" filter (`RegressionTestWorker.java:129-131` → `:509-512` → `CandleRepository.java:60-61`; timeline built at `:550-560`).
2. For each timeline entry, the indicator snapshot uses only closed candles at or before that open time:
   - DATABASE mode: `TechnicalIndicatorService.java:186-200` and `CandleRepository.java:51-52`.
   - DATASET mode: `TechnicalIndicatorService.java:135-145`, `ReplayDataset.java:33-45`, and the closed-only loader at `RegressionTestWorker.java:475-480`.
3. The snapshot's candle identity is the latest closed candle (`TechnicalIndicatorService.java:318-322`). The generated signal copies that identity (`AnalysisService.java:220, 409`).
4. The evaluation time is the close time of the unclosed timeline entry (`RegressionTestWorker.java:584, 616`).

**Result:**
- An unclosed row makes Replay analyse the previous closed candle again, at a later time.
- That produces a second signal with the same candle identity. Production's close-transition path would not produce it [AI; I did not re-trace the Production path this round].
- For these rows the two Replay tables disagree on which candle the signal belongs to:
  - `analysis_test_signal` stores the unclosed row's open time (`:646`).
  - `trade_signal_test` and the lineage lookup use the snapshot's identity (`:672-683`).
- `verifyEventResolution` only counts such rows; it does not exclude them (`:514-533`).

This confirms `RPR-0.4_REVIEW_RESPONSE.md:33-34` and makes it more precise. It is not look-ahead (the data used is older), but it inflates Replay signal counts with stale duplicates [AI].
