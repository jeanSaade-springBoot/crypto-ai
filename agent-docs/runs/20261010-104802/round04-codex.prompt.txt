### B. Replay can create a stale duplicate signal that Production cannot [PE]
In round 2 this was partly inference. I have now traced both paths.

**Production checks candle identity twice.**
- The live worker calls `calculateAndPersist(…, event.openTime())` (`CandleClosedAnalysisWorker.java:130-137`). That call returns nothing when the newest closed candle is not the expected one (`TechnicalIndicatorService.java:102-106`), and the work ends as `HISTORY_UNAVAILABLE`.
- It then skips any candle that already has a signal (`CandleClosedAnalysisWorker.java:142-158`).
- The recovery path does the same (`ScheduledAnalysisService.java:158-175`) and scans closed candles only (`CandleRepository.java:76-88`).

**Replay has neither check.**
- Neither Replay snapshot method takes an expected candle (`TechnicalIndicatorService.java:118-145`).
- The worker never compares the snapshot's candle with the timeline candle. It also never checks for an existing signal before persisting (`RegressionTestWorker.java:590-616, 636-683`).

**The code comment is wrong.** The comment at `:575-577` says Replay analyses "EVERY closed candle in the timeline". The timeline actually comes from a loader with no "closed" filter (`:509-512`, `CandleRepository.java:60-61`).

**The duplicate is used downstream.**
- It is added to the as-of context (`:620`) and to shadow execution (`:622`, `:199-201`).
- Replay's "latest signal" lookups select by `generatedAt` (`ExecutionReplayScope.java:106-120`). So the stale duplicate becomes the latest 1m signal one interval later.

**Impact [AI].**
- Suppose the original BUY was not executed. The duplicate is then re-evaluated against newer context and can open a shadow trade that Production could not.
- If the original BUY was executed, `BUY_CONTINUATION` likely blocks the duplicate (`TradeExecutionValidationService.java:67-78`).
- How often this happens needs the database.

### C. New: a REST candle import can swallow a live candle close [PE + AI]
**What happens.**
- `importCandles` writes each REST candle whose close time has passed as `closed=1` (`MarketDataService.java:37-50`).
- That write uses an upsert that finalises an existing `closed=0` row without a close token (`CandleRepository.java:173-188`). The comment at `:175-176` says this is intended.

**Where it can run while the live stream is active.**
- Coin activation reloads the WebSocket streams first (`DynamicCoinActivationService.java:21`) and then runs the import (`:28` → `MarketDataBootstrapService.java:72-96`).
- `POST /api/market-data/import` runs it directly (`MarketDataController.java:16-24`).

**Result if the import commits before the live final kline arrives.**
- The live update finds the candle already closed, so no `CandleClosedEvent` is published. The only trace is an INFO `DUPLICATE_CLOSE` log line (`BinanceKlineService.java:110-117`).
- The follow-up audit call only updates candles that reconciliation recovered (`LocalReconciliationAuditRepository.java:51-57`), so nothing durable is recorded.
- Scheduled analysis is switched off (`application.yml:125`).
- So that candle gets no analysis and no recorded outcome.

**Scope and status.**
- Startup is probably not exposed [AI]. The startup import runs as an ApplicationRunner, which in Spring Boot should finish before `ApplicationReadyEvent` starts the WebSocket (`BinanceWebSocketManager.java:95-96`). I did not test this.
- It has not been observed: the current log has no `DUPLICATE_CLOSE`, activation or import lines.
- It conflicts with two `AGENTS.md` local-candle rules: backfill must never finalise a live row through a duplicate-key update, and every candle needs one durable outcome. Whether those rules cover this import path, and not only the reconciliation insert (`CandleRepository.java:147-168`, which never overwrites), is for the user to decide.
