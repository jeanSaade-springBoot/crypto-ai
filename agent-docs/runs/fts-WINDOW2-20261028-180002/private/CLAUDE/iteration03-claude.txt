### T2. Normal exits fire only on the next price tick, not when the signal arrives (PROJECT EVIDENCE: code + DB)

**Code.** `LivePositionProtectionService.onPrice` (`LivePositionProtectionService.java:75-244`) is the only caller of `PositionExitPolicy.evaluateNormalExit` (`:235`). It is invoked only from the 1m kline price callback (`BinanceKlineService.java:106-108`). A newly persisted SELL signal therefore does not close a position by itself. The exit waits for the next Binance 1m kline WebSocket message for that symbol.

**Measured delay** (first moment the exit rule became true → exit):

| ID | Rule became true (UTC) | Exit tick / wallet SELL (UTC) | Delay | Signal price → exit price |
|---|---|---|---|---|
| 137 | 5m SELL 156852 @ 18:00:02.921 | 18:00:08.935 | **6.0 s** | 3.988 → 3.987 |
| 158 | 5m SELL 166821 @ 00:30:01.464 | 00:30:04.217 | 2.8 s | 1.4089 → 1.4090 |
| 162 | 1m STRONG_SELL 168277 @ 01:26:02.794 | 01:26:04.134 (signal path `SIGNAL_SELL`) | 1.3 s | 0.08675 → 0.08675 |
| 172 | 5m NEUTRAL 172588 @ 04:15:04.578 (1h SELL already set) | tick 04:15:43.462, wallet 04:15:43.492 | **38.9 s** | 0.00000548 → 0.00000548 |
| 182 | 5m STRONG_SELL 176934 @ 07:05:03.926 | tick 07:05:18.446, wallet 07:05:18.504 | **14.6 s** | 0.1880 → 0.1880 |

- **AGENT INFERENCE:** this is a design property, not a defect. The P&L effect on these six trades was 0 to −1 tick.
- On illiquid symbols, where SHIB's price-event gap reached 56.5 s and ACE's 57.6 s (DBQ-CLAUDE-I2-005), a confirmed exit can wait almost a minute.
- Replay shares the same price-event-driven design (FIX-052), so this should be reproducible there.
- Whether any tick arrived inside these windows is checked by DBQ-CLAUDE-I3-003.

### T3. Exits were held correctly by the coded policy (PROJECT EVIDENCE)

`PositionExitPolicy.java:20-50` behaved as written on every trade:
- **158:** a run of 1m SELLs from 00:21:00 to 00:29:00 UTC was held because 5m was NEUTRAL. It exited on the first bearish 5m.
- **172:** the 1h SELL at 04:00:06.106 was held because 5m was WATCH, which counts as "supportive", at 04:00, 04:05 and 04:10. The trade exited when 5m turned NEUTRAL at 04:15:04.
- **182:** 1m SELLs at 07:02:03 and 07:04:02 were held (5m NEUTRAL). The trade exited at the 5m STRONG_SELL.

Two observations:
- **Downgraded 5m signals:** the 182 window contains 5m rows whose `original_decision` was STRONG_SELL but whose `decision` was NEUTRAL (176655, 176792). The policy reads `decision`, so the exit was delayed until the 07:05 5m signal. **AGENT INFERENCE:** price was 0.1881 against an exit at 0.1880, so the effect was negligible. The downgrade stage is unidentified (U-I3-4).
- **No freshness check on exit:** the exit lookup uses `findTop…OrderByGeneratedAtDesc` (`:95-97`) with no age bound. The ages at close were all appropriate for their interval: at most 58 s for 5m, and 1h signals belonged to the current hour. So nothing went wrong here. Note that the "freshness before execution" rule in AGENTS.md is not applied on this exit path.

### T4. Trade 143's lock-vs-TP mismatch is explained; no defect (PROJECT EVIDENCE)

This resolves iteration-2 F5.

**Lifecycle (UTC → KSA):**
- **Lock activation** at 19:40:23 UTC (**22:40:23 KSA**). At that point TP was still 4.064697, so the 70% activation level was 4.0552. The 19:40 candle's high was 4.067, so activation was consistent.
- **First TP extension** at 19:40:41.050 (**22:40:41 KSA**), market price 4.067: TP 4.064697 → 4.080545.
- **Second TP extension** at 19:41:13.036 (**22:41:13 KSA**), market price 4.081: TP 4.080545 → 4.104317.
- **Lock level:** `highest` reached 4.101, which is 95.35% of the new geometry. The lock was 4.07579 and the hard floor was entry × 1.0005 = 4.0350165, as coded at `LivePositionProtectionService.java:210`.

Both extensions follow `newTP = oldTP + 0.5 × (oldTP − entry)` exactly, as in `LivePositionProtectionService.java:108-110`.

**The breach:**
- The last tick before the breach was 19:43:27.038 at 4.100.
- The next tick was 19:43:35.021 at **4.027**. That is an **8.0 s gap with a −1.78% jump**, and the first observed price was already below both the lock and the floor.
- The wallet SELL followed **24 ms** after that tick (19:43:35.046), and the paper close followed 1.2 s later (19:43:36.229 UTC → **22:43:36.229 KSA**).
- Later ticks were 4.018 and 4.016, and the candle low of 3.994 came later still, below the SL of 4.0102.

**Classification:** a valid loss caused by a gap in observed prices. Protection reacted to the first ticks that were available. A stop-loss would have filled worse.

**Re-entry whipsaw (PROJECT EVIDENCE):**
- Trade 142 sold at 3.996 (PROFIT_LOCK_EXIT, 19:39:42.840 UTC).
- Trade 143 bought at 4.033 just 22.0 s later, which is 0.93% higher.
- I found no re-entry cooldown in production: grep for `cooldown|reentry|recentlyClosed|lastExit` returned only replay, monitor and REST-gate files.
- This is a candidate rule gap, not a defect claim.

### T5. Unexplained 8–14 s silences in a fast EGLD market (PROJECT EVIDENCE + EXTERNAL RESEARCH; open)

- Binance documents a kline update speed of 2000 ms for the 1m interval.
- During trade 143, which had RVOL about 21×, EGLD price events had gaps of 13.98 s (19:43:05.040 → 19:43:19.021) and 7.98 s (19:43:27.038 → 19:43:35.021).
- The latency from observation to persistence on the persisted ticks was only 3–35 ms, so there was no consumer backlog.
- Rejected observations (`STALE_PRICE` or `FUTURE_TIMESTAMP`) are **never persisted**: `MarketPriceEventService.recordPending` returns null and only logs (`MarketPriceEventService.java:53-58`). So the DB cannot tell "Binance sent nothing" apart from "the app rejected it".
- **AGENT INFERENCE:** either Binance emits only when the kline changes, or messages were dropped or rejected. DBQ-CLAUDE-I3-002 (density across symbols in the same seconds) and the 10-11 log, if it still exists, should discriminate.
- This is the only remaining open timing question for trade 143.

### T6. The protection transaction lasts 1.2–3.2 s after the wallet SELL (PROJECT EVIDENCE + AGENT INFERENCE)

- Gap from wallet `executed_at` to paper `closed_at` on mechanical exits: 137 3.19 s, 158 2.42 s, 172 1.99 s, 182 1.98 s, 143 1.18 s.
- The paper open also lags the wallet BUY by 1.5–2.2 s on all six trades.
- `executeMechanicalExit` runs inside the `onPrice` transaction. It takes the global daily-statistics row lock `FOR UPDATE` (`WalletAutoExecutionService.java:488`, `:553`), then calls `currentPortfolioValue()` and `captureSnapshot()`. Each of those runs one latest-closed-candle query per wallet asset (`WalletService.java:484-490`, `:592-607`).
- **Inference:** the lock is held for seconds and serialises every symbol's exit and entry.
- **No P&L effect**, because the price is fixed before this. But it may explain the 1.7–1.9 s observe-to-persist outliers in windows 158, 162 and 172, and possibly part of T5. DBQ-CLAUDE-I3-001 and I3-005 test this.

### DB_REQUEST
QueryId: DBQ-CLAUDE-I3-001
Purpose: Observe→persist latency by second-of-minute in each holding window; tests T6 contention around candle-close analysis
SQL:
SELECT p.id AS pid, SECOND(e.observed_at) DIV 5 * 5 AS sec_bucket, COUNT(*) AS n,
       ROUND(AVG(TIMESTAMPDIFF(MICROSECOND, e.observed_at, e.created_at))/1000,1) AS avg_ms,
       ROUND(MAX(TIMESTAMPDIFF(MICROSECOND, e.observed_at, e.created_at))/1000,1) AS max_ms
FROM paper_position p
JOIN market_price_event e ON e.symbol = p.symbol AND e.observed_at BETWEEN p.opened_at AND p.closed_at
WHERE p.id IN (182,172,162,158,143,137)
GROUP BY p.id, sec_bucket
ORDER BY p.id DESC, sec_bucket
LIMIT 100;
