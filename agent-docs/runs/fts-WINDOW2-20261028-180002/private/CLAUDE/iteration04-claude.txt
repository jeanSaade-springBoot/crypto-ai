## FINDINGS

### R1. Entry route: R:R floors differ by route, and the four routes these trades used have none (PROJECT EVIDENCE)

The R:R gates in `ExecutionIntelligenceService.java`:

| Route | R:R gate | Location |
|---|---|---|
| SCOUT_ENTRY | ≥ 1.25 | `:1055` |
| Progressive adds | ≥ 1.15 / 1.20 | `:1098`, `:1128` |
| Breakout retracement | ≥ 1.15 | `:212`, `:1539` |
| Retracement | ≥ `RETRACEMENT_MIN_CURRENT_RR` | `:1631` |
| DEFERRED_CONTINUATION | ≥ 1.0 | `:1756-1764` |
| HTF_TRANSITION / exceptional probe | only > 0 | `:1397`, `:1455` |
| **IMMEDIATE_VALIDATION** (137, 172, 182) | **none** | `:651-694` |
| **SETUP_TIMEFRAME_ATR** (143) | **none** | `:628-641` |
| **SETUP_CONFIRMATION_WAKEUP** (158), **ACCUMULATED_EVIDENCE** (162) | **none** | |

These four routes only call `applyInitialEntryQualityGuard` (`:1171-1211`). That guard checks the score alone (`CHASE_ENTRY_CUTOFF = 50`, `:229`).

The score starts at 100 (`:976`), and R:R below 1 subtracts only 30 (`:991`). So **an R:R below 1 with no other penalty scores 70, which is GOOD_ENTRY and allows 40%**. The inverted R:R from F1 (0.35–0.74 on five of six trades) can never block an entry by itself.

**AGENT INFERENCE:**
- This is a policy inconsistency rather than a coding error. The engine requires at least 1:1 to *chase a continuation* (`:1762`, "will not chase … with less than 1:1"), yet allows R:R of 0.35 on the primary direct route.
- Combined with F1 (the `AtrRiskService.java:34-45` stop is floored at 0.50% while the TP is a bare 3×ATR), this is the **main systemic mechanism behind the losses in five of six trades**.
- DBQ-CLAUDE-I4-001 and I4-003 test it.

### R2. Confluence turns bearish signals NEUTRAL but lets conflicting BUYs through (PROJECT EVIDENCE)

This closes U-I3-4 at code level. `AnalysisService.java:303-377` stores `originalDecision = baseDecision` and `decision = FinalDecisionService` output after `MultiTimeframeConfluenceService.evaluate`.

`MultiTimeframeConfluenceService.java`:

- **TREND_FOLLOWING, BUY against a higher-timeframe SELL:** `preserve(CONFLICT, BUY, entryAllowed=true)`, with only reduced confidence (`:124-127`). The BUY is vetoed only by STRONG_SELL or a low-trend SELL (`:120`, `:146-150`).
- **TREND_FOLLOWING, SELL against any bullish higher timeframe:** turned into **NEUTRAL** (`:132-138`).
- **BREAKOUT, SELL with no bearish higher timeframe:** NEUTRAL (`:209-211`).
- **DEFENSIVE, SELL with any bullish higher timeframe:** NEUTRAL (`:231-233`).

Effect on the route:
- **Entry:** 182 and 172 entered as `confluence_status=CONFLICT` BUYs (iteration-2 F7). That is allowed by design.
- **Exit:** `PositionExitPolicy` reads the 5m `decision` (I3 T3). A 5m bearish reading is suppressed whenever 1h is bullish, which delays confirmed exits (182: 5m rows 176655 and 176792 were STRONG_SELL turned NEUTRAL).

**AGENT INFERENCE:** the asymmetry is coded and consistent. It favours holding and entering long. On these six trades it cost at most about 1 tick (I3 T3), so it is not the loss driver. DBQ-CLAUDE-I4-002 confirms which branch neutralised 176655 and 176792.

### R3. One combined WebSocket session processes every symbol serially, including exit transactions (PROJECT EVIDENCE + AGENT INFERENCE)

**The route** (traced in code):
1. `BinanceWebSocketHandler.handleTextMessage` (`:42-67`)
2. `BinanceKlineService.processKline` (`:55-137`), which takes `observedAt` from Binance `E` (`:94`)
3. `KlineTransactionCoordinator.process` (`:36-92`), which runs in order:
   - INPUT transaction: candle upsert plus `recordPending`
   - PROTECTION transaction: `onPrice`, which may run `executeMechanicalExit`
   - OBSERVER transaction
   - CLOSE_DISPATCH transaction

All of these are synchronous on the session's callback thread. The manager connects a single URL (`BinanceWebSocketManager.java:255-261`).

**Inference:** a 1–3 s exit transaction (I3 T6, I3-005) delays the processing of every other symbol's message. It does not drop any. This explains the 1.7–1.9 s observe-to-persist outliers. It does **not** explain EGLD's 14 s silence, because other symbols kept persisting.

### R4. Classifying the EGLD silence (PROJECT EVIDENCE + AGENT INFERENCE)

An observation is discarded without a database row only if it is FUTURE (more than 2 s ahead) or STALE (more than 15 s old), at `MarketPriceEventService.java:40-58`. Equal-timestamp duplicates *are* persisted as NON_CANONICAL (`:66-72`), and I2-005 shows none.

In the 143 window, latency was 3–104 ms with no measurable offset. FUTURE and STALE are therefore implausible.

**Inference:** Binance most likely sent no EGLD 1m kline update during 19:43:05–19:43:19 and 19:43:27–19:43:35 UTC (22:43:05–22:43:35 KSA). The only way to prove this is the `[FIX-153][PRICE_NOT_CANONICAL]` log line, but no 2026-10-11 log exists (I3 T8). This stays **unproven**. Either way, trade 143 stays a valid gap loss.

### R5. Exit and re-entry route (PROJECT EVIDENCE, carried and confirmed)

- **Exit route:** `onPrice` → lock/TP/SL checks → `PositionExitPolicy.evaluateNormalExit` (exit lookup with no age bound, `:95-97`) → `executeMechanicalExit`, all in the one PROTECTION transaction.
- **Re-entry:** nothing on the entry route consults the last exit time. Grep for cooldown or re-entry found only replay/monitor code, which allowed the 22 s re-entry of 142 → 143.
- **Replay:** `ExecutionIntelligenceService`, `MultiTimeframeConfluenceService` and `AtrRiskService` are shared by Replay (`ExecutionIntelligenceService.java:1042` registry note; replay scope at `MultiTimeframeConfluenceService.java:105-108`). R1, R2 and R5 should therefore reproduce in Replay.
- **Replay's limit:** Replay can only reproduce exit *timing* if the APPLIED tick set is used, as FIX-052/`find()` does. That set is complete: all events in the six windows are APPLIED (I2-005).

### DB_REQUEST
QueryId: DBQ-CLAUDE-I4-003
Purpose: System-wide outcome by entry-signal R:R bucket across all closed paper positions (R1 systemic test, U-I4-3)
SQL:
SELECT CASE WHEN s.risk_reward_ratio IS NULL THEN 'NULL'
            WHEN s.risk_reward_ratio < 0.5 THEN 'a <0.5'
            WHEN s.risk_reward_ratio < 1.0 THEN 'b 0.5-1.0'
            WHEN s.risk_reward_ratio < 1.5 THEN 'c 1.0-1.5'
            ELSE 'd >=1.5' END AS rr_bucket,
       COUNT(*) AS n, SUM(p.realized_pnl > 0) AS wins, SUM(p.realized_pnl < 0) AS losses,
       ROUND(SUM(p.realized_pnl), 6) AS pnl_sum, ROUND(AVG(p.realized_pnl), 6) AS pnl_avg
FROM paper_position p
LEFT JOIN trade_signal s ON s.id = p.signal_id
WHERE p.status IN ('CLOSED','STOPPED') AND p.closed_at IS NOT NULL
GROUP BY rr_bucket
ORDER BY rr_bucket
LIMIT 10;
### END_DB_REQUEST
