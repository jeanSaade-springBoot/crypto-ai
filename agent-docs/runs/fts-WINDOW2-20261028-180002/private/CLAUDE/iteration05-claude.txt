## FINDINGS

### C1. Correction: R:R below 1 is not shown to be the systemic loss driver (PROJECT EVIDENCE)

In iteration 4 I called the inverted R:R "the main systemic mechanism behind the losses in five of six trades." I4-003 contradicts that:
- System-wide, entries with R:R below 1 had a 58% win rate and roughly flat P&L.
- The R:R ≥ 1.5 bucket carries almost all of the losses.

The frozen trades point the same way:
- None of the six hit its stop-loss.
- All six were closed early by an exit signal or a profit lock, so the inverted geometry never produced a full-stop loss.
- Realised wallet losses were small: −0.13% to −0.34% (I2-003: 454 −0.212%, 407 −0.345%, 346 −0.300%, 359 −0.149%, 429 −0.182%, 401 −0.128%).

**What remains true:**
- The geometry caps the upside. Target distances were only 0.17–0.37%.
- The R:R floor still differs by route (iteration-4 R1 table). That is now a **policy-consistency observation**, not a proven loss driver.

**AGENT INFERENCE:** the −4.13 in the ≥ 1.5 bucket has an average loss about 25× larger than the other buckets. It is probably dominated by a few large losses, possibly from an older sizing era. I5-003 tests this.

### E1. Three of six entries sat exactly on the score cutoff (PROJECT EVIDENCE)

How the guard works:
- It blocks only when `q.score() < CHASE_ENTRY_CUTOFF (50)` (`ExecutionIntelligenceService.java:1173`, `:229`).
- So a score of exactly 50 passes. A score of 50–54 is LATE_ENTRY (`:1021`), which only caps size at 25% (`:1183`).
- FIX-119 documents this deliberately: "the shared guard intentionally treats that range as a sizing warning rather than a timing block" (`fix-registry.js:48`).

LATE_ENTRY becomes a timing block in only two places:
- BALANCED_EARLY (FIX-041, `:672-684`).
- ACCUMULATED_EVIDENCE with no 1m BUY in the accumulated evidence and no fresh 5m BUY (FIX-119, `:1257-1280`).

How each of the three passed:
- **158** (SETUP_CONFIRMATION_WAKEUP): neither block applies to this route.
- **182** (IMMEDIATE_VALIDATION): it passed, so its validation code was not BALANCED_EARLY (inference; I5-001 will confirm).
- **162** (ACCUMULATED_EVIDENCE): it passed FIX-119. The 5m context was WATCH (I2-002 `confluence_higher_decision`), so the accumulated evidence must have contained at least one 1m BUY. This is inference, and assumes FIX-119 was deployed on 2026-10-12, which is unproven (U8). I5-002 tests it.

**AGENT INFERENCE:** all three behaved as designed. The design lets an entry scored 50 with R:R 0.35–0.48 open, sized at 15–25%.

### E2. Breaking down each stored score (PROJECT EVIDENCE for R:R; AGENT INFERENCE for the remainder)

The stored score is the **execution-time** score (`PaperTradingService.java:377-385` → `assessEntryQualityAtPrice`).

- **The R:R penalty was the largest single deduction on five of six trades.** Without it, 158, 162 and 182 would have scored 80 (GOOD).

- **158, 162 and 182:** −20 matches an ATR extension above 4 (`:984`). Because the 1m ATR was tiny (0.05–0.08%), about 0.2–0.3% of movement above the 30-minute reference already counts as "4 ATR." This is inference.

### E3. The score is purely geometric and has no momentum or overbought input (PROJECT EVIDENCE)

`assessEntryQuality` (`:865-1030`) uses only:
- expansion from the reference price
- ATR extension
- opportunity age
- R:R
- the rejection zone
- the HIGH_VOLATILITY regime
- the STOP_EXPOSED liquidity status
- a BREAKOUT bonus

RSI and Bollinger position are not inputs. That is why **143 entered at RSI 84.3** and 4.35 ATR above SMA20, on a 1m `WAIT_FOR_RETRACEMENT` plan with 0% recommended size (I2-002), and still scored **70 (GOOD)**. Trade 162 likewise entered at the upper Bollinger band at RSI 68.

**AGENT INFERENCE:** this is a design gap, not a coding defect. I raise it only as a recommendation.

### E4. Candidate defect: the execution-time rescore uses the 1m ATR on the 5m-setup route (PROJECT EVIDENCE)

- **Decision time:** on the SETUP_TIMEFRAME_ATR route, entry quality uses the **5m** ATR. The code comment at `:631-633` says this is deliberate: "Using the much smaller 1m ATR here can falsely label a valid 5m setup as a 9-10 ATR chase."
- **Execution time:** `revalidateAtExecutionPrice` (`:1167`) calls `assessEntryQualityAtPrice` (`:857-858`), which passes the signal's own `atrAtSignal`, which is the **1m** ATR. The score stored on the position (`PaperTradingService.java:377-378`) comes from the same call.

So the final guard contradicts the route's stated intent. A valid 5m setup could be blocked or downsized at fill time.

- **Effect on 143:** none. It still scored 70 and kept 25%.
- **Classification:** a code-level inconsistency with no outcome impact on these trades.
- **Replay:** `ShadowProductionReplayService.java:300,335` calls the same method, so Replay shares the behaviour.

### E5. Candidate ambiguity: an ATR plan of 0% is sized as 100% (PROJECT EVIDENCE)

`PaperTradingService.java:328-330` treats an ATR recommended size of 0 or less as "unset" and uses 100% instead.

Signal 159408 (trade 143) had `atr_recommended_position_percent = 0` (WAIT_FOR_RETRACEMENT). It was executed at the full route size of 25%.

This may be intended, since the 5m plan owns the ATR risk on this route. But 0 ("do not enter") and "no plan" are the same value here. **U-I5-3.**

### E6. Allocation explained (PROJECT EVIDENCE)

- **162 and 182:** the ATR plan was REDUCED_POSITION at 60% (I2-002). The score-50 cap is 25%. Since 60% × 25% = 15% (`PaperTradingService.java:331-333,358-360`), the 15% allocation matches.
- **The others:** STANDARD_ENTRY at 100% × 25% = 25%. 143 is 0 treated as 100 (E5), × 25% = 25%.

Purpose: Decompose the R:R>=1.5 loss concentration from I4-003 by month and close reason (C1, U-I5-4)
SQL:
SELECT DATE_FORMAT(p.closed_at, '%Y-%m') AS ym,
       CASE WHEN s.risk_reward_ratio IS NULL THEN 'NULL'
            WHEN s.risk_reward_ratio < 1.0 THEN 'a <1.0'
            WHEN s.risk_reward_ratio < 1.5 THEN 'b 1.0-1.5'
            ELSE 'c >=1.5' END AS rr_bucket,
       p.close_reason, COUNT(*) AS n, SUM(p.realized_pnl > 0) AS wins,

FROM paper_position p
LEFT JOIN trade_signal s ON s.id = p.signal_id
WHERE p.status IN ('CLOSED','STOPPED') AND p.closed_at IS NOT NULL
GROUP BY ym, rr_bucket, p.close_reason
ORDER BY ym, rr_bucket, pnl_sum
LIMIT 120;
