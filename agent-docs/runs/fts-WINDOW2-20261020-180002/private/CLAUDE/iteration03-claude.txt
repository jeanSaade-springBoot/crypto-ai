- In OFF mode the only caller of `LivePositionProtectionService.onPrice` is `BinanceKlineService.java:108`, once per 1m kline push.

- So a signal that completes an exit condition takes effect only at the first price event processed after that signal is **committed**.

**Event cadence (EXTERNAL RESEARCH):**
- Binance documents a 2000 ms update speed for non-1s kline streams.
- The stored EGLD events show 2 s spacing with gaps of 6 s (19:40:01→:07), 12 s (19:41:39→:51), 14 s (19:43:05→:19) and 8 s (19:43:27→:35).
- During the 433-trade minute, an 8 s gap is not explained by the documented cadence.

**Can a processing stall create these gaps? (PROJECT EVIDENCE plus AGENT INFERENCE)**
- A stall delays rows rather than removing them, because `observed_at` is E (`BinanceKlineService.java:94`).
- A missing E slot can therefore only mean one of:
  - Binance did not push;
  - the input transaction failed (no row, `[FIX-153][KLINE_PHASE_FAILED_OR_UNCONFIRMED]`);
  - a STALE (>15 s) or FUTURE rejection (no row, `[FIX-153][PRICE_NOT_CANONICAL]`; `MarketPriceEventService.java:53-57`).
- DBQ-CLAUDE-I3-002 separates these by checking whether every symbol lost the same seconds.

### F13. Exit and entry transactions spend 1–3 s on portfolio valuation on the ingestion thread (PROJECT EVIDENCE for code; magnitude is AGENT INFERENCE)

**Code chain:**
- The WebSocket handler calls `processKline` synchronously per message (`BinanceWebSocketHandler.java:62`). There is one primary session, and Spring delivers one session's messages serially.
- The protection transaction runs inside that call (`KlineTransactionCoordinator.java:57`).
- After the wallet SELL row is saved (`executedAt=Instant.now()`, `:548`), the same transaction does the following:
  - re-locks daily statistics FOR UPDATE (`:553`);
  - calls `walletService.currentPortfolioValue()`;
  - calls `captureSnapshot()`;
  - each of those runs one candle query **per `wallet_asset` row** (`WalletService.java:484-490, 592-607`), plus realized/invested aggregates.
- `closePaper` follows (`LivePositionProtectionService.java:391-411`).

**Measured gaps:**

| Trade | Wallet SELL → `paper_position.closed_at` |
|---|---|
| 137 | 3.19 s |
| 158 | 2.42 s |
| 172 | 1.99 s |
| 182 | 1.98 s |
| 143 | 1.18 s |

On the entry side, wallet BUY → paper open took 1.49–2.24 s (I1-002, I1-003).

**Implication:**
- While these seconds run, kline processing for **all symbols** waits behind them, and the transaction holds the global daily-statistics lock.
- Other open positions' protection is delayed by that much. The rows are delayed, not lost.
- No frozen trade's P&L was affected, so this is a latency or cross-symbol risk, not a cause of these losses.
- `fix129_stage_timing` records any stage ≥1000 ms (`KlineTiming.java:46`), so DBQ-CLAUDE-I3-004 can measure it directly.

### F17. Possible Replay–Production timing difference (AGENT INFERENCE from code)

- **Replay:** processes live prices with `observedAt <= signal.generatedAt` before applying the signal (`ShadowProductionReplayService.java:129`). A signal is visible from its **generation** time.
- **Production:** sees a signal only once it is **committed**, 1.3–2.3 s later.
- **Example, 158:** the event at 00:30:02.320 UTC falls between the 5m generation (01.464) and its commit (02.811).
  - Replay would exit on that event.
  - Production exited on the 04.319 event.
  - The price is identical (1.4090), so P&L matches, but the exit timestamp would differ by about 2 s.
- **Same mechanism as F1:** it also affects which 5m signal Replay treats as visible.
- **Not verified:** no Replay run was performed, because that would create Replay state.
