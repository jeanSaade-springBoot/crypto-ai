## FINDINGS

### F0. Timestamp display contradiction: affects every timeline (PROJECT EVIDENCE)

How the stored values are written and how our session displays them:
- **App writes UTC.** The app's DB session runs with `SET time_zone='+00:00'`, `connectionTimeZone: UTC` and `forceConnectionTimeZoneToSession` (`src/main/resources/application.yml:13-35`). So the instants stored in `TIMESTAMP` columns are correct UTC.
- **The investigator session is KSA.** `ai_investigator` runs with `session_tz=SYSTEM` and `system_tz=Arab Standard Time`, offset +180 min (W1-I1-001). MySQL converts `TIMESTAMP` columns to the reader's session zone, so query output shows **KSA wall time**, not raw UTC.
- **Proof.** For trade 137, `wallet_trade.execution_price_observed_at` displays as `2026-10-11 20:55:00.032`. The app's own `execution_message` says `priceObservedAt=2026-10-11T17:55:00.032Z` (W1-I4-002). `UNIX_TIMESTAMP(opened_at)` = 1791741304, which is 17:55:04 UTC.

**Consequences:**
- For `TIMESTAMP` columns, UTC = displayed value − 3h. `DATETIME` columns (for example `trade_signal.btc_context_evaluated_at`) are not converted. DBQ-CLAUDE-I1-001 confirms which columns are which.
- This contradicts the study instruction "DB timestamps are UTC" if that instruction is applied to displayed query output. Labelling displayed values as UTC would shift every timeline by 3h. Both agents and the Coordinator need to know this.
- All UTC times below are displayed value − 3h. Where an app message gives a `Z` timestamp, it matches.

### Cross-cutting candidates (to be tested in later iterations)

**C1: Structural risk/reward below 1 (PROJECT EVIDENCE plus AGENT INFERENCE)**
- In `AtrRiskService.assess` (`src/main/java/com/crypto/service/AtrRiskService.java:34-45`):
  - stop distance = max(2×ATR, 0.50%×price), capped at 8% (`application.yml:137-144`);
  - target distance = 3×ATR, with no floor.
- So R:R falls below 1 whenever ATR is under about 0.167% of price.
- Five of the six trades had R:R between 0.35 and 0.74, and their SL sits at exactly 0.995 × decision price. I checked the arithmetic for 182: TP − entry = 3 × 0.000151214 exactly.
- A grep found `riskRewardRatio` used only for display and persistence, not as an entry gate. Unconfirmed; I need to trace the execution path.

**C2: Fees not accounted for (EXTERNAL knowledge, not verified this session)**
- Automatic trades record `fee_usdt=0` (W1-I1-003). Binance spot fees are typically around 0.1% per side, so about 0.2% per round trip.
- The TP distances on 158, 162, 182 and 137 (0.17–0.32%) would earn close to zero, or less, after fees. Every gross loss above would be larger net.

**C3: All exits were small losses, none at SL**
- Four were higher-timeframe SELL confirmations (137, 158, 172, 182), one was a signal STRONG_SELL (162), and one was a protection hard-floor exit after a price gap (143).
- Each loss was 0.13–0.34% of price, against a 0.5% stop.

**C4: Weak or soft upstream context was allowed through**

- In 182 the 5m was originally STRONG_SELL before its downgrade. The legacy `5M_BEARISH_VETO` appears to read the downgraded decision, not the original. Needs a code trace.
