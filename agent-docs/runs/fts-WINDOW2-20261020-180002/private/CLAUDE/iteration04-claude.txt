### F22. Replay would very likely not reproduce 143, and possibly not 158 either (PROJECT EVIDENCE for code; outcome is AGENT INFERENCE, not executed)

**How Replay orders signals:**
- Replay sets each signal's `generatedAt` to **the candle close time** (`RegressionTestWorker.java:584`).
- At equal close times it processes **1h, then 5m, then 1m** (`:557-560`, `intervalOrder` `:787-793`).
- `ExecutionReplayScope.recent` (`:106-116`) includes signals with `generatedAt <= ref`.

**143 in Replay:**
- The 1m (19:39 candle) and 5m (19:35 candle) both close at 19:40:00. The 5m WATCH (immediate entry=0, 60%) would be visible to the 1m.
- `setupTimeframeAtrAuthoritySignal` would return null (`EIS:1486`, 5m not bullish).
- The 1m then reaches `ATR_ENTRY_BLOCKED` (`:644-649`). Result: **no entry**.

**158 in Replay:**
- The 5m BUY is processed before the 23:34 1m signal exists. The wakeup's 1m lookup would find the 23:33 signal, 60 s old, which exceeds the 45 s limit (`EIS:71, 420-428`). So the wakeup returns none.
- The later 1m WATCH then goes through `evaluateBuy`, and its route is not determined from code alone.

**Why this matters:**
- Production ordering at a shared candle boundary is a race between asynchronous analyses: 2 ms for 143, 21 ms for 158. Replay ordering is deterministic and puts higher timeframes first.
- This makes iteration-2 F1 a **Production↔Replay parity defect** as well as an entry-input defect.
- **Verification needed:** an approved Replay run over 2026-10-11 19:35–19:45 UTC (EGLD) and 23:30–23:40 UTC (XRP). Out of scope for analysis-only.
