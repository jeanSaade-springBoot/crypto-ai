### 2. Missing, partial or diverged

**a. Candle-close selection bound: missing.**
- Every FIX-154 lookup filters only on `generatedAt ≤ reference` (TEVS:367-379; OCS:214-220; ExecutionReplayScope.java:106-120) (PE).
- The existing lookups that also bound by candle close are not used (TradeSignalRepository.java:37; ExecutionReplayScope.java:122-137) (PE).
- The new test at TradeExecutionValidationServiceTest:215-239 only excludes a signal whose `generatedAt` is in the future (PE).
- Current exposure is low, because every analyzer sets `generatedAt` at or after candle close (AnalysisService:150, 173; CandleClosedAnalysisWorker:163; ScheduledAnalysisService:203-204) (INF).

**b. Freshness evidence is inconsistent.**
- Decisions measure age from `generatedAt`.
- The audit measures age from a derived candle close (open time + interval − 1 ms) (BAS:85-86, 105-109) (PE).

**c. 5m data quality is never read.** Quality is only checked on the 1h signal (HTF:27, 36, 41, 46-48) (PE). Consequences:
- `hard_confirmation_present` is set to true even when the bearish 5m has false or NULL quality. This contradicts design:105 and design:113-115 (PE).
- HARD 1h + non-bearish 5m with invalid quality is vetoed (fail-closed). The design does not cover this case (INF).
- SOFT 1h + non-bearish 5m with invalid quality is allowed with the 25% cap. The design says such a 5m "cannot act as … a soft-conflict release" (design:115), and AGENTS.md:221-222 requires a quality-valid 5m (PE). The code took the permissive reading (INF).

**d. Audit columns.**
- The audit has no profile-context column (PE).
- The usability reason merges false and NULL into one value, `QUALITY_UNKNOWN` (BAS:82-89) (PE).
- `signal_mode` is correctly absent, as the Round-5 addendum requires (PE).

**e. `replay_mode` is always false and Replay writes no audit.**
- The insert hard-codes `FALSE` (BAS:66), and Replay is skipped before any write (BAS:41-44) (PE).
- The design requires the mode to be recorded and equivalent evidence in both modes (design:166-167, 214-215).
- Rejections from `validateBuy` and consolidation are never saved to opportunity records (EIS:653-731) (PE). FIX-154 rejection reasons therefore exist only in the best-effort Production audit (INF).

**f. Health metrics.**
- Counters are not grouped by execution path, which design:180-182 requires (PE).
- The consolidation path increments neither the untrusted-block counter nor the soft-cap counter (OCS:64-68, 139) (PE).
- The consolidation audit swallows failures silently, with no counter or log (OCS:168-170) (PE).
- Counters have no Replay guard (TEVS:416, 429, 448-450) (PE). Replay runs in the same process on a per-thread scope (ExecutionReplayScope:31), so Replay runs will inflate the Production counters (INF).

**g. Configuration.**
- The 70 threshold is a code constant (HTF:13) and is stored on each audit row (BAS:71). That meets "named and persisted" but cannot be changed by configuration (PE).
- The only property is `fix154.audit.queue-capacity`, default 500, and it is not declared in YAML (PE).
- There is no on/off switch (PE). A startup schema check (Fix154RuntimeSchemaChecks.java:15-25), Hibernate schema validation (application.yml:30) and automatic Flyway (application.yml:36-39) together mean that deploying the build applies V107 and turns FIX-154 on. The design's "before enabling FIX-154" (design:225-226) has nothing to act on (INF).

**h. Audit path names differ from the design.**
- The design lists `DIRECT_BUY`, `BUY_CONTEXT`, `CONSOLIDATION`, `PROGRESSIVE_TREND_ADD`, `CONFIRMATION_ADD` and `ACCUMULATED_EVIDENCE_ADD` (design:161-163).
- The code writes `DIRECT_BUY` (TEVS:96, 111), `ACCUMULATED_EVIDENCE` (TEVS:124), `SETUP_WAKEUP` (EIS:435), `CONSOLIDATION` (OCS:167) and `PROGRESSIVE_ADD` (TEVS:430) (PE).
- Four of the design's names are never written, and the add stage is not distinguished.

**i. Defect: the progressive audit-only hook can throw into the trading decision.**
- Its lookups and assessment (TEVS:423-427) are not wrapped in try/catch (PE).
- It is called from EIS:1083, inside the transactional `evaluateBuy` (EIS:459-464) (PE).
- A repository exception there would therefore reach the BUY decision, which design:269-271 forbids (INF).

**j. Consolidation reject code.**
- A missing 5m returns `MISSING_5M_CONTEXT` (OCS:59), not `MISSING_5M_CONFIRMATION` as in design:65, 98 and 203-204 (PE).
- `MISSING_1H_CONTEXT` matches (OCS:62) (PE).
- Whether the 5m code predates FIX-154 is unknown.

**k. Tests (PE).**
- Present:
  - 9 assessment tests (HigherTimeframeBuyAssessmentServiceTest:12-81).
  - SOFT cap and NULL-quality bearish tests (TradeExecutionValidationServiceTest:115-194; OpportunityConsolidationServiceTest:55-70).
  - Audit-failure isolation (TradeExecutionValidationServiceTest:197-212).
  - Replay audit suppression (BuyHtfAssessmentAuditStoreTest:16-32).
  - Production/Replay decision parity for one SOFT case (TradeExecutionValidationServiceTest:215-239).
  - A text check that V107 contains certain strings (Fix154MigrationContractTest:13-17).
- Missing:
  - Full decision-matrix coverage. The test helper takes a primitive boolean, so NULL quality cannot be expressed (HigherTimeframeBuyAssessmentServiceTest:83-85).
  - 5m with false or NULL quality combined with a HARD or SOFT 1h.
  - Stale and missing inputs combined with each band.
  - The database flush/clear test proving the stored decision is unchanged (design:259-261).
  - Candle-close look-ahead.
  - Audit evidence parity between Production and Replay.
  - `SOFT_HTF_ADD_BLOCKED`.
  - The successful audit-insert path.
  - BNB #150b end-to-end reaching `REJECTED_RISK_REWARD`. Line 80 of the assessment test is only a comment.
  - Any test that actually runs V107. FIX-154 assertions briefly appeared in `LocalCandleMySqlIT.java` and were then removed; the file now checks only V106 (lines 95-102).

**l. V107 does more than the design registers.**
- It also adds five columns to `trade_signal_test`, including FIX-153's `signal_mode` (V107:9-14) (PE).
- The startup check requires that column (Fix154RuntimeSchemaChecks.java:18) (PE).
- This repairs the Replay writer, which copies every TradeSignal column by reflection (RegressionTestWorker.java:741-771) (PE).

**m. New defect: Replay run archiving fails after V107.**
- `trade_signal_test` and `trade_signal_test_archive` were always kept column-for-column in step (V69:19-25; V70:7-11; V72:17, 29). V107 widens only `trade_signal_test` (PE).
- `archiveRun` (RegressionTestService.java:245-246, transactional) copies rows with `INSERT INTO trade_signal_test_archive SELECT ?, r.* …` and no column list (line 268) (PE).
- MySQL requires such an insert to supply every column of the target table (EXT).
- After V107 the select returns five extra columns, so archiving will fail and roll back. I'm confident of this but did not execute it (INF).

### 3. Is `btcContextEntryAllowed` used as an HTF gate?
No, not in FIX-154 (PE).

Older routes outside FIX-154 still check this flag on a non-current signal: the 5m trigger at EIS:357 and EIS:1427, and the breakout-origin 1m at EIS:1602. None of these reads a 1h signal's flag (PE). I could not confirm whether they predate FIX-154.

### 4. Is `trade_signal.data_quality_valid` persisted correctly?
Yes (PE).
- The column is a nullable Boolean (TradeSignal:73-74; V107:3-4).
- It is written from `marketContext.dataValid()` in the single signal builder (AnalysisService:424). Every analysis path goes through that builder: live (148-153), recovered (167-175), recovery-executable (118-125) and regression (183-190).
- `dataValid` is a primitive boolean (MarketContextSnapshot:22), so new rows are never NULL.
- Nothing backfills the column.
- NULL is treated as untrusted (HTF:48).

Caveat on what "quality-valid" means:
- `dataValid` only checks that price > 0 and that EMA20, EMA50 and EMA200 are present (MarketContextService:74-75) (PE).
- When it is false, the final decision is neutralized (FinalDecisionService:54-62, 296-298) (PE).
- So after deployment, bearish rows with quality = false should be rare. The trust check will mostly separate pre-V107 (NULL) rows from new ones, rather than judge data quality (INF).

### 7. Raw-1h checks the design leaves untouched (PE + INF)
FIX-154 replaced only three methods. Other raw-1h checks remain, so the stated goal ("a bearish 1h blocks a BUY only if fresh, quality-valid and strong") is not achieved end to end.
- **Signal generation.** For a 1m signal, multi-timeframe confluence reads both 5m and 1h (MultiTimeframeConfluenceService.java:297). In trend-following strategies it turns a 1m BUY into WATCH, with entry blocked, whenever any fresh higher-timeframe signal is STRONG_SELL (at any confidence or quality) or a SELL with trend score ≤ 6 (lines 120-123, 146-151; consumed at FinalDecisionService:122-126). A SOFT STRONG_SELL below 70 therefore never reaches `validateBuy` on that path.
- **Accumulated evidence.** It rejects any raw bearish 1h or 5m as `HIGHER_TIMEFRAME_BEARISH` (EIS:1982-1985) before it calls `validateBuyContext` (EIS:2039). The SOFT relaxation and the FIX-154 audit can never be reached there.
- **Retracement routes.** They can still enter at reduced size with an old, non-worsening bearish 1h (EIS:1550-1564, 1643-1662), which bypasses the HARD trusted veto.
- **FIX-014 wake-up.** It still requires a raw 1h of WATCH or bullish (EIS:332-339).

## OBJECTIONS
1. **Process.** The tree was edited during a read-only round, and FIX-154 code exists without the specification and dual-agent approval that AGENTS.md requires. I don't know who is making the edits (PE).
2. **Defect.** Replay archiving will fail after V107 (2m) (PE + EXT + INF).
3. **Defect.** The progressive audit-only hook can throw into the trading decision (2i) (PE + INF).
4. **Trading-impacting ambiguity.** The design never settles how 5m data quality should affect the decision (2c). The code's SOFT path is more permissive than the design text and AGENTS.md (PE + INF).
5. **Design non-compliance (PE):**
   - no candle-close bound (2a);
   - no Replay audit, and `replay_mode` is always false (2e);
   - metrics are not grouped by path, are incomplete, and are inflated by Replay (2f);
   - audit path names differ (2h);
   - no profile-context column (2d);
   - consolidation uses a different missing-5m code (2j).
6. **Docs disagree** with the code and with each other (section 5) (PE).
7. **Scope.** Untouched raw-1h checks make the business goal unachievable as designed, and retracement routes can enter despite a HARD trusted bearish 1h (section 7). This is a gap in the design's scope rather than a code-vs-design mismatch (PE + INF).
8. **Statistics.** The 70 split rests on a 30-day row count ("203 rows ≥70, 192 below", CHANGELOG:192-193), not on outcomes (PE).
   - There is no out-of-sample or Replay profit evidence, after fees and slippage, for the extra 25% SOFT entries.
   - The quality check is weak (section 4), so after deployment "trusted" mostly means "generated after V107".
   - The false-positive rate is unknown (INF).
9. **Release coupling.** FIX-154 cannot ship on its own from this tree (PE + INF):
   - V107 adds the FIX-153 column `signal_mode` to `trade_signal_test`.
   - V108 is required.
   - Hibernate schema validation requires V106's `signal_mode`.
   - Uncommitted FIX-153 code sits in the same tree.
   
   This conflicts with AGENTS.md:204-205 ("do not merge it into the local-candle change").
