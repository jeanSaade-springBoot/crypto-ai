# FINDINGS

Both verdicts stay **REJECTED**, but both reviews got some things wrong. I made no changes to source, config, the database, git or anything at runtime. No tool to write the plan file was available, so this response is the whole output.

**Corrections to my earlier findings:**
1. **I overstated OBSERVE mode.** It doesn't run collector execution alongside direct ingestion. In OBSERVE, the shared consumer reads the collector feed and inserts delivery rows. It then marks each one `OBSERVED` and returns before any protection or analysis runs. The analysis dispatcher only works in LIVE. So OBSERVE still connects to `crypto_ai_v2` and writes `shared_market_*` tables, which breaks the OFF-mode isolation. But it does not break the rule against running "direct ingestion and the shared-market executors together".
2. **I overstated the detector gap.** When the detector gives up within its lookback window, it does write a durable `ANALYSIS_EXPIRED` outcome. The real gap is narrower: after a crash or an outage longer than the lookback (180–600 s), its in-memory retry state is gone. Older closed-but-unanalysed candles are then never revisited and never get an outcome.
3. **The backfill race is now confirmed, not unknown.** Coin activation reloads the WebSocket first and then runs the backfill, so the two overlap. The manual `POST /api/market-data/import` endpoint can run the same backfill against a live symbol at any time.

**Corrections to Codex:**
1. **Codex finding 6 / main objection is wrong.** As above, OBSERVE does not execute anything from the collector feed.
2. **Codex finding 10 is low severity.** The empty lock path is deliberate: the deploy script always passes `--local-candle.instance-lock-path`.
3. **Codex finding 11 leaves out B105.** B105 is the in-source attempt to remove the V103 blocker. The blocker is still unproven (never run on MySQL), but it isn't unaddressed.
4. **Codex missed the duplicate top-level `local-candle:` key** in `application.yml`, even though it cited line 454, which sits inside the second block.
5. **Codex finding 4 is incomplete.** It's true that recovery uses update-only and insert-only paths. But the bootstrap/import backfill still uses insert-or-update, and that can close an open live row (see objection 2).
6. **Codex missed that there is no Binance REST rate-limit or ban handling anywhere.**

**What both reviews got right:**
- In OFF, the trader owns the WebSocket and the startup backfill, and writes only `crypto_ai.candle`.
- Closes are dispatched by a token, and updates never reopen a closed row.
- The transaction order is input → protection → observer → close dispatch, and analysis runs on a separate executor.
- In LIVE, the trader depends on the collector.
- Automatic recovery is switched off by default.
- V103 needs the collector's table when it runs.

# OBJECTIONS

1. **Duplicate top-level `local-candle:` key.** This probably stops the application from starting; at best one block silently replaces the other. No test catches it.
2. **The backfill can close an open live row with no token** (manual import endpoint, or coin activation after the WebSocket reload). That candle then gets no analysis and no terminal outcome. This breaks AGENTS.md's rules that each candle gets one durable outcome and that updates only move forward. Two code comments misdescribe this behaviour.
3. **Automatic recovery is switched off.** That conflicts with "Candle recovery is automatic… no manual repair step". The 2026-10-09 failure (a reconnect at a candle close leaves a row open, which blocks that lane) is still possible in every deployed configuration.
4. **No shared Binance REST rate-limit or ban handling,** which AGENTS.md requires.
5. **The detector's state is lost on a crash.** After an outage longer than its lookback, candles are left with no outcome.
6. **OBSERVE still couples the trader to the collector** (connection pool, reads, writes to shared tables). It's a legacy mode, not the target, but nothing stops someone selecting it alongside direct ingestion.
7. **Trader-only bootstrap is unproven.** B105 has never run on MySQL, and it's unknown whether this Flyway edition applies `B` migrations.
8. **Smaller points:**
   - `activation-approved` defaults to `true` in the yml.
   - The startup schema check requires V106 but not V107 (my earlier finding; not re-checked).
   - The Replay concerns from my earlier findings still stand; I didn't re-verify them.
