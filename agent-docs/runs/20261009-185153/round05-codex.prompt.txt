## FINDINGS

- The checked-in default is `shared-market.mode=OFF`. In OFF, the trader itself owns Binance kline WebSocket ingestion, REST bootstrap/import, local persistence, runtime close dispatch, and optional reconciliation. Candles are written to the local `crypto_ai.candle` table.

- `LIVE` is the retained collector architecture: direct WebSocket, bootstrap, and import are disabled; the trader reads collector tables from `crypto_ai_v2` and consumes them through local delivery tables.

- `OBSERVE` is architecturally contradictory to the pending direction. Direct trader ingestion remains enabled because only `LIVE` disables it, while `SharedMarketConsumer` also schedules collector discovery, price, and analysis loops. It does not execute collector-driven protection/analysis—it marks deliveries `OBSERVED`—but it still connects to and reads collector infrastructure alongside direct ingestion. This contradicts the stated “do not run direct ingestion and shared-market executors together” rule.

- Runtime close handling is structurally sound only for the WebSocket path: `upsertRuntime` writes a close-transition token only when an open row becomes closed; only the receipt owning that token publishes the close event. The event is after commit and analysis is submitted to an executor rather than run on the Binance thread.

- The ordinary REST import path is materially unsafe versus the pending design. `MarketDataService.importCandles()` sends already-final Binance candles to `CandleRepository.upsert()`, whose `BACKFILL` duplicate-key clause can update an existing `closed=0` runtime row to closed, without a token, outcome, or dispatch. This can happen in the reachable overlap where dynamic activation reloads WebSockets before bootstrap, and through the manual import API.

- That unsafe ordinary backfill can leave a closed candle permanently unanalysed: a later WebSocket close cannot own a token; the local detector selects only token-bearing non-`BACKFILL` rows; reconciliation selects only `closed=0` rows. No terminal `candle_analysis_outcome` is written by that path. The repository comment claiming backfill “inserts missing identities only” is false for the implemented `upsert()` method.

- A separate reconciliation implementation does meet several pending-design mechanics: it is OFF-only; exact recovery only finalizes open non-backfill rows; gap repair is insert-if-absent; both avoid tokens and record historical-only outcomes. However, it is disabled in checked-in config, so automatic reconnect recovery is not part of the checked-in operational behavior.

- Reconciliation also does not meet the durable-age-out requirement. `PENDING` audit rows are due indefinitely with a maximum retry delay but no attempt or time ceiling. Once candidates age out of the active quality window, they are no longer selected and can remain `PENDING` without a terminal analysis outcome. The open-candidate query applies `LIMIT 50` before due/loss-evidence filtering, allowing ineligible old rows to crowd out eligible work.

- No reviewed implementation establishes shared Binance REST handling for 429/418, `Retry-After`, rate budgets, or bans across bootstrap, reconciliation, and exchange-clock callers. The REST client creates separate clients and timeouts, but no visible shared rate-limit policy.

- Fresh Replay loads every closed candle solely by closed/time predicates and then generates fresh signals for every candle in its timeline. It does not filter `ingestion_source`, close token, reconciliation audit, or local analysis outcome. Therefore source review does not prove parity with production’s deliberate exclusion of recovered/backfilled/token-less candles from live close dispatch.

- The target direction remains not deployment-ready. The source has substantial local-candle implementation, but the checked-in mode is not evidence of a production deployment. No production systems were accessed.
