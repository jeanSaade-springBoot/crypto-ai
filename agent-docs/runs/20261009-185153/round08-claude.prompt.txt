## FINDINGS

1. The checked-in default is `shared-market.mode=OFF`, so the trader—not the collector—owns Binance WebSocket kline ingestion and ordinary REST bootstrap/import in that configured mode. Candles are written to local `crypto_ai.candle`.

2. In `LIVE`, the trader rejects direct WebSocket and REST ingestion, reads candles through a read-only connection configured for the collector schema, and rejects local candle writes. The collector therefore owns live candle supply in this legacy mode.

3. `OBSERVE` is materially contradictory to the pending direction: direct trader WebSocket and REST ingestion remain enabled, while `SharedMarketSource` opens the collector connection and `SharedMarketConsumer` polls collector stream/cursor tables. This is simultaneous direct and shared-market operation.

4. Runtime close handling has the intended basic structure: the runtime upsert sets a close-transition token only on an atomic open→closed transition; the successful receipt publishes after input → protection → observer → close-dispatch; committed events enter an asynchronous dispatcher.

5. Ordinary REST import is not the pending recovery design. Its `BACKFILL` duplicate-key clause can finalize an existing open candle, preserves its existing `RUNTIME` provenance and token state, creates no token, and produces neither reconciliation audit nor candle-analysis outcome. An interrupted runtime row can therefore be closed by bootstrap before reconciliation sees it, because reconciliation selects only `closed=0` rows.

6. A specialized reconciliation implementation slice exists, but is disabled by default and is OFF-only. It correctly uses update-only repair for an open existing row and insert-if-absent for an absent gap; recovered work receives a historical-only outcome and is not dispatched for trading. It is not proof of a release-ready recovery path.

7. The supplied claim that the detector has no terminal outcome after a “longer outage” is overstated. While running, it records durable `ANALYSIS_EXPIRED` after retry expiry. The real concern is that retry/admission state is in memory and the SQL lookback is short: a process stopped long enough for a tokened candle to fall outside the query window can leave no detector-created outcome.

8. Reconciliation has unresolved control flaws: candidate SQL limits to 50 before audit-due and loss-evidence filtering; transient `PENDING` candidates can age outside the active window without a demonstrated terminal age-out route; and the REST client contains timeouts but no shared 429/418, `Retry-After`, ban, or global request-budget policy across bootstrap, reconciliation, and clock sync.

9. Replay reads generally closed candles by time/identity, not by ingestion provenance, close token, reconciliation outcome, or historical-only classification. It does enforce an important but narrower price-event condition. Local-candle admission parity is therefore unproven.

10. Fresh trader-only bootstrap remains blocked: migration `V103` explicitly checks and alters `crypto_ai_v2.market_data_stream_event`. This is startup-time coupling rather than OFF runtime access, but it contradicts an independently installable trader database.

11. Documentation conflicts:

   - `codex-docs` correctly identifies ordinary backfill finalization and a disabled reconciliation slice, but presents parts of the implemented reconciliation as “pending” design.

12. Production behavior is unknown. This investigation did not access production, runtime logs, database state, deployed artifact, or environment overrides. Checked-in defaults do not prove the actual production mode or that the source has run.
