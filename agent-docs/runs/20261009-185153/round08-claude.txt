# Round 5: candle ingestion, as implemented vs. the pending local-candle direction

The verdict stays **REJECTED**. This round I re-read the backfill SQL, the reconciliation service, the closed-candle detector, the bootstrap order and the coin-activation path. That found one new defect: adding a coin can silently lose a live candle close. It also tightened two of the earlier objections and corrected one statement of my own.

## FINDINGS

### Ownership (questions 1–5, 9, 11): unchanged from earlier rounds
- **In OFF mode (the checked-in default):**
  - The trader owns both WebSocket and REST kline ingestion.
  - It writes to local `crypto_ai.candle`.
- **In LIVE mode:** the collector supplies candles and the trader reads them read-only.
- **In OBSERVE mode:** both paths run at once. Direct WebSocket and REST ingestion only reject LIVE (`BinanceWebSocketManager.java:28,97`; `MarketDataService.java:19,32`).
- **Production:** I have no evidence about production. I did not access it.

### New 1: adding a coin can lose a live candle close (OFF mode, not covered by any test)
`DynamicCoinActivationService.java:21` calls `webSocketManager.reload()`. That call is synchronous: it waits up to 30 seconds for the new session (`BinanceWebSocketManager.java:126-130`). Only after that does `bootstrapSymbol` run (`DynamicCoinActivationService.java:28`). So the WebSocket is already streaming the new symbol while the REST import runs. The race:

1. The WebSocket writes candle N as an open `RUNTIME` row.
2. N closes. `importCandles` reads the Binance server time after the close but before the WebSocket's final closed-kline message has been processed (`MarketDataService.java:37,45`).
3. The backfill upsert closes the row (`CandleRepository.java:173-188`). It sets no token and leaves provenance as `RUNTIME`.
4. The WebSocket's final message arrives. The token is only set when the row goes from open to closed (`IF(closed=0 AND VALUES(closed)=1 …)`, `:201`), and the row is already closed. The read-back token check therefore fails (`:120`), so nothing is dispatched.
5. Nothing else ever picks the candle up:
   - the detector only looks at rows that have a token (`LocalClosedCandleDetector.java:50`);
   - reconciliation only looks at `closed=0` rows (`LocalCandleReconciliationService.java:131`);
   - OFF-mode bootstrap does no analysis (`MarketDataBootstrapService.java:107-110`).

**Result:** a fresh candle close that could have led to a trade gets no analysis and no recorded outcome. That breaks the AGENTS.md rule that each candle path writes one durable outcome.

The window is short: the gap between a candle's close and the WebSocket delivering it. So this probably happens rarely, but when it does it is silent.

**Correction to my round-4 framing:** at startup this race cannot happen. The WebSocket starts on `ApplicationReadyEvent` (`BinanceWebSocketManager.java:95`), which fires after all `ApplicationRunner`s finish, including the bootstrap. The race only exists when a coin is activated at runtime.

### New 2: every coin change reconnects every stream, with no automatic repair
`reload()` replaces the WebSocket session for all symbols. AGENTS.md warns that Binance may not resend the final closed kline after a reconnect at a candle boundary. Reconciliation is the only repair path, and it is off by default (`:44,93`).

So after an admin coin change, a lost final kline leaves the row open with no outcome indefinitely. The only thing that closes it is the next restart's bootstrap, and that writes no audit row or outcome either. This breaks the AGENTS.md rule that recovery must be automatic.

### Sharpened: the `LIMIT 50` problem is worse than Codex or I said
- The open-row query (`LocalCandleReconciliationService.java:129-133`) filters by interval only. It has no symbol filter and no enabled-coin filter.
- So the 50 slots per interval are shared across every symbol, including disabled ones.
- The due-date and loss-evidence filters run only after the limit (`:139-140`).
- One kind of loss evidence, `lastReconnectAdmission`, is in-memory and global (`:40,61,206`). After a restart it is null until the next reconnect.

### Confirmed (Codex's point 7): detector outcome after a long outage
- The detector's retry state is in memory (`LocalClosedCandleDetector.java:28-29`).
- Its lookback is at least 180 seconds (`:47-49`).
- The `ANALYSIS_EXPIRED` outcome is written only when the detector is running and finds the candle (`:99-104`, `:140-141`).
- If the process is down longer than about one interval plus the lookback, a candle that has a token but no analysis is never written as an outcome.

### Corrections to my own earlier statements
- **"Startup closes these rows before reconciliation could ever see them":** this is not guaranteed. Reconciliation's first scan is scheduled 15 seconds after the scheduler starts (`:58`), and a long bootstrap could still be running then. With reconciliation off by default the point makes no practical difference, but the "before" ordering was overstated.
- **Earlier findings that still hold:**
  - backfill closes an open row without audit, outcome or provenance change;
  - Replay selects candles by time only;
  - the corrected V103/B105 status from round 4;
  - the `claude-docs` error about OBSERVE;
  - three source comments that contradict their SQL;
  - the hard-coded default admin password in B105 (outside the question's scope).
- **Bootstrap Javadoc:** `MarketDataBootstrapService.java:21-24` ("only missing Binance rows are inserted") is a fourth comment that contradicts the code.

## OBJECTIONS (unresolved, material)
1. Ordinary backfill closes an open runtime row without audit, outcome or provenance change. At coin activation this can also take over a live candle close, which is then never analysed (new finding).
2. Every coin change reconnects all streams, and with reconciliation off by default there is no automatic repair.
3. Reconciliation:
   - it is off by default;
   - the `LIMIT 50` slots are shared across all symbols and filled before the due/evidence filters;
   - aged-out `PENDING` candidates get no final outcome;
   - its loss evidence is in memory only.
4. The detector writes no outcome after an outage longer than its lookback.
5. OBSERVE runs direct ingestion and the collector together in the main trader.
6. There is no shared Binance REST rate-limit or ban handling.
7. Replay parity with live admission is not shown.
8. Documentation has drifted: AGENTS.md calls the design "pending", the V103 blocker text is out of date, `claude-docs` misdescribes OBSERVE, and four source comments contradict their code.
