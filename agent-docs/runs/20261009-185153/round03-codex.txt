## FINDINGS

The working tree implements a local-candle ingestion path, but it does not meet the pending architecture’s release criteria. The checked-in default is `shared-market.mode=OFF`, where the trader owns Binance WebSocket and REST ingestion and persists into its local `crypto_ai.candle` table.

`LIVE` retains collector ownership: the trader reads collector tables in `crypto_ai_v2` and processes copied delivery records locally. `OBSERVE` starts both the trader WebSocket and the collector-reading consumer, but the consumer marks deliveries `OBSERVED` and returns before protection or analysis. Therefore the earlier claim that OBSERVE executes both pipelines is incorrect; it is still collector-coupled and violates the intended OFF isolation boundary.

The material confirmed defect is separate: ordinary REST bootstrap/import backfill uses duplicate-key update logic. During dynamic coin activation, WebSocket reload occurs before backfill; the backfill can close an already-open runtime row without a close-transition token. That prevents the normal live close from dispatching analysis, while the detector requires a token and reconciliation requires `closed=0`. The affected candle can therefore receive neither live analysis nor a terminal analysis outcome.

Automatic reconciliation exists but is disabled by default. It also lacks demonstrated shared Binance rate-limit/ban control. The local-candle path is consequently implemented in source but not shown deployment-ready.

## OBJECTIONS

1. Ordinary REST import/backfill can finalise a live open candle without a close token or terminal outcome. This directly contradicts the pending architecture’s monotonic close-admission and durable-outcome rules.

2. Reconciliation is disabled in the checked-in configuration, contrary to the pending direction that reconnect-gap recovery be automatic and require no manual repair.

3. No inspected Binance client/control path establishes shared handling for `429`, `418`, `Retry-After`, rate budgets, or bans across bootstrap, reconciliation, and clock synchronization. This is a required design constraint, not a cosmetic omission.

4. The detector cannot guarantee durable recovery/outcome coverage across an outage longer than its bounded scan window.

5. OBSERVE is not execution-concurrent as previously alleged, but it does connect to collector infrastructure and writes shared-market state while direct trader WebSockets are active. That conflicts with the intended isolation of the OFF cutover and should not be treated as the target runtime.

6. Replay includes recovered/backfilled closed candles in fresh replay input, while production structurally excludes those records from live close dispatch. No reviewed code proves the required production/Replay evidence alignment.

7. `application.yml` contains two top-level `local-candle` mappings ([lines 40 and 447](C:/workspace/crypto-ai-trader-mysql/src/main/resources/application.yml:40)). Source review cannot establish whether the deployed YAML loader rejects duplicates or resolves them, but either outcome requires validation.

8. The documentation conflicts with source:
   - AGENTS.md describes local-candle as pending/not deployed, but source selects OFF/direct ingestion by default.
   - Some documentation reports no reconciliation implementation, while source includes one but disables it.
   - Documentation that treats V103 as the only bootstrap state is incomplete because B105 exists; B105 remains unproven.
