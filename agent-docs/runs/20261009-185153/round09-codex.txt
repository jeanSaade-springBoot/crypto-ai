## FINDINGS

1. Default checked-in mode is `OFF`; in that mode the trader owns Binance WebSocket and REST candle ingestion and persists locally to `crypto_ai.candle`. `LIVE` disables those direct paths and reads candles through the configured collector datasource. No production environment was accessed.

2. `OBSERVE` is materially unsafe against the pending direction: direct WebSocket/REST ingestion is disabled only for `LIVE`, while `SharedMarketConsumer` starts its collector polling/dispatch clocks in every non-`OFF` mode. Therefore OBSERVE can operate both paths concurrently.

3. Runtime candle persistence has a real monotonic close mechanism. A runtime close gets a token only on an atomic `closed=0 → 1` update; later open updates and duplicate closes cannot overwrite the completed candle or generate another dispatch token. The close event is published only after input, protection, and observer transactions.

4. Ordinary REST bootstrap/backfill violates the pending recovery contract. Its `ON DUPLICATE KEY UPDATE` can finalize an existing open runtime candle, but preserves the existing provenance/token and creates neither reconciliation audit nor a `candle_analysis_outcome`. It is therefore not “insert missing identities only,” despite the source comment.

5. The reported coin-activation race is technically credible. Activation reloads the all-symbol combined WebSocket before running bootstrap. If bootstrap finalizes a just-closed, already-open runtime candle before its final WebSocket close message is processed, that later close cannot obtain a token or dispatch analysis. The detector excludes it because it has no token; reconciliation excludes it because it is no longer open. I found no test covering this interleaving.

6. A specialized reconciliation slice exists and is materially safer: it uses update-only recovery for an existing open row and insert-if-absent for a wholly absent candle, records audit/outcome evidence, and never dispatches recovered work. But it is disabled by the checked-in configuration, so it is not the current active default behavior.

7. Reconciliation still has unproven/material weaknesses even if enabled:
   - It takes `LIMIT 50` per interval before due-status and loss-evidence filtering.
   - It does not restrict open candidates to enabled symbols.
   - Reconnect loss evidence is process-local (`lastReconnectAdmission`) and disappears across restart.
   - Retryable candidates age out of the quality window without a demonstrated terminal age-out outcome.
   - REST clients have bounded timeouts but no shared 429/418, `Retry-After`, ban, or global request-budget coordination.

8. The detector addresses the commit-to-dispatch crash window only while a tokened candle remains inside its bounded lookback. Retry state is in memory; after a sufficiently long outage, an old unanalysed tokened candle falls outside SQL selection without a detector-created terminal outcome. This is confirmed by code and even directly reflected in the unit test that asserts old runtime candles are not analysed.

9. Replay reads closed local/selected-source candles by symbol, interval, time, and `closed=true`. It does not classify provenance, close token, reconciliation audit, outcome, or “historical-only” recovery state. It provides narrower price-event checks, not demonstrated parity for candle recovery/admission behavior.

10. Documentation has material drift:
    - AGENTS.md and `codex-docs/ARCHITECTURE.md` call V103 an unconditional fresh trader-only blocker, but `B105` expressly establishes a trader-only baseline intended to bypass V103; a source-level resolution test exists. A real disposable-MySQL success report was not found, so this corrects the categorical claim without proving deployment readiness.
    - `claude-docs/ARCHITECTURE.md` incorrectly groups OBSERVE with LIVE/shared-only operation; code allows direct ingestion in OBSERVE.
    - `MarketDataBootstrapService` and `CandleRepository` comments claim missing-only backfill, contradicted by their implementation.

## OBJECTIONS

- Default OFF-mode bootstrap can silently consume a live close without analysis/outcome evidence.
- Default reconciliation is disabled; enabled reconciliation still lacks demonstrated fair candidate selection, durable restart evidence, terminal ageing, and coordinated Binance rate-limit handling.
- OBSERVE permits direct and shared-market ingestion together, contrary to the pending architecture.
- Replay parity does not cover the implemented recovery/admission classifications.
- Required MySQL, crash/restart, concurrency, replay, and deployment-replacement proof is absent.

Candidate for later solution review only: separate ordinary historical import from authority to finalize an existing runtime-open row, then test the activation/reconnect boundary against disposable MySQL.

- Whether every administrative coin mutation invokes stream reload; the documented reload paths do, but no runtime audit was inspected.
- Open-position protection coverage during application replacement.
