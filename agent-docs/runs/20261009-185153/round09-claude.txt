### Correction 1: my round-5 race has more triggers than I said
The race itself holds: REST import closes an open `RUNTIME` row with no token, so the WebSocket's final message never creates a dispatchable transition.
- Mechanism: MySQL evaluates `ON DUPLICATE KEY UPDATE` left to right, and `closed=` is assigned last (`CandleRepository.java:188,203`). So the token test `IF(closed=0 AND …)` at `:201` sees the row as already closed. The read-back at `:120` then fails, and nothing is dispatched.
- I limited it to adding a coin. It is wider:
  - **Re-enabling a coin:** `PUT /api/administration/coins/{id}/enabled` also calls `activate` (`CoinConfigurationController.java:41`).
  - **A failed reload:** if `reload()` times out after 30 seconds, the exception is caught (`DynamicCoinActivationService.java:23`) and the import still runs (`:28`).
  - **The import endpoint (broadest):** `POST /api/market-data/import` (`MarketDataController.java:16-22`) can be called at runtime for any symbol that is already streaming. No reload is needed. I did not check whether it requires authentication.

### New 1: ordinary import skips the close grace period that reconciliation uses
- Ordinary import skips only candles whose `closeTime` is after `exchangeNow` (`MarketDataService.java:45`). It has no grace period.
- Reconciliation waits `live-close-grace (10s) + safety-margin (2s)` (`LocalCandleReconciliationService.java:127`), as AGENTS.md requires.
- Once the import closes a row, every field is frozen (`CandleRepository.java:177-188`). A later WebSocket final kline cannot correct it.
- So candle values read from REST at the close boundary become permanent. Whether Binance REST can return non-final values for a candle whose `closeTime` is at or before server time is **unknown**.

### New 2: dropped 1m and overflow closes can end with no recorded outcome
- When work backs up, the dispatcher drops a committed, tokened close in two ways:
  - **1m candles:** a newer close replaces the pending one (`PENDING_REPLACED`).
  - **Higher timeframes:** the queue holds 4 entries, and an overflow is rejected (`LANE_OVERFLOW`).
- In both cases the only trace is a log line and an in-memory counter (`CandleAnalysisDispatcher.java:74-81, 91-97`). No durable outcome is written.
- The detector is the only thing that could write a final outcome later:
  - It admits work only when the lane is idle: `idle()` at `:29`, the check at `:38`, and the detector's own check at `LocalClosedCandleDetector.java:46`.
  - It only looks back about 180 seconds (`:47-50`).
- If the lane stays busy for longer than that, the dropped candle ages out with no outcome. That breaks the AGENTS.md rule that each candle path writes one durable final outcome.

### New 3: the historical-only path is only a code branch, not a separate component
- When stale work is recovered, the worker routes it to `analyzeRecovered` (`CandleClosedAnalysisWorker.java:160-165`), so it does not trade today. That answers one possible objection.
- But the same class holds `paperTradingService` (`:37`) and calls it twenty lines later (`:175`).
- AGENTS.md asks for historical-only recovery that is *structurally unable* to reach execution. A branch inside the executing class does not meet that.

### New 4: `application.yml` declares `local-candle:` twice at the top level (lines 40 and 447)
Codex flagged this as an unknown. I add:
- There is no `@SpringBootTest` in `src/test`, and there are no test resource files. No test in the tree has ever loaded this YAML.
- From memory, not checked here: Spring Boot's YAML loader has rejected duplicate keys, and the project uses Spring Boot 4.1.0 (`pom.xml:9`). If that still holds, the checked-in configuration would fail at startup. If it doesn't, one block silently overrides the other.
- Either way, "reconciliation is off by default" still holds, because the code default is also `false` (`LocalCandleReconciliationService.java:44`).

### Correction 2: my round-5 point about the in-memory reconnect evidence was wrong

- My `LIMIT 50` objection stands unchanged (`:129-140`): the limit is shared across every symbol, has no enabled-coin filter, and is applied before the due and loss-evidence filters.

## OBJECTIONS (unresolved, material)
1. **Ordinary import:**
   - It closes open runtime rows without audit, outcome or provenance change, and without a close grace period.
   - Three runtime triggers (adding a coin, re-enabling one, the import endpoint) can lose a live close entirely.
2. **Dropped closes:** 1m replacement and queue overflow write no outcome, and the idle-only, lookback-bounded detector cannot guarantee one later.
3. **Reconciliation:**
   - It is off by default.
   - The `LIMIT 50` is applied before filtering.
   - `PENDING` candidates that age out get no final outcome.
   - Its retry evidence is in memory.
4. **Detector:** it writes no outcome after an outage longer than its lookback.
5. **Historical-only work:** it is separated from execution only by a code branch, not structurally.
6. **OBSERVE:** it runs both ingestion paths, and the startup import executes trades.
7. **Rate limits:** there is no shared Binance REST rate-limit or ban handling.
8. **Replay:** parity with live admission and recovery is not shown.
9. **Configuration:** the duplicate YAML key was never loaded by any test.
10. **Documentation drift:**
    - AGENTS.md calls the design "pending" and its V103 blocker text is out of date.
    - claude-docs misdescribes OBSERVE.
    - Four source comments contradict their own SQL or code.
