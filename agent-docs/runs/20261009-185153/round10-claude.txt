### Correction 2: I described the token-loss mechanism wrongly
Round 6 blamed MySQL's left-to-right evaluation. Actually, left-to-right evaluation is what makes a *normal* close work:
- The token check at `CandleRepository.java:201` reads `closed=0` before `:203` sets it to 1.

The real race happens across two separate statements:
1. Ordinary import (`upsert` → `BACKFILL` branch, `:173-188`) has already set `closed=1` on the open runtime row.
2. When the WebSocket's final kline arrives, the check at `:201` sees `closed=1` and keeps the token NULL.
3. The read-back at `:120` therefore returns `transitionedToClosed=false`, and nothing is dispatched.

The conclusion holds. The comment at `:205` ("backfill inserts missing identities only") is still contradicted by the clause at `:173-188`.

### Correction 3: dropped closes are usually recovered — I overstated the risk
- A close dropped by 1m replacement or queue overflow (`CandleAnalysisDispatcher.java:74-81, 91-97`) keeps its token and has no outcome or signal. The detector's `missing()` check (`LocalClosedCandleDetector.java:135-139`) therefore treats it as unanalysed.
- So the detector picks it up again once the lane goes idle within the lookback (`:46-51`).
- After more than 6 attempts it writes a durable `ANALYSIS_EXPIRED` outcome (`:99-104, 113-119, 140-142`).
- What remains of my round-6 objection:
  - The lane stays busy for the whole lookback (at least 180 s; `:46` skips the lane without counting an attempt).
  - Or the process restarts: the `retries`/`analysedUntil` maps are in memory (`:28-29`).
  - In either case the candle drops out of the SQL window with no outcome.

### New 1: the detector's deadline-based expiry practically never fires
This is derived from the code, not tested.
- **The query:** a candle is a candidate only while `open_time >= now - interval - lookback` (`:49-50`).
- **Binance convention:** `closeTime = openTime + interval - 1 ms`. This comes from Binance's public convention; I did not re-check it in this repo.
- So a candidate always has `closeTime + lookback >= now - 1 ms`.
- **The expiry test:** it fires when `!retryDeadline.isAfter(now)` with `retryDeadline = closeTime + lookback` (`:97-99, 111-113`). That is true only in a window of about 1 ms. A detector pass runs every 2 s, so it almost never lands there.
- **Effect:** a durable terminal outcome comes, in practice, only from the attempt count (`attempts>6`). A candle that gets fewer than 7 counted attempts ages out silently. That matches Codex's point 8, but the cause is more specific than "bounded lookback".

### New 2: the import endpoint needs a login, but not an admin role (round-6 unknown resolved)

## OBJECTIONS (unresolved, material)
1. **Ordinary import:**
   - It closes open runtime rows without audit, outcome or close grace period, so a live close can be lost.
   - Any authenticated user can trigger it, as can adding or re-enabling a coin.
   - The comment at `CandleRepository.java:205` is false.
2. **Detector terminal outcomes:**
   - Deadline-based expiry practically never fires.
   - A lane that stays busy, or a restart, lets a tokened candle age out with no outcome.
   - A saved signal alone counts as completion.

   - It is off by default.
   - Its `LIMIT 50` is applied before filtering.
   - It has no proven terminal outcome when candidates age out.
   - It has no shared Binance REST rate-limit or ban handling.
