## FINDINGS

1. The repository implements two mutually exclusive intended paths:
   - `OFF`: trader-owned Binance WebSocket ingestion, local `crypto_ai.candle` writes, local close detection/dispatch.
   - `LIVE`: collector-backed shared-market consumption from `crypto_ai_v2`.
   
   This broadly matches the pending local-candle direction in `AGENTS.md`, but it is not deployment-ready.

2. In `OFF`, the trader owns Binance kline WebSocket ingestion. The WebSocket handler calls `BinanceKlineService.processKline`, which persists the local candle and canonical 1m price event, runs protection and observer work, then publishes a close event only after an atomic close transition.

3. In `OFF`, REST bootstrap/backfill is trader-owned:
   - `MarketDataBootstrapService` invokes `MarketDataService.importCandles`.
   - It writes closed REST data to local `candle` and explicitly suppresses analysis/execution for bootstrap in OFF mode.
   - A separate reconciliation implementation exists for authoritative recovery/gap backfill, but is disabled by default.

4. Local candle persistence is implemented through `CandleRepository` writing `crypto_ai.candle` when not in LIVE mode. Runtime updates preserve monotonic closure; recovery has distinct update-only and insert-if-absent paths.

5. In `LIVE`, the trader has an explicit runtime dependency on the external collector:
   - a read-only pool connects to configured `crypto_ai_v2`;
   - `SharedMarketConsumer` reads `market_data_stream_event` / cursor tables;
   - it writes local shared-delivery/state tables and dispatches work from them.
   
   This is retained legacy/shared functionality, not the target OFF architecture.

6. Material architectural defect: `OBSERVE` is neither isolated nor mutually exclusive. `SharedMarketSource` treats only `LIVE` as enabled, so direct Binance WebSocket ingestion remains enabled in `OBSERVE`; but `SharedMarketConsumer` also starts its collector polling for every non-OFF mode. Thus `OBSERVE` can run direct ingestion and collector consumption together, violating the documented “do not run direct ingestion and shared-market executors together” rule.

7. Close handling in OFF is substantially aligned with the pending safety direction:
   - runtime upsert uses an immutable close-transition token;
   - duplicate close and late-open updates do not re-admit work;
   - the transaction order is input → protection → observer → close dispatch;
   - analysis is dispatched asynchronously, not on the WebSocket callback thread.

8. Recovery/backfill behavior is partly implemented but operationally inactive by default. The reconciler requires `OFF` and `local-candle.reconciliation.enabled=true`; the checked-in default is `false`. Recovery finalizes existing open rows without a token; gap recovery is insert-if-absent with `BACKFILL` provenance and records a non-live terminal outcome. It does not dispatch analysis or execution.

9. Replay uses candle data through `CandleRepository`: local `crypto_ai.candle` in OFF and the collector-side reader in LIVE. Replay also consumes persisted `market_price_event` evidence for exact-price behavior when available. I found source-level parity machinery, but no executed Replay validation evidence in this investigation.

10. The current default configuration is OFF, but the checked-in default cannot start OFF mode as-is: `local-candle.instance-lock-path` is empty while startup requires an explicit absolute path. This is a deliberate fail-fast control, but it means default OFF configuration is not independently runnable.

2. **The docs contradict the code and each other.**

   - codex-docs says the trader-only bootstrap is "pending" (`ARCHITECTURE.md:85-88`), yet B105 exists.

3. **The yml has a duplicate top-level key.** Both `local-candle:` blocks sit at the top level of the same YAML document. My understanding is that this stops startup; at best, one block silently wins. Either way it's a material configuration defect.
4. **Automatic recovery is off, which conflicts with AGENTS.md.** The rule says "Candle recovery is automatic… no manual repair step". With recovery disabled, a reconnect at a candle close leaves the row open, and the zero-missing-candles quality rule then blocks that lane. That is exactly the 2026-10-09 incident, which was fixed by hand (`codex-docs/INVESTIGATION_LOG.md:12-21`). In practice, only a restart's bootstrap fixes it.
5. **No shared Binance rate-limit or ban handling.** AGENTS.md requires it across recovery, clock sync and bootstrap. I found none anywhere.
6. **The startup/coin-activation backfill uses insert-or-update** and can close an open row. If that happens while the WebSocket is live for that symbol, the live close becomes a duplicate. No token is created, so the detector also skips the candle. It then only gets a late-close audit row, with no terminal analysis outcome. The startup run happens before the WebSocket starts, so it's safe. Whether the coin-activation path can overlap with a live stream is **unknown**.
7. **Detector gaps against AGENTS.md:**
   - **Not durable across long outages:** the detector's lookback is 180–600 s and its retry state is in memory. After a crash or outage longer than that, a closed candle that was never analysed is never revisited and gets no terminal outcome. That conflicts with "each candle/work path must write one durable terminal analysis outcome".
   - **Possible out-of-order live execution:** a 1m candle that was replaced in the queue can be re-sent by the detector while still inside its 90 s grace. It would then be analysed as live, after a newer candle. I found no guard against this in `execution/`; whether one exists elsewhere is **unknown**.
8. **Replay is likely to diverge from production.** Replay analyses BACKFILL/recovered candles and candles that were replaced in the 1m queue. Production deliberately records those as not live, or never analyses them. I found no exclusion based on candle origin or production outcome.
9. **OBSERVE mode runs both paths at once.** In OBSERVE, the trader's own WebSocket runs alongside the shared-market discovery loop. That conflicts with "do not run direct ingestion and the shared-market executors together". It's not the default mode, but nothing prevents it.
10. **Smaller points:**
    - `activation-approved` defaults to `true` in the yml.
    - The startup schema check doesn't require V107, although recovery and outcome recording need it.
