## FINDINGS

1. **Implemented default is trader-owned local ingestion.** Checked-in `shared-market.mode` defaults to `OFF`. In OFF, the trader opens Binance combined kline WebSockets, performs REST imports, and writes the local `crypto_ai.candle` table.

2. **LIVE is the only mode that disables direct ingestion.** WebSocket, REST import, and bootstrap check `mode == LIVE`, not `mode != OFF`. Therefore **OBSERVE runs direct Binance ingestion while also connecting to the collector and starting shared-market clocks**. This contradicts the pending direction’s “do not run direct ingestion and shared-market executors together.”

3. **Current local candle close behavior is mostly monotonic.** Runtime kline upsert preserves a completed candle and emits a close-transition token only for an atomic open-to-closed transition. The close event is published after the coordinator’s input, protection, and observer phases.

4. **Ordinary REST import is not compliant recovery/backfill.** It calls the generic BACKFILL upsert. On a duplicate open runtime candle, that SQL updates OHLCV and sets `closed=1`, but preserves provenance and transition token. It produces neither reconciliation audit evidence nor an analysis-outcome record. Its nearby comment claiming “inserts missing identities only” is false.

5. **A real live-close loss interleaving exists.** A REST import can finalize an already-open runtime candle before the final WebSocket close arrives. The later WebSocket upsert sees a completed row and cannot install its token; no normal close event is dispatched. The detector requires a token and reconciliation selects only `closed=0`, so neither path recovers that specific admission gap. Runtime triggers include authenticated `/api/market-data/import` and coin activation, which reloads streams then bootstraps.

6. **The specialised reconciliation implementation is closer to the pending design but is disabled by default.** It waits for exchange-time finality plus configured grace, finalizes only an existing open row, uses insert-only for an absent identity, records audit/outcome evidence, and never dispatches recovery work. However, checked-in `local-candle.reconciliation.enabled=false`.

7. **Enabled reconciliation has unresolved gaps.** Its open-row query applies `LIMIT 50` before due/loss-evidence filtering and does not restrict candidates to enabled symbols. Reconnect evidence is process-local. REST requests have no demonstrated shared handling of Binance 429/418, `Retry-After`, bans, or cross-client request budget.

8. **Close-dispatch durability is bounded, not fully durable.** The detector can repair tokened close-to-dispatch gaps only within a bounded lookback and while the lane is idle. Retry state is in memory. A prolonged outage or sustained busy lane can age a tokened candle outside selection without a terminal durable outcome.

9. **Dispatcher saturation can discard closed-candle analysis admission.** For 1m, a pending candle may be replaced; for higher intervals, a fifth pending item is rejected. These paths log and increment in-memory diagnostics only. The detector may later recover a dropped item, but cannot guarantee it if the lane remains non-idle or the candle passes the lookback window.

10. **Historical-only recovery is behaviorally, not structurally, separated from execution.** The worker branches to `analyzeRecovered` for stale/non-live work and returns before paper trading. But that same class injects `PaperTradingService`; this does not meet AGENTS.md’s stronger structural-isolation requirement.

11. **Replay does not establish local-ingestion parity.** Its ordinary replay loader selects candles by symbol/interval/time without filtering `closed`; the dataset path does filter forward candles by `closed=true`. Neither path models provenance, close tokens, reconciliation audit/outcomes, grace timing, or recovery admission. Replay parity for the pending recovery design is not shown.

12. **Production behavior is unknown.** No production systems, configuration overrides, database history, logs, or runtime processes were accessed.

## OBJECTIONS

- The checked-in OBSERVE mode violates the pending no-dual-ingestion rule.
- Default OFF-mode REST import can consume an active live close without durable analysis/outcome evidence.
- Reconciliation is disabled and, when enabled, lacks demonstrated durable restart evidence, fair candidate selection, and shared rate-limit/ban handling.
- Dispatcher/detector bounds do not prove the required durable terminal outcome for every close path.
- Replay does not prove equivalence of ingestion, recovery, and admission behavior.
- The architecture remains unproven for the pending migration/bootstrap and crash/restart release gates.

- Actual deployed mode, overrides, Flyway history, collector availability, and replacement-time position protection.
- Whether the disposable-MySQL integration test has been run successfully.

Corrections to prior reports:
