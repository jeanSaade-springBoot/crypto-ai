# FINDINGS

**Summary:** the trader-owned local-candle design that AGENTS.md calls "pending" is already the default code path in the working tree. Its automatic candle recovery is turned off by default, and several things contradict it:
- **Config:** `application.yml` defines the top-level `local-candle:` key twice.
- **Docs:** AGENTS.md, codex-docs and claude-docs no longer match the code.
- **Rules:** a few AGENTS.md rules are not met.

What's running in production is unknown.

1. **Kline WebSocket ingestion.** `shared-market.mode` defaults to `OFF`, and in OFF the trader owns the WebSocket. The chain is `BinanceWebSocketManager` → `BinanceKlineService.processKline` → `KlineTransactionCoordinator`. These components turn themselves off only in `LIVE`. In `OBSERVE` the trader's own WebSocket still runs.
2. **REST / backfill / recovery.** There are three paths, all owned by the trader:
   - **Startup bootstrap:** `MarketDataBootstrapService` → `MarketDataService.importCandles` → `CandleRepository.upsert`, tagged BACKFILL. In OFF it loads data only: no analysis and no trades.
   - **Automatic recovery:** `LocalCandleReconciliationService` can close a stuck open row (update-only) or fill a missing candle (insert-only). **It is disabled by default** (`local-candle.reconciliation.enabled: false`), and the deploy script doesn't turn it on.
   - **Diagnostics only:** `LocalClosedCandleDetector` re-sends candles that closed but were never analysed. It doesn't repair missing close data.
3. **Where candles are stored.** In OFF, all reads and writes go to the trader's own database. `SharedMarketSource.reader()` returns the local connection, and the OFF branch never creates the collector connection pool. In LIVE, reads go to `crypto_ai_v2.candle` and local candle writes are refused.
4. **`crypto_ai.candle` vs collector tables.** In OFF, the runtime paths I traced don't read or write `market_data_stream_event`, `market_data_stream_cursor` or `shared_market_*`. The shared-market health check returns local health first, and the shared-market consumer stops early in OFF. The exception is the Flyway migration V103, which needs `crypto_ai_v2.market_data_stream_event` to exist when it runs.
5. **Configuration.** The defaults match the target in AGENTS.md: mode OFF, both `fix142` flags false, scheduled analysis false. The deploy script forces the same values on the command line. Two problems:
   - **`local-candle:` is defined twice** at the top level of `application.yml` (lines 40 and 447). As far as I know, Spring Boot's YAML loader rejects duplicate keys, so the file would fail to load at startup. I haven't verified this by running it. If duplicates were accepted instead, one block would silently replace the other.
   - **`activation-approved` defaults to `true`** in the yml, while the deploy script forces it to `false`.
6. **Candle close handling.** Updates only move forward: once a row is closed, nothing reopens or changes it. Each closing receipt carries a unique token. The token is only written when the row actually changes from open to closed, and reading it back decides whether to dispatch analysis. The four transactions run in the order AGENTS.md requires: input → protection → observer → close dispatch. Analysis then runs on a separate executor, never on the WebSocket thread.
7. **Recovery and backfill.**
   - **Automatic recovery** (`LocalCandleReconciliationService`, the off-by-default path) follows the AGENTS.md rules: it waits until the exchange's time says the candle is final, uses an exact REST match, keeps durable audit rows with retries, creates no token, and records "not live" or "data unavailable" outcomes.
   - **The startup/coin-activation backfill is different.** It uses insert-or-update, so it can close an open row that live data was still writing.
8. **Analysis after a close.** The listener fires after commit and hands off to `CandleAnalysisDispatcher`, which has one lane per symbol and timeframe.
   - For 1m, only the newest waiting candle is kept; for higher timeframes, at most 4 wait in order.
   - The worker then runs: data-quality check → indicators → check for an existing signal → freshness check (1m/5m/1h allow 90/120/300 s after close) → either live analysis or history-only analysis.
9. **Coupling to the collector.**
   - **At runtime in OFF:** I found none in the paths I traced.
   - **Remaining coupling:**
     - The V103 migration.
     - The collector pool, opened in OBSERVE and LIVE.
     - OBSERVE mode runs the trader's WebSocket and the shared-market discovery loop at the same time.
     - Collector credentials are still in the yml defaults.
10. **Replay.** Replay reads candles through the same `CandleRepository`, so in OFF it reads local candles. It evaluates every closed candle and ignores where it came from (live, backfill or recovered) and what production recorded for it.
11. **Production.** Unknown; I had no access, as instructed. What I can see:
    - The docs say FIX-153 is uncommitted and not approved for production.
    - The 2026-10-09 evidence in codex-docs is from the local `crypto_ai` database, not production.
12. **Implemented vs pending.**
    - **Implemented (working tree):**
      - Trader-owned ingestion is the default.
      - Updates only move forward, and close tokens decide dispatch.
      - There is a detector that re-sends missed analysis.
      - Durable tables for analysis outcomes and recovery audit exist (V107).
      - Automatic recovery code exists.
      - There is a trader-only baseline migration (B105).
      - There are drain support and an instance lock.
    - **Still pending or not met:**
      - Automatic recovery is switched on nowhere.
      - The live-close grace period is still a provisional value.
      - There is no shared handling of Binance REST rate limits or bans.
      - B105 hasn't been tested on MySQL.
      - Protecting open positions while the application is replaced is unresolved.
      - Replay doesn't distinguish candle origin.
      - The Java 21 / MySQL validation gates haven't been run.

# OBJECTIONS

1. **AGENTS.md is out of date.** It says the target design is "not an implemented/deployed change", but it is the default code path in the working tree. AGENTS.md also says V103 blocks a trader-only install until a forward policy exists, while the source already contains a B105 baseline meant to solve that (untested on MySQL).
2. **The docs contradict the code and each other.**
   - claude-docs says nothing repairs the reconnect gap automatically (`ARCHITECTURE.md:96-99`, `INVESTIGATION_LOG.md:11`) and that a fresh install fails because of V103. The code has both a recovery service and B105.
   - codex-docs says the trader-only bootstrap is "pending" (`ARCHITECTURE.md:85-88`), yet B105 exists.
   - codex-docs also correctly says recovery is "disabled by default" (`:137-141`).
3. **The yml has a duplicate top-level key.** Both `local-candle:` blocks sit at the top level of the same YAML document. My understanding is that this stops startup; at best, one block silently wins. Either way it's a material configuration defect.
4. **Automatic recovery is off, which conflicts with AGENTS.md.** The rule says "Candle recovery is automatic… no manual repair step". With recovery disabled, a reconnect at a candle close leaves the row open, and the zero-missing-candles quality rule then blocks that lane. That is exactly the 2026-10-09 incident, which was fixed by hand (`codex-docs/INVESTIGATION_LOG.md:12-21`). In practice, only a restart's bootstrap fixes it.
5. **No shared Binance rate-limit or ban handling.** AGENTS.md requires it across recovery, clock sync and bootstrap. I found none anywhere.
6. **The startup/coin-activation backfill uses insert-or-update** and can close an open row. If that happens while the WebSocket is live for that symbol, the live close becomes a duplicate. No token is created, so the detector also skips the candle. It then only gets a late-close audit row, with no terminal analysis outcome. The startup run happens before the WebSocket starts, so it's safe. Whether the coin-activation path can overlap with a live stream is **unknown**.
7. **Detector gaps against AGENTS.md:**
   - **Not durable across long outages:** the detector's lookback is 180–600 s and its retry state is in memory. After a crash or outage longer than that, a closed candle that was never analysed is never revisited and gets no terminal outcome. That conflicts with "each candle/work path must write one durable terminal analysis outcome".
   - **Possible out-of-order live execution:** a 1m candle that was replaced in the queue can be re-sent by the detector while still inside its 90 s grace. It would then be analysed as live, after a newer candle. I found no guard against this in `execution/`; whether one exists elsewhere is **unknown**.
8. **Replay is likely to diverge from production.** Replay analyses BACKFILL/recovered candles and candles that were replaced in the 1m queue. Production deliberately records those as not live, or never analyses them. I found no exclusion based on candle origin or production outcome.
9. **OBSERVE mode runs both paths at once.** In OBSERVE, the trader's own WebSocket runs alongside the shared-market discovery loop. That conflicts with "do not run direct ingestion and the shared-market executors together". It's not the default mode, but nothing prevents it.
10. **Smaller points:**
    - `activation-approved` defaults to `true` in the yml.
    - The startup schema check doesn't require V107, although recovery and outcome recording need it.
