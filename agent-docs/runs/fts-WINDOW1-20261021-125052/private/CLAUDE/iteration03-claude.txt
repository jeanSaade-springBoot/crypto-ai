**F-23 (study-wide, blocks every absolute time): the result files show KSA, not UTC.** [PROJECT EVIDENCE + EXTERNAL RESEARCH]
- **How the database works:** the columns are `TIMESTAMP(6)` (V1 and B105 migrations), so MySQL converts them to the reading session's time zone. The application sets its session to UTC (`application.yml:21-25, 35`). None of the coordinator's queries or mine set a session time zone (DBQ-FTS-001…005, all Claude SQL files).
- **Evidence 1, the application's own UTC timestamps.** Each execution message contains `priceObservedAt`, which Java prints in UTC. The value comes from the price-event row the application read back over its UTC session (`ExecutionPriceAuthorityService:46-48`, `PaperTradingService:383`). In every case, the stored column shows that time **plus 3 hours** (DBQ-CLAUDE-I2-002):

- **Evidence 2, Binance price history.** Binance's EGLDUSDT 1-minute candles for 2026-10-11 **19:39–19:43 UTC** match trade 143 exactly:
  - 19:39 closes at 4.032, the decision price.
  - 19:40 reaches a high of 4.067, where the take-profit was passed.
  - 19:41 reaches a high of 4.101, the trade's peak.

  - The same window at 22:35–22:47 UTC trades at about 3.966–3.982, which matches nothing.

  - The "KSA" values I gave earlier are 6 h ahead of UTC and are wrong.
  - The application log files write UTC (for example, `logs/crypto-ai-trader.log:177` shows log time 14:32:32 next to `observedUtc=…14:32:32Z`). When matching DB rows to log lines, subtract 3 h from the displayed DB value.
  - DATABASE_INVESTIGATION_RULES.md:35 ("Raw MySQL timestamps are UTC") is right about storage. It is broken in practice when the client session isn't UTC. I'm reporting this contradiction rather than accepting it.

**F-24: F-13 is confirmed. Trade 143 entered on a 5-minute BUY that the latest 5-minute candle had already downgraded to WATCH.** [PROJECT EVIDENCE] Severity: high, likely defect.
- The execution opportunity row 36524 records `five_minute_decision=BUY`, route `SETUP_TIMEFRAME_ATR`, and "the fresh 5m BUY remains the setup-risk authority" (I2-003).
- That 5-minute candle (19:35–19:40 UTC) had already produced 5-minute signal **159407 = WATCH**. Its own ATR check said not to buy immediately (`atr_immediate_entry_allowed=0`, `PULLBACK_ENTRY`, `atr_overextended=1`).
- Mechanism:
  - The 5-minute signal is chosen by `latestAtOrBefore` → `findTop…GeneratedAtLessThanEqual…(…, current.getGeneratedAt())` (`ExecutionIntelligenceService.java:2455-2462, 2608`).
  - In production, `generatedAt` is simply the clock time when analysis of that candle started (`Instant.now()`, `AnalysisService.java:150`).
  - 159407 started 1.999 ms after the 1-minute signal 159408, so it was excluded. The previous 5-minute signal, **159285 BUY 83**, was used instead.
- **Timing (as shown → UTC 19:40):**
  - 159407 row written: 22:40:02.9406.
  - 159408 row written: 22:40:02.9487.
  - Wallet fill: 22:40:03.115.

  So the WATCH signal was already in the database before the buy executed. It was skipped because of the rule's `generated_at` boundary, not because of a timing delay.
- **How common is this (I2-008)?**
  - Among the 32 positions opened since 10-11, the 5-minute signal for the same candle close was generated **after** the 1-minute signal in 28 cases.
  - So any route triggered by a 1-minute signal normally judges the 5-minute timeframe from the **previous** 5-minute bar, which can be up to 5 minutes old.
  - Among the frozen trades, only 143 had its decision changed by this.
- **Replay probably behaves differently.** [AGENT INFERENCE]
  - Replay uses the same `generatedAt` rule (`ExecutionReplayScope.java:110-119`), but its `generatedAt` comes from a supplied `evaluationTime`, or from candle open time if none is supplied (`AnalysisService.java:172, 190`).
  - If the 1-minute and 5-minute signals for the same candle close get equal times, the WATCH would be visible in Replay, and trade 143 would likely **not** be admitted.
  - That would be a gap between Replay and Production. Not verified (U-14).

**F-25: Trade 143's sale below its profit floor came from a real crash, not a data delay; holding on would have done worse.** [PROJECT EVIDENCE + EXTERNAL RESEARCH] This settles U-12.
- Binance's 19:43 UTC candle traded between 4.100 and **3.994**. That low is below the stop (4.0102), the hard floor (4.0350) and the entry.
- The system sold at 4.027, 25 ms after the price update at 22:43:35.021 (shown time = 19:43:35 UTC). Within the next 60 minutes the price reached 3.940 (I2-009).
- **Still unexplained:** the 8-second gap with no stored price updates (22:43:27 → 22:43:35 as shown) during a heavy move.
  - [EXTERNAL RESEARCH, from memory, not re-fetched] Binance pushes 1-minute candle updates about every 2 seconds, so 3–4 updates are missing. Possible causes: duplicates being dropped, a stalled stream, or Binance simply not sending them. See DBQ-CLAUDE-I3-002.
- **Classification:** the outcome was made worse by extending the target (F-14), but this exit followed the rules and saved money.

### DB_REQUEST
QueryId: DBQ-CLAUDE-I3-003
Purpose: Price-feed write lag by second within the minute during the six holds (U-19)
SQL:
SELECT SECOND(e.observed_at) AS sec_of_min, COUNT(*) AS n, ROUND(AVG(TIMESTAMPDIFF(MICROSECOND, e.observed_at, e.created_at))/1000,1) AS avg_lag_ms, ROUND(MAX(TIMESTAMPDIFF(MICROSECOND, e.observed_at, e.created_at))/1000,1) AS max_lag_ms
FROM paper_position p JOIN market_price_event e ON e.symbol=p.symbol AND e.observed_at BETWEEN p.opened_at AND p.closed_at
WHERE p.id IN (182,172,162,158,143,137)
GROUP BY SECOND(e.observed_at) ORDER BY sec_of_min
### END_DB_REQUEST

### DB_REQUEST
QueryId: DBQ-CLAUDE-I3-006
Purpose: How often an entry's recorded 5m decision differs from the 5m signal for the same candle close (F-24 generalisation)
SQL:
SELECT p.id, p.symbol, o.execution_source, o.five_minute_decision AS used_5m, s5.id AS same_boundary_5m_id, s5.decision AS same_boundary_5m, TIMESTAMPDIFF(MICROSECOND, s1.generated_at, s5.generated_at) AS five_minus_one_us
FROM paper_position p
JOIN trade_signal s1 ON s1.id=p.signal_id
JOIN execution_opportunity o ON o.symbol=p.symbol AND o.executed_at=p.opened_at
LEFT JOIN trade_signal s5 ON s5.symbol=s1.symbol AND s5.interval_code='5m' AND s5.candle_open_time + INTERVAL 5 MINUTE = s1.candle_open_time + INTERVAL 1 MINUTE
WHERE p.opened_at >= '2026-10-11 00:00:00'
ORDER BY p.id
