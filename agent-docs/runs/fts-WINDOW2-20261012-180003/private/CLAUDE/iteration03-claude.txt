# Iteration 3 of 8: log and timing forensics (Claude, self-review only)

The study's application logs couldn't be read, so this timing reconstruction rests on database timestamps and code tracing. The logs for 2026-10-11 and 2026-10-12 exist only as `.gz` archives, and my tools can't decompress them.

From those sources:
- **Exit delays:** every signal-confirmed live exit was delayed by up to 39 s. In the four cases where I have the tick prices, the delay cost nothing.
- **Trade 143's entry:** it relied on a 5m signal that was one bar old. It lost a 2 ms race against the newer 5m signal.
- **2 s write delay:** every wallet transaction spends about 2 s on a portfolio snapshot before the paper row is written.

No code, config, database writes, git or deploy. I didn't read the Codex folders, LIVE_TEAM_STATUS or LIVE_EVENTS. Times are shown as raw UTC → KSA (UTC+3).

**F21. Live exits only fire on a price tick, and new signals reach that path late.** (PROJECT EVIDENCE: code + DBQ-CLAUDE-I1-007/008)
- `LivePositionProtectionService.onPrice` is the only evaluator for SELL_CONFIRMED and HTF_SELL_CONFIRMED (`:235-238`). It reads the newest committed signals by `generated_at` (`:95-97`).
- A `trade_signal` row's `created_at` comes 1.3–2.3 s after its `generated_at`; for example, 168277 was generated at 04:26:02.794 and created at 04:26:04.094 (DBQ-CLAUDE-I1-002). So a signal can't be seen until after its `created_at` at the earliest.

| 137 | 5m 156852 at 21:00:02.921 → 00:00:02 | 21:00:09.033 → 00:00:09 | about 6 s | none: 3.987 → 3.987 (no tick between 21:00:01.023 and 21:00:09.033) |

- For 158, the tick at 03:30:02.32 → 06:30:02 KSA came after both signals' `generated_at` but did **not** trigger the exit. My explanation is that the signals hadn't committed yet. That is AGENT INFERENCE until DBQ-CLAUDE-I3-001.
- Classification: a design-level latency (exits are driven by ticks, and signals become visible only on commit). In these trades it caused no measurable loss; 172 is still unresolved.

**F22. Trade 143 entered on the previous 5m bar because of a 2 ms race.** (PROJECT EVIDENCE: code + data; the exact 5m ID used is still unconfirmed)
- The 22:40 boundary produced two signals:
  - 1m 159408 at 22:40:01.633945;
  - 5m 159407 (22:35 candle, **WATCH**, BREAKOUT) at 22:40:01.635944, which is 2 ms *later*.
- How the 5m signal is chosen:
  - `setupTimeframeAtrAuthoritySignal` takes the latest 5m with `generated_at ≤ current.generatedAt` (`ExecutionIntelligenceService.java:1485`, `:2608`).
  - So 159407 was excluded, and the only qualifying 5m BUY is 159285 (22:30 candle, generated at 22:35:01.55). The execution message calls this "the fresh 5m BUY" (wallet_trade 358).
- At 20:55, trade 137 won the same race: the 5m signal (156721) was generated 18 ms *before* the 1m signal, and the audit confirms it was used (DBQ-CLAUDE-I2-002, row 1938).
- What this means:
  - Whether the just-closed 5m candle counts at a 5m boundary depends on millisecond ordering between concurrent analysis threads.
  - Replay uses as-of `generated_at` (`TradeExecutionValidationService.java:372-378`), so it may not reproduce this race. That is a Replay-parity risk.
- Classification: a **candidate logic/timing defect**. It turns F14's hypothesis into a mechanism.

**F25. Every wallet transaction spends about 2 s on a portfolio snapshot.** (PROJECT EVIDENCE: code + post-window timing log; the attribution to these trades is AGENT INFERENCE)
- **Where the time goes in code:**
  - `executeMechanicalExit` sets `executedAt`, then runs `currentPortfolioValue()` and `captureSnapshot()` (`WalletAutoExecutionService.java:548-560`).
  - Those call `currentPrice()` once per wallet asset (`WalletService.java:607`). Each call runs `SELECT * FROM candle … ORDER BY close_time DESC LIMIT 1`, but the candle index is on `open_time`, not `close_time`.
  - Only after that does `closePaper` stamp `closed_at` (`LivePositionProtectionService.java:405`).
- **Supporting timing from after the study window:** in `database-timing.log:119-1239`, transaction `41cf3d85` ran 17 or more of these queries back to back. Each took 19–323 ms, about 1.7 s in total.
- **This matches the gaps in the trade data** (wallet `executed_at` → paper `closed_at`/`opened_at`): 1.98 s for 182's exit, 2.24 s for 182's entry, 2.2 s for 162's entry.
- **Risk:** this snapshot work runs inside the ~30 s `PROTECTION_TRANSACTION` on the WebSocket thread (`KlineTransactionCoordinator.java:57`). That stalls kline intake by about 2 s per exit.
- It doesn't explain any of the six losses.

- Comparisons below 200 ms between local and exchange timestamps are unreliable. For example, 137's exit appears to execute *before* its trigger tick was observed. Use local timestamps only for local ordering.
