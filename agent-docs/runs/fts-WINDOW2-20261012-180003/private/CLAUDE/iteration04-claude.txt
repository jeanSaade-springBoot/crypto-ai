## FINDINGS

**F31. The study's database timestamps appear to be shown in KSA, not UTC. Every earlier "UTC → KSA" label is likely 3 h too late.** (PROJECT EVIDENCE; root cause is AGENT INFERENCE until DBQ-CLAUDE-I4-001/002)

- **Where the true UTC comes from:** each wallet BUY message contains `priceObservedAt=<Instant>Z`. The app writes this from `rs.getTimestamp("observed_at").toInstant()` (`PaperTradingService.java:383`, `MarketPriceEventService.java:133-145`).
  - The app's connection is pinned to UTC: `connectionTimeZone=UTC`, `forceConnectionTimeZoneToSession`, `preserveInstants`, and `SET time_zone='+00:00'` (`application.yml:13-35`).
- **What the query results show:** the same column, `wallet_trade.execution_price_observed_at` (DBQ-CLAUDE-I1-003), is exactly 3 h later in all six trades:

| Trade | Message (true UTC) | Query result |
|---|---|---|
| 137 | `17:55:00.032Z` | 20:55:00.032 |
| 143 | `19:40:01.028Z` | 22:40:01.028 |
| 158 | `23:35:00.328Z` | 02:35:00.328 |
| 162 | `01:02:02.580Z` | 04:02:02.580 |
| 172 | `03:36:01.457Z` | 06:36:01.457 |
| 182 | `06:57:02.437Z` | 09:57:02.437 |

- **Likely mechanism:** the time columns are `TIMESTAMP(6)` (`B105…baseline.sql:21,151,187-188,656,1445`). MySQL shows TIMESTAMP values in the *session* time zone.
  - The read-only query wrapper rejects `SET` (`DATABASE_INVESTIGATION_RULES.md:27`), so the query session runs on the server default.
  - That default is most likely SYSTEM on a UTC+3 host; the local startup logs show `+03:00` offsets (`logs/fix145-startup.log:22`).
- **What is affected:**
  - Durations, the order of events, and millisecond races are unaffected.
  - Every absolute label in F1, F16 and the F21/F28 tables is wrong.
  - The iteration-3 log-request windows are 3 h too late.
  - The rule "raw DB timestamps are UTC" in `DATABASE_INVESTIGATION_RULES.md:35` and the study prompt does not hold for this access path.
- **Handling:** I'm reporting the contradiction rather than silently accepting either side.
- **How times appear below:** all times are **DB-display** values. The true UTC is DB-display − 3 h (this is the instant the app itself recorded), and the true KSA is the DB-display value. Trade 137, for example, entered at 17:55:03 UTC → 20:55:03 KSA.

**F33. The SETUP_TIMEFRAME_ATR route (trade 143) skips every check `validateBuy` applies.** (PROJECT EVIDENCE: code; impact on 143 is PROJECT EVIDENCE + AGENT INFERENCE)

- **What the code does:** `:628-641` returns before `validationService.validateBuy` at `:653` is reached. `setupTimeframeAtrAuthoritySignal` (`:1472-1492`) checks only three things:
  - the 1m is not bearish;
  - the latest 5m with `generated_at` at or before the 1m is BUY, final-allowed and ATR-immediate;
  - the 1h is not bearish. A missing 1h is allowed.
- **What it therefore skips:**
  - the FIX-154 higher-timeframe assessment. DBQ-CLAUDE-I3-003 has no audit row for 159408 or 159285; the only rows in that window belong to a different reference, 159410.
  - the FIX-112A consumed-BUY check (`TradeExecutionValidationService.java:67-79`);
  - the required fresh 1h context.
- **The 5m BUY was reused for a second entry:**
  - The previous EGLD position (171) entered through the same route at 22:36:03 DB-display (19:36:03 UTC), from signal 159321.
  - The only 5m signal generated between 22:35:01 and 22:40:01 is 159285, so both entries must have relied on it. That is AGENT INFERENCE until DBQ-CLAUDE-I4-004.
  - Position 171 profit-locked out at 22:39:41. Trade 143 then re-entered 21 s later, 0.043 higher (3.990 → 4.033), on the same 5m authority.
- **No re-entry cooldown exists:** a search of production `src/main/java` for `cooldown|reentry|re_entry|lastExit|recentlyClosed` finds only REST-gate, monitor and replay-service matches.
- **The 5m signal was already visible:** 159407 (WATCH) was committed at 22:40:02.94, before 143's fill at 22:40:03.115. The route still excluded it, because it filters on `generated_at ≤ 1m.generated_at`, and 159407 was generated 2 ms later (F22).
- **F22's mechanism is now confirmed:** the issue is the selection rule, not commit visibility.
- **Classification:** confirmed **route-design gap**. Re-entry chasing on a consumed or stale 5m authority is a logic defect candidate for 143. Whether it is intended is a design question; the code comments say only "neutral 1m is timing-neutral".

**F34. The ACCUMULATED_EVIDENCE route (162) allows a BALANCED_EARLY + LATE_ENTRY combination that the direct route blocks.** (PROJECT EVIDENCE)

- The FIX-041 guard (`ExecutionIntelligenceService.java:672-684`) blocks direct BUYs that have BALANCED_EARLY authority and a LATE_ENTRY classification.
- The comment at `:668-670` explicitly exempts accumulated evidence.
- Trade 162 entered on exactly that combination: a 1m WATCH, authority `BALANCED_EARLY`, `Entry Quality 50/100 (LATE_ENTRY)` (wallet_trade 403).
- **Classification:** the code does what it was written to do. A weaker signal (WATCH) gets a looser price-quality gate than a fresh BUY would. This is a candidate design inconsistency, not a defect against the coded rules.

**F35. The 5m-versus-1m race decides the route in both directions.** (PROJECT EVIDENCE)

- At 5m boundaries, the 1m and 5m signals run as separate analysis jobs, so which one gets the earlier `generated_at` is down to milliseconds:
  - **137:** the 5m was 18 ms earlier, so the 5m NEUTRAL counted.
  - **143:** the 5m was 2 ms later, so the stale 5m BUY counted.
  - **158:** the 1m was 21 ms earlier, so the wake-up found a current 1m (`:420-428`). Had the 1m been later, the wake-up would have returned `none()` and the 1m's own direct path would have rejected a WATCH.
- **Existing fix pattern:** FIX-141 already fixed the same class of problem for BTC context by selecting on candle time (`ExecutionReplayScope.java:122-137`).
- **Replay:**
  - `ExecutionReplayScope.latestAtOrBefore` uses the same `generated_at` filter as production (`:106-120`). Replay over *stored* production signals should therefore reproduce these choices.
  - Replay that *regenerates* signals assigns its own `generated_at` (`appendSignal`, `:99-104`), so it may not reproduce the race. That part is AGENT INFERENCE.
- This refines U7.
