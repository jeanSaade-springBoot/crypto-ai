# Iteration 2 of 8: database forensics (Claude, self-review only)

All six frozen trades now have a reconstructed timeline from my 11 iteration-1 query results plus code tracing. Every exit followed the coded rules. The losses come mainly from three entry-side mechanisms, which apply across trades:

- **Risk/reward:** a risk/reward that is structurally below 1 is allowed through with no gate.
- **Fees:** take-profit targets are about the size of the round-trip fee.
- **Masked bearish signals:** bearish 5m signals are rewritten as NEUTRAL, so the 5m BUY veto can't see them.

Nothing was changed: no code, config, database writes, git or deploy. I didn't read the Codex folders, LIVE_TEAM_STATUS or LIVE_EVENTS.

Timestamps are written as raw UTC → KSA (UTC+3). The execution time I use is `wallet_trade.executed_at`. `paper_position.opened_at/closed_at` lag it by about 2 s (for example, trade 182's sell executed at 10:05:18.50 but the position shows closed at 10:05:20.49). I'm correcting the iteration-1 F1 times to the wallet times.

## FINDINGS

**F9. Risk/reward is below 1 by construction whenever ATR is under about 0.167% of price, and nothing blocks it** (PROJECT EVIDENCE)
- How the levels are computed (`AtrRiskService.java:34-45`):
  - stop distance = max(2×ATR, 0.5% of price);
  - target distance = 3×ATR, with no floor.
  - Settings come from `application.yml:137-143`; the stored values match these defaults exactly.
- What was recorded (DBQ-CLAUDE-I1-002, `risk_reward_ratio`):

  | Trade | R:R |
  |---|---|
  | 137 | 0.644 |
  | 158 | 0.327 |
  | 162 | 0.438 |
  | 172 | 0.744 |
  | 182 | 0.482 |
  | 143 | 1.50 (the only one where 2×ATR beat the 0.5% floor) |

- Worked example, trade 158: target = 1.4109 + 3×0.00076962 = 1.413209 ✓. Stop = 1.4109 × 0.995 = 1.403846 ✓.
- `riskRewardRatio` is only read by the dashboard and inspector (`DashboardApiController:1203,1312,1373`, `TradeInspectorService:1099`). No decision code reads it.
- The explanation text "Stop uses 2.0 ATR" is wrong whenever the 0.5% floor applies.

**F10. Target distances are about the same as the round-trip fee** (AGENT INFERENCE + EXTERNAL RESEARCH, not re-verified in this iteration)
- Target distance as % of entry: 137 0.32%, 158 0.16%, 162 0.22%, 172 0.37%, 182 0.24%.
- Binance's standard spot taker fee is 0.1% per side, so about 0.2% round trip.
- All wallet rows record `fee_usdt = 0` (DBQ-CLAUDE-I1-003).
- So even a take-profit hit would have netted roughly zero after fees on 158, 162 and 182.
- Estimated losses after fees (0.1% on each side's notional): the six total about −0.53 USDT, against −0.273 recorded.

**F11. The 5m BUY veto can't see 5m bearishness that confluence has rewritten as NEUTRAL** (PROJECT EVIDENCE for the data and code; the per-signal branch needs DBQ-CLAUDE-I2-001)
- `HigherTimeframeBuyAssessmentService.java:20-24` vetoes on `getDecision()`, which is the final decision after confluence.
- `MultiTimeframeConfluenceService.java:136-138` rewrites a bearish signal to NEUTRAL whenever a higher-timeframe context counts as "bullish".
- A context counts as bullish when its decision is BUY/STRONG_BUY **or** its trend score is ≥15 (`:337-338`). So a 1h WATCH with trend 16 counts.
- **Trade 182 (ACEUSDT), DBQ-CLAUDE-I1-007:**
  - 11 consecutive 5m bars, from the 09:00 candle to the 09:50 candle (12:00–12:50 KSA), had `original_decision` SELL or STRONG_SELL. All were published as NEUTRAL (175399 … 176655).
  - The 1h context during that time was 175258, WATCH with trend 16/25.
  - Entry was at 09:57:04 → 12:57:04 KSA, with 5m showing "NEUTRAL".
  - As soon as the 1h became NEUTRAL (176791, 10:00:06 → 13:00:06 KSA), the next 5m was published as STRONG_SELL (176934, 10:05:03.9 → 13:05:03 KSA). That closed the trade at 10:05:18.5 → 13:05:18 KSA.
- The same masking shows up on 1m signals before 162 and throughout 158 (`original_decision`=SELL, `decision`=NEUTRAL).
- Classification: a candidate logic defect, in that the veto is blind to suppressed bearish evidence. FIX-154's "preserve legacy 5M_BEARISH_VETO" rule may make this behaviour intended, so I'm not calling it confirmed.

**F13. Trade 143: the loss came from one tick jumping straight through the profit-lock floor** (PROJECT EVIDENCE, DBQ-CLAUDE-I1-004/006/009)
- Entry was at 22:40:03.1 → 10-12 01:40:03 KSA, at 4.033. The decision price was 4.032, so one tick of slippage.
- The profit lock activated at 22:40:23 → 01:40:23 KSA. The take-profit was extended twice: 4.0647 → 4.0805 → 4.1043.
- The high was 4.101, with the lock at 4.07579.
- Price events went from 4.100 at 22:43:27.04 straight to **4.027 at 22:43:35.02** (→ 01:43:35 KSA), with nothing in between. That one tick was below the lock (4.0758), below the hard floor (4.03502 = entry × 1.0005), and below entry.
- The fill was at that tick price, 4.027. The exit code behaved as written.
- The loss is inherent to a model that fills at the next tick and never holds a resting stop order. It is not a logic defect.
