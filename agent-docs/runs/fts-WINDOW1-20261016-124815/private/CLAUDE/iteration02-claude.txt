### F-I2-02 — Structural risk/reward inversion: stop is floored at 0.5%, target is not (PROJECT EVIDENCE, code + DB)

`AtrRiskService.java:34-45` computes `stopDistance = max(2×ATR, 0.5% × price)` but sets `takeProfit = price + 3×ATR` with no matching floor. The floor comes from `application.yml:143`, `minimum-stop-percent: 0.50`. When ATR is below 0.25% of price, the stop is wider than the target.

| Pos | ATR% | SL distance | TP distance | R:R |
|---|---|---|---|---|
| 182 | 0.080 | 0.500% (6.2 ATR) | 0.241% | **0.48** |
| 172 | 0.124 | 0.500% | 0.372% | **0.74** |
| 162 | 0.073 | 0.500% | 0.219% | **0.44** |
| 158 | 0.055 | 0.493% (from fill) | 0.171% | **0.35** |
| 137 | 0.107 | 0.500% | 0.322% | **0.64** |
| 143 | 0.270 | 0.565% | 1.768% | 3.13 (TP differs from signal TP; see U-05) |

- I found no minimum-R:R gate in the code. `riskRewardRatio` is only computed and persisted (`AnalysisService.java:540`). This is AGENT INFERENCE from a Grep search and needs confirmation in a later iteration.
- The entry text says "Stop uses 2.0 ATR". For 5 of the 6 positions this is false, because the floor overrode it.

**Classification (AGENT INFERENCE):** the code behaves as written. This is a strategy/risk-geometry design issue, not a runtime defect.

### F-I2-03 — Fee-adjusted outcome (EXTERNAL RESEARCH + AGENT INFERENCE)

Automatic trades record `fee_usdt = 0` (I1-006; TRADING_RULES §6). At the standard Binance spot rate of 0.10% per side (from third-party sources; I did not reach Binance's own fee page):

- **Target hits would barely pay:** the net gain at TP would be only 0.02% for 162 and 0.04% for 182. For 158 it would be −0.03%, a net loss even on a full TP hit.

### F-I2-04 — Position 143: a trade that reached 95% of its target closed at a loss (PROJECT EVIDENCE + open question)

**What the records show:**
- The audit (I1-003) says progress reached 95.35% of TP distance, implying a high near 4.101 (+1.69%).
- The lock level was 4.0758, which is about +1.06% locked.
- The exit was at **4.027**. That is below the hard floor of 4.0350165 (= entry × 1.0005) and below entry.
- The explanation text matches `LivePositionProtectionService.java:207-217`: the lock-triggered branch, where price is below the hard floor.

**Code expectation:** at the 1h=NEUTRAL recorded at entry, any tick between 4.035 and 4.0758 after the trigger should have produced a `PROFIT_LOCK_EXIT` (`PositionExitPolicy.java:52-92`). A `PROFIT_LOCK_HOLD` happens only if 1h was BUY/STRONG_BUY, or 1h was WATCH with 5m supportive and 1m not bearish.

**Open question:** two explanations fit the data:
- (a) 1h/5m changed to a HOLD-eligible state, and the position held through the lock.
- (b) Prices gapped from at least 4.0758 straight to 4.027 between ticks. EGLD averaged about one event per 3.3 s.

This is the top **defect candidate** and needs the I2-004/005/006/008 results.

**Context:** wallet_trade 357 closed the previous EGLD position (wallet 171) with PROFIT_LOCK_EXIT at 3.996 at 22:39:41 UTC (01:39:41 KSA). Its lock was 4.0255, so that exit was also about 0.73% below the lock level. Position 143 opened **19 s later at 4.033** (+0.93%). That entry came from a WATCH signal at RSI 84.3, 4.35 ATR above SMA20, with RVOL 21.9; the 1m plan said WAIT_FOR_RETRACEMENT at 0%. The SETUP_TIMEFRAME_ATR route overrode it using the 5m ATR. I have not checked for a same-symbol re-entry cooldown (U-06).

### F-I2-05 — Positions 172 and 182: ATR at or below tick size (AGENT INFERENCE from DB prices)

- **SHIBUSDT (172):** observed prices moved only between 5.48e-6, 5.49e-6 and 5.50e-6, which implies a 1e-8 tick, or 0.18% per tick. ATR14 was 6.8e-9, **less than one tick**. In practice TP 5.5104e-6 needs 5.52e-6 (+3 ticks, +0.55%) and SL needs 5.46e-6 (−3 ticks). The exit at 5.48e-6 was exactly −1 tick.
- **ACEUSDT (182):** prices stayed in the 0.1880–0.1884 band (33 events). The position **never traded above entry**.

ATR-based levels are not meaningful at this granularity. This is to be confirmed with the distinct-price query I2-003.

### F-I2-08 — Lineage gaps (PROJECT EVIDENCE; not loss causes)

- **Missing exit_signal_id:** `paper_position.exit_signal_id` is NULL for all five live-path exits. `closePaper` never sets it (`LivePositionProtectionService.java:391-411`). Only the audit's `source_signal_id` keeps the link.
- **Work row not linked (158):** `signal_processing_work` for 165412 has `paper_position_id = NULL` and completed at 02:35:02.882, *before* the wallet BUY. The entry came from the 5m wakeup (165415), not this work item.
- **Advisory analysis said HOLD:** the audit's `position_recommendation` was HOLD for 5 exits that the live policy closed anyway. Two exit authorities disagreed; the advisory one was not used.
- **Close-time gap:** `closed_at` is `Instant.now()`, written 1.2–3.2 s after the wallet SELL on the live path. Whether that time is spent inside the protection transaction on the socket thread is unknown (U-08).

### DB_REQUEST
QueryId: DBQ-CLAUDE-I2-003
Purpose: Post-entry-only price excursion, distinct-price granularity, non-APPLIED events, and the time of the first high.
SQL:
SELECT x.*, (SELECT MIN(m2.observed_at) FROM crypto_ai.market_price_event m2
             WHERE m2.symbol = x.symbol AND m2.price = x.max_price
               AND m2.observed_at BETWEEN x.opened_at AND x.closed_at) AS first_at_max,
       (SELECT MIN(m3.observed_at) FROM crypto_ai.market_price_event m3
             WHERE m3.symbol = x.symbol AND m3.price = x.min_price
               AND m3.observed_at BETWEEN x.opened_at AND x.closed_at) AS first_at_min
FROM (
  SELECT pp.id, pp.symbol, pp.entry_price, pp.stop_loss, pp.take_profit, pp.opened_at, pp.closed_at,
         COUNT(*) AS events, COUNT(DISTINCT mpe.price) AS distinct_prices,
         SUM(mpe.delivery_status <> 'APPLIED') AS non_applied,
         MIN(mpe.price) AS min_price, MAX(mpe.price) AS max_price,
         MIN(mpe.observed_at) AS first_obs, MAX(mpe.observed_at) AS last_obs
  FROM crypto_ai.paper_position pp
  JOIN crypto_ai.market_price_event mpe
    ON mpe.symbol = pp.symbol AND mpe.observed_at BETWEEN pp.opened_at AND pp.closed_at
  WHERE pp.id IN (182,172,162,158,143,137)
  GROUP BY pp.id, pp.symbol, pp.entry_price, pp.stop_loss, pp.take_profit, pp.opened_at, pp.closed_at
) x
ORDER BY x.id DESC;
### END_DB_REQUEST

### DB_REQUEST
QueryId: DBQ-CLAUDE-I2-005
Purpose: The latest 1m/5m/1h signals at or before each entry and exit, to check the exit policy inputs and HTF freshness.
SQL:
WITH anchors AS (
  SELECT id AS pid, symbol, 'ENTRY' AS phase, opened_at AS t FROM crypto_ai.paper_position WHERE id IN (182,172,162,158,143,137)
  UNION ALL
  SELECT id, symbol, 'EXIT', closed_at FROM crypto_ai.paper_position WHERE id IN (182,172,162,158,143,137)
), ranked AS (
  SELECT a.pid, a.phase, a.t, ts.interval_code, ts.id AS signal_id, ts.candle_open_time, ts.generated_at,
         ts.decision, ts.original_decision, ts.total_score, ts.confidence_score, ts.market_regime,
         ts.signal_mode, ts.data_quality_valid, ts.final_entry_allowed, ts.latest_price,
         TIMESTAMPDIFF(SECOND, ts.generated_at, a.t) AS age_seconds,
         ROW_NUMBER() OVER (PARTITION BY a.pid, a.phase, ts.interval_code
                            ORDER BY ts.generated_at DESC, ts.id DESC) AS rn
  FROM anchors a
  JOIN crypto_ai.trade_signal ts
    ON ts.symbol = a.symbol AND ts.interval_code IN ('1m','5m','1h')
   AND ts.generated_at <= a.t AND ts.generated_at >= a.t - INTERVAL 3 HOUR
)
SELECT * FROM ranked WHERE rn = 1 ORDER BY pid DESC, phase, interval_code;
### END_DB_REQUEST
