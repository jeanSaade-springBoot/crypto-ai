### F-I3-02: Position 143 was not an ingestion or protection-latency failure. It was a 680 ms flash drop (EXTERNAL RESEARCH + PROJECT EVIDENCE).

- **No missed ticks:** there were no trades from 19:43:26.04 to 19:43:34.341 UTC. So there were no kline updates to receive, and no ticks were lost between DB 22:43:27 and 22:43:35.
- **The drop:** 95 trades fell from 4.097 to 4.025 between 34.341 and 35.021.
  - Price first reached ≤4.075 (the lock 4.0758) at **34.816**.
  - It first went below the 4.035 floor at **34.993**.
  - The lock-to-floor band existed for about **177 ms** of market time.
- **Reaction time:** the next kline push (observed 35.021, stored 35.030) triggered the wallet SELL at 35.046. That is about 25 ms from tick to decision.
- **Fill realism:** the paper fill of 4.027 matches the market prints (4.024–4.034).
- **Resolved I2 open question:** explanation (b) in F-I2-04, a gap between ticks, is confirmed. A PROFIT_LOCK_HOLD is ruled out.
- **The decision that mattered (PROJECT EVIDENCE):** `position_management_event` 51/52 shows the original TP 4.0647 was reached at 22:40:41 KSA (4.067). It was converted into a **TAKE_PROFIT_EXTENDED** (continuation PASS) rather than an exit, and extended again at 4.081 (`LivePositionProtectionService.java:100-164`).
  - This also resolves U-05: the wallet TP 4.1043 comes from two extensions.
  - Classification: the outcome follows policy, not a timing defect. Exiting at TP would have locked about +0.84%.
- **Prior position 171:** its exit at 3.996 was a real wick. Price went from 4.053 to 3.990 between 19:39:39.14 and 19:39:40.84 UTC, then recovered to 4.021 by 42.1.

### F-I3-03: Tick gaps mean "no trades," not lost data (EXTERNAL RESEARCH + AGENT INFERENCE)

- **Docs vs observation:** Binance documents a 2000 ms kline update speed. In both EGLD windows I checked, missing seconds lined up with periods of no trades.
- **Inference:** pushes appear to happen only when the candle changes.
- **Consequence:** sparse symbols get sparse protection evaluations. ACE had 30 events in 8 min and SHIB 200 in 40 min (I2-003).
- **Code basis:** every 1m message writes a price event and runs protection (`BinanceKlineService.java:101-111`). So event cadence equals the cadence at which protection is evaluated.

### F-I3-04: Live-path exits wait for the next tick after bearish confirmation (PROJECT EVIDENCE + AGENT INFERENCE)

Exit policy reads the latest committed signal for each interval (`LivePositionProtectionService.java:95-97`), and it only runs on a price tick.

| Pos | Last needed signal generated (displayed) | Exit tick → wallet SELL (displayed) | Wait |
|---|---|---|---|
| 182 | 5m STRONG_SELL 176934, 10:05:03.93 | 10:05:18.446 → 18.504 | about 14.5 s |
| 172 | 5m NEUTRAL 172588, 07:15:04.58 | 07:15:43.46 → 43.49 | about 39 s |
| 158 | 5m SELL 166821, 03:30:01.46 | → 03:30:04.22 | about 2.8 s |
| 137 | 1h NEUTRAL 156853, 21:00:02.97 | → 21:00:08.94 | about 6 s |

- **Signal visibility:** signals become visible about 1.3 s after `generated_at`.
- **Cost:** 172 and 182 exited at the same price that was already showing, so the delay cost nothing here.
- **Classification:** this is a latent latency property for illiquid symbols, not a cause of these losses. The tick sequences are requested in I3-005.

### F-I3-05: The entry pipeline is fast and consistent (PROJECT EVIDENCE: I1-004/005/006)

All six entries follow the same sequence:

1. Candle close → `generated_at`: 1.47–2.81 s.
2. → signal `created_at`: +1.31–1.34 s (182: +2.28 s).
3. → work registration: +4 ms (`next_attempt_at − 30 s`, `SignalProcessingStore.java:61`).
4. → wallet BUY: +0.07–0.17 s.
5. → paper open: **+1.5–2.25 s**.

- **Correction to I2:** the fill price's age at BUY is up to **2.99 s** (137), not 2.66 s. That is still inside the 15 s rule.
- **Freshness:** no stale-data or execution-delay defect was found.

### F-I3-06: Wallet → paper gap of 1.2–3.2 s inside the protection transaction (PROJECT EVIDENCE for the code path; the cost is a HYPOTHESIS)

- **Measured gap:** exit `wallet_trade.executed_at` → `paper_position.closed_at` was 1.98 / 1.99 / 2.42 / 1.18 / 3.19 s (182 / 172 / 158 / 143 / 137).
- **What runs in that gap:** after the SELL row is stamped, `executeMechanicalExit` re-locks `daily_statistics FOR UPDATE` and calls `currentPortfolioValue()` + `captureSnapshot()` (`WalletAutoExecutionService.java:553-560`). Each of those iterates every `wallet_asset` and does a per-asset candle lookup (`WalletService.java:484-490, 600-607`). Only then does `closePaper` run.
- **Where it runs:** all of this is inside the `@Transactional` protection call, executed synchronously on the WebSocket handler thread (`BinanceWebSocketHandler.java:62`, `KlineTransactionCoordinator.java:57`).
- **Risk:** while that runs, ingestion and protection for other symbols can stall, and the global daily-stats row lock is held.
- **Classification:** not a cause of the six losses (exit prices were fixed at the trigger). It is a systemic risk candidate.
- **How to confirm:** `fix129_stage_timing` persists any stage ≥1000 ms (`KlineTiming.java:46`, `KlineTimingStore.java:41`). See I3-002/003/004.

### F-I3-07: The JVM clock appears to run behind Binance (AGENT INFERENCE, minor)

- **Signals generated before candle close:** five 1m signals have `generated_at` before their candle's close, for example XRP 03:02:59.987 and EGLD 20:52:59.987 (displayed).
- **Why that implies skew:** `generated_at = Instant.now()` at analysis start (`AnalysisService.java:150`), and analysis is dispatched only on a Binance closed kline (`BinanceKlineService.java:110`).
- **Supporting sign:** the lowest ingest lag is 0.29 ms (event 1788822), which is below plausible network latency.
- **Classification:** no look-ahead; not a loss cause. See I3-006.

### F-I3-08: Analysis slows at 5m/1h boundaries (PROJECT EVIDENCE)

- At :00/:05 boundaries the 1m analysis starts 1.4–9.2 s after close. The worst case is DOGE 167615 at 9.2 s, on the hour.
- This is within the 90 s freshness rule.

### DB_REQUEST
QueryId: DBQ-CLAUDE-I3-004
Purpose: Cross-symbol ingestion lag during each exit's wallet→paper window (does a protection transaction stall other symbols?).
SQL:
SELECT w.pos, COUNT(*) AS events, COUNT(DISTINCT m.symbol) AS symbols,
       MAX(TIMESTAMPDIFF(MICROSECOND, m.observed_at, m.created_at))/1000 AS max_lag_ms,
       SUM(TIMESTAMPDIFF(MICROSECOND, m.observed_at, m.created_at) > 500000) AS lag_over_500ms,
       SUM(m.delivery_status <> 'APPLIED') AS non_applied
FROM (SELECT 182 pos, '2026-10-12 10:05:17' a, '2026-10-12 10:05:24' b UNION ALL
      SELECT 172, '2026-10-12 07:15:42', '2026-10-12 07:15:48' UNION ALL
      SELECT 158, '2026-10-12 03:30:03', '2026-10-12 03:30:09' UNION ALL
      SELECT 143, '2026-10-11 22:43:34', '2026-10-11 22:43:39' UNION ALL
      SELECT 137, '2026-10-11 21:00:07', '2026-10-11 21:00:15') w
JOIN crypto_ai.market_price_event m ON m.observed_at BETWEEN w.a AND w.b
GROUP BY w.pos ORDER BY w.pos DESC;
### END_DB_REQUEST

### DB_REQUEST
QueryId: DBQ-CLAUDE-I3-006
Purpose: Clock-skew and boundary-latency distribution: ingest lag, and 1m signals generated before candle close.
SQL:
SELECT 'INGEST_LAG' metric, COUNT(*) n,
       MIN(TIMESTAMPDIFF(MICROSECOND, observed_at, created_at))/1000 min_ms,
       AVG(TIMESTAMPDIFF(MICROSECOND, observed_at, created_at))/1000 avg_ms,
       MAX(TIMESTAMPDIFF(MICROSECOND, observed_at, created_at))/1000 max_ms,
       SUM(created_at < observed_at) negatives
FROM crypto_ai.market_price_event
WHERE observed_at BETWEEN '2026-10-11 20:50:00' AND '2026-10-12 10:10:00'
UNION ALL
SELECT 'SIG_1M_CLOSE_TO_GEN', COUNT(*),
       MIN(TIMESTAMPDIFF(MICROSECOND, candle_open_time + INTERVAL 60 SECOND, generated_at))/1000,
       AVG(TIMESTAMPDIFF(MICROSECOND, candle_open_time + INTERVAL 60 SECOND, generated_at))/1000,
       MAX(TIMESTAMPDIFF(MICROSECOND, candle_open_time + INTERVAL 60 SECOND, generated_at))/1000,
       SUM(generated_at < candle_open_time + INTERVAL 60 SECOND)
FROM crypto_ai.trade_signal
WHERE interval_code='1m' AND generated_at BETWEEN '2026-10-11 20:50:00' AND '2026-10-12 10:10:00';
### END_DB_REQUEST

### DB_REQUEST
QueryId: DBQ-CLAUDE-I3-007
Purpose: Wallet snapshot timing vs wallet trade and paper times (where the 1.2–3.2 s goes), and the wallet_asset row count.
SQL:
SELECT wt.id AS wallet_trade_id, wt.symbol, wt.side, wt.executed_at, wt.created_at,
       (SELECT MIN(s.captured_at) FROM crypto_ai.wallet_snapshot s
         WHERE s.captured_at BETWEEN wt.executed_at AND wt.executed_at + INTERVAL 10 SECOND) AS first_snapshot_after,
       (SELECT COUNT(*) FROM crypto_ai.wallet_asset) AS wallet_asset_rows
FROM crypto_ai.wallet_trade wt
WHERE wt.id IN (451,454,426,429,403,407,392,401,358,359,344,346)
ORDER BY wt.id;
