RPR-0.4 stays rejected, and the response still isn't enough to write the next specification from. Most of Codex's claims hold. This round I found a source defect that neither document mentions, corrected one claim that both agents made, and corrected seven points in my own Round 3.

Three things change the picture:

1. **Replay signals have no IDs.** Replay never saves the signals it regenerates, so every Replay signal's ID is null. Two shared rules depend on that ID. As a result, the near-TP partial harvest can never happen in Replay, and the BUY-continuation block never applies. Unit tests hide this because their test signals are given explicit IDs.

These can partly verify entry decisions made while Production held no position in the symbol.

### 3. New findings

**N17: Replay signals have null IDs, which disables two shared rules in Replay.** [PE]

- **Why the IDs are null.**
  - Replay builds its signals through `buildSignal`, which never sets an ID (`AnalysisService:183-196, 550-551`). The ID is assigned only when the database saves the row (`TradeSignal:14-15`).
  - Replay inserts its rows with plain SQL and never reads a key back (`RegressionTestWorker:636-658, 741-768`).
  - No code in `src/main/java` assigns an ID to these signals.
- **(a) Near-TP partial harvest can't happen.**
  - The policy counts a 1m signal as new evidence only when `oneMinute.getId() != null` (`position/service/NearTpFailureProtectionPolicy:121-122`).
  - The bearish-signal streak therefore stays at 0, while a harvest needs a streak of 2 (`:29, 154-158`).
  - This affects both Replay price paths (`ShadowProductionReplayService:517-521, 674-676`). Production's signals have IDs, so Production can harvest (`LivePositionProtectionService:260-302`).
- **(b) The BUY-continuation block never fires.**
  - The check runs on Replay's direct-BUY path (`ExecutionIntelligenceService:653` → `TradeExecutionValidationService:67-78`).
  - Recording a null ID as consumed does nothing, and a null ID is reported as "not consumed" before the Replay branch is reached (`ExecutionReplayScope:85-92`; `EntryConsumptionPolicy:21`; `ShadowProductionReplayService:340, 362`).
- **(c) Audit gap.** Replay's `fix122_evaluation` rows have a NULL `signal_id` (`StopLossEvidenceService:145`). This affects audit only.
- **Why tests didn't catch it.** `src/test/.../Fix117NearTpExtensionStateTest:133` uses `.id(978L)`, and `ExecutionReplayScopeModeTest:57-66` uses explicit IDs.
- **Checked and not affected:** the list of supporting signal IDs in opportunity evidence is audit-only (`ExecutionIntelligenceService:2289-2299, 2353, 2711`).
- **[AI] Consequences.**
  - Any window where Production harvested at near-TP, or blocked a re-entry with BUY_CONTINUATION, cannot match in Replay today.
  - Existing Replay results don't demonstrate parity for these two rules.
  - `claude-docs/ARCHITECTURE.md:161` and `TRADING_RULES.md:106` imply parity that doesn't exist.
  - This comes from reading the code; I didn't run anything.

**N18: Replay's older-window (fallback) signal path uses a different order and adds a label check.** [PE]

- **Production's signal path:**
  1. take-profit;
  2. profit lock triggered, which closes the position **without checking signal labels**;
  3. stop-loss;
  4. rebase floor;
  5. SELL, which is suppressed while the lock is active.

  (`PaperTradingService:170-203`)
- **Replay's fallback path:**
  1. take-profit;
  2. stop-loss;
  3. lock update;
  4. rebase floor;
  5. lock triggered, then hard floor, then a **label check** (`evaluateProfitLockBreach`);
  6. normal exit;
  7. 1m SELL, with no lock suppression.

  (`ShadowProductionReplayService:562-666`) The comment at `:651-653` claims it uses the same order.
- [AI] **Effect.** When the price is at or below both the stop-loss and an active lock, Production records PROFIT_LOCK and Replay records STOP_LOSS. Only STOP_LOSS creates a FIX-122 stop boundary (`ExecutionReplayScope:49-50`; `StopLossEvidenceStore:41`), so later entries diverge too.

**N19: Opportunity memory carries long-lived state that Replay's warm-up can't rebuild.** [PE]

- Entry Quality sets its chase reference from the opportunity's start time (the anchor counts for 120 minutes) and from its anchor and best prices, which persist for the opportunity's whole life (`ExecutionIntelligenceService:898-951, 2549-2560`).
- Production closes the opportunity at every position exit and marks it on execution (`:789-809, 821-837`).
- Replay's 3-hour warm-up never trades, so neither happens (`ShadowProductionReplayService:286-303`).
- [AI] So a Production entry or exit up to about two hours before the window starts can change Entry Quality inside the window, even if the account holds nothing at the start.

**N20: Production already stores non-wallet evidence that can partly verify entry decisions.** [PE]

- **`fix122_evaluation`.**
  - Each FIX-122 initial-entry evaluation (`evaluateBuy` or a wake-up) writes a row. It records whether entry was allowed, the route, the result code, evidence counts, the position percentage and the stop boundary used (`StopLossEvidenceService:48-51, 140-157`).
  - A PRICE_RECHECK row is also written at execution-price revalidation (`:119-137`).
  - The row is written in its own transaction, so it survives a rollback. That write has a 2-second timeout, and a failed write is only logged (`StopLossEvidenceStore:24-35, 48-55`; `StopLossEvidenceService:157-159`).
  - `Fix122DiagnosticsController:38-45` already lists Replay and Production rows side by side.
- **`signal_processing_work`.**
  - It records each signal's processing status (completed, expired, review required and so on), its completion time, any failure stage, and a paper position ID (`SignalProcessingStore:101-124`).
  - For a symbol with no open position, a non-null position ID means that signal opened a position.
- **`buy_htf_assessment_audit`.** It records each FIX-154 higher-timeframe check result (`V107:8-38`; `V109:11-12`).
- **Limits.**
  - FIX-122 rows exist only while FIX-122 is enabled and the symbol has no open position.
  - Because writes are best-effort, nobody can prove the rows are complete.
  - Production also writes rows for 5m and 1h context-only calls that Replay never makes (`PaperTradingService:310` vs `ShadowProductionReplayService:271-284`), so a comparison must filter them out.
  - Some fields come from wallet data: the stop boundary (`stopExecutionId`, `stopAt`) and `paper_position_id`.
- [AI] Processing for one symbol is serialised by a symbol lock (`SignalProcessingCoordinator:71-77`). So `completed_at` could show the order in which Production processed signals at the same candle boundary. I haven't verified that every processing path takes that lock.

**N21: Production reads the newest committed signals, not those as of the signal's time.** [PE]

- Production's recent-signal lookup reads the 20 newest rows with no time bound (`ExecutionIntelligenceService:2601-2603`). Live protection also reads the newest 1m, 5m and 1h rows (`LivePositionProtectionService:95-97`).
- Replay limits both lookups to the reference time (`ExecutionReplayScope:106-120`).
- [AI] In normal live operation the two agree. They differ when processing is late or retried: newer rows then take places in Production's 20-row window and are filtered out, so Production uses fewer rows. This supports correction 4.
