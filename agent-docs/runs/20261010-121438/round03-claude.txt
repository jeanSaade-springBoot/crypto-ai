### 2. Corrections to my own Round 2

1. **N6 was overstated.** [PE] Replay's scope does contain the BTC signals, but they don't become visible at the same moment as in Production.
   - At an equal close boundary, Replay orders the BTC signal before the primary symbol's signal (`RegressionTestWorker:557-560`), and its lookup accepts a signal generated at exactly the reference time (`ExecutionReplayScope:129-136`).
   - Production sees the BTC signal only if its analysis was committed before the primary symbol's query (`BtcMarketContextService:77-86`).
   - So the visibility-time problem (N4) also covers BTC context.
2. **R-27 left out V106.** [PE] Three kinds of record start at V106 (`V106:2-10`):
   - the signal mode;
   - the candle's ingestion source and close token;
   - the price event's ordering slot and outcome reason.

   Before V106, Production's LIVE and HISTORICAL_ONLY signals can't be told apart.
3. **R-19 timing was imprecise.** [PE]
   - Production creates the daily budget row on the first `executeBuy` *attempt* of the UTC day. The row is created before sizing and stays even when sizing then declines (`WalletAutoExecutionService:97-109, 689-715`).
   - Replay recomputes the budget at the first *signal* of each UTC day (`ShadowProductionReplayService:292-299`).
4. **R-15 and R-16 missed the price-authority dependence.** [PE]
   - Production evaluates the profit lock on the signal path only when the signal's price is authoritative. Otherwise it treats the lock as inactive (`PaperTradingService:133-137`).
   - So even when a lock is persisted as active, a signal with a non-authoritative price is not stopped from selling (`:199`) and doesn't block a progressive add (`:217`).
   - Replay's exact-price add path has no lock gate at all (`ShadowProductionReplayService:342-366`).
5. **The "silent false" was imprecise.** [PE] When the wallet declines an initial entry, it is logged (`PaperTradingService:390-391`). When it declines a progressive add, nothing is logged (`:249-255`). Neither is stored in the database.
6. **N2 needs clarifying.** [PE]
   - FIX-154's "data quality" means only that the price is positive and the 20-, 50- and 200-period EMAs are present (`MarketContextService:74-75`). It is not the candle data-quality check (`CandleDataQualityService`).
   - Signals stored before V107 have NULL quality. A NULL-quality bearish 1h signal is rejected with `1H_BEARISH_VETO` (`HigherTimeframeBuyAssessmentService:27-28, 48`).
   - Replay regenerates the same 1h SELL with quality true, which is allowed as a SOFT_CONFLICT entry capped at 25% (`:33-34`).
   - So for up to 3 hours after V107, Replay can open entries that Production refused.

### 3. New findings

- **N7: Replay fills one price update earlier than Production.**
  - [PE] Replay takes the fill price from the last price event it consumed at or before the candle boundary (`ExecutionPriceAuthorityService:37-43`; `ShadowProductionReplayService:126-130, 310-311`). Each price event's time is Binance's event time `E` (`BinanceKlineService:94`).
  - [PE] Production looks up the price at wall-clock time, after live protection has already applied the candle's closing message (`PaperTradingService:342-343`; `BinanceKlineService:101-111`).
  - [AI] If the closing message's `E` falls after the boundary (likely, but not measured), Replay always fills at the last update before the close, while Production fills at the close price or later.
- **N8: Stored evidence can't identify the candle-closing message.**
  - [PE] `market_price_event` has no closed flag and no candle open time (`V64:4-13`; `V89:22-25`; `V106:5-8`).
  - [PE] Production runs protection before analysis specifically for the closing message (`BinanceKlineService:101-111`), so Replay can only infer which row that was.
  - [PE] A closing message that was rejected as stale leaves no row at all (`MarketPriceEventService:53-58`).
- **N9: Derivatives also change which strategy is selected.**
  - [PE] A crowded-longs or crowded-shorts market context selects the DEFENSIVE strategy (`MarketStrategyService:43-47`).
  - [PE] When derivatives are enabled, Replay's market-context result is always UNAVAILABLE (`MarketContextService:56-58`), so Replay can never take that branch.
  - Together with N1, derivatives affect three things: strategy selection, confidence (`FinalDecisionService:222, 270-279`), and the crowding veto (`DerivativesPositioningService:75-86`).
- **N10: A processing outcome changes later decisions, not just the current one.**
  - [PE] `evaluateBuy` saves opportunity memory to `execution_opportunity` (`ExecutionIntelligenceService:2621-2623`) inside the coordinator's transaction (`SignalProcessingCoordinator:64-103`).
  - [PE] An EXPIRED signal never reaches that step (`:99`). A daily-loss throw rolls the save back (`PaperTradingService:326, 552`; coordinator `:113-131`).
  - [PE] Replay always saves it.
  - [AI] So later wake-ups and evidence scores can diverge after any such outcome.
- **N11: FIX-122's stop history is account state.**
  - [PE] Production reads the most recent STOP_LOSS sell from `wallet_trade` (`StopLossEvidenceStore:37-45`).
  - [PE] Replay uses only its own stops (`StopLossEvidenceService:43-45`; `ExecutionReplayScope:49-59`). That list starts empty, because the 3-hour warm-up never trades (`RegressionTestWorker:51`; `ShadowProductionReplayService:286-303`).
  - [PE] Replay takes the FIX-122 on/off setting from the run request, not from Production's `trading.fix122.enabled` (`StopLossEvidenceService:32, 41`; `ShadowProductionReplayService:113-116`).
- **N12: The execution decision reads Production wallet-derived state.**
  - [PE] Besides N11, three other places do this:
    - The BUY_CONTINUATION check looks up an executed BUY in `wallet_trade` (`EntryConsumptionPolicy:29-30`; `TradeExecutionValidationService:67-78`).
    - Progressive adds read `wallet_managed_position` and `wallet_trade` (`PaperTradingService:218-233`).
    - Opportunity memory is read from `execution_opportunity` (`ExecutionIntelligenceService:2617`).
  - [AI] So parity at the analysis (signal) level doesn't depend on the account, but parity at the execution-decision level does.
  - [AI] Under strict isolation (decision U-2(a) below), neither execution-decision nor lifecycle parity can be verified for any window. Even proving that Production's account was flat at the window start needs those reads.
- **N13: Production and Replay record a different position open time, which changes price authority.**
  - [PE] Production records the open time as the wall clock at execution (`PaperTradingService:412`; `WalletAutoExecutionService:755-763`).
  - [PE] Replay records the execution signal's `generatedAt` (`ShadowProductionReplayService:333`). For a 5m wake-up, that is an earlier 1m signal's time.
  - [PE] The price-authority check compares a candle's close time with the open time (`PositionPriceAuthorityPolicy:23-30`).
  - Once R-15 is built, this difference decides which signal prices can trigger an exit.
- **N14: Another shared side effect.** [PE] Through the BTC-context path, Replay increments Production's context metrics, including Micrometer counters (`BtcMarketContextService:97-100`; `SignalContextMetrics:10-32`, which has no Replay check).
- **N15: Deployment records can't reconstruct the configuration.**
  - [PE] `process.json` stores the JAR's SHA-256 and the command-line overrides. It doesn't store the commit, the external `application.yml`, or environment variables (`scripts/deploy/Deploy-Trader.ps1:84, 123-142`).
  - [PE] The evidence copy is overwritten on every deploy (`:142`). Per-release copies survive only while their release folders are kept.
- **N16: claude-docs contradict the source.** [PE] Reported as AGENTS.md requires; not updated, since that isn't authorised this round.
  - `ARCHITECTURE.md:19` and `TRADING_RULES.md:124` say FIX-154 isn't implemented.
  - `ARCHITECTURE.md:24` lists migrations only up to V106.
  - `ARCHITECTURE.md:161` says Replay writes only `*_test` tables; it also writes `fix122_evaluation` (`StopLossEvidenceStore:48-55`). The same line lists `ReplayParityValidator` as in use.

**Paths checked and found equivalent** [PE]:
- **Entry stage:** Production passes the stored decision source as the "entry stage", while Replay derives it from the allocation. `progressivePositionDecision` never reads that value (`ExecutionIntelligenceService:1032-1143`).
- **FIX-154 audit table:** writes to it are skipped during Replay (`BuyHtfAssessmentAuditStore:43-44`). Only the counters leak.
- **Signal-path lock exit:** the "triggered" flag is recomputed from price alone on every evaluation (`ProfitLockPolicy:51`). So when live protection holds a lock breach, the signal path still closes the position at the next candle close at or below the lock. This confirms the response's "label-free" item (CR-03).
