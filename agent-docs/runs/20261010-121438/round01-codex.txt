## OBJECTIONS

- **PROJECT EVIDENCE:** The response is directionally correct but still insufficient as the sole requirements source for the next revision. It must explicitly carry forward a complete, deny-by-default live-I/O inventory: Binance, other HTTP clients, websocket/bootstrap paths, and indirect service calls. A parity run requires a test proving zero outbound calls, not only a statement that particular historical evaluators do not call Binance.

- **PROJECT EVIDENCE:** “Decision parity” needs a precise oracle registry. For each decision, the next specification must define the durable source record, its as-of timestamp, its availability timestamp, its lineage identity, the compared fields, and the result when those records are absent. A stored `trade_signal` alone does not prove processing, entry, protection, or committed exit.

- **PROJECT EVIDENCE:** The next specification must define the exact event sequencing contract for both live-price and signal paths. Timestamp sorting alone is inadequate because Production has separate protection and close-analysis transactions ([BinanceKlineService.java](C:\workspace\crypto-ai-trader-mysql\src\main\java\com\crypto\service\BinanceKlineService.java:101)); equal-time ordering needs durable event IDs/commit lineage or parity refusal.

- **PROJECT EVIDENCE:** The next revision must choose one first-release scope: single symbol/account with explicit multi-symbol refusal, or deterministic multi-symbol scheduling and atomic global-limit claims. RPR-0.4 proposes the latter without an executable design; the response appropriately identifies this but the replacement must settle it.

- **PROJECT EVIDENCE:** Baseline parity must suppress, not merely describe, the replay-only observers. They currently run in ordinary Replay and write replay observation data ([ShadowProductionReplayService.java](C:\workspace\crypto-ai-trader-mysql\src\main\java\com\crypto\regression\service\ShadowProductionReplayService.java:100), [line 173](C:\workspace\crypto-ai-trader-mysql\src\main\java\com\crypto\regression\service\ShadowProductionReplayService.java:173)). Retiring their data/UI remains a separate user product decision.

## UNKNOWNS

- **PROJECT EVIDENCE:** No read-only database/Flyway-history inspection was performed in this review. Therefore migration application state, checksums, and target-database compatibility remain unverified; the next specification must supply bounded read-only evidence.

- **PROJECT EVIDENCE:** No current complete Production-versus-Replay scenario suite demonstrates equality through initial entry, add, partial harvest, wallet controls, price protection, and final exit. Current tests/comments cannot substitute for that evidence.

- **AGENT INFERENCE:** Full lifecycle parity may be available only for a future evidence era, after availability-time capture and immutable configuration/version capture exist. Earlier windows should normally be simulation or explicit refusal, not a parity claim.
