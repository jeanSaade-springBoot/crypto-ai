## OBJECTIONS

- **PROJECT EVIDENCE:** Do not approve a next specification unless it includes these registered requirements:

  1. A frozen full-tree baseline, target deployment/version/configuration fingerprint, Flyway compatibility policy, and explicit resolution of code-versus-guidance contradictions.
  2. Pre-write parity eligibility: exact whole-window qualification before generated-signal, shadow-wallet, or certificate writes.
  3. A precise oracle registry: decision, execution, protection, exit, and terminal-work outcomes; durable record, identity, as-of/availability time, equality rule, and absent-evidence result.
  4. A strict read boundary: Production wallet/position/settings data never influences replay decisions; any post-run oracle reads are enumerated, read-only, non-locking, and isolated.
  5. A context matrix for derivatives, order book, sentiment, fundamentals, BTC, and higher timeframes: recompute, inject persisted result, or refuse. Require field-sufficiency proof and no future-data use.
  6. A source-era/event-order contract retaining immutable price-event IDs; explicit tie handling; closing-message ordering; trailing price events; candle admission/outcome/queue-drop handling.
  7. Full orchestration treatment for signal exits, protection, locks, fills, expiry, retries, daily clocks, global limits, and all shared-policy transaction/latency effects.
  8. An order-book completeness policy addressing the live `HOLD` versus Replay `UNAVAILABLE` inversion; incomplete historical windows must refuse parity.
  9. First-release scope fixed as single-symbol with multi-symbol refusal, unless deterministic global scheduling and account-state semantics are completely specified.
  10. A complete no-live-I/O test, pre-write-refusal test, no-look-ahead tests, Production regression suite for every shared class, disposable-MySQL migration proof, cancellation/resource-isolation tests, and random/incident-window refusal and mismatch reporting.
  11. A user decision table for replay-only observers and legacy modes; baseline isolation is required now, deletion remains a separate approved product decision.

- **PROJECT EVIDENCE:** The response’s three outcome classes are directionally right, but “lifecycle parity” cannot be asserted merely because a virtual starting state is authorised. It must also prove the historical account constraints were non-binding or reproduce them from immutable, sufficient evidence. Otherwise the permitted conclusion is decision parity, simulation, or refusal.

- **PROJECT EVIDENCE:** `ReplayParityValidator` is not a lifecycle oracle: it compares signal-level fields only, and no production code invokes it.
