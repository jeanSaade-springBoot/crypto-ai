# Iteration 3: log and timing forensics for the six frozen trades (Claude)

The most important result is about time labels. The timestamps I reported as UTC in iterations 1 and 2 are very likely KSA already. Each one is probably 3 hours later than true UTC. This changes the clock labels on every finding, but not the gaps between events.

The other results this round:
- Trade 101's loss is now explained, and the stored data rules out a bad price print.
- The fill-time check has no minimum risk/reward.
- The application log files that cover the trade times are gzipped. My tools cannot search them, so I could not use any application log evidence.

This was analysis only: no code, config, DB, git or deploy changes. Plan mode was active, but no plan-file write or ExitPlanMode tool was available, so this text is the whole deliverable.

## FINDINGS

**T1. The DB times in our evidence files are most likely KSA, not UTC (PROJECT EVIDENCE; this contradicts DATABASE_INVESTIGATION_RULES.md)**

| Wallet trade | Stored `execution_price_observed_at` | `priceObservedAt` written by Java in the message | Difference |
|---|---|---|---|
| 195 | 2026-10-10 17:35:04.248 | 2026-10-10T14:35:04.248Z | +3h |
| 257 | 2026-10-11 02:12:03.690 | 2026-10-10T23:12:03.690Z | +3h |
| 264 | 2026-10-11 05:35:04.601 | 2026-10-11T02:35:04.601Z | +3h |
| 231 | 2026-10-10 21:40:03.473 | 2026-10-10T18:40:03.473Z | +3h |

Why the Java value is the true UTC one:
- The message value is a Java `Instant`, which always prints in UTC (`PaperTradingService.java:383`, `ExecutionPriceAuthorityService.java:51`).
- The application writes with session `time_zone='+00:00'` and Hibernate `time_zone: UTC` (`application.yml:13-35`).
- Every relevant column is MySQL `timestamp(6)` (DBQ-CLAUDE-I1-007, I2-005, DBQ-FTS-001). MySQL converts these to the reading session's time zone when they are read.
- `scripts/agent-db-query.ps1` never sets `time_zone`. So the investigation session most likely uses the server's default (SYSTEM), which is KSA on this host.
- The live log `logs/crypto-ai-trader.log` prints `14:08:01` for `candleOpenTime=14:07:00Z`, so its clock is UTC.

Consequences:
- **The application is not affected.** It reads and writes in UTC. Only our investigation output shows shifted times.
- **Durations, ordering and price paths are unchanged.**
- **Every absolute "UTC" time in iterations 1 and 2 is likely KSA.** The true UTC is that time minus 3 hours. For example, trade 104 opened at 05:35:07 KSA, which is 02:35:07 UTC.
- **Queries that compare to fixed times are still consistent**, because the same session shifts both sides. That includes I2-003 and I2-006.
- DBQ-CLAUDE-I3-001 is the decisive check. Until it returns, the tables below show times exactly as the DB returned them, labelled "DB-shown".

**T2. Trade 101 (AERO): the loss came from FIX-118/120's TP-extension rebase, not from a gap or bad price (PROJECT EVIDENCE: I2-002, I2-003, I2-004, I1-005, I1-008)**

Timeline (DB-shown times, 2026-10-11; the gaps between events are exact):

| DB-shown time | Event |
|---|---|
| 02:16:04 | Average entry becomes 0.948789 after the second buy (wallet trade 258) |
| 02:18:39.8 → 02:18:41.7 | Price jumps 0.9508 → 0.9564 (+0.59% in one 2-second update; events 1475622 → 1475629) |
| 02:18:41.676 | Profit lock activates. Progress to the old target is about 77%, above the 70% activation level. Lock price is 0.954694, about +0.62% above entry |
| 02:19:19.684 | Price 0.9588 reaches the take-profit (TP) of 0.958631. The continuation check passes (1h=BUY) and the TP is extended to 0.963551 (event 31) |
| same moment | Measured against the new target, progress is 67.8%, below 70%. The lock moves to state `TP_EXTENSION_REBASE` (`DynamicProfitLockService.java:238-245`) |
| 02:20:43–02:20:45 | Price 0.9549 → 0.9541 crosses the earned lock of 0.954694. No exit: during the rebase the lock is deliberately not allowed to trigger (`:107-111`) |
| 02:21:23.7 → 02:21:25.7 | Price 0.9497 → 0.9487 (10 ticks in one 2-second update) crosses the hard floor of 0.949263 (entry × 1.0005, `:164-166`) |
| 02:21:25.706 | Exit (wallet trade 259) at the price that triggered it, 0.9487. That is below the entry of 0.948789, giving −0.004681 USDT |

What this shows:
- The 0.9586 level from iteration 2 was real: about 25 normal updates traded at 0.957–0.9588.
- There was no outlier print and no missing price event.
- Under the rules as coded, the TP extension at +1.06% replaced an earned lock at +0.62% with a floor at +0.05%. That floor is smaller than one normal 2-second move.
- `LivePositionProtectionService.java:187-190` says earned profit is "not left completely unprotected". In practice almost all of it was.
- **Classification: a confirmed protection design defect. The code ran exactly as written.**
- The same pattern appears before FIX-154 too: a pre-V107 `PROFIT_LOCK_HARD_EXIT` loss of −0.0779 USDT (DBQ-CLAUDE-I2-007).

**T3. No minimum risk/reward is checked at fill time (PROJECT EVIDENCE: `ExecutionIntelligenceService.java:1150-1168`)**
- `revalidateAtExecutionPrice` checks only two things: the fill price is above the stop, and below the target. It then runs the entry-quality cap.
- That confirms iteration-2 F4 and F5:
  - Trade 78 was filled with a real risk/reward of about 0.76.
  - Trades 82 and 91 were entered from signals with risk/reward of 0.45 and 0.55.
- The only risk/reward minimum I found is `BREAKOUT_RETRACEMENT_MIN_RR=1.15` (`:212`, `:1539`). It applies only to the breakout-retracement path.
- The wake-up path also uses the 1m signal's stop and target, not the 5m trigger's. Trade 91 traded at 0.546 although its 5m trigger 121201 had 1.136. Trade 104 traded at 1.09 against 1.50 on its trigger 133251 (I2-008 and the messages in I1-008).

**T4. The HTF_SELL exit mismatch is fully proven for 78, 91 and 104 (PROJECT EVIDENCE: I2-001)**
- The SETUP_WAKEUP audit rows are 1106, 1318 and 1560.
- Each read the 1h signal as raw SELL, treated it as NEUTRAL, classed it `SOFT_CONFLICT` with a 25% cap, and approved it as `BALANCED_STRONG`.
- The 1h SELL was 2104 s, 2404 s and 2103 s old at entry.
- The exits then used that same 1h SELL (DB-004 shows no new 1h signal). That closes iteration-2 U1.
- Ages in the audit are measured from candle close time, not from when the signal was generated. For example: 18:03:02.926 − 3782 s = 17:00:00.9.

**T5. Timing and latency: no execution delay contributed (PROJECT EVIDENCE: I1-005, I1-008, I2-001, I2-004, I1-006)**

- Every entry used a fresh price, 0.4–2.6 s old at execution.
- The paper position always closes 1.2–2 s after the wallet. `paper_position` close times are therefore not the execution times.
- Trade 91's 25 s exit delay is unexplained. The exit runs only when a new price event arrives (`onPrice`), so SHIB updates were probably sparse or rejected. DBQ-CLAUDE-I3-005 checks this.
- **Classification: no stale-data or execution-delay defect for any of the six entries.**

**T6. A signal gap at the DB-shown 18:00 boundary on 2026-10-10 is likely global (PROJECT EVIDENCE plus AGENT INFERENCE)**
- For XLM, the 5m candle opening at DB-shown 17:55 and the 1h candle opening at DB-shown 17:00 have no signals (DB-004). Both close at DB-shown 18:00.
- DBQ-CLAUDE-I2-006 returned an empty file for **all** symbols. There was not even a header, so a wrapper error cannot be ruled out.
- If T1 holds, that boundary is 15:00 UTC, which is 18:00 KSA.
- Two causes fit: a WebSocket reconnect or application restart right at the close boundary, or a missed final closed-kline event. AGENTS.md already names the closed-kline case. Neither is proven.
- Effect on trade 82: its entry used a 1h signal 3782 s old and a 5m signal 482 s old. Both were within limits, so this is not a rule breach. Its effect on the trade's outcome is unknown.
- Signals at hour boundaries arrive about 9 s after close instead of about 4 s (17:00:09 and 19:00:08 DB-shown). That is a normal load pattern.
