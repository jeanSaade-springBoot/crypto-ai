**F2 – When entries and exits happened (AGENT INFERENCE from F1)**
- Every entry happened 3–7 s after a 1-minute candle closed. That fits normal 1m analysis rather than a delayed execution.
- Every `HTF_SELL_CONFIRMED` exit came 9–30 s after a 5-minute boundary: 05:40:11, 22:45:09, 21:45:30 and 17:50:12 UTC.
- None of these exits fell on an hour boundary.
- So a new 5m signal most likely triggered each exit, not a new 1h signal. The 1h SELL the exit relied on most likely already existed when the position was opened. This needs proof from DB-003 and DB-004.

**F3 – Entry and exit rules disagree in the working-tree code (PROJECT EVIDENCE: code)**
- **Entry:** `HigherTimeframeBuyAssessmentService.java:33-34` allows a BUY when the 1h signal is a quality-valid SELL and the 5m signal is not bearish. It labels this `SOFT_CONFLICT` and caps it at 25%. `TradeExecutionValidationService.java:93-111` applies that rule to direct BUYs.
- **Exit:** `PositionExitPolicy.java:25-33` closes the position with `HTF_SELL_CONFIRMED` whenever the 1h signal is SELL/STRONG_SELL and the 5m signal is not BUY, STRONG_BUY or WATCH.
- **Consequence:**
  - A BUY admitted with 1h SELL and 5m NEUTRAL is exitable on the very next accepted price tick.
  - A BUY admitted with 5m WATCH/BUY is exited as soon as the next 5m signal turns NEUTRAL.
  - This matches the F2 pattern. It is a candidate design defect, not yet confirmed for these trades.

**F4 – The exit reads the latest signals with no freshness or quality check (PROJECT EVIDENCE: `LivePositionProtectionService.java:95-97`)**
- The exit loads the newest 1m, 5m and 1h `trade_signal` rows by `generated_at`.
- It does not check freshness, `signal_mode` (it does not exclude `HISTORICAL_ONLY` signals), `data_quality_valid`, or whether the signal is newer than the position.
- Entry, by contrast, does check freshness (`TradeExecutionValidationService.java:81-91`).
- Whether this affected any of the six trades is not yet known.

**F5 – Trade 101: a profit-lock hard exit below entry (PROJECT EVIDENCE: `LivePositionProtectionService.java:191-216`; claude-docs/TRADING_RULES.md §7)**
- The hard floor is entry × 1.0005. If the floor works as intended, a hard exit should land slightly above entry.
- A negative P&L means the exit price was below entry. Possible explanations, none confirmed:
  - the price jumped past the floor between accepted price events;
  - the hard-floor branch for a TP extension / rebase (FIX-118, line 191) uses a different floor;
  - the paper and wallet records disagree on quantity or price.
- This needs DB-002, DB-005 and DB-007.

**F6 – Trades 78 and 96 lost exactly the same amount (PROJECT EVIDENCE)**
- Both PEPEUSDT trades show realized P&L of −0.061576354680.
- The likely explanation is the same quantity combined with the same tick-quantised price drop. This is a hypothesis to check against `wallet_trade`, not yet a defect.

**F7 – Possible contradiction with AGENTS.md: is FIX-154 deployed? (PROJECT EVIDENCE vs governance text)**
- AGENTS.md describes FIX-154 as "not-yet-implemented".
- The working tree contains it: `HigherTimeframeBuyAssessmentService`, plus migrations `V107__fix_154_trusted_higher_timeframe_buy.sql` and `V109`. Git status shows uncommitted changes.
- Whether Production was running with FIX-154 on 10-10 and 10-11 is unknown, so F3 only applies if it was deployed. DB-001 checks this.
- I am reporting this contradiction, not resolving it.

**F8 – What the selection leaves out (PROJECT EVIDENCE: DBQ-FTS-002 and DBQ-FTS-003)**
- `CLOSED` rows: 74 in total, 19 losing. `STOPPED` rows: 45 in total, all losing.
- That adds up to 64 losing positions, which equals the 64 losing `wallet_trade` SELLs.
- Under the frozen selection rule, stop-loss losers never enter this study. This is a note on scope only; I have not substituted any trade.
