### I4-F02: Trade 143 re-entered on pre-exit setup and evidence (CANDIDATE DEFECT: intent mismatch; PROJECT EVIDENCE + AGENT INFERENCE)

**Timeline** (KSA; UTC = −3 h):

| Time | Event |
|---|---|
| 22:35:01.553 | 5m #159285 **BUY**, `atr_immediate_entry_allowed`=1 (I3-002, I3-004) |
| 22:36 | Opportunity #36481 opens position 171 through SETUP_TIMEFRAME_ATR, using that 5m (I2-003) |
| 22:39:41.052 | Position 171 exits by PROFIT_LOCK_EXIT at 3.996 (wallet #357) |
| 22:40:01.634 | 1m #159408 (WATCH, ATR-extended). New opportunity #36524 appears **already scored**: evidence 8, health 95 |
| 22:40:03.115 | Wallet BUY #358 at 4.033, through SETUP_TIMEFRAME_ATR on the **same** 5m #159285 |

**Code path:**
1. `evaluateBuyInternal` reaches `setupTimeframeAtrAuthoritySignal` (`ExecutionIntelligenceService.java:628`, `:1472-1492`).
2. The 1m signal is WATCH and not bearish. The 5m lookup returns #159285: it is BUY, its final entry was allowed, and its ATR plan allowed immediate entry.
3. The route never checks whether that 5m has already been used for a position that is now closed.

**Evidence score:**
- `evidence()` recounts the raw 1m signals from the last 30 minutes (`:2241-2311`, `EVIDENCE_WINDOW=30m` at `:47`).
- The only filter that removes pre-exit signals is FIX-122's `StopLossEvidenceService.eligible`.
- Its boundary comes from `StopLossEvidenceStore.latest`, which selects only `execution_reason='STOP_LOSS'` (`StopLossEvidenceStore.java:39-42`). Replay matches this: `ExecutionReplayScope.recordStop` ignores any other exit reason (`:50`).
- After a profit-lock exit there is no boundary, so the 1m signals from position 171's own lifecycle counted again toward the new entry.

**Contradiction with the documented rule:**
- FIX-020's Javadoc says that after *any* terminal exit, "including … profit lock … its pre-exit evidence may never finance a brand-new position" (`:812-819`).
- The code enforces this only by setting the opportunity record to `COMPLETED` (`:821-840`). It does not filter `evidence()` and does not block re-use of the 5m setup in SETUP_TIMEFRAME_ATR.

**Re-check at fill time:** `revalidateAtExecutionPrice` re-checks only the FIX-122 boundary, stop and target, and Entry Quality (`:1150-1169`). It never re-reads the 5m, so the WATCH 5m #159407 saved 175 ms before the fill was never seen. This adds to I3-F02.

**Classification:**
- Entry defect A (I3-F02, confirmed): an outdated 5m was selected.
- Entry defect B (this finding, candidate): an exit evidence boundary is missing for exits other than stop-loss.
- Before calling B confirmed, DBQ-CLAUDE-I4-002/003 must show that the evidence score of 8 came from 1m signals generated before 22:39:41.

**Side note (AGENT INFERENCE, low impact):**
- At signal time, SETUP_TIMEFRAME_ATR scores Entry Quality using the **5m** ATR (`:634`). The comment there warns that using the 1m ATR mislabels valid setups.
- At the fill-time re-check it uses the **1m** ATR (`assessEntryQualityAtPrice`, `:857-858`).
- The two scores are therefore not on the same basis. This did not block trade 143.

- This is unproven for trade 143 until DBQ-CLAUDE-I4-003 shows the status history.

### I4-F04: Boundary race, Replay reachability and population effect (PROJECT EVIDENCE + AGENT INFERENCE)

**How Replay's lookup works:**
- Replay execution loads the whole signal timeline up front, stamps every signal with its candle close time, and sorts them with 1h first, then 5m, then 1m (`ShadowProductionReplayService.java:68-72`, `ExecutionReplayScope.open :40-44`).
- Lookups use `!generatedAt.isAfter(ref)`, so a signal with the same timestamp is included (`ExecutionReplayScope.java:106-120`).

**Trade 143 in Replay:**
- The 1m `evaluateBuy` would see the new WATCH 5m, which closed at the same time.
- SETUP_TIMEFRAME_ATR would then reject at `:1486`.
- The entry most likely **cannot** be reproduced. This upgrades I3-F03 to a code-level proof.

**Trade 158 in Replay:**
- The 5m wake-up (`evaluateConfirmedSetupWakeup`, `:397-457`; Replay call at `ShadowProductionReplayService.java:258-268`) looks up the 1m at the same timestamp, age 0 s (limit 45 s, `:71`).
- **Reproducible.**
- In Production, the 1m #165412 was generated 21 ms *before* the 5m #165415 (I3-002), so both paths reach the same 1m.
- I retract the iteration-3 wording "triggered by a fresh 5m … matched". The correct basis is this code path.

**How the race affected entries (I3-004, 40 entries in total):**

Some routes need a bullish 5m to proceed. Where the old 5m was bullish, the newly closed 5m was not, and the new one was saved **before** the fill:
