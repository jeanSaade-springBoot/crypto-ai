### F-06 — The close_reason tells us which code path closed each trade (PROJECT EVIDENCE, code)

- **`SELL_CONFIRMED` and `HTF_SELL_CONFIRMED`** are emitted by `PositionExitPolicy.evaluateNormalExit` (`PositionExitPolicy.java:29,42`). That runs from the live price-tick path (`LivePositionProtectionService.java:235-239`), so the exit price is the tick price. This applies to 182, 172, 158 and 137.
  - SELL_CONFIRMED requires a bearish 1m, a bearish 5m, and a 1h that is not bullish.
  - HTF_SELL_CONFIRMED requires a bearish 1h with a 5m that is not supportive.
- **`STRONG_SELL`** is the signal-path code. It is written by `closeFromSignal(..., signal.getDecision().name(), ...)` after `validateSell` passes (`PaperTradingService.java:204-208`), using `signal.latestPrice`. This applies to 162, whose close at :04 seconds fits close-triggered analysis.
- **`PROFIT_LOCK_HARD_EXIT`** can come from three places: `LivePositionProtectionService.java:195` (rebase floor), `:213` (lock triggered and price below entry×1.0005), or `PaperTradingService.java:194` (signal path). 143 closed mid-minute (:36s), so the live path is more likely (AGENT INFERENCE).

### F-07 — Trade 143's loss on a profit-lock exit needs priority review (PROJECT EVIDENCE + AGENT INFERENCE)

- The live hard floor is `entry × 1.0005` (`LivePositionProtectionService.java:210-213`). The exit fires at whatever tick price breached the floor. There is no lower bound, so a loss is mechanically possible.
- For this exit to produce a loss, two things had to happen within 3m31s:
  1. Profit-lock activation (≥70% progress to TP), or a TP extension with a rebase.
  2. A fall from above the lock to below entry. With the floor band only 0.05% wide, the first sub-floor tick would already be below entry.
- The possible explanations are not yet separable: a very tight TP distance (small ATR), a price gap between observations, or a stale or incorrect `highest_price_usdt` or progress calculation. **No defect is claimed.** DBQ-CLAUDE-I1-005, 008 and 009 are needed.

### F-08 — Three entries landed right at a 5-minute boundary (PROJECT EVIDENCE timestamps; AGENT INFERENCE hypothesis)

- Trades 137 (20:55:04), 143 (22:40:04) and 158 (02:35:04) opened about 4–5 s after a 5m candle close.
- All six entries opened 4.5–6.5 s after a 1m boundary. That fits close-triggered 1m entries; confirmation needs the signal `generated_at` values.
- **How the 5m signal is picked:** `TradeExecutionValidationService.latestAtOrBefore` selects the 5m signal by `generatedAt <= the 1m signal's generatedAt`, and accepts one up to 20 minutes old (`TradeExecutionValidationService.java:42,367-368`).
- **Hypothesis H-01 (unverified):** at a 5m boundary, the 1m BUY may have been validated against the *previous* 5m signal, because the new 5m analysis had not been persisted yet.
- **Why it matters:** 137 then exited on SELL_CONFIRMED about 5 minutes later, which needs a bearish 5m. That fits a 5m turning bearish across the boundary. This could be a validation-timing weakness rather than a valid losing trade. DBQ-CLAUDE-I1-007 tests it.

### F-09 — Several trades were whipsawed (PROJECT EVIDENCE durations; AGENT INFERENCE)

- 143, 137 and 182 closed within 3.5–8.2 minutes. Opening on a 1m BUY and closing on a 1m+5m SELL within one or two 5m candles points to weak entry timing or a regime shift.
- Two EGLDUSDT losses (137, then 143) happened 1h45m apart. FIX-122's stop-loss evidence exclusion applies only after a stop-loss, so it does not cover re-entry after a SELL_CONFIRMED loss. Whether a cool-down was intended is unknown.

### F-10 — Loss counts agree across tables, but only in total (PROJECT EVIDENCE, DBQ-FTS-002/003)

- Losing paper positions total 26 + 75 = 101; `wallet_trade` has 101 rows with negative P&L.
- This is a count match only, not a row-by-row reconciliation. DBQ-FTS-003 is not filtered by side.
- Automatic trades record `fee_usdt = 0` (claude-docs/TRADING_RULES §6), so the true losses are larger than stored. Fees are not yet computed.
