# Claude: FTS WINDOW2, Iteration 3 (log and timing forensics, self-review)

The six frozen trades are 182, 172, 162, 158, 143 and 137, all Production paper positions in `crypto_ai`. This was analysis only: no code, config, database, git or deploy actions. Plan mode was active, but neither a Write nor an ExitPlanMode tool was available, so this report is returned inline. I read none of Codex's files, `LIVE_EVENTS.log`, `LIVE_TEAM_STATUS.md` or `DATABASE_QUERY_LOG.md`.

**Bottom line:** I have strong evidence that the timestamps our query wrapper returns are KSA, not UTC. That would make every KSA time I gave in Iterations 1–2 three hours too late. One query (I3-001/002) will settle it. Trade 143's entry is now a confirmed entry-selection defect: it used an older 5m BUY and missed a newer 5m WATCH by 2 ms. Exit 143's protection gap could come either from the exchange feed or from our ingestion; I can't tell which yet. Population results also correct my earlier F1: most losses come from stop-outs, not from the low-R:R exits.

## FINDINGS

### T1. Stored timestamps are probably displayed to us in KSA, not UTC (PROJECT EVIDENCE + AGENT INFERENCE; critical; confirm with I3-001/002)

**What I found:**
- **The gap is always 3 hours.** For all six entries, the `priceObservedAt=…Z` value in `wallet_trade.execution_message` is exactly 3 h earlier than the same price event as the database shows it (I2-004 against I2-003 and I1):

  | Trade (wallet_trade) | Logged `priceObservedAt` (Java, UTC) | Stored price-event time as displayed |
  |---|---|---|
  | 143 (#358) | 19:40:01.028Z | 22:40:01.028 |
  | 137 (#344) | 17:55:00.032Z | 20:55:00 |
  | 158 (#392) | 23:35:00.328Z (10-11) | 02:35:00 (10-12) |
  | 162 (#403) | 01:02:02.580Z | 04:02:02.580 (I1 evidence) |
  | 172 (#426) | 03:36:01.457Z | 06:36:01.5 (inferred from the −3 h pattern) |
  | 182 (#451) | 06:57:02.437Z | 09:57:02.4 (inferred from the −3 h pattern) |

- **The Java side really was at the earlier time.** `ExecutionPriceAuthorityService.resolve` (`ExecutionPriceAuthorityService.java:46-48`) rejects any price older than 15 s, measured against `Instant.now()`. Every BUY passed that check, so the app's own clock read about 19:40Z at the 143 entry. The logged Instant is true UTC unless the host OS clock was wrong.
- **Locally logged UTC times match the Java Instants.** In `logs/crypto-ai-trader.log` (a local run on 10-17), line timestamps match `observedUtc` exactly, e.g. line 37 `00:11:59.950` against `observedUtc=…00:11:59.950945600Z`.
- **The app writes and reads in UTC.**
  - The app forces UTC on its own connections: `application.yml:22-26` sets the session to `+00:00`, uses `connectionTimeZone: UTC`, and sets `preserveInstants: true`.
  - The startup log confirms `sessionTimezone=+00:00`.
- **The columns are `TIMESTAMP(6)`.** For example `V1__initial_schema.sql:15/74/145/182` and `V67:5`. MySQL stores these in UTC and shows them in whatever time zone the reading session uses.
- **Our query wrapper never sets a time zone.**
  - `scripts/agent-db-query.ps1:19` calls `mysql.exe` without one, and it blocks `SET` statements.
  - So results appear in the server's default zone.
- **This machine's clock is set to KSA.** `run-failure-trade-study.ps1:27` names the run folder from local `Get-Date`. The folder is `…-20261018-180002`, which equals the stated SNAPSHOT KSA 18:00:02.

**Conclusion (AGENT INFERENCE, high confidence):**
- The wrapper's session defaults to the KSA system zone, so `TIMESTAMP` values appear as **KSA wall-clock**.
- True UTC = displayed value − 3 h.

**Consequences:**
- **Earlier reports:** every "KSA" time I gave in Iterations 1–2 is 3 h too late.
- **Unaffected:** durations, latencies, ordering and the frozen-trade selection.
- **Rule contradiction:** `DATABASE_INVESTIGATION_RULES.md` says "Raw MySQL timestamps are UTC". For `TIMESTAMP` columns read through this wrapper, that appears to be wrong.
- **Mixed-zone hazard:**
  - `DATETIME` columns such as `trade_signal.btc_signal_generated_at` (V18) store the literal UTC value and would still display as UTC.
  - One result row could therefore mix both zones.
- **Action:** I am reporting this contradiction, not resolving it. No document has been updated; it needs dual-agent review.

### T2. F2 is now confirmed: trade 143 entered on a superseded 5m BUY because of a 2 ms race (PROJECT EVIDENCE; logic defect)

- **The execution message identifies the 5m signal used.** #358's message says the "fresh 5m BUY … ATR plan explicitly allows immediate entry at 100%".
  - That describes **159285**: BUY, `STANDARD_ENTRY`, 100% (I2-005).
  - It does not describe **159407**: WATCH, `PULLBACK_ENTRY`, 60%, "wait for retrace near 4.0158".
- **How the 2 ms decided it:**
  - Both are "displayed" times (see T1).
  - The selection rule is `generated_at <= current.generatedAt`, in `ExecutionIntelligenceService.java:2455-2461` → `:2608`.
  - 1m signal 159408 was generated at 22:40:01.633945.
  - The same-boundary 5m signal 159407 was generated at 22:40:01.635944, so it was excluded.
- **The newer evidence was already stored before the BUY.** 159407 was persisted at `created_at` 22:40:02.940614 and its work completed at 22:40:02.985620. The wallet BUY executed at 22:40:03.115, so 159407 had existed for 130–175 ms when the system bought.
- **The authority signal's plan no longer fitted the price.**
  - 159285 closed at 3.986, about 5 minutes old (generated 22:35:01.55).
  - Its own stop was 3.96607 and its own target 4.01322.
  - The fill was **4.033, above that authority's own target**.
  - The position's 4.1043 target came from the extended 1m plan; `revalidateAtExecutionPrice` did not reject this. Exactly why is open (U-T2).
- **Replay can't currently show this.** All Replay/test tables are empty (I2-011), and Replay parity depends on reproducing the exact `generated_at` ordering of signals analysed in parallel.
- **Classification:** logic defect. The outcome depends on millisecond ordering between parallel 1m and 5m analysis at a 5m boundary, and it ignores superseding same-boundary evidence that was available before execution.

### T3. Trade 143 exit: gap-through on a thin feed; whether the exchange or our app caused it is still unknown (PROJECT EVIDENCE + AGENT INFERENCE)

- **EGLD price events (I2-001):**
  - Before the exit they arrive about every 2 s (on odd seconds).
  - They are missing at :07–:17 (6 expected pushes) and :29–:33 (3 expected pushes).
  - In the second gap the price went from 4.100 (:27.038) to 4.027 (:35.021). That is −1.78% in 7.98 s, through the lock (4.0758), the hard floor (4.035) and the entry price (4.033).
- **The feed as a whole kept running** every second except :17 (I2-002), so this was not a full ingestion outage.
- **The minute was extremely busy.** The 22:43 1m candle had 433 trades and 6,382.8 volume, about 9.5× the previous minute (I2-003).
- **EXTERNAL RESEARCH:** Binance documents a 2000 ms update speed for kline streams. It does not say whether unchanged klines are skipped. `observed_at` is Binance's event time `E` (`BinanceKlineService.java:94`).
- **Two possible causes:**
  - (a) Binance sent no EGLD push in those windows. The 1.8% drop would then have happened inside one 2 s window.
  - (b) Pushes arrived but were rejected before insert. Rejection as `STALE_PRICE` or `FUTURE_TIMESTAMP` writes **only a log line, with no database row** (`MarketPriceEventService.java:53-57`, `[FIX-153][PRICE_NOT_CANONICAL]`).
- **Which is more likely (AGENT INFERENCE):** (a). Other symbols were inserted normally through the same thread, so a stale or future-timestamp rejection hitting only EGLD is unlikely.
- **Durable-evidence gap (PROJECT EVIDENCE):** a rejected observation leaves no durable record. A database-only investigation, or Replay, cannot tell a missing exchange push from a dropped observation.

### T4. All protection runs on one shared thread, so one exit delays every symbol by about 1.2 s (PROJECT EVIDENCE)

- **Code:** input and protection callbacks run inside `transactions.process` on the WebSocket thread (`BinanceKlineService.java:101-111`).
- **Log:** `PRICE_OUTCOME_COMMITTED` is logged on `WebSocketClient-SecureIO-1` (10-17 log, lines 254+).
- **During the 143 exit:**
  - Event 1789409 was created at 22:43:35.030 and the position closed at 22:43:36.229, a 1.2 s transaction.
  - Meanwhile, another event observed in second :35 was not inserted until 22:43:36.244974, followed by a burst of 10 inserts in second :36 (I2-002).
- **Impact:**
  - It did not change the P&L of any of the six trades (AGENT INFERENCE).
  - In a broad sell-off it would delay protection across symbols.
  - Close-analysis is not on this thread, which is consistent with AGENTS.md.
