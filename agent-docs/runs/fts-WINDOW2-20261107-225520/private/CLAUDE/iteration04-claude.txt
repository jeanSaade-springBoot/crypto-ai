## FINDINGS

### F-I4-01: Confirmed defect. 143 entered on a 5m signal that had already been replaced

[PROJECT EVIDENCE: I3-001, I3-002, code]

This settles U-I3-1 and promotes F-I3-03 from "candidate" to confirmed.

**Timestamps (I3-001):**
- 1m signal 159408 was generated at 22:40:01.633945 UTC (10-12 01:40:01.634 KSA).
- 5m signal 159407, for the same boundary, was generated at 22:40:01.635944 UTC, which is **2.0 ms later**. It said WATCH.
- The entry executed at 22:40:04.857700 UTC (01:40:04.858 KSA), **3.2 s after** that WATCH already existed.

**How the code chooses the 5m signal:**
- `setupTimeframeAtrAuthoritySignal` (`ExecutionIntelligenceService.java:1472-1492`) calls `latestAtOrBefore` (`:2455-2462`).
- That lookup goes through `findTopBySymbolAndIntervalAndGeneratedAtLessThanEqualOrderByGeneratedAtDesc` (`:2606-2609`).
- So it selects by **analysis completion time**, compared with the 1m signal's own `generated_at`. It does not select by candle identity.
- It therefore returned 159285, a BUY from the 22:30 candle generated at 22:35:01. That signal was 5 minutes old but inside the 20-minute `FIVE_MINUTE_MAX_AGE` (`:66`).

**Why the race exists:**
- `CandleAnalysisDispatcher` serialises work only per `symbol|interval` (`CandleAnalysisDispatcher.java:34`).
- The pool `candleAnalysisExecutor` (8–16 threads, `CandleAnalysisAsyncConfig.java:36-38`) runs the 1m and 5m analyses for the same boundary **in parallel**.
- Production stamps `generated_at` with `Instant.now()` when the analysis finishes (`AnalysisService.java:160-161`).
- So which 5m signal the 1m path sees is a race decided by milliseconds.

**Nothing re-checks the 5m before execution:**
- `PaperTradingService.java:349` calls `revalidateAtExecutionPrice` (`ExecutionIntelligenceService.java:1150-1169`).
- That only re-checks the stop, the target and Entry Quality at the fresh price. It never re-reads the 5m signal.

**The race only fails in one direction:**
- If the fresh 5m is *more* bullish, `SETUP_CONFIRMATION_WAKEUP` catches it, because that path is triggered by the 5m signal itself (`:397-457`).
- If the fresh 5m is *less* bullish, nothing revokes an approval already granted on the stale 5m.

**Counterfactual (AGENT INFERENCE):** with 5m = WATCH, line 1486 returns null and the `SETUP_TIMEFRAME_ATR` route is closed. The later route at `:644` then rejects as `ATR_ENTRY_BLOCKED`, because the 1m was `WAIT_FOR_RETRACEMENT` at 0%. **So 143 would not have opened.**

**Classification:** a logic defect in how the 5m approval is chosen at the boundary. It is not stale data and not an execution delay.

### F-I4-03: Replay almost certainly cannot reproduce 143 or 158 (parity gap)

[PROJECT EVIDENCE: code. Running Replay to confirm: AGENT INFERENCE]

This settles U-I3-6.

**How Replay orders signals:**
- Fresh Replay sets `generatedAt` to the candle close time (`RegressionTestWorker.java:584,616`, `AnalysisService.java:183-190`). So the 1h, 5m and 1m signals for one boundary all share **the same instant**.
- Signals are sorted 1h → 5m → 1m at equal timestamps (`RegressionTestWorker.java:557-560`, `ShadowProductionReplayService.java:68-71,1000`).
- Replay lookups include equal timestamps (`ExecutionReplayScope.java:112`, `!isAfter(ref)`).
- So in Replay, the same-boundary 5m is **always** processed before, and visible to, the 1m. Production is a race (F-I4-01).

**Trade 143 in Replay:** the 1m would see 5m = WATCH, so `SETUP_TIMEFRAME_ATR` is closed and the entry most likely does not happen.

**Trade 158 in Replay:**
- The 5m wakeup (`ShadowProductionReplayService.java:258-268`) runs **before** the same-boundary 1m exists.
- `latestSignalAtOrBefore` therefore returns the 1m from the previous minute, which is 60 s old.
- That fails `SETUP_WAKEUP_1M_MAX_AGE = 45 s` (`ExecutionIntelligenceService.java:71`, `:423-424`), so the wakeup does nothing.
- 158 would then go through `evaluateBuy` on the 1m with 5m = BUY, a different route and possibly a different outcome.

**Scale:** about 30 Production `SETUP_CONFIRMATION_WAKEUP` entries in I3-002 depend on the "1m finishes before 5m" order. **This is a structural Replay ≠ Production divergence affecting a whole entry route,** not only trade 143.

**Precedent:** FIX-141 already moved the BTC-context lookup to candle-identity selection for exactly this parity reason (`ExecutionReplayScope.java:122-137`, `TradeSignalRepository.java:34-39`, used in `BtcMarketContextService.java:84`). That fix was not applied to the 5m and 1h approval lookups in `ExecutionIntelligenceService` or `TradeExecutionValidationService` (`:367-378`).

### F-I4-04: 172 was approved on a 5m signal whose own entry gate had rejected it (design inconsistency)

[PROJECT EVIDENCE: I3-001, code]

- The 5m signal 171559 said BUY with `final_entry_allowed=0` and confidence 49. It was generated at 06:35:04 UTC (09:35:04 KSA).
- `validateBuy` (`TradeExecutionValidationService.java:81-112`) passes only the 5m's **decision label** into `HigherTimeframeBuyAssessmentService.assess` (`:20-37`) and then into `balancedBuy` (`:300-309`).
- `balancedBuy` maps 5m BUY + 1h NEUTRAL to `BALANCED_STRONG` at 75%, and it neither checks `final_entry_allowed` nor reads the 5m's confidence.
- The other routes do require it: `SETUP_TIMEFRAME_ATR` (`ExecutionIntelligenceService.java:1487`) and the confirmation wakeup (`:402`) both require `five.isFinalEntryAllowed()`. The same 5m would have been refused as approval on those routes.
- Allocation was capped to 25% by Entry Quality (score 60). That did limit the size, but it did not block the entry.
- **Classification:** a design gap, not a race. Whether it caused the loss is unproven; 172 lost −0.18% on an HTF_SELL exit.

### F-I4-05: 182's entry depended on one 1h trend score, 16 against a threshold of 15

[PROJECT EVIDENCE: I2-006, code]

**How the 5m bearish signals were masked:**
- `MultiTimeframeConfluenceService.java:136-138` downgrades a bearish 5m to NEUTRAL (status CONFLICT) when any higher-timeframe context counts as "bullish".
- "Bullish context" is defined as decision BUY or `trend_score >= 15` (`:24`, `:337-339`).
- The 1h signal 175258 was **WATCH with trend score 16**. It was generated at 09:00:04 UTC (12:00:04 KSA).
- So all 12 of ACE's 5m SELL and STRONG_SELL signals from 09:05 to 10:00 UTC were shown as NEUTRAL. That is F-I3-06.

**How the entry was then approved:**
- `HigherTimeframeBuyAssessmentService.assess` checks `bearish(five)` on the **final decision**, which was NEUTRAL, not on `original_decision` (`:20-26`). So the "5m bearish veto" did not fire.
- FIX-11G then granted 25% on 5m NEUTRAL + 1h WATCH (`TradeExecutionValidationService.java:263-284`).
- **The same 1h WATCH was used twice:** first to neutralise the 5m bearish signal, then as the non-bearish 1h approval for the BUY.

**What happened next:**
- The next 1h signal, 176791, was generated at 10:00:06 UTC (13:00:06 KSA) with decision NEUTRAL and trend score 13.
- That is below the threshold, so the masking stopped and 5m 176934 came through as an actual STRONG_SELL at 10:05:03 UTC (13:05:03 KSA). The position exited on it.

**Classification:** losing trade that followed the rules; an entry-quality weakness. It should be weighed alongside the FIX-154 direction, but it is **not** the FIX-154 1h-veto case: here the 5m bearish evidence was hidden, not the 1h.

## Remediation direction (recommendation only, not authorised)

1. **Select 5m and 1h approval by candle identity**, the way FIX-141 does for BTC context. Use the latest 5m whose `candle_open_time + 5m ≤ the 1m candle close`. When the same-boundary 5m analysis is still pending, defer (stay BUILDING), with a durable, bounded outcome; consistent with the AGENTS.md automation direction.
2. **Re-read the 5m inside `revalidateAtExecutionPrice`**, or make it reject when a newer, non-bullish 5m for the same boundary exists.
3. **Apply one consistent 5m approval contract across all routes:** `final_entry_allowed`, and consider `original_decision` when a CONFLICT has masked a bearish 5m.
4. **Fix the Replay order** once the Production fix exists, so Replay and Production use the same candle-identity rule.

**Regression checks:**
- Replay EGLD 2026-10-11 22:30–22:45 UTC and XRP 2026-10-12 02:30–03:31 UTC under Production parity, and compare against paper positions 143 and 158.
- Unit cases: 1m before 5m and 5m before 1m at the same boundary, for every route that reads the 5m.
