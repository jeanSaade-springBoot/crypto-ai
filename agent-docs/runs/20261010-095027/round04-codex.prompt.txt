### E. New evidence this round (both agents missed it)

**E1. Missing order-book data has opposite effects in Production and Replay.** [PE]
- With no observations in the window, Production returns `INSUFFICIENT_DATA_HOLD` and blocks the entry (`OrderBookLiquidityService:190-199, 209-218`).
- With no stored rows, Replay returns `UNAVAILABLE` and leaves the entry permission unchanged (`:154-159`).
- The final decision combines that permission with AND (`FinalDecisionService:143-148`), so Replay can enter exactly where Production held.
- Snapshot storage is best-effort and silently drops rows when its queue is full or an insert fails, leaving no completeness marker (`OrderBookSnapshotService:44-66`).
- Production decides from an in-memory window, which can differ from the stored rows and is emptied on restart.
- So the spec's §5.6 test ("evidence exists") cannot prove completeness: a partly stored window looks valid.

**E2. The spec's parity goal conflicts with its own no-look-ahead rule.** [PE + AI]
- Production's HISTORICAL_ONLY path (`CandleClosedAnalysisWorker:160-165` → `AnalysisService:166-175`) still calls the **live** derivatives service (`AnalysisService:331-335`). That service fetches current funding and open-interest data whatever timestamp it is given (`DerivativesPositioningService:52-60`). In the same analysis, `MarketContextService:56-58` uses the historical stub.
- Those signals are saved (`AnalysisService:174-175`), and later Production decisions read them as context:
  - live protection labels (`LivePositionProtectionService:95-97`);
  - entry/exit validation (`TradeExecutionValidationService:376-378`);
  - multi-timeframe confluence (`MultiTimeframeConfluenceService:109-111`).
- In periods when scheduled analysis was enabled, recovered signals were also executable (`ScheduledAnalysisService:203`; `AnalysisService:118-126`).
- [AI] Reproducing these signals exactly needs data from after the replay clock, which §6.4 and RPR-T-05 forbid. The spec does not address this.
- Live analysis also calls the derivatives service twice (`MarketContextService:59`; `AnalysisService:334`), so any capture under RPR-06 must record both results.

**E3. The ordering reversal (D1) can make Replay skip entries entirely.** [PE + AI]
- Replay applies the 15-second price-freshness rule to the last observation at or before the candle boundary (`ExecutionPriceAuthorityService:37-43`).
- Production applies it at the moment of processing, which is after the closing observation (`:46-48`; `PaperTradingService:342-343`).
- When the last in-candle update is more than 15 s before the boundary, Replay skips an entry or add (`ShadowProductionReplayService:310-312, 345-347`) that Production executed.
- [AI] This is plausible for thinly traded symbols. An earlier investigation (non-authoritative memory, not re-checked this round) recorded gaps of 2–59 s between applied SHIB price events.

**E4. Historical settings are not versioned, so §5.8 cannot be met for any past window.** [PE]
- `wallet_settings` is a single, mutable row (`V28:13`), and I found no settings-history table in the migrations.
- Replay also re-reads the current settings on every price event (`ShadowProductionReplayService:726, 757, 777, 1012`), so a single run can mix settings if they are edited mid-run.
- Derivatives make it worse: when enabled, every decision passes through the derivatives stage (`FinalDecisionService:135-141`) and its confidence adjustment (`MarketContextService:98`), so §5.7 refuses every request in that period.
- Result: parity mode cannot succeed for any window before forward capture exists, unless some configuration history exists outside the database.
