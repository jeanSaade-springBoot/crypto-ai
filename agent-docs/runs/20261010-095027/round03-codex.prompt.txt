### B. Codex claims I challenge
**B1. Dropping the event ID does not lose tie order, and it is not the ordering defect.**
- **[PE]** Replay re-sorts the SQL-ordered list by `observedAt` using `Stream.sorted`. **[AI]** That sort is stable for ordered streams, so the SQL `id` order survives on ties.
- **[PE]** Within one symbol, FIX-153 events cannot tie:
  - canonical rows take `ordering_slot=1` under the unique key `uk_fix153_price_receipt(symbol, observed_at, ordering_slot)`;
  - protection marks any event older than an already-APPLIED one as `OUT_OF_ORDER`.
  - So APPLIED rows per symbol are unique and rise in `observed_at`, which matches Production's commit order.
- **[AI]** The ID only matters for LEGACY rows with a NULL slot, since MySQL unique keys allow repeated NULLs, and for merging symbols under RPR-04. The real ordering defect is D1 below.

**B2. "Unrecorded prices could make the certificate falsely positive" has the wrong mechanism for FIX-153-era data.**
- **[PE]** In OFF mode, the recorded kline path is the only caller of protection.
  - `finish(APPLIED)` commits in the same transaction as the protection effects, and `executeMechanicalExit` joins that transaction.
  - Invalid, rejected and unapplied observations are all excluded.
  - So a price Production never marked APPLIED is a price Production never acted on, and leaving it out cannot make Replay's logic diverge.
- **[AI]** A gap in APPLIED rows, such as during a WebSocket outage, is a period when Production was also unprotected.
  - Parity means reproducing that gap. Refusing on gaps produces false refusals, and filling them would break parity.
  - Coverage still needs defining, but as **applied-set completeness + evidence era + Production order**, not market coverage.
  - The real false-positive risks are D1, D2 and D5, plus my F4 look-ahead inputs.

**B3. Refusing parity on missing derivatives is correct, but it makes the default mode unreachable.** **[PE]**
- Derivatives with veto are on by default, and `evaluateHistorical` always returns UNAVAILABLE.
- The two UNAVAILABLE cases also score differently: −10 when the live call fails, 0 for the historical stub.

### D. New evidence from this round (both agents missed it)
**D1. Replay reverses Production's order at every candle close.** **[PE]**; how often it happens is **[AI]**.
- In Production, one kline message runs input → protection → observer → close-publish. A candle's signal cannot exist until the closing price from that message has gone through protection.
- Replay stamps each signal at `openTime + interval` and only consumes price events with `observedAt ≤ generatedAt`. `observedAt` is Binance's event time `E`.
- So whenever the closing message's `E` is later than the boundary, Replay processes the boundary signal first, then protects at the close price:
  - it runs SELL validation or a progressive add before protection;
  - protection then sees the new 1m signal already set as `latest1m`, while Production still sees the previous one;
  - Replay fills use the last price at or before the boundary, while Production fills at processing time.
- This contradicts Replay's own documented intent ("newly closed 1m signal is intentionally not visible yet") and the spec's §6.5 tie order. Ordering needs to follow which message closed the candle, not a timestamp comparison.

**D2. Production's signal path has two exit routes that exact-price Replay lacks.** **[PE]**
- **Label-free profit-lock exit.** When labels favour holding, the live path logs a "protected hold" and the lock stays ACTIVE. At the next candle close, `triggered = active && price ≤ lock`, and `PaperTradingService` closes with `PROFIT_LOCK` without checking any labels. Production overrides the live hold; Replay keeps holding. This is a routine scenario, not an edge case.
- **Advisory stop-loss.** `PositionManagementService.analyze` runs first and can apply a wallet `POSITION_STOP_LOSS` at the signal price. Replay never calls it.

**D3. Multi-symbol RPR-04 needs changes to the shared `ExecutionReplayScope` that are not registered.** **[PE + AI]**
- Its per-thread state holds a single `opportunity` and a single `latestPrice`.
- The spec gives no rule for ordering competing claims on global limits across symbols.

**D4. Replay analyses `closed=0` candle rows.** **[PE]**
- `candles()` filters neither on `closed` nor on provenance.
- The snapshot takes the latest closed candle at or before the open time, without checking it is the right candle.
- The result is a signal built from the previous candle but stamped at the later boundary. Production never dispatches such a row.

**D5. Price-evidence meaning depends on the era, and the spec treats all eras alike.** **[PE]**
- On the shared-market (FIX-150) path, protection runs and its outcome goes to `shared_market_event_delivery`. The code I read does not update `market_price_event` there.
- Collector-era rows can be `HISTORICAL_ONLY`.
- In OFF mode, `assertReplayEvidence` returns before its collector-era check.
- Qualifying those windows would mean reading retired shared-market tables, which AGENTS.md:185 restricts in OFF mode.

**D6. Shared signal generation already branches on Replay flags, against §6.2.** **[PE]**
- `buildSignal` branches on `historicalReplay`/`regressionReplay` for market context, derivatives and order book.
- Complying means changing Production `AnalysisService`, which is not registered.
