## Headline

- **Prices were fresh.** At entry, every signal has `data_quality_valid=1` and every fill is within 3.0–4.2 s of the 1m candle close. I found no evidence of stale prices or slow execution at entry.
- **Main pattern:** these trades lost money mainly because of how the stop and target are placed.
  - In low volatility, the stop is held at a minimum 0.5% below entry, while the target stays at 3 ATR.
  - Five of the six entries therefore had a reward smaller than their risk (R:R 0.33–0.74), and I found no gate that blocks that.
  - Paper fees are recorded as 0. That hides the fact that three of the targets were smaller than a normal Binance round-trip fee.
- **Two possible code defects need verification:**
  - **Trade 143:** it may have taken its 5m approval from a superseded 5m signal at a 5-minute boundary.
  - **Sizing:** a 0% ATR size recommendation is turned into 100% (`PaperTradingService.java:328-330`).
- **Trade 143's exit followed the code as written,** but the design is weak. A position that reached about 95% of its target closed below entry.

## FINDINGS

### F2-1 Stop/target placement gives R:R < 1 in low volatility [PROJECT EVIDENCE: code + DBQ-CLAUDE-I1-003]
**How the code places them:**
- The stop distance is the larger of 2 ATR and 0.5% of price (`AtrRiskService.java:34-40`; `application.yml:143` sets `minimum-stop-percent: 0.50`).
- The target is always 3 ATR (`:41`).
- So R:R = 3·ATR / max(2·ATR, 0.5%·P). It drops below 1.5 once ATR is under 0.25% of price, and below 1.0 once ATR is under 0.167%.

Every stored SL/TP matches this formula exactly. For example, 158: 1.4109 × 0.995 = 1.4038455 = SL, and 1.4109 + 3 × 0.000769622546 = 1.413208867638 = TP.

| Pos | ATR % of price | Target (TP) distance | SL distance | Stored R:R | Realized % |
|---|---|---|---|---|---|
| 137 | 0.107 | +0.322% | 0.50% | 0.644 | −0.300% |
| 143 | 0.270 | +0.81% (before extension) | 0.54% | 1.500 | −0.149% |
| 158 | 0.055 | +0.164% | 0.50% | 0.327 | −0.128% |
| 162 | 0.073 | +0.219% | 0.50% | 0.438 | −0.345% |
| 172 | 0.124 | +0.372% | 0.50% | 0.744 | −0.182% |
| 182 | 0.080 | +0.241% | 0.50% | 0.482 | −0.212% |

`grep` finds `riskRewardRatio` only where it is persisted (`AnalysisService.java:540`). There is no minimum-R:R entry gate. Some routes check `EntryQuality.rewardRisk()`, for example the transition route at `:1455` and breakout retracement at `:1539`, but I have not exhaustively checked every route [AGENT INFERENCE].

**Classification:** this is a configuration/design weakness, not a code defect. It works as coded.

**Correction to iteration 1, F-3:** `paper_position.realized_pnl` is in USDT. It exactly matches `wallet_trade.realized_pnl_usdt` for all six trades.

### F2-6 Trade 143: entry approval may have come from a superseded 5m signal [PROJECT EVIDENCE + AGENT INFERENCE → candidate defect, unverified]
- **The 1m signal said wait:** 159408 was `WAIT_FOR_RETRACEMENT` with a recommended size of 0%, `atr_overextended=1`, RSI 84.32 and price 4.35 ATR above SMA20 (I1-001/003).
- **It filled anyway, at 25 USDT:** the fill (`wallet_trade` 358) used the `SETUP_TIMEFRAME_ATR` route.
- **That route needs a bullish 5m signal:** `ExecutionIntelligenceService.java:1485-1486` takes it from `latestAtOrBefore(current, "5m", 20min)`, which means generated at or before the 1m signal's `generated_at` (`:2455-2461`).
- **The new 5m signal was written 2 ms after the 1m signal:** 159407 (5m, candle 22:35 UTC, decision **WATCH**) was generated at 22:40:01.635944, 2 ms after 1m signal 159408 at 22:40:01.633945. The entry reason quotes "5m=**BUY**", so the bullish 5m it used was most likely the previous one (candle 22:30, closed about 5 min earlier).
- **Hypothesis H2-6:** at 5-minute boundaries, the 1m and 5m analysis lanes race each other. The setup approval can come from a 5m signal that is replaced within milliseconds by a non-bullish one.

Trade 158 shows the same race, but harmlessly. Its 1m signal 165412 (02:35:01.469) cited "5m=WATCH", while 5m BUY 165415 arrived at 02:35:01.490, and that 5m BUY was the trigger for the wake-up route.

**Classification:** candidate defect (wrong higher-timeframe evidence used at a boundary). Not confirmed until DBQ-CLAUDE-I2-001/003.

### F2-7 Trade 143: a 0% size recommendation is treated as 100% [PROJECT EVIDENCE: code; AGENT INFERENCE on effect]
- `PaperTradingService.java:328-330` reads `getAtrRecommendedPositionPercent() <= 0 ? 100 : …`.
- For 143 the execution signal recommended 0%, so the ATR size multiplier became 100%. The effective size was then set only by the route's cap (`DEFERRED_POSITION_PERCENT=30`, `:104`).
- The wallet notional was 25 USDT, the same as the full-size entries 137, 158 and 172. How the wallet sizes trades is not yet traced, so this is a candidate sizing defect, not a confirmed one. DBQ-CLAUDE-I2-003 should provide the execution message.

### F2-8 Trade 143 exit: about 95% of the way to target, closed at a loss — the code did what it says [PROJECT EVIDENCE: I1-001/005/008 + code]
Timeline (UTC):
1. **22:40:03.115 — entry** at 4.033. Signal TP 4.0647; SL 4.0102.
2. **22:40:41 — first TP extension.** Price 4.067 was at or above TP, so TP moved 4.0647 → 4.0805 (`position_management_event` 51), 38 s after entry.
3. **22:41:13 — second TP extension.** TP moved 4.0805 → 4.1043 (event 52) at price 4.081.
4. **Then:** a peak of about 4.101 is inferred from "95.35% of TP distance" (≈ +1.68%). The lock was set at 4.07579 (activation 70%, initial lock 40%, trail 10%).
5. **22:43:35.046 — hard exit** at 4.027 (`PROFIT_LOCK_HARD_EXIT`, wallet 359). That is below the hard floor of 4.0350165 (entry × 1.0005).

**Why it played out this way:**
- When the lock triggers, the code exits only if `evaluateProfitLockBreach` confirms the exit. Otherwise it logs a "protected hold" (`LivePositionProtectionService.java:219-230`).
- The only exit that needs no confirmation is the floor at entry + 0.05% (`:210-216`). The exit source signal 159487 was NEUTRAL, which fits a "protected hold" through the lock level. I can't confirm that because I have no logs.
- **Result:** an open profit of about +1.68% became −0.149%.

**Classification:** behaved as coded; this is a design weakness, not a code defect. The price filled 0.20% below the floor, which depends on how often price events arrive (DBQ-CLAUDE-I2-005).
