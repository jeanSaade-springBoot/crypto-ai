## Time convention (CONFIRMED, PROJECT EVIDENCE)

The wrapper returns `TIMESTAMP` columns in KSA, not UTC (DBQ-CLAUDE-I3-001):
- The session time zone is `SYSTEM` = Arab Standard Time, offset +180 min.
- Wallet 358 `execution_price_observed_at` shows as `2026-10-11 22:40:01.028`. Its epoch is `1791747601.028`, which is 2026-10-11T19:40:01.028Z.

So MySQL stores UTC, but this wrapper displays KSA. That contradicts both `DATABASE_INVESTIGATION_RULES.md:35` and this task's "DB timestamps are UTC". I am reporting the contradiction rather than silently accepting the rule. Below, "KSA" means a wrapper-displayed `TIMESTAMP` value and "UTC" means that value minus 3 h.

**New caution (AGENT INFERENCE):** some columns are `DATETIME(6)`, not `TIMESTAMP` (`btc_context_evaluated_at`, `btc_signal_generated_at`; I1-002). MySQL does not convert `DATETIME` for the session zone. Given the app writes with `time_zone='+00:00'`, those columns probably display UTC while the `TIMESTAMP` columns beside them display KSA. Neither agent should compare the two kinds directly without converting.

### F4-2 At 5m boundaries the 1m entry decision usually reads the previous 5m signal — CONFIRMED [PROJECT EVIDENCE: I3-002, I3-003, code]

**Mechanism:**
- Production stamps `generatedAt = Instant.now()` when analysis finishes (`AnalysisService.java:150, 550`).
- Every entry-side higher-timeframe lookup is `generated_at <= 1m.generated_at`: `EIS:2455-2461`, `TEVS:81, 133, 376-378`, and the FIX-154 assessment inputs at `TEVS:93, 145`.
- Nothing ties the lookup to the 5m candle that closed at the same instant.

**Scale (I3-002):** in 10,028 boundary pairs (10-11 00:00 to 10-12 18:00 KSA), the 5m signal was generated after the 1m in **8,614 (85.9%)**. The average lag was 385 ms and the maximum 10.2 s.

**Boundary load (I3-003):** at 5m boundaries the 1m close-to-signal latency averages **5.50 s**, against 1.72 s otherwise. Analysis is visibly queued at boundaries (AGENT INFERENCE on cause).

**Effect:**
- The 5m signal for the candle that just closed stays invisible to that minute's 1m decision.
- The 5m arrives about 0.4 s later and re-runs only the wake-up paths (`PaperTradingService.java:298-305`).
- **A 5m that flips BUY → WATCH cannot undo a 1m entry already made on the stale BUY.**

### F4-3 Trade 143 is a confirmed rule violation; the system's own management path saw the correct 5m 38 s later [PROJECT EVIDENCE: I1-008, I2-003, I3-004]

- **The route requires a bullish 5m with immediate entry allowed** (`EIS:1486-1487`).
  - The 5m candle that closed with the entry candle produced signal 159407: **WATCH, immediate entry not allowed**.
  - It was generated 2.0 ms after the 1m (I3-004).
  - So the route must have used 159285 (the BUY from the 19:30–19:35 UTC candle).
- **Management saw the correct 5m.** Position-management event 51 at 22:40:41.050 KSA (19:40:41 UTC) records "Continuation PASS … **5m=WATCH**, 1h=NEUTRAL".
  - Live protection reads the newest rows with no as-of bound (`LPPS:95-97`), so it saw 159407.
  - **Entry and management therefore judged the same position on different 5m evidence 38 s apart.**
- **Other SETUP_TIMEFRAME_ATR boundary entries in I3-004 where the same-cycle 5m was WATCH but the 5m was saved after the 1m:**

  | Wallet | Symbol | P&L (USDT) |
  |---|---|---|
  | 119 | ENA | +0.041 |
  | 255 | ONG | +0.032 |
  | 358 | EGLD (trade 143) | −0.037 |

  By the code, each of these would have returned null under same-cycle evidence. **The P&L effect is mixed (net +0.036)**: this defect is about evidence correctness, not a proven loss driver. Wider scope is DBQ-CLAUDE-I4-001.

### F4-4 Replay cannot reproduce the trade-143 entry — CONFIRMED by code; the Replay run itself is not done [PROJECT EVIDENCE]

- **How Replay orders signals:**
  - It stamps every signal `generatedAt = candle close time` (`RegressionTestWorker.java:584, 612-616` and `AnalysisService.java:190`).
  - It sorts ties as 1h → 5m → 1m (`RegressionTestWorker.java:557-560, 787-793`).
  - It includes ties (`ExecutionReplayScope.java:112`, `!isAfter(ref)`).
- **Consequence:** in Replay the 1m decision **always** sees the same-cycle 5m; in Production it does in about 14% of boundary cases. Replay would have seen 159407 = WATCH and, by the code, not entered 143 through SETUP_TIMEFRAME_ATR.
- **Classification:** a **Production/Replay parity defect** for every boundary entry. Under AGENTS.md, Replay must not claim parity here.
- **Not verified:** an actual Replay run for 10-11 19:35–19:45 UTC.

### F4-5 Trade 143 re-entered on evidence from before the previous position's exit [PROJECT EVIDENCE + AGENT INFERENCE on intent]

- **Sequence:** wallet 357 closed EGLD position 171 (PROFIT_LOCK_EXIT at 3.996) at 22:39:41 KSA (19:39:41 UTC). 20 s later, wallet 358 re-bought at 4.033 (+0.93%), and the 1m signal itself was ATR-extended.
- **Evidence used:** the 5m authority, 159285, was generated at about 22:35:01.55 KSA, before that exit.
- **What FIX-020 says:** "pre-exit evidence may never finance a brand-new position" (`EIS:812-839`). But it only marks the opportunity row COMPLETED. `setupTimeframeAtrAuthoritySignal` (`EIS:1472-1492`) reads `trade_signal` directly and never checks the exit boundary.
- **Classification:** a probable gap in FIX-020's coverage. Whether FIX-020 was meant to cover higher-timeframe authority signals is unconfirmed (no design doc read).

### F4-6 Exit mechanics [PROJECT EVIDENCE: code + I1-006]

- **Live exits** (137, 158, 172, 182) happen on a **price update**, using the newest 1m/5m/1h rows (`LPPS:75-97, 235-243`). They close at the observed price.
  - That explains F3-5's 1.3–39.6 s delays: the exit fires on the first applied price update after the last required signal is saved.
  - Thin or large-tick symbols update less often (I3-006: 15 of 60 EGLD gaps were ≥ 5 s).
- **The signal-linked exit** (162, SIGNAL_SELL) fills at `signal.getLatestPrice()` (`WalletAutoExecutionService.java:230`), not a fresh execution price. There was no cost here (1.34 s), but this path has no price-freshness check. That is a latent mismatch with FIX-056 and the AGENTS.md freshness direction.
- **Exits are judged against a different snapshot than entries:**

  | | Entries | Exits |
  |---|---|---|
  | Lookup | "as of" the 1m `generated_at` | newest row |
  | Result | stale at boundaries | current |

  So the system can enter on an old BUY that an exit check reading the current 5m would already treat as WATCH.
- **The exits followed the policy.** In hindsight, 158, 172 and 182 sold 11–32 min before TP was reached. That is a design trade-off, not a defect: SELL_CONFIRMED and HTF_SELL fire on a 1m/5m SELL or 1h SELL with the 5m not supportive, with no "minimum loss" or confirmation requirement.

### F4-7 Paper P&L includes no fees [PROJECT EVIDENCE + EXTERNAL]

- `fee_usdt = 0` on every BUY and SELL (I1-006; also `WalletAutoExecutionService.java:173, 260`).
- Binance spot's base fee is 0.1% per side [EXTERNAL RESEARCH: prior knowledge, not re-fetched this iteration].
- Adding about 0.2% per round trip would roughly double these six losses (−0.13% to −0.34%). It would likely turn many small "wins" negative, for example the 0.007–0.05 USDT profit-lock exits in I3-004.
- AGENT INFERENCE: the measured edge is overstated. DBQ-CLAUDE-I4-005 estimates by how much.
