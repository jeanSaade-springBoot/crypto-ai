## Headline

1. **The timestamps were mislabelled.** The DB wrapper returns `TIMESTAMP` columns in KSA (UTC+3). In iterations 1–2, I called those values "UTC" and then added another 3 h to show "KSA".
   - The study's time rule "raw DB timestamps are UTC" does not hold for this query path.
   - Event order, durations and trade selection are unaffected.
2. **Trade 143 entered on a superseded 5m signal, and the cause is systematic.** At every 5-minute boundary in the sample, the 1m signal's `generated_at` comes 2–35 ms before the matching 5m signal's. Because the lookup is by `generated_at`, the 1m execution always uses the 5m signal from 5 minutes earlier.
   - For 143, the 5m candle that had just closed said **WATCH**. It was already saved 175 ms before the fill, but the decision used the earlier **BUY**.
   - This upgrades H2-6 from a hypothesis to a **probable logic defect**.
3. **Trade 143's exit was not a "protected hold" (this refutes my F2-8).**
   - Price never broke the 4.07579 lock before the crash.
   - The next price update fell from 4.100 to 4.027 in one 8-second gap, crossing the lock and the hard floor at once.
   - Exit latency on that update was 24 ms.
   - The loss came from a flash drop between updates. Binance confirms the same minute traded down to 3.994.
4. **Signal-driven exits waited 1.3–39.6 s after their exit signal.** I infer they wait for the next price update. On these six trades it cost at most 1 tick.

## FINDINGS

### F3-1 DB timestamps returned to agents are KSA wall-clock time, not UTC — **CONFIRMED** [PROJECT EVIDENCE + EXTERNAL RESEARCH]

**1. Why it happens:**
- The time columns are MySQL `TIMESTAMP(6)` (I1-002: `generated_at`, `candle_open_time`, `executed_at`, `observed_at`, `opened_at`). MySQL stores these in UTC and converts them to the session time zone when they are read.
- `scripts/agent-db-query.ps1:19` runs `mysql.exe` with no session time zone, and line 12 of the wrapper forbids `SET`. So the session inherits the server/system zone.
- The app itself writes correctly in UTC (`application.yml:22-26,35`: `SET time_zone='+00:00'`, `connectionTimeZone=UTC`, `preserveInstants=true`, and the entities use `Instant`).

**2. Proof from the trader's own text:** `PaperTradingService.java:383` writes `priceObservedAt=` + `Instant.toString()`, which is always UTC ("Z"). For every one of the six trades, the DB value shown is exactly +3h from that UTC value (I2-003 vs I1-006):

### F3-3 At 5-minute boundaries, the 1m signal is always generated before the 5m signal, so the execution uses the 5m signal from 5 minutes earlier — **probable logic defect** [PROJECT EVIDENCE + AGENT INFERENCE on system-wide scope]

**How the lookup works (code):**
- `ExecutionIntelligenceService.latestAtOrBefore` (`:2455-2461`) uses `findTopBySymbolAndIntervalAndGeneratedAtLessThanEqualOrderByGeneratedAtDesc(..., current.getGeneratedAt())` (`:2608`).
- `TradeExecutionValidationService:367-379` and `OpportunityConsolidationService:214-219` select the same way.
- The 1m signal's own confluence check is also evaluated "as of" `signalGeneratedAt` (`AnalysisService.java:321`). That timestamp is fixed before the signal is built (`:220, :550`).
- **Nothing checks whether the chosen 5m signal is for the 5m candle that closed at the same moment as the 1m candle.**

**EGLD boundary pairs (I2-001).** Each 1m and 5m candle here closes at the same instant. Times shown are seconds past the minute, KSA as returned:

| Boundary | 1m `generated_at` | 5m `generated_at` | 5m later by |
|---|---|---|---|
| 22:20 | 01.665431 (158906) | 01.677419 (158905) | 12 ms |
| 22:25 | 01.669138 (159029) | 01.704145 (159031) | 35 ms |
| 22:30 | 01.686096 (159158) | 01.703602 (159155) | 17 ms |
| 22:35 | 01.544745 (159281) | 01.552862 (159285) | 8 ms |
| 22:40 | 01.633945 (159408) | 01.635944 (159407) | 2 ms |

XRP at 02:35 KSA follows the same pattern: 1m 165412 at 01.469, 5m 165415 at 01.490 (21 ms later). That is **6 of 6 samples with 1m first**. In other words, the 1m decision cannot see the 5m candle that just closed.

**Trade 143:**
1. **What the code needs:** the execution message says it relied on a "fresh 5m BUY … ATR plan explicitly allows immediate entry at 100%". `:1487` requires `atrImmediateEntryAllowed=true`, and `:1496` takes the 100% from the 5m's `atr_recommended_position_percent`.
2. **What it used:** only 5m **159285** fits: BUY, immediate entry allowed (1), 100%, 5m candle 19:30–19:35 UTC.
3. **What it should have used:** the 5m candle 19:35–19:40 UTC closed at the same instant as the entry candle. Its signal, **159407**, was **WATCH**, immediate entry not allowed (0), 60%.
4. **Timing:** 159407 was `created_at` 22:40:02.941 KSA, 175 ms before the 22:40:03.115 fill, but it was excluded by 2 ms of `generated_at`.

Under the latest closed 5m candle, the `SETUP_TIMEFRAME_ATR` route would have returned `null` at `:1486`. From the code it then appears 143 would not have been entered by this route [AGENT INFERENCE: other routes were not re-simulated].

**Classification:** a logic defect in how higher-timeframe evidence is chosen at boundaries. The data itself was fresh; it was the wrong candle's evidence. It conflicts with AGENTS.md's freshness direction ("enforce freshness from persisted candle close time"). The open question is how often it happens system-wide (DBQ-CLAUDE-I3-002/003/004).

**Replay:** Replay uses the same `generatedAt` ordering (`ExecutionReplayScope.java:106-119`). Whether Replay assigns 1m/5m `generatedAt` in the same order is unknown, so reproducibility is unknown.
