### F-4 Entry timing fits 1m candle-close admission [AGENT INFERENCE]
All six entries land 4.5–6.5 s after a minute boundary. That fits a 1m close, then analysis, then execution. Only 1m signals can open positions (TRADING_RULES §4). This needs confirmation against `trade_signal.candle_open_time`/`generated_at` and `wallet_trade.execution_price_observed_at`.

### F-5 Close reasons map to two different exit authorities [PROJECT EVIDENCE: code]
- **`SELL_CONFIRMED` / `HTF_SELL_CONFIRMED`:** produced only by `PositionExitPolicy.evaluateNormalExit` (`PositionExitPolicy.java:29`, `:42`). That method is called from the live price path (`LivePositionProtectionService.java:235-238`).
  - The rule fires on 1h bearish with 5m not supportive, or on 1m bearish with 5m bearish and 1h not bullish.
  - The closes for 182 (10:05:20) and 172 (07:15:45) are mid-minute, which fits a tick-driven exit [inference].
- **`STRONG_SELL` (162):** comes from the signal path in `PaperTradingService.java:197-208`. There, `closeReason = signal.getDecision().name()` after `validateSell`. The close at 04:26:04, about 4 s after a minute boundary, fits a 1m-close signal [inference].
- **`PROFIT_LOCK_HARD_EXIT` (143):** comes from `LivePositionProtectionService.java:191-198` (rebase hard floor) or `:210-216` (triggered lock below entry×1.0005). The signal-path equivalent is `PaperTradingService.java:190-195`.

### F-6 Trade 143: a "profit lock" exit that booked a loss after 3.5 minutes [PROJECT EVIDENCE + AGENT INFERENCE]
The hard floor fires whenever `price < entry × 1.0005` (`LivePositionProtectionService.java:210-211`). Nothing stops it from firing far below entry, so a price gap through the floor realizes a loss under a "profit" label.

For the lock to be active at all, one of these must have happened within 3m31s:
- price reached ≥70% of the way to TP (ProfitLockPolicy activation), or
- TP was extended (`TAKE_PROFIT_EXTENDED` makes the rebase floor apply).

Possible explanations, all unconfirmed:
- (a) a genuine fast spike followed by a reversal, i.e. a valid loss;
- (b) a stale or wrong `highest_price_usdt`/lock state carried over from position 137 on the same symbol;
- (c) TP geometry too tight, so 70% progress was trivial.

`position_management_event` and `wallet_managed_position` evidence is needed.

### F-7 EGLDUSDT re-entry after a loss [PROJECT EVIDENCE + AGENT INFERENCE]
- Position 143 opened 1h39m52s after 137 closed at a loss (-0.075, the largest in the set).
- The FIX-122 evidence exclusion (`StopLossEvidenceService`) is documented as keyed on the last *stop-loss* (TRADING_RULES §4). 137 closed by `SELL_CONFIRMED`, not by a stop-loss. So that guard probably did not apply [inference, not verified in code this iteration].
- This is a candidate pattern, not a defect.

### F-8 Signal exits fire before SL is reached [AGENT INFERENCE]
Five of the six trades closed on multi-timeframe bearish confirmation, not on SL. Holds ran from 3.5 to 55 minutes. Whether these exits saved money (price later went lower) or wasted it (price recovered to TP) is the main outcome question. Following AGENTS.md, I'll evaluate that separately from entry quality.

### F-9 The code baseline may differ from the code that ran [PROJECT EVIDENCE]
The working tree has many uncommitted modifications (git status), including `LivePositionProtectionService` and `ExecutionIntelligenceService`. The code citations above describe the *current working tree*. The version deployed on 2026-10-11/12 is not established.
