## FINDINGS

**F1 – The BUY decision cannot be reproduced in Replay without either changing Production code or ignoring the document's own rules.**
- The document requires Replay-local copies of the decision rules. Rules O-1, R156-09, RET-08 and T156-05c, and your finding USR-REV-002, all say Replay must never call the shared BUY validation (`validateBuy`).
- But Replay's BUY decision today is Production's own `ExecutionIntelligenceService.evaluateBuy`. That method calls `validateBuy`, and the wake-up path calls `validateBuyContext`.
- So avoiding `validateBuy` means one of two things:
  - change Production code, which is forbidden; or
  - rewrite the whole BUY path inside Replay (`ExecutionIntelligenceService` is over 2,600 lines). INFERENCE: that copy would drift every time Production changes, which breaks your rule that Production enhancements must also reach Replay.
- Your `wallet_settings` waiver allows the other route: reuse the shared services. The document has not been revised to say so.

**F2 – Nothing in the document keeps Replay in step with future Production changes.** There is no rule that a Production fix must update Replay and add a register row. There is no test that fails the build when a Replay copy and its Production counterpart disagree.

**F3 – Some registry items would require editing Production classes, and none says whether it is Replay-only or Production-loaded.**
- R156-05 names `ExecutionReplayScope`. That class is checked by 12 Production classes, including `ExecutionIntelligenceService`, `TradeExecutionValidationService`, `EntryConsumptionPolicy` and `BtcMarketContextService`.
- R156-06 names the price-event projection and DTO. `MarketPriceEventService` is a Production class, and its `PriceEvent` record has no `id`.
- D50–D52 ask for "fail closed" behaviour inside `EntryConsumptionPolicy`, which is also a Production class.

**F4 – The document is out of date and is not self-contained.**
- The required specification file still holds the old RPR-0.4 draft. Its items RPR-02, RPR-03 and RPR-04 call for a Replay account profile, extracting a paper-wallet policy with Production adapters, and a multi-symbol coordinator. All three contradict your rules.
- Section 3.3.1, rows D02–D29 and S01–S14 exist only in RPR-0.9.12, which is in your Downloads folder, not the repository.
- §12 says no FIX-156 code has started. In fact a Replay-only foundation already exists: the `regression/replay/*` classes, migration `V110`, and two tests. The status report and `JEAN_REVIEW_FIX-156.md` both say so.
- §12 also requires approval from both agents, but your formal review mode (JEAN_REVIEW) is active and removes that requirement.

**F5 – Waiving `wallet_settings` also waives decision settings that are not about the wallet.**
- That table holds the execution profile (`executionProfile`: CONSERVATIVE, BALANCED or AGGRESSIVE) and the new-BUY-transition switch (`requireNewBuyTransition`).
- It also holds the dynamic-profit-lock switch and its percentages.
- No history or audit table exists for these settings. Historical values cannot be rebuilt, so Replay will always use today's values.
- As a result, R156-04(b), the dated policy profile, has no data source.

**F6 – A run-id collision defect in the foundation.**
- "Delete Data" resets the run-id counter for `analysis_test_run`, so ids get reused.
- It does not purge the new `replay_*` tables, and `replay_policy_profile` uses `run_id` as its primary key.
- Once ids are reused, a new run either fails on a duplicate key or picks up an old run's fixtures and output.

**F7 – Some Replay table access is not on any allow-list.**
- Replay reads `fix122_replay_revision`, which is not on any allow-list. That read also still drives the pre-FIX-122 selector that RET-05 is supposed to retire.
- `ReplayAccessPolicy` checks only table names, so it cannot enforce the per-statement rules in §4.2a. This confirms your USR-REV-001.

**F8 – D22 is confirmed.** Production's take-profit-extension path passes a literal `true` for the profit-lock switch. Replay passes the administration toggle instead. Production's normal profit-lock path checks the toggle first and then passes `true`, so it is equivalent there.

**F9 – D56 is confirmed, and it affects decisions.** Signals regenerated in memory have no id. A missing id is treated as "not consumed", so in Replay the new-BUY-transition rule never blocks a repeat entry, while Production does block it. INFERENCE: Replay can fix this on its own side with synthetic negative keys.

**F10 – Two gaps not in the register.**
- FIX-154 (the higher-timeframe BUY check) is not in the register. Replay inherits it today only because it calls `evaluateBuy` directly. Whether regenerated signals carry the right data-quality flag (`dataQualityValid`) as of their own time is not proven.
- When Replay runs `validateBuy`, it increments Production's FIX-154 metrics. The audit write is guarded against Replay; the metric counters are not.
