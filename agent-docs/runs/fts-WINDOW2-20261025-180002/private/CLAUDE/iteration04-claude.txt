**F-I4-01: trade 182 entered while the 5m was bearish; the BUY checks never saw it. (PROJECT EVIDENCE + code)**

1. **The 5m was originally bearish for 12 bars in a row.** Signals 175399 to 176792 (generated 09:05:03 to 10:00:05 KSA = 06:05–07:00 UTC) all had `original_decision` SELL or STRONG_SELL, but their stored `decision` was NEUTRAL (I2-003).

2. **Why they were neutralized.** A 5m signal checks the 15m and 1h signals above it (`MultiTimeframeConfluenceService.java:297-298`).
   - Under TREND_FOLLOWING, `isBearish(decision) && counts.bullish() > 0` turns the signal NEUTRAL (lines 136-138).
   - A higher-timeframe signal counts as "bullish" when its trend score is at least 15, even if its decision is only WATCH (lines 24, 337-339).
   - The 1h signal 175258 (generated 09:00:04 KSA) was **WATCH with trend 16**. That alone qualifies.
   - The timing fits exactly:
     - 5m 176792 (10:00:05.676 KSA) was still neutralized. The new 1h 176791 (NEUTRAL, trend 13) was written 0.34 s later, at 10:00:06.015.
     - The next 5m, 176934 (10:05:03.926 KSA), kept **STRONG_SELL**, because the 1h trend was now 13, below 15.
   - The 15m context is unverified (DBQ-CLAUDE-I4-001).

3. **The BUY route read only the post-neutralization decision.**
   - The FIX-154 check `HigherTimeframeBuyAssessmentService.java:20-25` vetoes on `decision`, not `original_decision`, so there was no `5M_BEARISH_VETO`.
   - Then `TradeExecutionValidationService.java:263-283` (FIX-11G) needs only "5m NEUTRAL + 1h WATCH". It granted a 25% entry with `BALANCED_NEUTRAL_5M_WATCH_1H` (wallet message 451).
   - **Net effect:** the same 1h WATCH (trend 16) both hid the 5m bearish signal and authorized the entry.

4. **Other routes do look at the original decision.** SETUP_TIMEFRAME_ATR, BREAKOUT_RETRACEMENT, REVERSAL_RETRACEMENT and SCOUT all check `isBearish(five.getOriginalDecision())` (`ExecutionIntelligenceService.java:1478, 1542, 1634, 1368, 1425`). Only the direct-BUY route skips it.

5. **The exit was the same switch flipping back.** At 10:05:18.504 KSA (07:05:18.504 UTC), 1m SELL + 5m STRONG_SELL + 1h NEUTRAL gave `SELL_CONFIRMED` (`PositionExitPolicy.java:35-44`). The market had not changed: the 5m had been bearish since 09:05. Only the 1h trend score crossing 15 changed what the system saw.

**Verdict:** this is a confirmed inconsistency in the entry logic (logic defect candidate). It is not stale data and not an execution delay. The study does not show how big its effect is across all trades; DBQ-CLAUDE-I4-004 measures that.

**F-I4-02: trade 143's entry used a 5m BUY that a 5m WATCH had replaced 2 ms later. (PROJECT EVIDENCE + code)**
- **The 2 ms race:**
  - 1m signal 159408 was generated at **22:40:01.633945 KSA** (19:40:01.634 UTC).
  - The 5m signal for the same close boundary, 159407 (WATCH, BREAKOUT), was generated at **22:40:01.635944 KSA**, 2 ms later (I2-001, I2-003).
- **Why the 1m saw the older 5m:**
  - Production sets `generatedAt = Instant.now()` when analysis *starts* (`AnalysisService.java:150`).
  - All context lookups are "at or before generatedAt" (`ExecutionIntelligenceService.java:2455-2461`; `MultiTimeframeConfluenceService.java:61-63, 109-111`).
  - So the 1m saw the previous 5m bar, 159285 **BUY** (22:35:01.553 KSA). Its stored `confluence_higher_decision = BUY` confirms this.
- **SETUP_TIMEFRAME_ATR depends on that 5m BUY.** It requires `isBullish(five.getDecision())` (`ExecutionIntelligenceService.java:1485-1487`). With 159407 (WATCH) the route returns null. The fill message even cites "the fresh 5m BUY".
- **The fill-time re-check did not catch it.** `revalidateAtExecutionPrice` (`ExecutionIntelligenceService.java:1150-1169`) re-checks the stop, the target and entry quality, but not 5m/1h context. The BUY filled at 22:40:03.115 KSA, 1.48 s after the WATCH existed.
- **Rest of the context:** the 1m itself was WATCH with `WAIT_FOR_RETRACEMENT`, 0% recommended size, and RSI about 84 (F-I2-05).

**Verdict:** this is a confirmed race at the 1m/5m candle boundary (logic defect candidate). When the 1m worker wins, it uses the previous 5m bar, and that bar is up to 5 minutes old. It is not look-ahead, but it is not the current state either.

**F-I4-03: Replay parity for F-I4-02 is doubtful. (AGENT INFERENCE + code)**
- Replay's `ExecutionReplayScope.recent` (`ExecutionReplayScope.java:106-116`) filters with `!generatedAt.isAfter(ref)`.
- Replay passes an explicit `evaluationTime` into `buildSignal` (`AnalysisService.java:172, 190`). If the 1m and 5m share the same evaluation time (the boundary), the 5m is included, the 1m sees the WATCH, and **Replay would not reproduce trade 143's entry**.
- Production's ordering depends on thread timing; Replay's is fixed.
- I have not traced who passes `evaluationTime` in Replay (U-I4-03).

### DB_REQUEST
QueryId: DBQ-CLAUDE-I4-003
Purpose: U-I4-04. For each executed initial BUY, compare the 5m the 1m confluence used with the 5m whose candle closed at the same boundary.
SQL:
SELECT w.id AS wallet_id, w.symbol, w.execution_reason, s.id AS sig_1m, s.generated_at AS gen_1m, s.confluence_higher_decision, s.confluence_higher_signal_generated_at,
 f.id AS five_same_boundary, f.generated_at AS gen_5m, f.decision AS five_decision, f.original_decision AS five_original
FROM crypto_ai.wallet_trade w
JOIN crypto_ai.trade_signal s ON s.id = w.signal_id

ORDER BY w.executed_at DESC
LIMIT 100;

### DB_REQUEST
QueryId: DBQ-CLAUDE-I4-004
Purpose: U-I4-05. Population of closed positions whose latest 5m at entry was "masked bearish" (decision non-bearish, original bearish), with outcomes.
SQL:
SELECT masked, COUNT(*) AS n, SUM(realized_pnl > 0) AS wins, SUM(realized_pnl < 0) AS losses, ROUND(SUM(realized_pnl), 6) AS pnl_sum
FROM (
  SELECT p.id, p.realized_pnl,
   (SELECT CASE WHEN f.decision NOT IN ('SELL','STRONG_SELL') AND f.original_decision IN ('SELL','STRONG_SELL') THEN 'MASKED_BEARISH_5M' ELSE 'OTHER' END
      FROM crypto_ai.trade_signal f
     WHERE f.symbol = p.symbol AND f.interval_code = '5m' AND f.generated_at <= s.generated_at
     ORDER BY f.generated_at DESC LIMIT 1) AS masked
  FROM crypto_ai.paper_position p JOIN crypto_ai.trade_signal s ON s.id = p.signal_id
  WHERE p.status IN ('CLOSED','STOPPED') AND p.closed_at IS NOT NULL
) t
GROUP BY masked
LIMIT 5;
### END_DB_REQUEST
