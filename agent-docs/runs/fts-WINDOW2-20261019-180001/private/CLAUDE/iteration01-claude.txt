### F-2: Selection scope [PROJECT EVIDENCE: DBQ-FTS-002]
The rule `status=CLOSED` leaves out all 75 `STOPPED` rows, and every one of them has negative P&L. Stop-loss closes are written as `PositionStatus.STOPPED` (`LivePositionProtectionService.java:178`, `PaperTradingService.java:183`). So this study only covers losses that happened above the stop: signal-driven or profit-lock exits. That matches the charter and does not affect the frozen set, but the final report needs to say it.

### F-3: Two exit paths, identified by close_reason [PROJECT EVIDENCE: code] [AGENT INFERENCE until audit rows are queried]
- **`SELL_CONFIRMED` / `HTF_SELL_CONFIRMED` (182, 172, 158, 137):** these codes come only from `PositionExitPolicy.evaluateNormalExit` (`PositionExitPolicy.java:29,42`). It runs from the live price path at `LivePositionProtectionService.java:235-238`. The signal path in `PaperTradingService.java:207-208` writes `signal.getDecision().name()` instead, meaning SELL or STRONG_SELL. So these four were most likely closed by the live price-event path.
- **`STRONG_SELL` (162):** matches the signal path (`PaperTradingService.java:197-208`), which passed `validateSell` and found no active profit lock. The exit price would then be `signal.latestPrice`, not a tick.
- **`PROFIT_LOCK_HARD_EXIT` (143):** two code paths can produce it:
  1. `TP_EXTENSION_REBASE` with price below entry×1.0005 (`DynamicProfitLockService.java:164-166`).
  2. Lock triggered with price below the hard floor (`LivePositionProtectionService.java:210-214`).

  Either way, within 3.5 minutes the position must have reached either the take-profit (TP extended) or about 70% progress, and then printed below entry without first touching the stop. A negative P&L on a "profit-lock" exit is possible because the floor check only looks at `price < floor` and does not require `price ≥ entry`. Which path fired is UNKNOWN until `position_management_event` is queried.

### F-4: Code observation to test, not a confirmed defect [PROJECT EVIDENCE: code]
`LivePositionProtectionService.java:95-97` takes the most recent 1m/5m/1h `trade_signal` by `generated_at`. It applies no freshness limit and does not filter by `signal_mode`, so `HISTORICAL_ONLY` signals are not excluded. `PositionExitPolicy` then acts on those decisions with no check on whether the trade is in profit or loss. Two consequences:
- Normal exits are allowed to close below entry by design.
- A stale or historical 1h/5m SELL could in principle drive `HTF_SELL_CONFIRMED` or `SELL_CONFIRMED`.

Whether that happened in any of the four live-path exits is what DBQ-CLAUDE-I1-004/005 should establish.
