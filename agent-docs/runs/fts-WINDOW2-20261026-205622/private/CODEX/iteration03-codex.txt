- The snapshot is 2026-10-26 18:07:57 UTC / 20:56:22 KSA. No accessible application-log archive is dated after 2026-10-19.

These files therefore cannot establish latency, errors, or protection behavior for any frozen trade unless DB rows later prove a trade fell within their historical coverage.

**PROJECT EVIDENCE:** The present application log contains no correlation line for paper-position IDs `182, 172, 162, 158, 143, 137`. Its short run also reports zero committed inputs and Binance DNS/bootstrap failures, so it is not evidence about the frozen trades.

**PROJECT EVIDENCE:** Current source has useful timing evidence, but it is not directly keyed to `paper_position.id`:

- Protection outcomes are durably identified by `market_price_event.id`, symbol, observation UTC/KSA, and outcome after transaction commit ([MarketPriceEventService.java](/C:/workspace/crypto-ai-trader-mysql/src/main/java/com/crypto/market/service/MarketPriceEventService.java:82)).
- Protection logs label `positionId` using the managed-wallet position identifier, not the authoritative paper-position ID ([LivePositionProtectionService.java](/C:/workspace/crypto-ai-trader-mysql/src/main/java/com/crypto/position/service/LivePositionProtectionService.java:193)).
- Paper closure stores `closed_at=Instant.now()` only after the mechanical-exit call succeeds, and does not emit the paper-position ID ([LivePositionProtectionService.java](/C:/workspace/crypto-ai-trader-mysql/src/main/java/com/crypto/position/service/LivePositionProtectionService.java:391)).
- JDBC timing logs redact bind values, so they cannot independently tie a statement to a frozen position ID ([JdbcTimingDataSource.java](/C:/workspace/crypto-ai-trader-mysql/src/main/java/com/crypto/infrastructure/diagnostics/JdbcTimingDataSource.java:103)).

**AGENT INFERENCE:** Any log claim needs a durable bridge from frozen `paper_position.id` to symbol, time window, linked signal, managed/wallet position, and relevant price-event IDs. Matching by a bare logged `positionId` would be unsafe.

**PROJECT EVIDENCE:** The source’s stage timer only logs successful Kline stages when they take at least one second; failures are logged. Thus, lack of a `[FIX-129][STAGE_TIMING]` entry cannot prove that a sub-second stage occurred or that no timing issue existed ([KlineTiming.java](/C:/workspace/crypto-ai-trader-mysql/src/main/java/com/crypto/infrastructure/transaction/KlineTiming.java:28)).

**PROJECT EVIDENCE:** Application file logging is asynchronous and configured never to block; saturation can drop file events. Missing log lines are therefore not proof that a trade action did not occur ([logback-spring.xml](/C:/workspace/crypto-ai-trader-mysql/src/main/resources/logback-spring.xml:32)).

### DB_REQUEST

QueryId: DBQ-CODEX-I3-001  
Purpose: Read the actual schema before choosing timing/linkage columns for the frozen trades.  
SQL:
```sql
SELECT
    table_name,
    ordinal_position,
    column_name,
    column_type,
    is_nullable,
    column_key
FROM information_schema.columns
WHERE table_schema = 'crypto_ai'
  AND table_name IN (
      'paper_position',
      'wallet_trade',
      'wallet_managed_position',
      'trade_signal',
      'signal_processing_work',
      'market_price_event',
      'position_management_event',
      'production_exit_audit'
  )
ORDER BY table_name, ordinal_position;

SELECT
    kcu.table_name,
    kcu.constraint_name,
    kcu.column_name,
    kcu.referenced_table_name,
    kcu.referenced_column_name
FROM information_schema.key_column_usage kcu
WHERE kcu.table_schema = 'crypto_ai'
  AND (
      kcu.table_name IN (
          'paper_position',
          'wallet_trade',
          'wallet_managed_position',
          'trade_signal',
          'signal_processing_work',
          'market_price_event',
          'position_management_event',
          'production_exit_audit'
      )
      OR kcu.referenced_table_name = 'paper_position'
  )
ORDER BY kcu.table_name, kcu.constraint_name, kcu.ordinal_position;
```
