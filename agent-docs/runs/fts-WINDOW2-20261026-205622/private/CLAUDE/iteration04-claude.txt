**F-21 — Live exits fire within 19–58 ms of the next price update** (PROJECT EVIDENCE: I3-001, I3-002, I3-004)

This corrects Iteration 3 F-14, which timed the lags from the 1m signal instead of the 5m/1h signal that completed the exit condition.

- **Why:** live exits are evaluated only inside `onPrice` (`LivePositionProtectionService.java:54-71`), and there is no timer.
- **Gaps between price updates:** SHIB had no recorded update from 07:15:03.48 to 07:15:43.47 UTC (10:15:03 to 10:15:43 KSA). ACE had none from 10:05:02.47 to 10:05:18.48 UTC.
- **No filtering in the ingester:** `BinanceKlineService.java:91-111` writes a price row for every 1m kline message without filtering. So a gap means either Binance sent nothing or a message was rejected or rolled back (Iteration 3 F-18). DBQ-CLAUDE-I4-006 checks trade counts in those candles.
- **Assessment:** a design property, not a defect. In these four trades it cost nothing. On a fast-moving symbol a 40 s wait could cost money.
- **Clock observation (minor):** several price rows were stored about 50–150 ms *before* their Binance event time (for example observed 21:00:00.021, stored 20:59:59.975). That suggests the server clock runs slightly behind Binance's. FIX-153 corrects for this in its freshness check (`:66`).

**F-22 — Trade 182: the 5m STRONG_SELL was neutralised by its own 1h check, and the 1m gates read only the neutralised decision** (PROJECT EVIDENCE: code + I3-005; the route code needs DBQ-CLAUDE-I4-001)

*How the 5m SELL became NEUTRAL:*
- The higher timeframes checked for a 5m signal are 15m and 1h (`MultiTimeframeConfluenceService.java:298`).
- The application only analyses 1m, 5m and 1h (`application.yml:93-96, 114-117`). So no 15m signal exists, and in practice the 1h signal is the only check on a 5m signal (I4-003 verifies this).
- Under TREND_FOLLOWING, a bearish 5m becomes NEUTRAL whenever any higher signal counts as bullish (`:136-138`). "Bullish" includes a 1h signal whose trend score is at least 15 (`:24, 337-338`), even if its decision is only WATCH.
- The trading decision is stored as `decision` and the raw strategy decision as `original_decision` (`AnalysisService.java:410-411`). Entry stays allowed (`:137`), which matches `primary_blocking_stage` NULL on #176655 and #176792.

*Where only `decision` is read:*
- **The 1m signal's own confluence check.** `hasHardBearishOpposition` (`:146-151`) checks `getDecision()` only. If 5m #176655 had kept STRONG_SELL, the BUY would have been vetoed to WATCH (`:120-122`). With 5m NEUTRAL and trend 10 (at the limit of 10), it falls into `hasNeutralWeakStructure`, which records CONFLICT but keeps the BUY (`:128-130`).
- **Execution approval.** Two entry rules approve a BUY when 5m is NEUTRAL: `balancedBuyWithNeutralFiveException` and the FIX-11G rule `BALANCED_NEUTRAL_5M_WATCH_1H` (`TradeExecutionValidationService.java:218-284`). The FIX-11G comment says "neither timeframe is bearish", but that is judged on the neutralised decision.
  - **Inference:** trade 182 entered through FIX-11G (5m=NEUTRAL, 1h=WATCH, 25% size). DBQ-CLAUDE-I4-001 confirms this from `wallet_trade.execution_message`.
- **The exit policy.** `PositionExitPolicy.decision()` (`:95-97`) uses only `decision`. With 5m held at NEUTRAL, `SELL_CONFIRMED` could not fire until #176934 kept STRONG_SELL.

*The inconsistency:*
- Other guards in the same service read the raw value through `strongerDecision(decision, original_decision)`:
  - the BALANCED_EARLY post-bearish guard (`ExecutionIntelligenceService.java:2092, 2100`)
  - the bearish-reversal anchor (`:2449`)
- So the codebase already treats a hidden bearish 5m as relevant evidence in some places and ignores it in others.

*Assessment:*
- A likely design gap, a "candidate logic defect". It is not confirmed until the route code is verified and the trade is replayed.
- It is separate from FIX-154, which covers bearish 1h evidence blocking a 1m BUY.
- The entry judgement uses only information available at 09:57 UTC (12:57 KSA).

**F-23 — The paper-close gap sits inside one transaction, probably a whole-portfolio revaluation** (PROJECT EVIDENCE: code; the cause is AGENT INFERENCE)

*The transaction:*
- `executeMechanicalExit` is `@Transactional` (`WalletAutoExecutionService.java:474`) and joins the outer `onPrice` transaction.
- The paper and wallet rows therefore commit together. The 1.2–3.2 s difference is only in when each timestamp was taken.

*What runs between the two timestamps:*
- `wallet_trade.executed_at` is set at `:548`. After that the code:
  1. Updates daily statistics, which calls `currentPortfolioValue()` (`:553-559`).
  2. Calls `captureSnapshot()` (`:560`).
- Each of those loops over every `wallet_asset` row and runs one latest-closed-1m-candle query per asset (`WalletService.java:484-490, 600-607`). `captureSnapshot` also sums all of `wallet_trade` and the cash flows.
- Only after that does `closePaper` stamp `closed_at = Instant.now()` (`LivePositionProtectionService.java:405`).

*Why it may be slow:*
- I found no index on `candle(symbol, interval_code, closed, close_time)` in the migrations I searched.
- The query sorts by `close_time DESC`, so it may sort every 1m row for each symbol. DBQ-CLAUDE-I4-003 checks this.

*Side effect (inference):* during those 1–3 s the transaction holds the global daily-statistics row lock (`SELECT … FOR UPDATE`). That would hold up every other wallet entry or exit, on any symbol, until the transaction commits.

*Consequences:*
- `paper_position.closed_at` is not the decision time. Exit timelines should use `wallet_trade.executed_at`.
- Exit prices are unaffected: the price is fixed before this work starts.
- **Resolves U-16 at code level and narrows U-11.** The timing split needs I4-003/I4-004.

**F-24 — Replay processes 5m before 1m at shared boundaries; Production races them** (PROJECT EVIDENCE: code; the per-trade outcomes are AGENT INFERENCE)

*How Replay orders signals:*
- Replay stamps each signal at exactly the candle-close boundary: `evaluationTime = openTime + interval` (`RegressionTestWorker.java:584`).
- At the same boundary it processes 1h, then 5m, then 1m (`:557-560, 787-793`).
- Lookups use generated time ≤ the reference time, inclusive (`ExecutionIntelligenceService.java:2606-2608`; `MultiTimeframeConfluenceService.java:105-112`).
- So a Replay 1m signal at :00 or :05 always sees the 5m signal for the bar that just closed.

*What Production did instead:*
- Production's choice depended on which signal happened to be generated first, by a few milliseconds (Iteration 3 F-12/F-13).

*Per-trade consequences (inference):*

| Trade | Production | Replay (inferred) |
|---|---|---|
| 143 | 1m #159408 used the older 5m BUY #159285; trade opened through `SETUP_TIMEFRAME_ATR` | Sees the 5m WATCH for the 22:35 candle; `setupTimeframeAtrAuthoritySignal` returns null, so **trade 143 probably does not open** |
| 158 | Entered later through the wake-up route, at 25% | The 1m sees 5m BUY directly; probably a different route, and possibly a different size |
| 137 | Used #156594 | Uses the #156721-equivalent; both NEUTRAL, so likely the same decision |

*Assessment:*
- A Production/Replay parity gap that affects 2 of every 10 1m signals: the ones at :00 and :05 of each 5-minute block.
- It is not a look-ahead in either system: both use only signals generated at or before the reference time.
- Confirming it needs a Replay run over 2026-10-11 22:30–22:45 UTC for EGLDUSDT and 2026-10-12 02:25–02:40 UTC for XRPUSDT. I cannot start one in analysis-only mode.
