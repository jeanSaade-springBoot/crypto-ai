## FINDINGS

### R1: In Production, the 1m signal usually cannot see the 5m signal for the same close. CONFIRMED by database and code
**PROJECT EVIDENCE**
- Query I3-002 looked at 11,434 1m signals that close on a 5m boundary, from 10-11 to 10-17.
- In **9,843 of them (86.1%)** the 1m was generated before its 5m, by 401 ms on average.
- Production looks up the 5m and 1h signals with "generated at or before the 1m's generation time":
  - `ExecutionIntelligenceService.java:2455-2462, 2606-2608`
  - `TradeExecutionValidationService.java:367-378`
  - `MultiTimeframeConfluenceService.java:105-113`
- So at those boundaries the 1m normally uses the previous 5m, which is 5 minutes older.
- Replay is different:
  - It stamps each signal at the candle close (`RegressionTestWorker.java:584, 616`).
  - It processes 1h, then 5m, then 1m when closes coincide (`:557-560`, `:787-793`).
  - Its lookup includes equal times (`ExecutionReplayScope.java:118-119`).
  - **So Replay always sees the 5m for the same close.**

**AGENT INFERENCE**
- This is a structural Production/Replay mismatch on about 20% of 1m decisions.
- FIX-141 already fixed the same problem, but only for the BTC context (`ExecutionReplayScope.java:122-128`).
- It breaks the "Replay = Production" rule written into `TradeExecutionValidationService.java:209-211, 259-262`.

### R2: The system only corrects for the late 5m when it is bullish. CONFIRMED by code and database
**PROJECT EVIDENCE**
- When the late 5m is a BUY, the FIX-014 and FIX-023 wake-up hooks re-check the opportunity (`ExecutionIntelligenceService.java:284-457`).
- When the late 5m is WATCH, NEUTRAL or SELL, nothing re-checks an entry already approved on the older 5m.
- I3-002 lists 30 wallet BUYs since 10-11 where the 5m for the same close arrived after the 1m:
  - **11** were wake-up entries, where the compensation worked.
  - **17** went through other routes while that later 5m was WATCH or NEUTRAL.
- One of the 17 repeats trade 143's pattern exactly: wallet trade **255 (ONG)**, SETUP_TIMEFRAME_ATR, with a 5m WATCH generated 1.0 ms after the 1m.

**AGENT INFERENCE**
- The bias favours entering: a stale bullish 5m counts as authority, and a late bullish 5m gets a second chance, but a late non-bullish 5m is never applied.
- The real effect on the 17 depends on each route; query I4-003 measures it.

### R3: Trade 143 would not have opened if 5m signal 159407 had been visible. This closes U2 with high confidence (code trace)
**PROJECT EVIDENCE.** Going through the route order in `evaluateBuyInternal` (`ExecutionIntelligenceService.java:548-649`):
- **Scout and breakout retracement** need ATR immediate-entry permission (`:1051`, `:1519`). Signal 159408 did not have it.
- **Deferred continuation** (`:1725-1754`) accepts a 5m WATCH or BUY alike. It already returned nothing with the BUY scoring 83, so it cannot pass with the WATCH scoring 76.
- **Reversal retracement** (`:1609-1637`) also returned nothing with the BUY.
- **Higher-timeframe transition** (`:1408-1424`) needs a bullish 1h. The visible 1h was NEUTRAL.
- **SETUP_TIMEFRAME_ATR** requires the 5m decision to be bullish (`:1486`). With WATCH 159407 it returns nothing.
- The entry then reaches the ATR check and is **rejected as ATR_ENTRY_BLOCKED** (`:644-648`).

**AGENT INFERENCE**
- The only remaining doubt is whether reversal retracement returned nothing because of the 5m momentum, MACD or RSI scores. Query I4-002 checks those.
- Trade 143 is upgraded to a **logic/parity defect: the entry existed only because of a 2 ms ordering race.** Replay would most likely not open it.

### R4: Trade 158 would take a different route in Replay. Code inference
**PROJECT EVIDENCE**
- The FIX-023 wake-up needs the latest 1m signal to be at most 45 seconds old (`SETUP_WAKEUP_1M_MAX_AGE`, `ExecutionIntelligenceService.java:71, 420-424`).
- In Replay the 5m is processed before the 1m for the same close, so the latest 1m it finds is the previous one, 60 seconds old. The hook therefore does nothing.
- Replay's own 1m signal 165412 would see the 5m BUY directly and take SETUP_TIMEFRAME_ATR, capped at 30% (`:1499`), instead of the wake-up's 25% cap (`:440`).

**AGENT INFERENCE**
- Replay probably reproduces the entry, but with a different route, size cap and audit trail.
- The same applies to all 11 wake-up entries in I3-002.

### R5: Trade 182 shows that code paths treat the original 5m decision inconsistently. CONFIRMED in code
**PROJECT EVIDENCE**
- Three routes explicitly reject a 5m whose original decision was bearish, even if it was later softened:
  - the FIX-014 wake-up (`ExecutionIntelligenceService.java:327, 337, 355`)
  - the higher-timeframe transition (`:1425-1426`)
  - reversal retracement (`:1634`)
- The direct-BUY path that opened 182 (`TradeExecutionValidationService.java:81-112`) reads only the softened decision.
- So 5m signal 176655, NEUTRAL but originally STRONG_SELL, was accepted by the 25% "5m NEUTRAL + 1h WATCH" rule (FIX-11G). That rule's own comment assumes "neither timeframe is bearish" (`:251-253`).
- The softening happens in `MultiTimeframeConfluenceService.java:136-138`: a bearish 5m becomes NEUTRAL when any higher timeframe counts as bullish. A 1h WATCH with trend score 16 counts, because the threshold is 15 (`:24`).

**AGENT INFERENCE**
- Classification: **logic gap (inconsistent rules), high confidence.** What the intended rule should be needs a decision from Jean or the team.
