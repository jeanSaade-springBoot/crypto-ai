### 3. New findings

**N22: In Production, stops taken on the signal path create no FIX-122 boundary. Replay gets this wrong in both modes.** [PE]
- **How Production handles it:**
  - On every signal while a position is open, Production first runs `PositionManagementService.analyze` (`PaperTradingService:115-121`).
  - If the price is at or below the stop, it sells the wallet position and records the reason as `POSITION_STOP_LOSS` (`PositionManagementService:73-76, 129-139`; `WalletAutoExecutionService:285-373`, reason at `:355`).
  - That sale closes only the wallet position. With no open wallet position left, the profit-lock check returns inactive (`DynamicProfitLockService:71-76`), so the signal path closes the paper position as `STOP_LOSS` (`PaperTradingService:182-185`). The wallet exit then finds nothing open and writes nothing (`WalletAutoExecutionService:216-222`).
- **Why FIX-122 ignores it:** FIX-122 reads boundaries only from sells recorded as `STOP_LOSS` (`StopLossEvidenceStore:14-16, 37-45`). Stops on the live price path are recorded as `STOP_LOSS` (`LivePositionProtectionService:174-183`), so only those count.
- **What Replay does:**
  - Fallback mode records a boundary for every signal-path stop (`ShadowProductionReplayService:596-597, 201`; `ExecutionReplayScope:49-55`).
  - Exact-price mode has no signal-path stop at all.
- [AI] **Consequences:**
  - A fallback run can exclude evidence that Production went on using.
  - In exact-price mode, suppose the live path didn't apply a candle's closing price (for example, it was rejected as non-canonical). Production then exits at that close through the advisory stop, while Replay stays open until a later accepted price. The exit price, exit reason and boundary all differ.
  - Paper and wallet records give different reasons for the same exit: `STOP_LOSS` vs `POSITION_STOP_LOSS`, and for profit-lock exits `PROFIT_LOCK` vs `POSITION_PROFIT_LOCK` (`PaperTradingService:467`; `WalletAutoExecutionService:449`). A comparison has to say which record it trusts.
  - The comment at `StopLossEvidenceStore:14-15` assumes signal-path stops are recorded as `STOP_LOSS`. So this may be unintended Production behaviour. It needs separate investigation and approval; Replay should reproduce it, not fix it.
  - It only happens when the live path didn't already apply that closing price, so it is probably rare. How often it happens is unknown.

**N23: A concrete case where timing at a candle boundary changes entries: the 5m wake-up.** [PE]
- A 5m wake-up entry needs a 1m signal generated no later than the 5m signal and at most 45 seconds earlier (`ExecutionIntelligenceService:71, 315-321, 420-428`).
- **Replay:**
  - Gives every signal its candle-close time as its generated time.
  - Processes the 5m signal before the 1m signal at the same boundary.
  - Holds the run's whole signal list and filters only by generated time (`ShadowProductionReplayService:65-69, 103, 1029`; `ExecutionReplayScope:106-120`).

  So the 1m signal from the same boundary is always visible, at age 0.
- **Production:** the generated time is the wall-clock time when analysis started (`AnalysisService:150`). The same-boundary 1m signal is visible only if its analysis started no later than the 5m's, and had been saved.
- [AI] So Replay can open wake-up entries that Production could not. Production's stored generated times show which analysis started first, but the save time isn't stored. That evidence is necessary but not sufficient. This should be a mandatory test case under R-14.

**N24: Replay signal IDs (R-36) must never be able to match a Production ID.** [PE]
- Production code looks up executed trades by signal ID (`PaperTradingService:228-231, 395-396`; `EntryConsumptionPolicy:29-32`).
- A signal is a database entity whose ID the database assigns (`domain/TradeSignal:14-15`).
- FIX-122 writes the signal ID into a table shared with Production (`StopLossEvidenceService:145, 157`).
- [AI] **Risks:**
  - Reusing the generated keys from `trade_signal_test` could produce numbers that equal real `trade_signal` IDs.
  - Setting an ID on an unsaved signal would make any later save update an existing row instead of inserting a new one.
  - Getting keys from `trade_signal_test` would also mean writing before the evidence check, which conflicts with R-11.

**N25: Production also exits on 5m and 1h signals.** [PE]
- Production checks TP, profit lock, stop loss and the hard floor on a signal of any interval whose price is valid for the position (`PaperTradingService:125-195`; `PositionPriceAuthorityPolicy:23-37`).
- Only SELL is limited to 1m signals (`TradeExecutionValidationService:354-357`).
- Replay's exact-price mode does none of these checks.
- [AI] At a shared candle boundary, whichever signal Production processes first closes the position. That signal is then recorded as the exit signal in opportunity memory (`ExecutionIntelligenceService:820-839`).

### 4. Production records that could serve as a comparison source (refined)

**`fix122_evaluation`** [PE]
- **What gets written:** Production writes a row for every entry check made while the symbol has no open position. That includes:
  - wake-up checks triggered by 1m and 1h signals, which produce `NO_WAKEUP` rows;
  - entry checks on 5m and 1h signals, which produce `CONTEXT_ONLY` rows.

  (`PaperTradingService:298-311`; `StopLossEvidenceService:48-56, 140-159`; `ExecutionIntelligenceService:470-472`.) Replay doesn't make those calls, so it writes none of these rows.
- **Timestamps:** in Production the evaluation time is the wall clock; in Replay it is the replay's reference time (`StopLossEvidenceService:42`).
- **IDs:** Replay rows have no signal ID.
- **So a comparison must:**
  - filter by stage, route and result code;
  - match on symbol plus the candle open time stored in the row's payload.

**`buy_htf_assessment_audit`** [PE]
- Written through a background queue that drops rows when full (`BuyHtfAssessmentAuditStore:46-52`).
- Skipped entirely in Replay.

**`signal_processing_work`** [PE]
- Records the completion time (wall clock) and any opened paper position ID (`SignalProcessingStore:101-109`).
