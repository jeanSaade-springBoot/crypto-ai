# FIX-150 — protection fence recovery without old-price replay

Status: development candidate. No Java 21 Maven or real MySQL run in this sandbox.

## Incident and confirmed mechanisms

Six events (3076221 ALLO, 3076705 ETH, 3077444 BNB, 3077451 BTC,
3077729 PEPE, 3084348 ACE) retain incomplete protection at phase 1 and matching
REVIEW_REQUIRED active markers. Original errors are unavailable. The mechanism
blocking future work is confirmed; the initiating failure is NOT established.
The source indexes in V103 improve selection but cannot release these fences.
BTC starvation is associated with explicit BTC_CONTEXT_BLOCKED entry vetoes.
Latest logs show 15 other symbols committing work, not full 21-symbol recovery.

## Recovery policy and existing rows

A five-second monitor now calls a separate recovery transaction BEFORE reporting
remaining fences. It runs without operational-readiness permission, but validates
unchanged durable cutover authority. It locks shared symbol state, deliveries,
then the wallet-symbol coordination row. A concurrently executing apply or phase
walker must finish/rollback before recovery obtains the symbol lock. Normal
position creation must finish before recovery obtains the wallet lock.

At most three candidates per symbol are returned per pass. Eligible rows are
canonical 1m, phase 0/1, observed over 15 seconds ago. Legacy/entered candidates
must also have started over 30 seconds ago; CLAIMED work needs no 30-second wait.
All candidates must have
analysis WAITING with no analysis start or linked processing work. A different
active marker prevents retirement. LIMIT bounds returned rows, not examined rows.

New CLAIMED evidence proves the entry-intent transaction was never crossed. An
expired such attempt can be retired without applying the old price, including
when a position exists. Existing LEGACY_UNKNOWN and entered APPLYING attempts
can be abandoned only if both wallet_managed_position and paper_position have
NO OPEN position for the symbol, checked while the wallet fence is held.
Missing trades alone is NEVER accepted as no-effect evidence.

Legacy/entered flat retirement sets protection_outcome=ABANDONED, not APPLIED or
REJECTED. It explicitly retains UNKNOWN_RETAINED past effects. It preserves the
original protection owner, start and last_error. It closes the operational slot,
sets phase 4/HISTORICAL_ONLY, analysis and observer NOT_APPLICABLE, marks a pending
price event HISTORICAL_ONLY, and clears ONLY that event's matching marker. The old
price and old candle are never replayed. No watermark or approval is rewritten.

The update, exact marker release and resolution audit are one transaction.
Every expected guarded mutation must affect one row. Audit failure rolls back
all changes. The audit includes UTC/KSA recovery time, old process and marker
owner, held wallet fence, position check and explicit effect uncertainty.
A delayed old caller sees terminal completion or lost marker ownership and
cannot re-apply the retired observation. This is abandonment policy, NOT a
claim that the original operation rolled back or produced no effects.

This covers the six existing rows ONLY if the runtime paper-position check is
also empty and all other guards still match. Current user results established
no open managed positions; paper state was not yet supplied. The code checks it.
With an open position and legacy/entered uncertainty, recovery remains fenced.
This candidate does NOT guarantee unrestricted recovery of unknown effects.

## Future claim/apply evidence

V104 adds protection_apply_state, with LEGACY_UNKNOWN for ALL existing rows.
No inference is made during backfill. New claims write CLAIMED. Both production
protection callers must commit APPLYING in a separate entry-intent transaction
BEFORE opening the business transaction. CLAIMED therefore means business was
not entered. APPLYING remains conservative uncertainty after crash/exception;
same-token equality never authorizes a second invocation. Business effects and
COMPLETED/outcome commit together in the existing apply transaction.

A late earlier observation or other guarded pre-business return restores
CLAIMED under the symbol lock. This restoration never runs after onPrice or an
exception. Expired CLAIMED observations are atomically retired as NOT_ENTERED/REJECTED by the monitor, together with
the marker/audit, without business invocation. Non-1m deliveries retain the NOT_APPLICABLE guard.

The entry-intent transaction adds a DB round trip/commit per actual protection
attempt. Measure this overhead and stop-crossing latency under MySQL load.
Do not increase pools/timeouts as a substitute for measurement.

## Trace and limits

executeMechanicalExit, dynamic profit-lock and production exit-audit helpers
use ordinary transactional methods in the inspected path. Mechanical exits
write a PAPER_AUTO wallet trade, managed position, balances and snapshot; the
inspected method does not submit a Binance order. Wallet symbol/global mutation
and daily-statistics locks plus snapshot/price reads are further contention
points. There is no proof that any one caused the original six failures.

## Logging, health and configuration

Independent apply failure now records the first exception/cause chain in
last_error after the failed transaction unwinds, without claiming rollback or
retrying effects. Timeout checks preserve that initiating error.
Application logs now persist in logs/crypto-ai-trader.log when launched from
Eclipse. The rolling async appender is bounded/nonblocking and can drop events
under saturation; the DB failure/audit remains the primary durable evidence.
Existing JDBC execute/fetch and transaction timing stays enabled separately in
logs/database-timing.log. Recovery transaction logs give UTC start/end/duration;
committed recovery logs include KSA. Health includes recent retirement audits
so legacy uncertainty does not disappear behind a healthy queue count.

shared-market.fix150.automatic-recovery-enabled defaults true, override via
SHARED_MARKET_FIX150_AUTOMATIC_RECOVERY. FIX-142 must also be enabled. This flag
never grants cutover authority or enables manual resolution endpoints.
V104 runs in crypto_ai. V103 still indexes crypto_ai_v2 source events; do not
change or repair the already-successful V103 history entry.
