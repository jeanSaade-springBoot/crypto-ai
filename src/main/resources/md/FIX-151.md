# FIX-151 — delivery-side contention candidate

Status: development candidate; do not treat as a proven production latency fix.
This candidate extends the FIX-150 source without changing its recovery policy.

## Evidence and scope

User snapshots show consumer-state lock waits for BNB/PEPE/BTC while the owning
transaction executes lane exposure COUNT or oldest unfinished delivery selection.
The original ACE selector chooses uk_shared_symbol_seq, using only symbol:
estimated 17,976 examined rows, no sort, cost 5961.83. Forcing idx_shared_work
estimates 8,536 rows plus a sort, cost 6468.57. These are estimates, not measured
elapsed time, actual rows read, physical I/O or proof of all wallet-lock failures.
Negative transaction ages in the supplied diagnostics are timezone artifacts.

V103/FIX-149 indexes the collector source table in crypto_ai_v2. V105 indexes
shared_market_event_delivery in the trader's active Flyway schema, crypto_ai.
It never targets or modifies the collector table. V1–V104 are unchanged.

## Oldest-delivery selection

The phase-stream fallback retains the exact predicate:
phase < 4 AND status <> 'REVIEW_REQUIRED'. V105 adds a virtual generated flag
phase_walk_pending and an index (symbol, phase_walk_pending, symbol_sequence).
No clock, process-local counter or independent maintenance writer is involved.
MySQL derives the flag from each row's current phase/status and maintains the
index. The query returns only one event ID, then fetches that full row by PK in
the SAME existing symbol-lock transaction. The active-marker ownership and timeout
branches run first exactly as before; fresh price and candle candidate priorities
are unchanged. This is not newer-first catch-up and does not move checkpoints.

The earlier four-phase candidate idea was replaced by this exact-predicate index:
it also preserves phase<4 behavior for unexpected negative phases and avoids
review prefixes needing to be scanned in each phase. No forced-index hint ships.

## Exposure count

The former OR predicate is decomposed into six ID-only SELECTs joined by UNION:
phase-4 uncertain/running/retry; phase-4 live pending/deferred closed window;
active/review marker before phase 4; started-unresolved protection before phase 4;
1m live observation before phase 4; live closed-candle window before phase 4.
UNION, not UNION ALL, counts a delivery once even if multiple evidence categories
match. Same lane, same inclusive clock windows, same single statement snapshot,
same symbol lock, same whole-batch reservation and reserved fresh capacity.
No query runs outside the lock and no reservation check is removed.

The marker branch uses its event PK. Existing analysis/protection/observation
indexes support other categories. V105 adds a covering closed-window index with
(symbol, interval_code, closed, candle_close_time, phase, analysis_status).
Always-counted retained reviews/started uncertainty are intentionally unbounded;
UNION is NOT a promise that all branches examine a constant number of rows or
that temporary materialization cannot become expensive. Measure the real plans.

## Compatibility and risks

Additive V105; no state/evidence UPDATE, delete, owner release or old-price replay.
Existing INSERTs specify column lists. Old binaries can ignore the generated
column/index; new binaries require V105 before using the fallback. Do not drop
V105 objects during a binary rollback. MySQL DDL can partially commit on failure:
inspect actual columns/indexes before repairing a failed migration; do not mark
it successful manually. Index creation requires table scanning/disk space and
metadata locks. Schedule migration while the trader is stopped. Stop old trader
instances before starting the new candidate to avoid overlapping writers.

Extra indexes add write maintenance; the fallback adds one PK round trip, while
UNION may allocate temporary storage. These costs require MySQL load validation.
Existing JDBC execute/fetch/acquisition/transaction logging remains enabled by
its existing configuration; no bind-value logging or retry policy is introduced.

Unresolved analysis reviews still require durable effect/owner reconciliation.
This read optimization does NOT automatically clear the five reviewed analysis
attempts identified in this incident. It also does not certify that wallet-symbol
lock timeouts, slow commits or database pressure have been eliminated.

Production/Replay strategy and exit code are unchanged, but Production timing
can affect operational outcomes. Compare matching Replay windows and run real
protective-exit/stop-crossing tests before deployment acceptance.

## Validation and next steps

Executed here: Java syntax parsing of changed production/test files; 486 old/new
exposure comparisons on 6,000 randomized rows via SQLite, with overlapping
categories, expired/future/null timestamps, retained reviews and missing lanes;
selector equivalence and 35 generated-flag transition checks; SQLite selector
index/no-sort access check. SQLite is NOT MySQL isolation/performance evidence.

Three JUnit/H2 regressions authored, inherited by the disposable MySQL suite:
old/new exposure equivalence, oldest selection across phases with retained reviews,
and generated flag phase/status transitions. These JUnit tests were NOT run here.
Java 21 Maven, actual H2 generated-column compatibility, V105 existing-data
migration, real MySQL plans/lock races and full application load are NOT run.

1. Stop Eclipse trader, use Java 21, run mvn -B -ntp clean verify. Keep collector
   running so durable source observations continue; no collector code is changed.
2. Run the existing fix142-mysql profile on an explicitly disposable test server
   using its schema/loopback/UUID guards. Include V105 existing-data/index checks.
3. On the local deployment database, confirm V105 success and run the included
   read-only scripts/FIX-151-read-only-plans.sql. Capture actual execute/fetch and
   transaction durations from logs; estimate-only EXPLAIN cannot prove recovery.
4. Reproduce backlog with all 21 symbols, compare before/after symbol-lock wait/
   hold, exposure/selector time, Hikari wait, commit duration, live signal close-to-
   generation delay, BTC freshness and protection freshness. Test mixed intervals,
   late arrivals, reviewed owners and crash recovery. Commit acceptance targets
   before the run. Reject the candidate if latency worsens or eligibility differs.
5. Address remaining analysis fences with evidence-based reconciliation, not a
   blanket status reset. Current live progression for ALL symbols is the acceptance
   outcome; successful migration or unit build alone is insufficient.
