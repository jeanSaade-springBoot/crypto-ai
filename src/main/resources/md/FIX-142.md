# FIX-142 development candidate v3 — 2026-10-03

This package implements the agreed admission, delivery ownership, protection, reconciliation and database diagnostics work in one release candidate. It has not been deployed. No production database was connected, no retention cleanup was run and no constraints were removed.

## Protection lockout review correction in v3

The v2 review found a real release blocker. Started-but-unresolved protection attempts had no operator resolution path. The outstanding count and earlier-order barrier could block future price protection indefinitely; a single earlier unresolved attempt can block progress, even before the two-slot cap fills. The previous README understated this as a capacity caveat. Keep v2 scheduling disabled.

V3 adds POST /api/fix142/resolve-protection, protected by ROLE_ADMIN, the existing manual-resolution-enabled flag and X-FIX142-Operator-Review: CONFIRMED. It requires exact symbol, event, protection owner and protection_started_at, the authenticated reviewer, independent owner-fencing proof and verified effects evidence. CONFIRMED_APPLIED must pair with COMMITTED; CONFIRMED_NOT_APPLIED must pair with CONFIRMED_NO_EFFECTS. Bare rollback, age or missing PID is insufficient. These are operator attestations, not a machine liveness proof.

The symbol -> delivery locked transaction records APPLIED or REJECTED and its resolution timestamp and audit together, checks exactly one mutation and audit row, and retains the original owner, start and error. No old onPrice call is replayed, and no marker, analysis or observer review is silently cleared. A fenced marker can subsequently use the existing separate RESUME/RELEASE operation after its own evidence review. An old worker sees completed/fenced state or a changed marker owner and cannot legitimately resume the resolved old attempt through these guarded paths. Truly unresolved cases continue to block until valid evidence exists.

A five-second scheduled monitor fences aged protection starts independently of the recent-price selector, emits PROTECTION_RECOVERY_REQUIRED, and retains uncertainty. The health endpoint reports CRITICAL_OPERATOR_RECOVERY_REQUIRED or UNKNOWN_MONITORING_FAILED; NO_AGED_FENCES_DETECTED only means this query found no aged starts, not that protection is globally healthy. Connect this severity and the recovery/monitor-failure log tags to operational alerting before enabling scheduling. No external notification integration or automatic human fencing is claimed.

Four new delivery regressions cover timeout outside the recent window, two-slot and phase-marker recovery, exact owner/time/effect checks, committed-attempt non-replay and audit rollback. Three controller tests cover disabled/default, confirmation/authentication and principal propagation. They are authored but unexecuted here. V3 changed Java files pass syntax parsing; type-checking/full Java21 and MySQL execution remain release gates. Historical v1 results are now named isolated-v1-test-results.txt to prevent confusion. README is a pointer to this canonical document rather than a second full copy.

See REVIEW-RESPONSE-FIX-142-v3.md for all review comments, operator steps and exact validation status.

## Implemented behavior and code map

- SharedMarketConsumer and Fix142DeliveryProtocol: fresh source admission without advancing the contiguous checkpoint, one symbol-locked whole-batch capacity decision across both admission paths, duplicate identity verification, expired untouched work excluded from admission exposure without deletion, durable event continuation across phase transactions, retained timeout fences, independent ordered 1m protection and recorded APPLIED/REJECTED outcomes. Non-1m deliveries advance normally without protection mutations.
- SharedAnalysisDispatcher: latest eligible live candle selection, live-only saved-signal execution retry, independent bounded completed-work acknowledgment with exact work/signal identity and audit, retained ambiguity/uncertainty, actual submission/commit counters. Historical priority remains oldest-first.
- SharedAnalysisExecutorConfig: historical dispatcher and executor capacity use one validated setting; default remains one, live remains eight. Rejects invalid capacity.
- Fix142HealthService / Fix142DiagnosticsController: cached admin diagnostics, per-lane latest candle timestamps, protection freshness, admission categories, ownership fences, retry/review counts with truncation disclosed, JDBC stats and separately sourced MySQL status. ## Important capacity contract and policy difference requiring review

Admission refuses new work when its lane exposure is already at the configured ceiling. This is an admission-time throttle, not a universal bound on all historical, retry and retained-review work. Active phase ownership is one per symbol; historical analysis is independently capped by dispatcher/executor capacity; uncertain reviews have no eviction cap. Admission reserve and ceiling do not secretly reserve executor slots.

The v15 assertion that an earlier-only ordering barrier limits outstanding protection attempts to one is false when an earlier observation arrives after a later attempt was claimed. This candidate explicitly allows at most TWO outstanding protection attempts per symbol, counted under the symbol lock. It orders/rechecks before application, retains started uncertainty, and logs/defers overload rather than evicting or replaying it. This is a deliberate policy difference, not an already-approved numerical detail. Longer late-arrival chains and stop-crossing behavior under overload must be reviewed and exercised before activation. It does not certify that protection can always remain current while uncertainty is fenced.

## Database start/end logging

Enabled by default: diagnostics.jdbc.enabled=true; slow threshold diagnostics.jdbc.slow-ms=250. Dedicated output defaults to logs/database-timing.log, configurable with diagnostics.jdbc.log-directory. Rolling files: 20 MB, five-day history, 256 MB total cap. Output is written on a dedicated worker, not on the JDBC caller.

Logs correlate operation IDs, transaction IDs and available symbol/event/phase scope. They include UTC and KSA start/end times, monotonic duration, datasource, calling component, SQL operation/table, redacted template/fingerprint, outcome, SQLState and affected/returned counts where available. Connection acquisition, execute, result fetching, transaction commit/full rollback/savepoint rollback and closed-unresolved transaction events are distinct. Autocommit statements are reported as such; no synthetic multi-statement transaction is invented. A transaction start represents first observed work in the transaction, not proof of the server's exact internal begin time. Batch entries cannot supply individual driver execution duration.

Raw bind values are not logged. Literal SQL values and comments are redacted; template length is capped. The log queue has 2,048 entries and 4,096-character lines; aggregate metric cardinality is capped at 1,024. Under logging overload events can be dropped: counters and console warnings explicitly report losses. There is no sampling, but this bounded non-blocking mechanism cannot guarantee lossless detail under arbitrary load. Release validation must demonstrate no unacceptable drops at expected throughput.

Execute/fetch duration is client-observed. It does not establish rows examined, physical disk reads, buffer-pool misses or lock hold. Read those from MySQL performance_schema/status and transaction instrumentation. Pool acquisition and commit have separate timings. Returned transaction-control calls are not proof of COMMITTED after an ambiguous communications failure.

## Defaults and local commands

Scheduling and reconciliation activation are opt-in:

```properties
shared-market.fix142.enabled=false
shared-market.fix142.acknowledgment-enabled=false
shared-market.fix142.manual-resolution-enabled=false
shared-market.fix142.admission-ceiling=32
shared-market.fix142.fresh-reserve=4
shared-market.analysis.historical-threads=1
```

Do not enable the new scheduling while legacy in-flight rows lack reviewed ownership. Startup rejects incompatible state; timeout fences retain IDs and tokens. No automatic release on elapsed age, missing PID, restart or absent evidence.

From the extracted project, run PowerShell:

```powershell
.\scripts\Verify-Fix142.ps1 -JavaHome 'C:\Program Files\Java\jdk-21'
```

For MySQL acceptance use a separate disposable local MySQL instance, pre-create a fix142_test_ bootstrap schema, verify its @@server_uuid independently, and run:

```powershell
.\scripts\Verify-Fix142.ps1 -JavaHome 'C:\Program Files\Java\jdk-21' -RunMySql -TestMySqlUrl 'jdbc:mysql://127.0.0.1:3308/fix142_test_bootstrap' -ExpectedTestServerUuid 'REPLACE_WITH_VERIFIED_TEST_UUID'
```

The MySQL fixture creates and drops only its own random test schemas, requires an explicit disposable-server assertion and verifies UUID before schema creation. Supply dedicated test credentials at the prompt. It needs CREATE/DROP plus performance_schema lock-wait visibility. Never target your trading server. The script builds/tests only; it never deploys.

Use scripts/mysql/FIX142-local-query-plans.sql and FIX142-source-query-plans.sql for read-only EXPLAIN/SHOW INDEX checks. Collector indexes remain subject to measured query-plan review in this same release; no collector DDL is guessed or issued automatically.

## Mechanical exit trace and uncertainty

The source trace reaches LivePositionProtectionService.onPrice (REQUIRED) and WalletAutoExecutionService.executeMechanicalExit (REQUIRED), repository position/trade/balance updates, daily stats and WalletService.captureSnapshot in the caller's local transaction. executeMechanicalExit records PAPER_AUTO and does not place an external exchange order in that method. This is a source trace, not an executable guarantee for every onPrice branch or in-process side effect. A call having occurred before a failed commit is never treated as proof it did not happen. Started-unresolved protection remains fenced; operator resolution requires independently established owner fencing and transaction outcome. The read-only diagnostic scan does not clear the original BTC timeout lane automatically.

4. Full Production/Replay freshness and observer parity, protective stop-crossing/exit regressions and all historical-context consumer checks. History retirement stays gated and unchanged.
5. Reproduce the 44,738-row backlog end-to-end with sustained collector traffic and the real analysis/scoring/wallet collaborators. Pre-commit latency/throughput targets for protection, newest closed candle -> phase 4 -> committed signal -> BTC context, including p95/p99 and unrelated-lane fairness. The supplied MySQL backlog test seeds this size and exercises a single fresh path with fixture analysis; it is NOT the full application load test.
6. Measure logging-enabled versus disabled overhead, disk/queue/drop rate and pool/commit latency; verify no unacceptable logging loss. Keep durability settings unchanged.

There is no claim that latency cannot recur. MySQL I/O, transactions held by other components, fences and sustained arrival rate can still dominate. Deploy one reviewed artifact only after these gates pass, then activate settings sequentially with measurements and a state-aware rollback plan.
