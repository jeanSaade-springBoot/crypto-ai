# FIX-121 — Historical acquisition quantity and investment

## Baseline and scope

Incremental on the verified FIX-120 source in `pom(20260907-205010).zip`.
The Production and Replay FIX-120 geometry-boundary implementations and their
existing runtime behavior is preserved byte-for-byte. The validation follow-up below updates one older test fixture. No trading rules, sizing, thresholds,
wallet authority, execution order, P/L computation, or Replay engine behavior changed.
This fix does not implement additional Replay performance instrumentation.

## User-visible behavior

Trade Inspector Entry cards show:

- Quantity acquired: cumulative actual BUY execution quantity.
- Unit Entry Price: the actual fill price for one BUY; gross-cost-weighted acquisition
  price across all BUYs for multiple entries (explicitly labelled weighted).
- Total Invested (before fees): cumulative gross BUY spend.
- Investment history availability, BUY count and explanation.

Remaining quantity on open cards and final SELL quantity on closed cards retain
separate labels and their existing values. Chart markers retain their original
execution-price values: a weighted historical acquisition price is not a chart fill.
Replay results, archived Replay results and saved Proven grids expose the same
investment fields in the existing entry-price cell. The Proven detail API also
returns investment metadata. Existing chart/exit/P&L behavior remains unchanged.

## Authoritative data and definitions

`wallet_trade`: `id`, `symbol`, `side`, `status`, `executed_at`, `quantity`,
`price_usdt`, `gross_amount_usdt`, `signal_id`.
Other mapped wallet fields inspected include `fee_usdt`, `net_amount_usdt`,
`cost_basis_usdt`, `decision_price_usdt` and `execution_price_observed_at`.

- Select only EXECUTED BUY/SELL rows, sorted by execution time and ID.
- Resolve one complete flat-to-flat quantity lifecycle. Include every add and
  partial SELL until the terminal SELL. Later same-symbol positions are separate.
- Open positions must match their initial signal and reconcile the remaining
  quantity with the managed position. The managed quantity is a consistency check,
  not the acquisition-quantity source.
- Quantity acquired = sum of BUY quantities; it does not shrink after partial SELLs.
- Total invested = sum of persisted BUY `gross_amount_usdt`. This is authoritative
  gross capital committed; fees are intentionally excluded. SELL `cost_basis_usdt`
  describes disposed inventory and is not cumulative investment after partial exits.
- If gross spend is absent from retained execution points, use exact BigDecimal
  BUY quantity × fill price. Because historical points do not store gross spend,
  this fallback may differ from the original spend by execution/storage rounding.
- Single-BUY unit price retains the actual fill price. Multiple-BUY unit price is
  cumulative gross cost / cumulative acquired quantity, HALF_UP at 12 decimals.
  After partial SELLs and later adds, this describes all historical acquisitions,
  not the remaining inventory's current average cost.
- Return decimal strings through JSON; never calculate investment in JavaScript.

`wallet_trade` has no managed-position foreign key. Quantity reconciliation provides
an auditable lifecycle boundary instead of the old quantity-match-first / latest-BUY
pairing heuristic. Existing unrelated pairing/chart semantics are preserved.

## Missing or ambiguous history

Missing initial BUYs, overdrawn sequences, duplicate IDs, invalid prices/costs,
unreconciled quantities or ambiguous Replay boundaries return null amounts and an
explicit UNAVAILABLE explanation. No fabricated zero amount or nearest-time match.
Only DECIMAL(...,12) storage-rounding tolerance is allowed, additionally capped at
one ten-billionth of acquired quantity so very small partial positions remain open.
An invalid sequence is not silently reset to invent a later lifecycle.

Closed investment calculation never reads today's asset balance or the zeroed
closed managed-position quantity. Retained historical wallet executions survive
later same-symbol trades independently. If the underlying execution evidence is
deleted entirely and no Proven copy exists, amounts cannot be reconstructed and
remain unavailable.

## Replay and historical retention

Replay uses `wallet_execution_test` scoped by exact `test_run_id` and symbol.
Archive reads additionally require `archive_batch_id`. The same quantity-lifecycle
calculator is used for Production history and Replay history. Position entry/exit
times must exactly identify one resolved lifecycle; ambiguity is not guessed.

Replay/Proven APIs derive this presentation metadata from existing persisted
executions; there are no new analysis or execution writes. Request-local caches
reuse ledger reads and quantity resolution for cards from the same symbol/run.

When the user explicitly copies a Production trade to Proven, complete resolved
wallet execution IDs replace the old expanded-time-window selection when available.
They are saved in the existing `proven_trade_execution_point` table. Its data can
supply investment values if the original wallet history is later unavailable.
Existing legacy copies can only supply totals if their saved execution sequence
reconciles. Replay-backed Proven records use retained live execution records first,
then the corresponding archived run. There is no speculative database migration.

## Validation follow-up — FIX-117 reflection fixture compatibility

The user ran Maven and reported 229 tests, 0 failures, 1 error. The error was
`Unhandled ShadowPosition component: profitLockState` in
`Fix117NearTpExtensionStateTest.productionAndReplayUseIdenticalTpExtensionStateTransitions`.

Investigation confirmed that the old fixture switch also lacked
`profitLockRebaseStartedAt`. FIX-118/120 already added both record components.
This fixture creates an inactive Profit Lock (`profitLockActive=false`, null lock
price), so its explicit values are now `ProfitLockState.INACTIVE` and `null`.
The strict default exception remains; future unknown fields still fail loudly.
No assertions, expected Near-TP transitions or Production/Replay runtime classes
were changed. The only additional test file changed is:
`src/test/java/com/crypto/position/service/Fix117NearTpExtensionStateTest.java`.

The corrected fixture has not yet been rerun through Maven. First run:

