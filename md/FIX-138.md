# FIX-138 — Fresh-candle priority and isolated historical analysis

## Problem and evidence

FIX-137 production logs showed a 55.7-second dispatch pass followed by roughly
3-second worker tasks. Persisted ACEUSDT signals advanced historical 1m candles
more slowly than new candles arrived. Old REVIEW_REQUIRED rows blocked each
symbol/timeframe. Signal persistence was functioning; timely dispatch was not.

## Intentional scheduling changes

- Eight dedicated live threads and one dedicated historical thread, with separate
  dispatch clocks. The existing legacy candle executor is unchanged.
- Live selection considers only phase-4 closed deliveries originally classified
  COMPLETED, still within the existing SharedEventPolicy grace window. It chooses
  the earliest eligible close in each lane. Old pending/deferred deliveries do
  not block a fresh delivery just because their sequence is lower.
- Historical selection considers expired closes only, and passes liveSource=false
  even for originally live deliveries. It never registers or invokes wallet work.
  It yields to ready fresh work in the same lane.
- A bounded round-robin visits at most 16 lanes per dispatch turn. Standard
  1m/5m/15m/1h/4h/1d plus configured intervals are considered for enabled symbols.
- No unbounded memory queue or caller-runs dispatch fallback. Pools have bounded
  capacity; known unsubmitted rejections release only their own durable claim.
- Candidate queries use a single symbol, interval, phase, status and close-time
  range. The old cross-backlog correlated anti-join and full pending-lane lock
  scan are removed. V95 creates the supporting close-time and owner-timeout indexes.
- Timeout monitoring runs on a separate clock, in bounded batches. Candidate
  selection outside a transaction uses the configured three-second JDBC statement
  timeout. Claim/outcome transactions have a five-second transaction timeout.
  Inside claim(), the fresh-candidate recheck participates in that transaction:
  Spring applies the remaining transaction timeout to the statement, overriding
  the configured JDBC timeout. These are not independent nested limits and are
  not overall connection-acquisition or wall-clock cancellation deadlines.

This intentionally changes processing order: fresh work can precede stale work.
Scoring, sizing, freshness thresholds, exit rules and Replay business formulas are
unchanged. No candle, signal, delivery or execution-history rows are deleted.

## Ownership and review handling

Both pools share a JVM lane admission set. Across instances, claims serialize on
consumer-state then delivery rows, with current locking checks. Any RUNNING owner
blocks another analysis in that lane, regardless of sequence. A historical task
already running is not preempted; fresh work in that same lane waits for it, while
other lanes can continue on the reserved live pool.

A REVIEW_REQUIRED row is isolated as ANALYSIS_ONLY_REVIEW only when:

1. phase is 4 and analysis_completed_at is present (age alone is never enough);
2. no signal_processing_work exists by source event, candle identity or matched
   signal ID;
3. no wallet_trade exists for any signal matching that exact candle.

Checks and classification run under the admission transaction. The original row,
error, owner and timestamps remain intact. The failed candle is NOT requeued and
is NOT reported as successful. A bounded batch limit leaves unusually large
review sets blocked. Missing completion, any work evidence or wallet evidence
retains REVIEW_REQUIRED and blocks admission. No uncertain trade is retried.

The worker also treats an existing signal for an expired close as historical,
instead of falsely requiring completed live work for that historical signal.
Signal existence never authorizes replay or re-registration of execution work.

## Logs enabled at INFO

- `[FIX-138][ANALYSIS_CONFIGURATION]`: eight live/one historical worker configuration.
- `[FIX-138][DISPATCH]`: mode, lanes checked, submitted, active tasks, elapsed time,
  and collector read-pool pressure. Heartbeat every 30 seconds or slow pass.
- `[FIX-138][SLOW_CANDIDATE]`: individual lane selection taking at least one second.
- `[FIX-138][CLAIM]`: event, lane, close time and claim duration.
- `[FIX-138][TASK_START]`: mode, queue wait and candle close age in milliseconds.
- `[FIX-138][WORKER_STAGE]`: stage-entry boundary with cumulative worker elapsed time.
- `[FIX-138][SIGNAL_SAVED]`: mode, event ID, persisted signal ID, symbol, interval,
  candle open and generated_at. Emitted after the transactional analysis-service
  call returns. This proves signal persistence, not wallet success.
- `[FIX-138][TASK_END]`: returned outcome and whether the owner-matched outcome
  transaction committed. Signal and outcome commits remain separate evidence.
- `[FIX-138][LANE_BLOCKED]`: running owner or unresolved review, rate-limited per lane.
- `[FIX-138][ANALYSIS_REVIEW_ISOLATED]`: evidence checks passed; the log explicitly
  states the surrounding transaction is pending commit. Verify persisted status
  if the same transaction subsequently fails.
- `[FIX-138][OWNER_TIMEOUT]`, `[FIX-138][OUTCOME_COMMIT_UNCONFIRMED]`: manual review,
  no automatic replay.
- `[FIX-138][DISCOVERY_PROGRESS]`: collector checkpoint, pending price phases,
  fetched count and last fetched observation. Existing CONSUMER_LAG warnings are
  rate-limited to 30 seconds per symbol.

FIX-137 worker start/end markers remain available. No DEBUG setting is necessary
for these FIX-138 markers. generated_at is historical evaluation time for recovery;
created_at is the signal's insertion timestamp.

## Scope and limitations

This patch retains shared_market_event_delivery. It separates analysis scheduling;
it does not replace the collector transport or price-protection pipeline.
Fresh closes must still be discovered and complete their existing price/observer
phases before phase-4 analysis. If CONSUMER_LAG persists or DISCOVERY_PROGRESS shows
old source observations, this upstream backlog still requires attention. No
checkpoint is silently advanced to skip price protection.

The database and collector read pool are shared resources. Thread separation is
not a guarantee of throughput or profit. Do not increase thread or DB pool counts
blindly. Historical reconstruction remains limited by the existing historical
context contracts; the patch does not invent missing market context.

## Worker redelivery review correction

The worker's sharedWorkEvidence JdbcTemplate is now a required final constructor
argument. Both manual construction sites supply it explicitly; the two-instance
fixture no longer injects the field by reflection. The evidence SQL and outcome
conditions are unchanged.

Two worker unit cases exercise fresh LIVE redelivery with an existing signal:
completed evidence count > 0 returns ALREADY_COMPLETED; count = 0 returns
REVIEW_REQUIRED. Both verify the evidence query and exact candle parameters,
no extra JDBC operations, and no scoring/registration or paper-trading calls.
The existing expired-redelivery test now also asserts no evidence JDBC interaction.
These mock-backed unit cases cover branch decisions, not real MySQL join or
transaction behavior. They have been syntax-parsed but not compiled or executed
in this environment; Java 21/Maven and MySQL acceptance remain required.

## Apply and verify

1. Overlay this patch in **crypto-ai-trader**, preserving your current trader pom
   and YAML. No collector/crypto-ai-next file or database is modified. The separate
   uploaded pom identified crypto-market-data and is deliberately not included.
2. Run `mvn -B -ntp clean test` with Java 21, then the normal package/deploy pipeline.
   Do not skip failed tests. Ensure the previous trader process is stopped for the
   deployment; retain the collector. V95 creates indexes during Flyway startup and
   may wait for existing database transactions. Do not rerun DDL blindly on timeout.
3. Confirm the new PID/release and ANALYSIS_CONFIGURATION marker. Observe fresh
   TASK_START / SIGNAL_SAVED / TASK_END across multiple symbols and intervals.
4. SIGNAL_SAVED mode=LIVE should refer to a recently closed candle; compare
   closeAgeMs with the existing interval grace. Historical backlog runs on shared-history threads. A fresh task that expires
   while waiting/processing can still fall back to historical-only on a live thread;
   this retains the existing freshness gate and cannot execute a stale trade. Check RUNNING/REVIEW blocks using the logged event ID.
5. Use bounded PK lookups rather than full-table aggregate scans during acceptance.
