# FIX-131 — Managed Binance kline ownership and candle-gap diagnostics

## Baseline and scope

Built only on `pom(20260923-212447).zip` for **crypto-ai-trader**, schema
`crypto_ai`. Do not install this package into crypto-ai-next.

Replaces the startup / reload / health-check connection ownership race, adds
receipt-to-commit and read-only candle coverage diagnostics, and temporarily
pauses FIX-043 scheduled analysis recovery. No wallet, scoring, protection
threshold, Replay business logic, or historical candle identity changes.
No schema migration is required. This is a source package, not a server deployment.

## Ownership contract

One lifecycle actor owns the combined Binance kline connection for this JVM.
Startup, reload and transport failure use that same owner. Each attempt has a
permanent generation number and persistent session/future facts. Messages require
an admission permit for that generation's primary session. The permit spans the
unchanged synchronous processKline call and all its transaction stages.

Gate transitions: PENDING -> ADMITTING -> REVOKED, or PENDING -> REVOKED.
Revocation cannot be undone. Both revoke and final release check for revoked AND
zero in-flight callbacks. Permits release exactly once even if processing throws.

Reconnect: revoke admission -> drain admitted work -> request transport close ->
confirm all tracked sessions closed AND handshake settled -> create replacement.
Close-return with session.isOpen()==false or a close callback establishes local
transport closure. A timed-out unresolved handshake remains tracked; no competing
attempt starts on the assumption that cancelling a Future would cancel a socket.
Duplicate session registrations retain both references for cleanup. Messages on
pending/revoked/extra sessions are rejected and counted. Late callbacks retain a
cleanup path; they cannot reactivate a revoked gate.

The guarantee is one manager-created attempt at a time within this application
instance. It does not coordinate another JVM, another application or another
machine. The transport client can deliver anomalous duplicate sessions; these are
closed, not adopted, rather than claimed impossible.

## Explicit availability trade-off

A hung callback, unresolved handshake or unconfirmed socket close blocks the next
connection. Timeout logging never overrides this safety condition. This can extend
an interruption indefinitely. No buffering, forced activation, async kline business
processing, new heartbeat policy, exponential backoff, or automatic candle repair
is introduced. Do not claim this proves or fixes the observed Pong timeout cause.

Interruption runs from predecessor revocation to replacement admission. Durations
use nanoTime; UTC timestamps locate events. Historical repair cannot restore missed
live protection or entry opportunities.

## Resource and timeout choices

* Actor: one daemon thread, at most 32 reload requests examined per pass. All
  persistent lifecycle facts are checked every pass; 500 ms idle poll. This is
  starvation prevention, not a hard real-time scheduling guarantee.
* Reload mailbox: 32; retained active waiters: 32. Excess receives BUSY explicitly.
* Connection/configuration worker: one thread, queue one. No concurrent handshakes.
* Close worker: separate one thread, queue one; a blocked close cannot consume the
  connection worker, although confirmed closure is deliberately required before
  another connection. Rejected cleanup remains tracked and retried.
* Connection deadline: 15 seconds. Drain/close alert threshold: 15 seconds since
  revocation. Pending timeout does not abandon an unresolved attempt.
* reload(): unchanged void/exception contract; caller wait 30 seconds. WAIT_TIMEOUT
  reports caller expiry; DRAIN_TIMEOUT/CLOSE_TIMEOUT report lifecycle deadlines.
  Returning/throwing to a caller never cancels cleanup. A later reload invalidates
  the pending attempt so its replacement loads fresh configuration.
* Shutdown: stop/activation serialized; shutdown caller waits up to 20 seconds.
  No actor blocking on the caller. SHUTDOWN_INCOMPLETE explicitly reports unfinished
  cleanup; no false successful-termination claim.
* Read-only gap scanner: one separate scheduled worker; eight streams per pass,
  ten-second fixed delay, two-second statement timeout, max 5,000 rows per stream.
  Scans use the existing datasource, so pool acquisition can additionally wait for
  its configured timeout. Queries never execute on the WebSocket callback/actor.

## Timing and searchable logs

All new logs carry `[FIX-131]`.

* `[WS-LIFECYCLE]`: CONNECTING, ESTABLISHED, ADMISSION_ENABLED, REVOKED, CLOSED,
  RETIRED, TRANSPORT_ERROR, CONNECTION_FAILED, CONNECTION_TIMEOUT, DRAIN_TIMEOUT,
  CLOSE_TIMEOUT, NO_MESSAGES, SHUTDOWN_INCOMPLETE.
* `[MESSAGE_REJECTED]`: first and every 100th pending/revoked message; retirement
  reports the total. This is visible interruption, not a claim of lossless handover.
* `[CANDLE_RECEIVED]`: callback entry wall time, generation, exact candle open,
  Binance event time, correlation ID, admission-plus-parse duration.
* `[CANDLE_INPUT_COMMITTED]`: emitted only after input transaction returns
  successfully, BEFORE protection/observer work; same correlation ID. Records
  receipt-to-commit time, not just SQL execution time.
* `[CALLBACK_FINISHED]`: entire callback duration and whether input committed.
  Final candles always log; slow in-progress callbacks (>= 1 second) log. Routine
  fast in-progress updates are omitted to limit volume. Failures have explicit logs.
* `[CALLBACK_FAILED]`: processing failed; never interpreted as a committed candle.
* Existing FIX-129 stage diagnostics remain available for individual transactions.

These new observations are retained in application logs. Existing FIX-129 database
stage timing remains unchanged; there is no new diagnostics table or trading UI.

## Read-only gap detection

The actual accepted combined-stream URL defines monitored symbol/interval pairs.
Observation start survives reconnects; removed/re-added pairs get a new start.
Only fully subscribed candles are expected: exclude the candle already forming at
initial subscription. Exclude still-forming candles and allow 30 seconds after close
for arrival/commit. Query only exact `symbol + interval_code + open_time` identities
with `closed=1`. UTC JDBC timestamp binding is explicit.

The scanner detects interior AND trailing missing rows without requiring the next
WebSocket message. `[DB_CANDLE_GAP]` lists exact consecutive missing ranges/counts.
This confirms missing CLOSED database rows at scan time; it does not prove which
upstream component caused them. Later arrival may resolve a gap.
`[DB_CANDLE_GAP_RESOLVED]` requires an actual returned closed row.
`[GAP_OUTSIDE_SCAN_HORIZON]` never means repaired. Query failure means unknown
coverage and logs `[GAP_SCAN_FAILED]`, never an empty successful scan.

Bounded horizon: last 72 hours since subscription. Fixed UTC-aligned intervals
1m/3m/5m/15m/30m/1h/2h/4h/6h/8h/12h/1d are supported. Unsupported calendar intervals
log explicitly. The scanner does not assess technical_indicator/trade_signal
coverage, backfill candle rows, execute missed trades, or diagnose all historical
gaps. Subscription starts and unresolved sets are in-memory: application restart
begins a new observation window. Preserve logs/baseline for cross-restart evidence.

## Temporary recovery setting

Bundled `application.yml` sets:

```yaml
trading:
  scheduled-analysis-enabled: false
```

This pauses **FIX-043 scheduled indicator/signal recovery only**. Startup candle
bootstrap, FIX-127 execution recovery, and other mechanisms are unchanged.
`[RECOVERY_CONFIGURATION]` logs the effective flag, including external overrides.
If the server uses an external configuration file, set that flag there as well.

Capture the pre-deployment coverage baseline. Collect diagnostics for the agreed
48–72-hour window, review coverage during it, and restore the flag to true when
finished (restart/redeploy with the effective configuration). Check remaining gaps
explicitly: FIX-043 has a bounded lookback and does not repair missing candles.

## Verification and rollout

See `FIX-131-VALIDATION.md` for actual Maven results and the exact command.
Tests cover forced busy-drain interleaving, closure before replacement, pending
admission, duplicate sessions, late handshake after timeout/shutdown, permit release,
recovery disabled, gap boundaries/ranges/horizon, and input commit diagnostics.
Tests use mocked transport and transaction managers; they are not a real Binance
soak test or a MySQL contention benchmark. No performance improvement is claimed.

Build in the Windows project folder:

```bat
mvn clean test
```

After deployment, display diagnostic lines from the trader server (CMD-compatible):

```bat
powershell -NoProfile -Command "Select-String -Path 'C:\apps\crypto-ai\crypto-ai.log' -Pattern '\[FIX-131\]' | Select-Object -Last 200"
```

Verify effective recovery=false, one active generation, clean retire-before-connect
ordering, and receipt/commit times. Diagnose CLOSE_TIMEOUT/DRAIN_TIMEOUT before
restarting; do not bypass the gate. Keep old logs and the previous application
package for rollback. Maven verification is required before deployment.
