# FIX-130 — Durable background price-move block finalization

Candidate built on FIX-129. User authorized moving retrospective finalization off the ingestion thread. No deployment or measured improvement is claimed. Java 21/Maven and MySQL gates remain pending.

## Measured finding

FIX-129 captured 68 finalizations across four rollovers (17 symbols each). Summed BLOCK_FINALIZATION durations were 34m51s, 26m22s, 40m39s and 57m44s. ENA took 421,304 ms inside an observer transaction taking 421,337 ms. This establishes the blocking operation; individual internal query cost remains unmeasured. Those totals exclude the enclosing observer measurements to avoid double counting.

## Contract 1: actual shared tables and mapping check

The finalization call chain is finalizeBlock -> finalizeCatch -> syncLiveCatch/applyBlame -> resolveBestSignalForMove/resolveExecutionOpportunity.

| Table | Finalization access | Mapping / lock detail |
|---|---|---|
| price_move_event | Read and write previous block's event | Scalar fields; no mapped relationships. Hardcoded crypto_ai schema retained. |
| wallet_trade | Read latest 100 executed trades for the symbol | LAZY signal and positionAnalysis relationships; this path reads only side, execution time and ID. No relationship is dereferenced. |
| trade_signal | Read by candle time and existing generated-at compatibility query | No entity associations found in this entity. Existing retrospective selectors preserved. |
| execution_opportunity | Read latest-signal and lifecycle-overlap candidates | LAZY latestSignal mapping; this path reads scalar direction and explanation fields. |
| price_move_finalization_work | New snapshot/state ledger | No FK to trading rows. |
| price_move_finalization_gate | New singleton execution gate | Short coordination transaction only; not held while historical queries run. |

No wallet_managed_position or signal_processing_work reference is reached by this finalization path. CandleRepository is used elsewhere by chart endpoints, not this finalization call chain. No repository query in the historical path requests FOR UPDATE or an EntityGraph. Shared tables still mean shared database load and possible contention: absence of an explicit locking query is not a claim of zero contention.

## Contract 2: exact concurrency, ownership and failures

Exactly ONE active finalization job across all instances sharing the new tables. Each process has one dedicated fix130-finalizer scheduled thread, polling every five seconds after completion of its previous poll. A singleton database gate serializes claims across instances. Historical queries run after the claim transaction commits. Their transaction uses READ_COMMITTED ordinary reads, writes diagnostic explanations only, and atomically commits FINALIZED plus gate release with those explanations.

One is deliberate: observed calls already take minutes on shared tables. Raising concurrency could increase pressure on wallet processing. This patch isolates the work, not optimizes its queries. The historical transaction has no new execution deadline; a JDBC timeout alone would not prove a stopped server-side query or justify takeover.

This implements conservative ownership, not an automatically expiring execution lease. A claim older than 30 minutes is marked REVIEW_REQUIRED when another poll observes it; the gate stays occupied. In a single process, its busy worker cannot simultaneously poll, so a hung call may remain FINALIZING with increasing visible age. A second instance or restarted process detects stale ownership. No elapsed time alone starts a replacement.

Automatic retry is limited to the exact MySQL deadlock rollback condition (1213 / 40001). Up to three attempts; backoff after attempts 1 and 2 is 60 and 120 seconds. A proven rollback releases the gate, including at exhaustion, so later jobs proceed. Unknown exceptions/commit outcomes retain the gate and mark REVIEW_REQUIRED. Failure to record the outcome is logged and does not release ownership. Invalid snapshot JSON is quarantined before finalization starts and releases the gate.

No code automatically abandons or overwrites an uncertain owner. See recovery procedure below.

## Contract 3: explicit live and completed-block states

Completed-block work uses FINALIZATION_PENDING, FINALIZING, FINALIZED, RETRYABLE_FAILURE and REVIEW_REQUIRED. New-block tracker state is COLLECTING. Live code does not read the previous job's unfinished explanation; the background worker never touches a live BlockTracker. This adds no entry rejection or wallet execution condition.

During enqueue failure, the active tracker stays on the prior block with ROLLOVER_PERSIST_FAILED, retaining incoming observer points. The existing coordinator catches the observer failure after input/protection, so close-event dispatch still follows the existing failure-isolation path. This failure may still delay ingestion up to existing connection acquisition / bounded enqueue query timing; zero database delay is not promised.

The retry buffer is explicitly bounded at 4,096 points per symbol. At exhaustion, the incoming observer point is not retained; REVIEW_REQUIRED, unrecordedPoints and [OBSERVER_POINT_UNRECORDED] make the gap explicit. Existing buffered points are still retried, so buffer exhaustion does not permanently prevent recovery. It never drops a market-input write or suppresses protection. The unrecorded-point count remains visible for that tracker session. A finalization status reports workflow completion, not proof that every observer point was captured.

Active tracker state is returned by the existing activeTracker endpoint. Completed-work status, queue age, global held job and pending count are available in Proven / Analyze Trades for runs, archives and saved trades. Queue age is measured from enqueue to the latest attempt start (or now if never started). These are current Production diagnostics, not simulated Replay output or a frozen archive.

## Contract 4: exact snapshot/reset/arrival order

Under the existing per-symbol Java monitor:

1. Retain the current point in the observer retry buffer.
2. Create an immutable record of the prior block identity and UP/DOWN candidate facts (start/end UTC time, prices, change, level, window).
3. Commit snapshot and FINALIZATION_PENDING work in an independent REQUIRES_NEW transaction (two-second transaction/query limit; DataSource connection acquisition follows existing configuration).
4. Only after successful commit, reset the live tracker.
5. Apply retained points in order, evaluate each once, and remove each applied point from the buffer. A buffered later block creates its own snapshot before another reset.
6. Persist the current live catches through the unchanged observer transaction.

Another same-symbol callback cannot enter between snapshot and reset. Snapshot contains no live references or JPA entity. Failed handoff leaves both prior tracker and triggering point intact for a later callback. Enqueue has a unique (symbol, block_start) key, exact-payload duplicate acceptance and conflict rejection. A crash after successful handoff does not lose the queued completed block. Multiple instances presenting different facts for the same block are rejected, not silently merged.

The guarantee is completed-block handoff, not total observer crash durability: uncommitted tracker data and retained points remain in memory and can be lost at process termination. Existing settings updates clear trackers as before. Observer point semantics continue to use the supplied observation time; no candle identity is invented for block work.

## Contract 5: lease contention, queueing and head-of-line delay

Enqueue inserts into the durable work table and NEVER acquires the singleton gate. Whether a worker is slow, busy, or awaiting review, a successfully enqueued symbol begins collecting its next block. There is no in-memory finalization task queue and no CallerRuns fallback.

A poll finding an occupied gate returns; it does not busy-wait. Pending rows remain in the database. When free, the worker chooses the oldest eligible next_attempt_at then ID. A backed-off retry does not block ready jobs from other symbols. Failed/poison work is not retried indefinitely. Jobs without caught moves still finalize as a no-op, maintaining explicit block accounting.

ONE worker necessarily means a slow active job delays other retrospective explanations. This is accepted diagnostic queue latency, exposed as pending count and age, not claimed eliminated. Ambiguous ownership can suspend the whole finalization queue; that is the explicit cost of forbidding concurrent takeover. It does not stop live collection, input persistence, protection or snapshot enqueue. No finite finalization latency guarantee is made. There is no automatic queue deletion or retention purge.

## Retrospective evidence timing limitation

Only price-move facts are frozen at handoff. Historical wallet/signal/opportunity reads happen later, in the worker. Existing selectors are deliberately unchanged, including the latest-100 wallet limit and retrospective generated-at compatibility path. Later database changes or enough newer trades can change the explanation relative to synchronous rollover evaluation. This patch is not historical database time travel and does not claim identical diagnostic labels. Trading formulas and Replay business services are unchanged. Immutable rollover-time evidence capture would be a separate design, not a hidden query change here.

## Failure recovery procedure

Pending and retryable rows resume automatically after startup. Interrupted FINALIZING work is not automatically replayed. For a held gate / REVIEW_REQUIRED owner:

1. Inspect the job, error and FIX-129/FIX-130 logs.
2. Stop every application instance that could own the worker and establish that its database transactions have ended. Do not rely only on a lease age or missing heartbeat.
3. In one DBA transaction, lock the singleton gate and its exact active job. Confirm the intended job and owner. Mark that job FINALIZATION_PENDING (or leave it quarantined after explicit review), clear owner_token, set next_attempt_at to current time, and clear that exact gate owner. Do not clear a different owner's gate or alter a FINALIZED job.
4. Restart one application and verify work state/output. No automatic administrative reset endpoint is introduced.

Diagnostic explanation writes and work completion are one transaction. A failure before commit rolls them back together. Unknown commit outcomes remain reviewable; no automatic wallet action is involved. Gate and work locks are acquired in the same order for claim/completion/failure state transitions.
