# FIX-128 — Bounded quarantine transactions

Implementation candidate for crypto-ai-trader / crypto_ai, based on FIX-127. Enabled when installed. No deployment performed here.

## Evidence and scope

The supplied trader-fix127-review.txt identifies one exception at 2026-09-09 16:45:06.371 +02:00. Original lines 32026–32069 show SignalProcessingStore.quarantineInterrupted executing a bulk UPDATE of signal_processing_work. Neither wallet_managed_position nor WalletManagedPosition occurs in that exception block. This establishes the victim operation, not all competing locks or transactions. No claim of complete independence from wallet activity or elimination of all deadlocks is made.

The FIX-127 scanner put quarantine and pending recovery in one outer try block. A quarantine error consequently skipped pending recovery for that cycle.

## Change

- Discover at most 50 RUNNING records older than the existing five-minute cutoff, ordered by signal_id, using a non-locking SELECT in a short independent transaction.
- Retain the candidate's signal_id, owner token and updated_at. Discovery grants no permission to overwrite a later state.
- For each candidate, open a separate REQUIRES_NEW transaction using the existing three-second transaction timeout. Lock the primary key first. Check RUNNING and the original owner, then UPDATE by primary key with the original timestamp and cutoff predicates.
- Completed, renewed, differently owned or deleted records are skipped. Successful quarantine remains REVIEW_REQUIRED / INTERRUPTED_ATTEMPT; attempts are not reset, and no automatic replay is authorized.
- Catch each candidate failure after transaction rollback and continue with later candidates. No immediate retry loop is introduced; a still-eligible record can be reconsidered on a later scan.
- Catch quarantine discovery failure separately so pending recovery is still attempted. Pending-signal failures retain existing per-signal isolation.

This bounds transaction scope to one candidate and scan size to 50. It is not a guaranteed wall-clock scan deadline: actual driver/lock-timeout enforcement must be validated on MySQL, and multiple slow candidates can delay pending recovery. Discovery can still examine more rows than the returned limit. No new index, isolation level, SQL session setting or schema migration is included. A perpetually failing low-ID group may delay later quarantine candidates; it cannot suppress the separate pending scan indefinitely by a single thrown exception.

## Observability

Search [FIX-128][QUARANTINED], [FIX-128][QUARANTINE_ROW_FAILED] and [FIX-128][QUARANTINE_SCAN_FAILED]. Row logs include signal_id. The scanner retains FIX-127 pending-recovery diagnostics and quarantine count summary.

Successful quarantine writes a FIX-128 explanation to the existing durable error_message field. Proven / Analyze Trades displays it through the existing Signal processing panel, whose explanatory text now describes bounded quarantine. A failed quarantine write does not claim a durable success; the original row stays authoritative and the failure is logged. No extra diagnostics table is introduced.

Production entry/exit rules, sizing, scoring, FIX-122, FIX-124, FIX-125 reservation and Replay business logic remain unchanged. The existing age threshold, origin restrictions, exact freshness checks and two-attempt processing limit remain unchanged. This correction changes housekeeping locking and recovery availability only. Missing-candle data-quality blocks are separate and untouched.
