# FIX-135 — Trader deployment ownership

## Incident and scope
The supplied pipeline stopped only port listeners, waited approximately 90 seconds for startup, then restored a backup over the same JAR path without finding a pre-listener JVM. Logs show V89 began, later multiple unrelated library classes could not load, and two actual Trader JVMs existed. The overwrite mechanism is confirmed in the script; its precise timing is inferred, not measured.

This correction changes only deployment tooling and the fix registry. It does not change trading decisions, Replay, application configuration, database migrations, or collector code. V89 schema/history reconciliation remains a separate operation. This package must NOT be deployed into the current inconsistent schema yet.

## Files and usage
Replace the repository-root Jenkinsfile and add scripts/deploy/Deploy-Trader.ps1. Jenkins must load that root Jenkinsfile from SCM (or paste its content into the job's pipeline definition). The script must be committed with it.

1. Set JAVA_EXE to the actual server JDK java.exe. Default: C:\Program Files\Java\jdk-21.0.12\bin\java.exe, previously observed on this host. Verify it exists. This makes Maven and deployed Trader use the same JDK; prior server Java 26 and local Java 21 differed. The corrected project was tested with Java 21. Do not select Oracle javapath/javaw.
2. Leave DEPLOY_TRADER=false. First run is build/tests only and cannot stop or start Trader. Tests must pass.
3. Resolve V89 using the separately reviewed recovery procedure. A JAR rollback does not roll back schema. Do not edit history by guessing a checksum.
4. Only then select DEPLOY_TRADER=true. The pipeline forces shared-market.mode=OFF and activation-approved=false on the command line. It cannot perform the eventual LIVE cutover.

## Process and artifact contract
- Jenkins serializes builds. A host-wide named mutex also excludes simultaneous deployment scripts from other jobs on this host. All automated deployment jobs must use this script; a manually launched process remains outside that coordination.
- Stage a unique releases/<UTC>-<UUID>/crypto-ai.jar and verify its SHA256 before stopping the old application. Never overwrite legacy crypto-ai.jar, backup JARs, or earlier release files.
- Match only Java -jar arguments for bare crypto-ai.jar (legacy launcher) or crypto-ai.jar under this deploy root. Absolute unrelated paths and crypto-ai-next.jar are excluded. Bare paths assume the established single Trader installation; remove that compatibility branch if another app uses the same bare filename.
- Stop matched JVMs, including ones not yet listening; verify creation time before stopping and wait until both processes and port are gone. Force-stop behavior is retained from the supplied pipeline; it is not a new graceful-shutdown implementation. Confirm no active migration before authorizing deployment. An unknown port owner aborts instead of being killed.
- Launch the actual JDK java.exe directly with -PassThru; preserve working directory for existing external configuration. Persist PID, start time, hash, JAR and logs in per-release process.json.
- Success requires the launched PID owns the listener plus its own log contains Started CryptoAiTraderApplication, across three samples. This is startup verification, not market-feed readiness or wallet/Replay correctness.
- Timeout defaults to 1800 seconds (observation limit, not a migration completion promise). On timeout leave the JVM and immutable JAR untouched for diagnosis; never launch rollback automatically. A later build must not blindly redeploy over an in-progress migration.
- Failure before launch leaves no new process. Failure after launch may leave Trader running. Inspect process.json and logs. Never interpret a failed Jenkins job as proof Trader stopped.
- Logs now live in the unique release directory, not C:\apps\crypto-ai\crypto-ai.log. Update operational log collection to the paths in process.json/Jenkins output. Originals are retained; snapshots are archived under target/deployment-evidence. Old cmd.exe redirectors may linger, but cannot redirect into the new unique log files.
- No automatic release cleanup; retention is a separate reviewed task. No edits to Flyway history or candle rename.
