# FIX-122 — Fresh entry evidence after a completed stop-loss

Project: crypto-ai-trader. Baseline: verified FIX-120 plus delivered FIX-121 and its FIX-117 test-fixture correction.

Status: implemented; enabled by default in Production paper trading and Replay. No remote deployment performed. Full Maven/JUnit and historical Replay validation remain pending.

## Behavior and evidence

The supplied BICO #1814/#1817, ALLO #1826 and ICP #1811 histories showed pre-stop BUY observations still available to later entries. ONG #1832 also had a pre-stop deferred origin. Opportunity completion alone did not restrict historical lookup. This finding does not prove a profitability improvement.

FIX-122 limits new-position evidence to observations whose exact 1m candle close is strictly after the latest executed full STOP_LOSS. Binance's inclusive candle close is open time + 60 seconds - 1 millisecond. Generation time is availability, never replacement lineage. A candle opening before the stop but closing after it is eligible. Missing lineage and equality are excluded under an applicable boundary.

Production reads the committed wallet_trade ledger: same symbol, EXECUTED SELL, reason STOP_LOSS, execution time no later than evaluation. The current executeSignalLinkedExit writer closes the managed position for this terminal reason. The separate POSITION_STOP_LOSS reason and partial harvests are excluded. The schema has no wallet_id; Production scope is the existing single-wallet database, not an invented wallet identity.

Replay uses only full simulated exits from its own run and their simulated timestamps. It never imports Production stop history. Warm-up retains existing behavior: it builds signals/opportunities but does not trade before the requested execution window. To reproduce a post-stop entry, start the execution window early enough to simulate its preceding position and stop.

## Integration

- StopLossEvidencePolicy is the pure candle eligibility rule.
- StopLossEvidenceStore performs bounded read-committed ledger queries using an independent read-only transaction, with no FOR UPDATE or managed-position locks.
- StopLossEvidenceService scopes the boundary to initial evaluations, filters evidence and records diagnostics. Its thread-local scope is always restored/removed in finally; additions bypass it.
- ExecutionIntelligenceService wraps ordinary and 5m-wakeup initial evaluations. It filters complete stale observations, prior health snapshots and the reversal/breakout/deferred-ATR origin selectors. Old opportunity totals cannot bypass filtered wake-up evidence.
- An initial approval carries a boundary stamp. Execution-price revalidation reads again and defers it if the committed boundary changed or became unavailable. Add approvals do not carry this stamp.
- ExecutionReplayScope records symbol-local stops and clears them on scope close. ShadowProductionReplayService updates the boundary at its actual simulated terminal exits.

Signal scores, thresholds, weights, Entry Quality formulas, sizing formulas, open-position additions, wallet writes, execution lock ordering and exits were not edited. Changed eligible history can still change health, route, qualification and resulting allocation. Excluding old negative observations can also improve some evaluations. No fixed cooldown and no new technical indicator are added.

The entry-only runtime service is mandatory Spring injection. Existing manually constructed unit-test fixtures retain their pre-FIX-122 path unless they inject it; the new FIX-122 tests inject and exercise the rule explicitly.

## Lookup failures and the separate concurrency issue

A successful query with no stop preserves the existing history. A failed query is different: FIX122_BOUNDARY_UNAVAILABLE defers this evaluation, without OLD fallback, automatic late BUY, or unbounded retry. Open-position management/exits do not depend on this lookup.

The query and independent transaction have two-second timeouts. These do not promise a two-second end-to-end bound: connection acquisition and driver/network behavior have their own limits. An audit persistence error is logged as DIAGNOSTIC_PERSIST_FAILED; it does not invent a successful persisted record or disable exit protection.

The price recheck observes committed stops; it is not atomic wallet serialization. The possible gap between recheck and wallet commit, and the team-reported deadlocks, are not repaired or claimed reproduced by this patch. WalletAutoExecutionService and PaperTradingService remain byte-for-byte unchanged from the FIX-121 baseline. FIX-124 reserves the reported deadlock investigation/repair; FIX-125 separately reserves transaction coordination through commit. This is the explicitly agreed separation, not a claim that the existing concurrency concern is solved.

## Persistence and visibility

Flyway V83 adds:

- fix122_evaluation: per-evaluation diagnostic JSON, including blocked evaluations, excluded signal IDs/candle lineage, source, boundary, fresh counts, health and final route/reason.
- fix122_replay_revision: run-specific enabled/OLD comparison setting.
- An index for the latest wallet STOP_LOSS lookup.
- proven_analyzed_trade.fix122_diagnostics_json: independent reviewed snapshot.

Diagnostics appear in Proven / Analyze Trades for the selected active or archived Replay window, with separately labeled actual Production rows. An evaluation qualifying is not a claim the wallet executed it. Saved Proven rows have a FIX-122 evidence button. Marking a Replay trade or copying a Production trade captures its diagnostic window in that Proven row, so Replay purge and run-ID reuse cannot change the saved explanation. Existing Proven records without a snapshot show not recorded.

Run-owned diagnostics/revisions are removed during the existing full Replay purge; Production diagnostics and saved Proven snapshots are retained. Archive preserves run identity and diagnostic access without copying wallet data into Replay decisions.

Search logs for [FIX-122]. Affected evaluation/recheck logs include symbol, signal, stop, exclusion count, final code and eligibility. Full excluded lineage is persisted and shown in expandable UI details. The registry includes implemented FIX-122 and separately planned FIX-123/FIX-124.

## Production default and comparison

Production defaults to trading.fix122.enabled=true without an activation step. An explicit configuration override to false retains the old Production path if rollback is necessary. It affects future evaluations, not completed trades.

Replay defaults to enabled independently of the Production override. The Post-stop entry evidence selector offers FIX-122 enabled or Before FIX-122 (Replay comparison only). This setting is independent of the existing OLD Database / NEW ReplayDataset data-access buttons and experimental modes. Existing historical runs without revision metadata are labeled not recorded, not passed.

For economic comparison, use identical execution windows, data source, settings, starting wallet and warm-up, changing only this selector. Include preceding stops, losing examples, winners and an unfiltered window. Report changes in eligibility in both directions, route/allocation changes, missed winners, avoided losses, net P/L, drawdown and trade count. The six team-protected positions require exact identifiers before claiming their check complete.
