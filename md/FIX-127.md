# FIX-127 — Signal-path lock ordering and durable processing recovery

Status: implementation candidate, enabled when installed. Not deployed from this workspace. Maven/JUnit, full Java compilation, MySQL migration/concurrency validation and historical parity remain pending.

Target: **crypto-ai-trader / crypto_ai**. Baseline: the complete FIX-124 + FIX-126 candidate, which already includes FIX-122 and the FIX-125 reservation. Do not apply this delta to FIX-118/119/120 or replace a newer server tree without comparing it first.

## Evidence and boundaries

The supplied trader-fix124-review.txt shows four FIX-124 initial-lock incidents recovered on attempt 2. It also shows six worker failures on the signal path through PaperTradingService → DynamicProfitLockService → the managed-position locking lookup. The scheduler calls the same PaperTradingService entry point independently of KlineTransactionCoordinator; the log excerpt alone does not prove that the scheduler was the competing transaction in any particular deadlock.

PositionManagementService.analyze runs before the old profit-lock lookup. It can insert position_analysis (with a managed-position foreign key) and can request POSITION_STOP_LOSS. It is not purely advisory. This creates a potential lock-upgrade/order conflict; the exact opposing MySQL transaction and lock cycle have not been established from a crypto_ai InnoDB report. FIX-127 therefore does not claim that all deadlocks are eliminated.

The separate recovery gap is structural: an existing trade_signal causes the worker and missing-signal scheduler to skip that candle, even if processing previously failed after the signal was saved. Signal existence cannot serve as a processing completion marker.

FIX-124's classes and live-kline retry logic are unchanged. WalletAutoExecutionService is unchanged. FIX-125 still concerns wallet monitor ownership through transaction commit and is not completed by this work. FIX-123 sizing is still planned separately.

## 1. Shared entry point and initial lock

PaperTradingService.processSignal, openFromSignal, openFromLatestSignal and recoverRegisteredSignal use one SignalProcessingCoordinator. These entry points require no ambient transaction (Propagation.NEVER); the coordinator also checks this directly. This prevents a retry from running inside the failed caller transaction.

Inside a fresh transaction the coordinator locks its claimed work row, then calls findFirstBySymbolAndStatusOrderByOpenedAtDesc(symbol, "OPEN"). After that lock is acquired, it reloads the persisted signal by exact ID, verifies its symbol, interval and candle_open_time against the ledger, and checks recovery freshness before entering the existing PaperTradingService business body. Ordinary signal/freshness reads occur after the lock wait, avoiding a pre-lock repeatable-read snapshot and evaluating grace after contention. The returned managed entity is retained in the same persistence context. Existing advisory, TP, profit-lock, SL, SELL and progressive-entry decision order is preserved.

Only a MySQL error with both code 1213 and SQLSTATE 40001 at that initial lookup receives a private retry marker. A private marker prevents a later callback from accidentally supplying retry permission. The failed transaction rolls back before another claim/attempt begins. Maximum: **two total attempts per signal**, including recovery after restart. A late wallet, advisory, database, timeout or commit exception is never automatically retried. MySQL 1205 lock-wait timeout is not treated as 1213.

This is a lock-order change, not a transaction-shortening claim. Acquiring the lock earlier holds it through more work and may increase contention. Empty-position locking queries may also acquire InnoDB gap/range locks. No symbol-global lock, new index, isolation-level change or wallet-monitor repair is bundled here. Source application configuration already has open-in-view=false; keep this configuration for fresh per-attempt persistence contexts.

Mandatory Spring injection supplies the coordinator. Existing manually constructed PaperTradingService policy fixtures can still call the legacy body without it; this compatibility branch is not a runtime feature flag. Normal Spring startup cannot omit the coordinator bean.

## 2. Durable work registration and completion

V86 creates signal_processing_work. It has no foreign keys, deliberately avoiding parent-row locks for claims. Its identity is signal_id plus the persisted, checked symbol + interval + candle_open_time lineage. No generated_at or nearest-candle fallback is used. There is no historical backfill.

| Caller | Signal creation / registration | Background recovery |
| --- | --- | --- |
| CandleClosedAnalysisWorker | analyzeForProcessing(..., WORKER), one transaction | Eligible, subject to exact freshness |
| ScheduledAnalysisService | Latest fresh newly recovered signal uses analyzeRecoveredForProcessing | Eligible, subject to exact freshness |
| Older scheduler gap repair | Existing analyzeRecovered; analysis only | Never registered for execution |
| MarketDataBootstrapService | analyzeForProcessing(..., STARTUP), one transaction | Never |
| Explicit existing-signal request | Coordinator registers EXPLICIT if absent | Never |
| Replay | Existing isolated analysis and execution paths | Never reads this Production work ledger |

AnalysisService wrappers register work in the same transaction that saves the signal. If registration fails, signal creation rolls back. Explicit registration never resets an existing origin, status or attempt count. The migration does not turn historical signals into pending work.

A short independent claim transaction locks one ledger row, checks status and origin, increments attempts and installs a UUID owner. The business transaction locks that row and verifies ownership before doing anything. Completion and business database writes commit together on the configured shared datasource/transaction manager. COMPLETED can represent a hold, rejection or other no-trade result; it does not imply a BUY/SELL.

A duplicate completed or currently owned signal is not processed again. Explicit open-from-latest retains its existing error when the callback cannot return a position; that attempt is review-only after rollback. This now also prevents repeated explicit execution of a completed signal, rather than treating the signal as reusable authority.

These transactions cannot make external side effects transactional. In-memory mutations and any independently committed participant state also cannot be undone by the outer database rollback. That is why no failure after business processing begins receives automatic retry permission. The package does not claim globally exactly-once wallet execution or closure of FIX-125.

## 3. Recovery-gap addendum

| Status | Meaning / next action |
| --- | --- |
| PENDING | Registered; no processing claim yet |
| RUNNING | Durable owner and attempt; no automatic duplicate execution |
| RETRYABLE_FAILURE | Confirmed initial-lock failure after rollback, one attempt left |
| COMPLETED | Processing transaction committed; not necessarily a trade |
| EXPIRED | Recovery/retry candle is no longer latest and fresh; no business callback |
| REVIEW_REQUIRED | Exhausted initial retries, later failure, uncertain outcome or interrupted owner; no automatic replay |

The independent background scan defaults to 30 seconds (`trading.fix127.recovery-delay-ms`). Newly registered rows become scan candidates after 30 seconds, allowing the immediate caller to claim first. It scans up to 50 due WORKER/RECOVERY rows, not missing historical signals. It runs independently of the old missing-analysis scan's enablement, since its input is already-registered eligible work.

Automatic recovery, and every second attempt, require the exact original candle to be the latest actual closed candle for the same symbol/interval with close_time <= current Production time. Its close must still be within existing FIX-043 grace: 1m 90 seconds; 5m 2 minutes; 1h 5 minutes; 4h 10 minutes; 1d 30 minutes; default 2 minutes. A missing candle, later exact candle, future close or expired grace prevents execution. Initial foreground calls retain existing eligibility checks. Operational recovery uses current Production time; Replay event semantics remain separate.

An interrupted RUNNING record older than five minutes becomes REVIEW_REQUIRED, not retryable. A live business transaction holds its ledger row; the quarantine update cannot overwrite a committed COMPLETED row after waiting for that lock. A delayed owner that has not entered business loses ownership and cannot execute after quarantine. This timeout can deliberately sacrifice liveness when the result cannot be established safely. There is no automatic startup/manual replay and no automatic reset from review to pending.

Claim/diagnostic database errors propagate or are logged by the recovery scanner. They never cause fallback to untracked business execution. A completion already committed cannot be overwritten by a later error handler because the failure update requires the old RUNNING owner. If an error cannot be recorded, its durable owner remains unavailable for replay and is eventually quarantined. The guarded no-update case logs **[FIX-127][FAILURE_RECORD_NOT_UPDATED]**.

The ledger retains the last initial-lock error even when attempt 2 completes. It is a durable current-state record, not a full event-sourced attempt history. There is no retention purge or automatic manual repair action in this patch.

## 4. Logs and Proven / Analyze Trades

Search `[FIX-127]`. Tags include ATTEMPT, COMPLETED, NOT_CLAIMED, EXPIRED, RETRYABLE_FAILURE, REVIEW_REQUIRED, FAILURE_RECORD_NOT_UPDATED, INTERRUPTED_REVIEW, RECOVERY_FAILED and RECOVERY_SCAN_FAILED. ATTEMPT includes exact signal/candle identity, origin and cumulative attempt count. COMPLETED is logged after transaction completion.

The Signal processing panel shows signal ID, symbol, interval, exact candle open, origin, status, attempts, update time, optional paper-position reference and last failure. It appears with run/archive detail and via a saved-Proven button.

This is **current Production processing state**, not simulated Replay output and not a frozen archive snapshot. Run/archive selection uses that window's symbol and candle-open range. A saved Proven trade includes the hour before entry through exit (or entry when open) for context; it does not infer a trade pairing. It can omit earlier timeframe origins outside that range; query the exact signal ID when needed. The first 500 records are shown with a truncation notice. Failed loads and empty/pre-FIX-127 history are explicitly not presented as successful processing/parity.

JavaScript inserts diagnostic values with textContent. No Replay service consumes the Production ledger. No Replay timing, Shadow-write optimization, verifyEventResolution removal, scoring, sizing, threshold or exit formula changes are included.

## Read-only trader verification queries

Run these on the trader connection. Confirm `SELECT DATABASE()` returns `crypto_ai`; the next application's `crypto_ai_v2` is not relevant evidence.

```sql
SELECT DATABASE();
SHOW CREATE TABLE signal_processing_work;

SELECT status, origin, COUNT(*) AS records, MAX(attempts) AS max_attempts
FROM signal_processing_work GROUP BY status, origin ORDER BY status, origin;

SELECT signal_id, symbol, interval_code, candle_open_time, origin, status,
       attempts, updated_at, completed_at, paper_position_id, failure_stage, error_message
FROM signal_processing_work
WHERE status IN ('REVIEW_REQUIRED','RETRYABLE_FAILURE','RUNNING')
ORDER BY updated_at DESC LIMIT 100;

-- Replace only the exact signal ID under investigation; do not guess a nearest BUY.
SELECT signal_id, symbol, interval_code, candle_open_time, origin, status,
       attempts, failure_stage, error_message
FROM signal_processing_work WHERE signal_id = 127;
SELECT id, signal_id, symbol, side, status, execution_reason, executed_at
FROM wallet_trade WHERE signal_id = 127 ORDER BY id;

SHOW ENGINE INNODB STATUS;
```

If a signal predates V86, absence from the work table is expected. Do not bulk-register historical signals to make the report look complete. REVIEW_REQUIRED needs examination of durable execution/position history; this delivery deliberately supplies no blind requeue command.
