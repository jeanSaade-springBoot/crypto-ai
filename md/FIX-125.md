# FIX-125 — wallet coordination through transaction completion

Status: implemented review candidate. Requires V92 even when shared-market mode is OFF. No server deployment was performed. Read FIX-125-FIX-132-review.md and FIX-132-test-results.txt before deploying.

## Evidence and scope

The old synchronized method could return before its surrounding Spring transaction committed. The historical fixture Fix125CommitVisibilityGapTest reproduces that mechanism, not an observed lost trade. The corrected caller inventory shows normal signal/protection callers already locked the managed position before entering the old monitor. The previously alleged direct-caller lock inversion is withdrawn. Do not cite it as a confirmed incident.

Flat symbols lacked a durable row to coordinate first entries. A separate shared-asset problem exists between manual and automatic writers (FIX-134). BUY took daily statistics before cash; SELL formerly took them after cash. This package changes transaction coordination and current reads, not trading formulas. Concurrent operational outcomes can change because lost updates and stale decisions about wallet balances are prevented.

## Explicitly approved implementation decision (2026-09-27)

Use a durable per-symbol row plus a wallet-wide mutation row, both InnoDB SELECT FOR UPDATE locks held by the existing owning transaction through COMMIT or ROLLBACK. No lease, detached transaction, after-commit unlock SQL or in-memory lock registry supplies authority.

See FIX-125-FIX-132-review-correction.md for the revised rank contract, repository enforcement and measured-test limitations.

The mutation row deliberately preserves global serialization of automatic wallet mutations and extends it through commit to manual asset/cash/settings writers. It does not serialize indicator computation, candle persistence or all signal evaluation. This is more conservative than parallel per-symbol wallet mutation. The former synchronized wallet methods have been removed only after adding the mutation guard, moving SELL statistics acquisition ahead of cash, and testing the replacement on MySQL. Narrowing/removing the mutation guard later requires a separate complete resource-order and cash/statistics review; it is not an optimization hidden in this delivery.

Order for signal-driven trading: provisioned symbol guard, owned signal-work row, managed-position row, wallet mutation guard, daily statistics, settings/current cash/coin rows, trade/statistics/snapshot writes. Direct automatic wallet entry points acquire symbol then managed position before mutation. Protection acquires symbol before the managed-position lookup. Manual asset/trade writers acquire symbol then mutation; cash/settings-only writers acquire mutation without subsequently requesting a symbol. No mutation holder may acquire another symbol guard. Shared delivery claim transactions finish before signal processing; protection retains its existing local delivery fence before the symbol lock.

V92 provisions configured pairs, existing managed symbols and wallet-asset pairs. Coin configuration additions/enabling and manual asset administration provision before entering the wallet mutation transaction. Unknown unprovisioned service-level pairs fail explicitly. Never delete coordination rows during normal operation; their existence is required when a position is flat. Direct integrations of WalletService.execute must provision a new pair first outside their mutation transaction.

Lock statements use JDBC setQueryTimeout(2), with no changes to pooled SESSION variables. This is a two-second statement cancellation request, not a two-second end-to-end/network deadline. Exceptions propagate to the transaction owner for full rollback; no new retry wraps business effects. The pre-existing initial-managed-lock retry scope is retained. A symbol/mutation lock failure is not silently broadened into that retry category. Unknown completion remains REVIEW_REQUIRED through the owning delivery/processing coordinator. JDBC/network failure recovery still depends on the configured driver and pool.

Cash and coin current reads use PESSIMISTIC_WRITE plus refresh; ledger idempotency uses a locking current read after coordination. This prevents an earlier repeatable-read snapshot or managed entity from hiding a just-committed change. Allocation, sizing, quantity arithmetic, keys, thresholds and wallet-exit reasons retain their prior formulas.

## Diagnostics and tests

[FIX-125][LOCK_WAIT] identifies the guard and measured acquisition time at 100 ms or more. [FIX-125][TX_COMPLETED] records rollback and slow transactions at INFO, fast commits at DEBUG. Elapsed time includes the wait through completion; it is not a database-only metric. Processing and delivery outcomes remain persisted and shown in Proven.

WalletCoordinationMySqlIT uses real MySQL/InnoDB, JPA repositories, Spring wallet transaction proxies and controlled pre-commit latches. It verifies real performance_schema.data_lock_waits before releasing the owner. Tests check quantities, cost basis, ledger counts and cash, rather than just successful thread completion. A signal test runs the actual PaperTradingService body through SignalProcessingCoordinator; decision/price collaborators are controlled mocks, so it is a transaction integration test, not full market-strategy parity. Valuation/snapshot collaborators are controlled. See the final test report for executed counts and remaining deployment gates.

Replay does not acquire Production database locks or mutate wallet tables. Existing shared sizing/entry/exit policies remain unchanged. Exact real-window Production/Replay outcome parity is still a measured acceptance gate, not inferred from concurrency tests.
