Query map and priority
TradeSignalRepository.java lines 22-49: latest/previous/top-20 and actionable
signal lists. Used by execution intelligence, execution validation, opportunity
consolidation, MTF context, paper entry, dashboard and live protection. Priority
index: (symbol,interval_code,generated_at). Symbol-only latest/history needs its
own (symbol,generated_at); one cannot substitute for the other.

LivePositionProtectionService.java lines 71-73: three full TradeSignal queries
per price update when an open managed position exists. This is on Binance's
canonical live-price protection path. First fix indexing; then evaluate one
batched lookup or a narrow immutable projection that preserves all policy inputs
and freshness/ordering. Avoid a blind TTL cache of trading decisions.

TradeSignalRepository.java lines 89-123 and TradeInspectorService.java lines
154,170,243: blocked BUY/SELL searches use UPPER(symbol), optional-symbol OR and
wide entities. Split symbol/all-symbol query branches and normalize parameters.
Use direct column equality for the symbol-specific branch; preserve original vs
final decision semantics. Start with (symbol,generated_at), then remeasure before
adding blocker/decision-specific indexes. UPPER removal alone is not a measured
fix and the SQL proposal alone does not optimize these repository predicates.

TradeSignalRepository.java lines 126-133: unpaged symbol generated/candle-time
history. Callers include TradeInspectorService.java line 954, TradeReplayService,
PriceMoveMonitorService.java lines 289-295 and RegressionTestWorker. All load wide
entities; historical consumers need paging/streaming or narrower projections
without silently dropping forensic/replay rows. (symbol,candle_open_time) is an
optional third index for cross-timeframe candle history.

TradeActivityService.java line 278: explicit projection with symbol and generated
time range, ordered by generated_at/id, capped at 5,000; (symbol,generated_at)
matches its range/order. Joins from wallet/opportunity tables to trade_signal.id
already use the primary key; their driving-table indexes are separate scope.

ScoreDiagnosticsService.java lines 35-43: already scalar projection and 60-second
cache. Do not add a large all-score covering index without workload evidence.
SystemHealthDailyService: already uses V76 for strategy/regime aggregates;
interval counts/staleness use generated-time filtering. Remeasure under actual
load before adding a separate covering index for those scalar queries.
Exact candle existence/read and recovery identity scans: existing unique
(symbol,interval_code,candle_open_time) is appropriate. Keep it intact.
AnalysisController.java line 28: latest 100 full entities. Index already suitable;
consider a summary DTO plus a detail endpoint if response transfer/mapping is slow.
findForInspectorAnalysis and findByGeneratedAtGreaterThanEqualOrderByGeneratedAtDesc
are repository declarations without current callers found; avoid optimizing dead
query paths at the expense of the actual blocked-signal queries.

Recommended sequence
1. Adopt the two priority index definitions through a new Flyway migration after
   review; do not run the proposal manually and later deploy duplicate DDL.
2. Split blocked-search symbol/all-symbol branches and remove UPPER on the column.
3. Run the same populated-window plans before/after; record rows examined, sorts,
   returned IDs/ordering, warm repeated timings, and insert throughput.
4. Reduce unused JSON fields in frequent reads; consider batching live protection
   context reads, keeping policy and temporal semantics unchanged.
5. Capture real production stage timing, JDBC/pool waits, response serialization,
   and endpoint p95/p99. There is no evidence yet that index changes solve the
   entire evaluation delay. Review buffer-pool sizing against available RAM.
6. Consider the optional symbol/candle index only if historical usage warrants it.
   Review redundant indexes separately; zero recent use alone is insufficient.
